大模型入门：从Token、上下文到幻觉

发表于 2025-01-12 更新于 2026-07-17 分类于 AI实践 阅读次数：

第一次使用大模型时，我把它当成了一个更聪明的搜索框：输入问题，等待正确答案。用了一段时间后才发现，这个理解会制造很多误判。模型不是从知识库里查出一段标准答案，而是在已有上下文后面，持续预测更可能出现的下一个 Token。

这句话看起来抽象，却能解释日常使用中的大部分现象：为什么同一个问题会得到不同答案，为什么一段无关日志会让结果变差，为什么模型能写出语法正确但根本不存在的 API，也能解释为什么“把需求说清楚”比反复要求它聪明一点更有效。

如果把模型当数据库，就会问“它明明知道，为什么还答错”；把它当概率生成系统，问题会变成“我提供的上下文是否足以约束下一步输出”。后一个问题更接近可操作的工程问题。

Token 不是汉字，也不等于单词

模型读取的基本单位不是“一个汉字”或“一个英文单词”，而是 Token。不同模型使用不同的分词方式，一段文本可能按完整词、词的一部分、标点或空格切分。

Token 直接影响三件事：

  1. 上下文容量：模型能同时处理多少输入和输出，通常以 Token 计量。
  2. 调用成本：API 常按输入与输出 Token 数收费。
  3. 响应时间：输入越长、输出越长，处理和生成通常越慢。

所以“我只发了一个文件”并不代表输入很小。一个两千行的压缩 Java 类、完整依赖锁文件、重复堆栈和打包后的 HTML，都可能消耗大量上下文，却没有提供等比例的信息。

上下文窗口更像工作台，不像长期记忆

上下文窗口可以理解成模型当前这次任务能够看到的工作台。系统指令、历史对话、用户输入、工具读取到的代码和模型已经生成的内容，都要占用这张工作台。

工作台很大，不代表可以随意堆东西。一个常见误区是：既然模型支持很长上下文，就把整个项目一次性贴进去。结果往往是关键约束被埋在中间，模型抓住了相似但无关的实现。

我更愿意把上下文分成四层：

层次 应提供的内容 例子
任务 这次到底要改变什么 “订单详情增加预计送达时间”
约束 哪些行为不能变 “JDK 8；不修改数据库；旧客户端兼容”
证据 当前系统真实是什么样 Controller、DTO、测试、报错日志
验收 怎样证明已经完成 指定测试、接口样例、构建命令

这四层都比“你是一个资深 Java 专家，请认真完成”更有约束力。角色设定可以影响表达方式，却不能代替项目事实。

上下文也不等于长期记忆。新对话里，模型通常不会天然知道上一次讨论的决策。对于长期项目，真正可靠的记忆仍然应该落在仓库中，例如：

  • README.md 说明运行方式；
  • AGENTS.md 记录编码约束；
  • ADR 记录架构决策；
  • 测试固定行为边界；
  • Issue 或设计文档解释需求背景。

能被版本管理的知识，比“希望模型下次还记得”可靠得多。

推理过程的本质仍然是生成

模型回复并不是一次性吐出整段文字，而是一个 Token 接一个 Token 地生成。每一步都会根据当前上下文给候选 Token 分配概率，再按配置选择结果。

采样参数越偏确定，模型越倾向选择高概率候选；采样越开放，表达可能更有变化，也更容易偏离。写创意文案和修复支付代码显然不该使用同一种容错态度。

所谓“推理模型”能在回答前进行更充分的中间计算，复杂任务上的表现通常更好。但它仍然不会自动获得项目权限、真实数据库状态或团队没有写下来的业务规则。推理能力提升，不能弥补输入事实缺失。

幻觉为什么看起来那么像真的

幻觉并不一定表现为胡言乱语。更危险的情况是：答案语法正确、解释流畅、命名符合生态习惯，但其中一个类、配置项或版本能力并不存在。

这与模型的目标有关。它擅长生成“像答案的内容”，不天然负责证明每句话来自可靠来源。

应对幻觉不能只靠一句“不要编造”。更有效的是让任务具备证据闭环：

  1. 要求引用来源：结论对应哪个文件、哪段日志或哪份官方文档。
  2. 允许表达不确定：证据不足时明确写“无法从当前上下文确认”。
  3. 让工具验证：搜索仓库、编译代码、执行测试，而不是凭记忆猜 API。
  4. 缩小修改范围：先处理可验证的小步骤，避免一次生成几十个文件。
  5. 人工阅读差异：模型写得越顺，越要检查被默认掉的前提。

入门阶段，我认为最值得保留的四个习惯

第一，把模型当协作者，不当权威。 它可以快速提出候选方案，却不替开发者承担上线结果。

第二，先给事实，再提要求。 文件、日志、版本、约束和验收条件，比堆叠形容词更有效。

第三，生成之后必须验证。 能执行测试就执行测试，能查官方文档就查文档，不能验证就明确风险。

第四，敏感信息默认不进入模型。 Token、密码、客户数据、生产日志和内部地址要先脱敏，并遵守团队的数据使用规则。

学会几个提示词技巧并不难，真正需要时间的是建立正确预期：大模型擅长在上下文中生成高概率答案，而工程交付要求我们把这个答案变成可追溯、可测试、可回退的改动。

理解这个差距，才算真正开始使用 AI 编程。
