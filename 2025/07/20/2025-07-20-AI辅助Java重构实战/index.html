AI辅助Java重构实战：拆解一个过长Service

发表于 2025-07-20 更新于 2026-07-17 分类于 Java进阶 阅读次数：

这次想记录一个更接近存量项目的 AI 使用场景：拆解一个 186 行的 createOrder 方法。

它同时做参数校验、商品查询、价格计算、库存扣减、订单落库、优惠券核销和通知发送。方法虽然长，却已经稳定运行两年。面对这种代码，最危险的需求不是“帮我重构”，而是“帮我一次重写得更优雅”。

重构的目标应该是改善内部结构而不改变外部行为。AI 可以加快识别重复和生成小函数的速度，但前提是我们先固定行为，再让每一步差异足够小。

仅看这段就能发现几个问题：

  • 六个基础类型参数容易传错位置，调用含义不直观；
  • 业务校验、计算和副作用混在同一抽象层；
  • 外部通知在数据库事务中，超时会长期占用连接；
  • 优惠券为空、库存扣减失败、重复请求等分支藏在内部方法；
  • 测试只能从入口准备大量 Mock，失败后很难看出是哪条规则变化。

不过“看见坏味道”和“知道怎样安全修改”是两件事。直接让 AI 按 SOLID 原则重写，它曾给出十一个新类、一套领域事件和一个当前项目根本没有的消息队列。结构更漂亮，风险也扩大了十倍。

我最后给这次改动设了三个约束：

第零步：先建立行为护栏

原方法只有两个正常流程测试。开始重构前，我让 AI 根据所有条件分支生成“行为清单”，再逐项与产品规则、线上日志和现有代码核对。

最后补了这些特征测试：

场景 要固定的行为
重复 requestId 返回第一次创建的订单，不重复扣库存
商品下架 返回 PRODUCT_UNAVAILABLE
数量超过限购 返回 PURCHASE_LIMIT_EXCEEDED
优惠券为空 按原价创建，不调用核销
优惠券失效 整笔订单不落库、不扣库存
库存不足 返回原错误码，不保存订单
通知超时 订单仍创建成功，产生可重试通知任务

最后一条不是原代码行为，而是本次明确要修复的缺陷，因此单独作为需求变更，不伪装成纯重构。

测试先在旧代码上运行。除了“通知超时”之外全部通过，说明我们至少拥有一张当前行为快照。没有这一步，重构后测试全绿也可能只是因为测试跟着实现一起改错了。

AI 最初使用了 Java record。它非常适合不可变数据载体，却不兼容这个 JDK 8 项目。模型知道现代 Java 的常见写法，并不代表它会始终记住当前仓库版本；编译是最直接的纠偏工具。

参数对象也不是越多越好。这里只有一组数据跨 Controller、校验器和应用服务反复传递，提取后能减少长参数列表。如果只是某个私有方法的两个值，没有必要为“面向对象”新建类型。

第二步：把规则校验从流程中移开

旧方法中的校验散落在查询前后。我将不产生副作用的规则提取到 OrderCreationValidator：

这里选择提前抛出，避免多层 if 嵌套。校验器只依赖输入和已查询商品，没有数据库写入，因此可以直接覆盖边界测试。

不是所有校验都被搬走。优惠券有效性依赖实时状态，并且核销需要并发控制，它仍由优惠券服务负责。把“名字像校验”的代码全部塞进一个类，只会形成新的大类。

AI 在这一步帮我找出了三段重复的数量判断，也指出两个错误码文本不同。我没有让它自动统一错误码，因为对外错误码是接口契约；看似重复的字符串可能承载兼容行为。

这一步还暴露了旧代码的一个隐含行为：优惠后金额可以是负数，保存前才在另一个方法里修正为零。重构没有顺手“优化”规则，而是先用测试固定，再把修正逻辑移动到 OrderPrice 构造器。移动与修改必须分开，否则出了问题无法判断是哪一种变化导致。

第四步：重新画事务边界

旧方法上的 @Transactional 包住了所有操作，包括通知 HTTP 请求。网络慢两秒，数据库连接就多占用两秒；通知失败还会回滚订单与库存，而对方可能已经收到请求，形成更难处理的不一致。

通知任务由现有定时任务发送，成功后更新状态，失败按退避策略重试。这里没有为了“解耦”突然引入 Kafka，因为项目已经有可靠任务表。架构选择应服从现有基础设施和故障处理能力。

还要注意 Spring 事务代理：如果把 persist 写成同一个类的 private 方法，或通过 this.persist() 自调用，@Transactional 不会按预期经过代理。将事务方法放进独立 Bean，既明确边界，也避开自调用失效。

有一个 calculateAmount 看似无引用，实际被 SpEL 规则通过方法名调用，普通静态搜索没有找到。幸好集成测试启动规则时失败，避免了误删上线。

动态调用、反射、XML Mapper、序列化字段和框架约定都是 AI 重构的薄弱区。模型读取了 Java 引用，不代表它已经看到运行时所有关系。

AI 在这次重构中犯过的错

除了使用 record，还有几类建议被人工拒绝：

  1. 用 Stream.toList() 收集结果，JDK 8 不支持；
  2. 把所有返回值改成 Optional 字段，增加序列化与调用复杂度；
  3. 统一替换历史错误码，破坏客户端兼容；
  4. 引入领域事件和新消息中间件，超出问题范围；
  5. 在没有并发测试的情况下，把重复请求判断改成先查后写；
  6. 为了减少类数量，把校验、价格和上下文工厂合并成新的 Helper 大类。

这些建议并不荒唐，它们在另一个项目里可能成立。问题在于模型倾向输出“普遍合理”的设计，工程师要判断它是否适合当前版本、团队和风险预算。

怎样证明重构没有把事情弄坏

最终验证不只是一句“测试通过”：

代码指标也有变化：入口方法从 186 行降到 24 行，六个参数变成一个命令对象，价格规则可以脱离 Spring 单测。类数量增加了四个，但每个类对应稳定职责，不是为了追求数字拆分。

我没有把“方法越短越好”当目标。真正的改善是：阅读入口时能看清业务顺序，修改价格不需要理解通知，调整通知也不会碰库存事务。

这类任务最适合怎样使用 AI

我的顺序是：

AI 在“快速读取、发现重复、生成测试骨架、执行机械移动”上很强；人在“哪些行为是契约、哪种抽象值得存在、风险是否可以接受”上不能缺席。

重构不是把旧代码替换成一份更现代的代码，而是在持续可工作的前提下，让下一次变化更容易。让 AI 参与后，这个过程可以更快，但“小步、测试、审查”反而比以前更重要，因为我们现在拥有了以极快速度制造大面积改动的能力。
