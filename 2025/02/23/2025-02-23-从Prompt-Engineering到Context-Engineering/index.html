从Prompt Engineering到Context Engineering：一次提示词改造实验

发表于 2025-02-23 更新于 2026-07-17 分类于 AI实践 阅读次数：

刚开始用 AI 写代码时，我把主要精力放在“怎么写出更厉害的提示词”上：你是一名资深工程师、请深入思考、请给出最佳实践。它们偶尔有用，但面对真实项目，决定结果的往往不是形容词，而是模型到底看到了哪些事实。

为了确认这个判断，我拿一个相同的小需求做了三轮实验。任务是给 Spring Boot 项目的订单查询接口增加一个 deliveryStatus 字段。三轮使用同一个模型，只改变输入上下文，不手工修正中间结果。

第一轮：一句话需求

模型很快给出了一套完整方案：修改 Entity、DTO、Mapper 和数据库脚本，还建议在 order_info 表增加 delivery_status 字段。

代码组织得很像一个正常 Spring Boot 项目，甚至主动补充了 Swagger 注解。但项目根本没有它假设的 OrderEntity，状态也不应该存到订单表。

第一轮得分：2/10。

得到的两分来自“字段确实加到了一个返回对象里”和“代码大致兼容 JDK 8”。其余内容主要由常见项目模式补全。模型不是故意忽略设计，它只是没有看到真实设计。

这轮让我意识到一个不太舒服的事实：输出越完整，越容易让人忘记检查前提。若我只浏览文件名，很可能会把这份错误方案当成高效率。

更清晰的提示词改善了任务纪律，却没有补上项目事实。它让模型更像一个会先问问题的工程师，但不能让工程师凭空看到仓库。

这次实验并不能证明提示词不重要。清楚的任务表达仍然能减少歧义，但在代码仓库里，它只是上下文的一部分。

上下文也会变质

上下文不是越多越好。我在后续任务中遇到过三个反例。

过期上下文

需求文档写的是旧接口，代码已经迁移到新服务。模型严格遵循文档，反而改错位置。重要事实要标明来源与时间，冲突时以当前可执行代码和明确决策为准。

相互冲突的上下文

全局规范要求所有异常转换成统一错误码，模块内却保留了旧的直接抛出方式。若不说明本次遵循哪一层，模型可能随机选择。冲突不能靠增加更多文本解决，需要人做决策。

没有优先级的上下文

我曾一次提供十几个“参考实现”。模型混用了其中三种风格。后来只给一个最接近的主参考，其余资料明确标注“仅用于理解字段，不复制结构”，结果稳定很多。

所以，上下文设计还需要三条规则：

  1. 保证来源真实且尽量新；
  2. 冲突信息写明优先级；
  3. 每份材料说明它在任务中的用途。

简单任务不必把每一项写成长文，但缺失项要心里有数。尤其是“怎样算完成”，如果人自己都没有答案，模型只能生成一个听起来合理的终点。

从 Prompt Engineering 走向 Context Engineering，对我最大的改变不是提示词变长了，而是开始把 AI 编程当成工程协作：先准备事实，控制信息流，再用真实反馈纠偏。模型负责快速探索和执行，人负责选择上下文、处理冲突并对结果签字。

这也许没有“一句话生成整个系统”那么有戏剧性，却更接近可以重复使用的生产力。
