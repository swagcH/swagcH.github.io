Vibe Coding不是完全不看代码

发表于 2025-05-18 更新于 2026-07-17 分类于 程序员随笔 阅读次数：

Vibe Coding 最吸引人的画面，是只描述想法，AI 持续修改代码，人看着页面变化说“再来一点”，直到产品能用。这个过程真实存在，而且非常适合探索。但当它被简化成“以后不需要看代码”，问题就从一种高效交互方式变成了责任错位。

我的理解是：Vibe Coding 可以降低表达想法的门槛，不能取消软件运行后的后果。

两种场景，不应该使用同一套纪律

周末做一个只在本机运行的小工具，最重要的是快速看到结果。数据丢了可以重来，页面崩了重新生成，没有用户依赖它。此时跟着感觉迭代很合理：先有可玩的东西，再理解实现。

但下面这些场景完全不同：

  • 修改支付、权限或数据删除逻辑；
  • 接触生产密钥和客户数据；
  • 在多人维护的仓库里引入新依赖；
  • 改变数据库结构或公共接口；
  • 让生成的服务长期对外运行。

它们共同拥有一个特点：失败成本会落到别人身上。只要影响从“我自己的时间”扩展到数据、资金、隐私和团队维护成本，开发方式就必须升级。

所以我会把 AI 编程分为两个模式：

模式 目标 可以接受 不能省略
探索模式 验证想法是否值得继续 临时代码、快速改写、少量手测 隔离环境、无真实数据、明确可丢弃
交付模式 让功能稳定进入真实系统 AI 生成大部分实现 Review、测试、安全检查、发布与回滚

前者可以更有“氛围”，后者必须留下证据。

不看每一行，不等于不理解系统

传统开发也很少要求工程师阅读依赖库的每一行源码。我们依赖抽象、接口、测试和社区维护来控制复杂度。AI 生成代码后，人同样不一定要逐字符检查，但至少要能回答：

如果这些问题都答不出来，所谓“不看代码”其实是“不知道自己交付了什么”。

尤其需要警惕一种假象：页面正常打开，主流程点得通，就认为功能完成。真实故障通常藏在重复提交、并发请求、空数据、超时重试、时区、权限绕过和升级兼容里。演示成功只能证明一条路径，不等于系统可靠。

我给 Vibe Coding 设的五条红线

1. 密钥不进入对话

配置文件、日志和截图里的 Token、密码、Cookie、客户信息先脱敏。模型能不能保密不是唯一问题，团队的数据合规要求才是边界。

2. 数据破坏操作必须人工确认

删除、覆盖、迁移、批量更新和生产环境操作，不允许因为模型“很确定”就自动执行。先备份、估算影响、准备回滚，再由有权限的人确认。

3. 权限代码必须读懂

登录、鉴权、租户隔离和资源归属校验不能只看测试绿灯。测试本身也可能只覆盖正常用户。至少要检查越权路径和默认拒绝策略。

4. 新依赖要说明代价

AI 很喜欢用一个新包解决十行代码的问题。依赖会带来许可证、漏洞、体积、升级和维护成本。能复用现有能力时，不为了生成方便扩大供应链。

5. 不接受“应该可以”作为验收

编译过、测试过、接口真实请求过，分别是不同证据。没有执行就写“未验证”，不能把推测包装成完成状态。

真正的新能力是驾驭反馈循环

Vibe Coding 并不是完全放弃工程，而是把编程界面从“逐行输入代码”扩展成“描述目标、观察结果、继续校正”。其中最重要的能力，也从记住 API 变成了设计反馈循环：

一个反馈循环是否可靠，取决于“可观察结果”是什么。若反馈只有视觉效果，模型会优先把页面调得像；若反馈包含类型检查、单元测试、性能数据、安全扫描和真实用户行为，生成方向才会逐渐靠近工程目标。

这也是为什么优秀的 AI 编程并不轻松。人不再敲每段样板代码，却要更快识别错误假设、更清楚地表达约束，并构造能让错误尽早暴露的测试。

初学者可以从小而可逆的任务开始

我不赞成因为有风险就拒绝 Vibe Coding。相反，它非常适合做这些事：

  • 生成一次性数据转换脚本，并对比转换前后数量；
  • 为已有函数补边界测试；
  • 制作内部原型或个人效率工具；
  • 解释陌生模块并画出调用关系；
  • 把重复代码整理成候选重构方案；
  • 根据明确规范调整样式和文案。

共同点是范围清楚、结果可验证、失败可恢复。先在这样的任务上练习，能逐渐建立对模型能力和失误模式的真实认识。

最后还是那句老话：谁提交，谁负责

AI 不会参加故障复盘，也不会在凌晨判断是否回滚。生成速度可以属于模型，合并代码的决定仍然属于提交者。

我愿意拥抱 Vibe Coding，因为它让很多想法能更快变成可运行的东西；我也不愿把它解释成“代码已经不重要”，因为软件最终仍然由代码、配置、数据和运行环境组成。

最舒服的状态不是完全不看，而是把注意力从机械输入转向真正重要的地方：问题是否值得解决，边界是否清楚，证据是否足够，系统失败时能否安全回来。
