Redis 缓存设计：穿透、击穿、雪崩的实际处理

发表于 2026-05-24 更新于 2026-10-16 分类于 Java ， 数据库 阅读次数：

“缓存穿透、击穿、雪崩”这三个词几乎每份面经都会出现，但实际项目里出问题的往往不是概念本身，而是方案选型时的取舍没想清楚：加布隆过滤器要不要考虑误判？互斥锁会不会把可用性问题变成响应时间问题？先删缓存还是先更数据库？

这篇文章按”现象 → 方案 → 代价”的方式整理一遍，最后给出我在项目里的实际做法。

先把三个概念分清

三者经常被混着说，但触发条件完全不同：

问题 触发条件 直接后果
穿透 查询根本不存在的数据 请求绕过缓存，每次都打到数据库
击穿 单个热点 key 过期瞬间 大量并发同时去数据库重建同一个 key
雪崩 大量 key 同时失效，或 Redis 整体不可用 数据库瞬间承接全部流量

一句话区分：穿透是”数据不存在”，击穿是”一个热点没了”，雪崩是”一大片同时没了”。

缓存穿透

现象

请求查询一个数据库里也不存在的 key（比如不存在的用户 ID、被删除的商品），缓存不会命中，请求直接落到数据库。

正常业务流量下这不是问题，但如果有人恶意用随机 ID 刷接口，每次都能绕过缓存，数据库就成了第一道防线。

方案与代价

方案一：缓存空对象

查不到也往缓存里写一个空值（或特殊标记），并设置较短的过期时间。

代价：如果攻击者用大量不同的随机 ID 刷，每个都会写入一个空值，内存会被打满。所以过期时间必须短，且最好配合下面的方案。

方案二：布隆过滤器

在缓存之前加一层布隆过滤器，把数据库里存在的 key 预先写进去。查询时先问布隆过滤器”这个 key 可能存在吗”，不存在就直接返回。

代价（这三个必须知道）：

  1. 有误判率：说”可能存在”时可能是误判（实际不存在），所以布隆过滤器只能挡住”确定不存在”的请求，不能替代真实查询
  2. 不支持删除：标准布隆过滤器删不掉元素。数据删除后过滤器里还在，会导致”明明删了却还被放行”。可以用计数布隆过滤器，或者定期重建
  3. 需要预热和同步：新增数据时要同步写入，否则新数据会被误挡

方案三：入口参数校验

最便宜的一层：ID 格式不对、超出范围、必填参数缺失的请求，在 Controller 层就拒掉，连缓存都不查。

我的实际做法

参数校验 + 缓存空值（短过期），没用布隆过滤器。原因：

  • 我们的 key 空间是可枚举的（用户 ID、设备 ID），攻击者能构造的”不存在 key”数量有限
  • 引入布隆过滤器需要额外的预热和同步逻辑，收益不匹配
  • 如果以后出现大规模随机 key 攻击，再上布隆过滤器

这不是”布隆过滤器不好”，而是”当前场景用不上”。 面试时被问到，说清楚这个判断过程比背方案更有说服力。

缓存击穿

现象

某个热点 key（比如首页配置、秒杀商品）过期的那一瞬间，大量并发请求同时发现缓存没了，一起去数据库查询并重建缓存。

注意：**击穿的前提是”热点”**。一个普通 key 过期，就算有几十个请求同时打过来，数据库也扛得住。

方案与代价

方案一：互斥锁重建

只让一个线程去查数据库并回填缓存，其他线程等待后重试。

代价：

  • 响应时间变长：没抢到锁的请求要等待。热点 key 重建如果本身很慢（比如要聚合多个服务），等待会很明显
  • 有死锁风险：必须给锁设过期时间，且要考虑业务执行超过锁时间的情况
  • 重试逻辑要防雪崩：如果重试太密集，等待的线程会形成新的压力

方案二：逻辑过期（不阻塞读）

缓存里存的 value 带一个过期时间字段，Redis 层面不设过期。读到发现逻辑过期时，返回旧值，同时异步触发一个线程去更新。

代价：

  • 会返回旧数据：业务必须能接受短暂的数据延迟（大部分场景可以，涉及金额的不行）
  • 实现更复杂：需要额外的线程池和锁管理
  • 缓存不会自动清理：逻辑过期不会删除 key，需要额外的清理策略

怎么选

场景 建议
数据一致性要求高，能接受短暂等待 互斥锁重建
响应时间敏感，能接受短暂旧数据 逻辑过期
key 极少且几乎不变 干脆不设过期，变更时主动更新

缓存雪崩

雪崩有两种成因，处理方式完全不同。

成因一：大量 key 同时过期

常见于”凌晨批量刷新缓存”的实现——如果所有 key 都设 expire = 3600，那么一小时后它们会同时失效。

方案：过期时间加随机偏移

这是成本最低、收益最高的一条，几乎零成本就能避免大部分雪崩。

成因二：Redis 整体不可用

单实例 Redis 宕机或网络分区，所有请求同时落到数据库。

方案（分层防御）：

  1. 高可用部署：哨兵（主从自动切换）或集群（分片 + 高可用）。这是基础，不是可选项
  2. 多级缓存：本地缓存（Caffeine）作为一级，Redis 作为二级。Redis 挂了本地还能挡一部分
  3. 熔断降级：检测到 Redis 不可用时，直接返回降级数据（默认值、静态兜底、友好提示），而不是让请求穿透到数据库
  4. 限流：对数据库的访问做并发限制，宁可拒绝部分请求，也不让数据库被打死

关键认知：数据库是最后的防线，任何方案的目标都是”不要让数据库裸奔”。

缓存与数据库的一致性

这是比”三兄弟”更容易出问题的地方。

Cache Aside（最常用）

  • 读：先读缓存，命中返回；未命中读数据库，然后写回缓存
  • 写：先更新数据库，再删除缓存（不是更新缓存）

为什么是”删除”而不是”更新”？

更新缓存有两个问题：

  1. 如果缓存值需要复杂计算，每次写都更新会浪费（很多写操作后根本没人读）
  2. 并发写时，两个线程的更新顺序可能和数据库提交顺序不一致，导致缓存里是旧值

删除更简单：下次读的时候自然会加载最新值。

为什么是”先更库再删缓存”？

反过来（先删缓存再更库）的问题：删除后、更新前，如果有读请求进来，会把旧值重新加载进缓存，然后数据库才更新——缓存里留下的是旧值，且不会自动纠正。

先更库再删缓存的不一致窗口更小（只在”更新完成、删除前”有极短时间）。

延迟双删

即使先更库再删缓存，仍有极小概率不一致。延迟双删的思路是：更新数据库后删一次缓存，延迟一段时间再删一次，把中间可能被写回的旧值清掉。

代价：延迟时间不好定（太短没用，太长影响一致性），且引入了异步任务。

更彻底的方案：订阅 binlog

用 Canal 之类的工具订阅 MySQL binlog，数据变更时异步删除对应缓存。

优点：业务代码完全不用管缓存，一致性由数据变更事件驱动
代价：引入额外组件和运维成本

我的选择：普通业务用 Cache Aside + 短过期时间。短过期是最后的兜底——即使中间出现不一致，最长一个过期周期后也会自动恢复。

几个容易被忽略的点

大 key

单个 key 的 value 过大（比如几 MB 的列表），会导致：

  • 读取时网络传输慢，阻塞其他命令
  • 删除时阻塞（Redis 单线程）

处理：拆分 key、控制集合大小、用 SCAN 分批处理而不是一次性取全部。

热 key

单个 key 的 QPS 过高，单实例 CPU 会成为瓶颈。

处理：本地缓存挡住大部分读、key 加随机后缀分散到多个实例（读时聚合）。

缓存预热

服务发布后缓存是空的，第一波流量会全打到数据库。

处理：发布后异步预热核心数据，或者用灰度发布控制流量爬升速度。

监控指标

光有方案不够，得能看到问题：

  • 缓存命中率（低说明 key 设计或过期策略有问题）
  • 慢查询（slowlog）
  • 内存使用与淘汰情况
  • 连接数与超时

落地检查清单

  • 缓存穿透：有参数校验；对不存在的 key 缓存空值（短过期）或使用布隆过滤器
  • 缓存击穿：热点 key 有互斥重建或逻辑过期方案
  • 缓存雪崩：过期时间已加随机偏移（最低成本的一条）
  • Redis 高可用：哨兵或集群，且验证过故障切换
  • 降级方案：Redis 不可用时有兜底数据，而不是直接打数据库
  • 一致性策略明确：Cache Aside 顺序正确（先更库再删缓存）
  • 有短过期时间兜底，不依赖”永远一致”
  • 大 key / 热 key 有监控和拆分方案
  • 发布后有预热策略
  • 监控覆盖命中率、慢查询、内存、连接数

小结

缓存问题的核心不是”背下几个方案”，而是知道每个方案的代价，并判断当前场景能不能接受：

  • 缓存空值 → 代价是内存（用短过期控制）
  • 布隆过滤器 → 代价是误判和运维复杂度
  • 互斥锁 → 代价是响应时间
  • 逻辑过期 → 代价是短暂旧数据
  • 延迟双删 → 代价是时间窗口不好定

我现在的默认组合是：参数校验 + 短过期兜底 + 过期时间加随机 + Redis 高可用 + 明确的降级策略。这几条覆盖了绝大多数问题，剩下的按具体场景再加。
