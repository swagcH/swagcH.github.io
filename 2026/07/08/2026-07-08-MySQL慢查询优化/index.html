MySQL 慢查询优化：从执行计划到索引设计

发表于 2026-07-08 分类于 数据库 ， 性能优化 阅读次数：

“加个索引”是解决慢查询最常见也最容易用错的建议。加错索引不但不解决问题，还会拖慢写入、占额外空间，甚至让优化器选错执行路径。

这篇文章按实际排查顺序组织：怎么定位慢查询 → 怎么读执行计划 → 怎么设计索引 → 哪些写法会让索引失效。最后给一份可以照着走的检查清单。

第一步：先定位，不要猜

优化最容易犯的错是”凭感觉猜哪个 SQL 慢”。先把慢的找出来。

慢查询日志

注意 long_query_time 的单位是秒，可以设小数（比如 0.5）。很多线上问题的 SQL 执行时间是几百毫秒，按默认 10 秒根本抓不到。

用 mysqldumpslow 或 pt-query-digest 聚合分析，按总耗时排序而不是单次耗时——一条 50ms 但每秒执行 1000 次的 SQL，比一条 2 秒但每小时执行一次的 SQL 危害大得多。

performance_schema

关键看 rows_examined 和 rows_sent 的比例。如果扫描了几十万行只返回 10 行，说明索引没用好。

第二步：读懂 EXPLAIN

EXPLAIN 是排查的核心工具。重点看这四列：

type：访问类型（最重要的列）

从好到坏：

type 含义 说明
system 表只有一行 极少见
const 主键或唯一索引等值查询 最优
eq_ref 联表时用主键/唯一索引 联表场景最优
ref 非唯一索引等值查询 常规业务的目标
range 索引范围扫描 可接受（BETWEEN、>、IN）
index 扫全索引树 比 ALL 好一点，仍需警惕
ALL 全表扫描 必须处理

判断标准：核心业务 SQL 至少要达到 ref 或 range。出现 ALL 或 index 就要具体分析。

key 与 key_len

  • key：实际使用的索引。如果 possible_keys 有值但 key 是 NULL，说明优化器认为走索引不划算（通常是索引选择性太差）
  • key_len：使用到的索引长度（字节）。可以用来判断联合索引用到了几列

key_len 的计算（以 InnoDB、utf8mb4 为例）：

类型 长度
INT 4 字节（允许 NULL 则 +1）
BIGINT 8 字节
VARCHAR(n) 4n + 2（utf8mb4 每字符最多 4 字节，+2 存长度）
CHAR(n) 4n
索引列允许 NULL 额外 +1

举例：联合索引 idx(user_id, status, create_time)，其中 user_id BIGINT NOT NULL、status TINYINT NOT NULL。

这是验证”联合索引到底用了几列”最直接的方法，比猜靠谱。

rows 与 filtered

  • rows：预估需要扫描的行数。这是优化器基于统计信息的估算，不一定准，但数量级有参考价值
  • filtered：扫描后满足条件的行占比（百分比）。rows × filtered% 才是真正参与后续操作的行数

如果 rows 是 100 万但 filtered 是 0.01%，说明索引只起到了部分过滤作用，剩下大量行是在 Server 层过滤掉的。

Extra：一定要看的提示

Extra 含义 处理
Using index 覆盖索引，不需要回表 ✅ 好
Using where Server 层还要过滤 结合 filtered 判断
Using filesort 需要额外排序，无法用索引顺序 ⚠️ 大结果集时是问题
Using temporary 用了临时表（常见于 GROUP BY / DISTINCT） ⚠️ 尽量消除
Using index condition 索引下推（ICP）生效 ✅ 好

Using filesort 是最常见的性能杀手。它不一定走磁盘，但需要在内存里排序，结果集大时会占用大量内存甚至落盘。

第三步：索引设计

原则一：最左前缀

联合索引 idx(a, b, c) 能支持的查询：

记住一条：范围查询（>、<、BETWEEN、LIKE）会让它后面的列无法使用索引。

原则二：把选择性高的列放前面

选择性 = 不重复值数量 / 总行数。越接近 1 越好。

status 只有几个值，选择性极低，单独建索引基本没用（优化器会直接放弃）。但放在联合索引里作为第二列是可以的——它能在 user_id 筛选后进一步缩小范围。

例外：如果某个低选择性列是高频等值查询条件，且能和其他列组成联合索引，仍然有价值。

原则三：覆盖索引

如果查询需要的列都在索引里，就不需要回表（Using index）。

这是最有效的优化手段之一，尤其对高频查询。代价是索引变宽、占用更多空间、写入稍慢。

注意：SELECT * 几乎不可能被覆盖，这也是”不要用 SELECT *“的实际原因之一。

原则四：索引下推（ICP）

MySQL 5.6+ 默认开启。作用是把 WHERE 中能用索引判断的条件下推到存储引擎层，减少回表次数。

没有 ICP 时：先用 user_id 找到主键 → 回表 → 再判断 name。
有 ICP 时：在索引上就判断 name，只有满足的才回表。

表现是 Extra 里出现 Using index condition。

第四步：这些写法会让索引失效

即使建了索引，下面这些写法仍会导致全表扫描：

1. 在索引列上做运算或函数

2. 隐式类型转换

这个坑很隐蔽：WHERE varchar_col = 123 会触发隐式转换，MySQL 把字符串转成数字比较，索引失效。反过来的情况（数字列传字符串）通常不会失效，因为数字列会优先转成数字。

3. 前导模糊匹配

4. OR 连接不同列

5. != / NOT IN / NOT EXISTS

这类”否定条件”通常无法有效利用索引（因为要扫描的范围太大）。但要注意：这不绝对 —— 如果 != 能排除掉绝大部分数据，优化器可能仍会走索引。用 EXPLAIN 验证，不要背结论。

6. 字符集/排序规则不一致的联表

统一字符集（现在推荐全部 utf8mb4）。

几个典型场景

深分页

方案二能生效的前提是子查询能走覆盖索引（只取 id）。

大表加索引 / 改表结构

MySQL 5.6+ 的 ALGORITHM=INPLACE 支持在线加索引（不阻塞 DML），但仍需注意：

生产环境建议用 gh-ost 或 pt-online-schema-change，它们通过建影子表 + 增量同步的方式，把风险控制得更小，且可暂停/回滚。

COUNT(*) 很慢

InnoDB 不保存精确行数（因为 MVCC），COUNT(*) 需要扫描。优化方向：

  • 用覆盖索引扫描（选最小的索引）
  • 业务上接受近似值（用 EXPLAIN 的 rows 估算）
  • 维护计数表（用触发器或应用层增量更新）

子查询 vs JOIN

MySQL 5.6 之前子查询性能很差（相关子查询会逐行执行）。5.6+ 优化器会把很多子查询改写成 JOIN，但不是所有都能优化。

建议：能用 JOIN 就用 JOIN，尤其是 IN (SELECT ...) 这种写法。用 EXPLAIN 确认执行计划符合预期。

优化检查清单

  • 慢查询日志已开启，long_query_time 设到合理值（不要用默认 10 秒）
  • 用 pt-query-digest 按总耗时排序找 TOP SQL，而不是按单次耗时
  • 检查 rows_examined 与 rows_sent 的比例（比例过大说明索引没用好）
  • 核心 SQL 的 type 达到 ref / range，没有 ALL
  • Extra 里没有大结果集的 Using filesort / Using temporary
  • 联合索引符合最左前缀，且高选择性列在前
  • 高频查询考虑覆盖索引（Using index），避免 SELECT *
  • 确认没有在索引列上做函数运算、隐式类型转换、前导模糊
  • 联表的字符集一致
  • 深分页已改为游标分页或延迟关联
  • 大表 DDL 走 gh-ost / pt-osc，不在业务高峰执行
  • 索引不是越多越好：定期用 sys.schema_unused_indexes 清理无用索引

小结

慢查询优化有一条稳定的顺序：

先量出来（慢日志 + performance_schema）→ 再看执行计划（EXPLAIN）→ 再改索引或 SQL → 最后验证效果。

跳过前两步直接”加索引”，很容易加出无用甚至有害的索引。

另外两点经验：

  1. 索引不是越多越好。每个索引都要在写入时维护，也会占用缓冲池空间。定期清理无用索引
  2. EXPLAIN 是唯一的裁判。上面列的那些”索引失效规则”都有例外，最终要看执行计划，不要背结论
