    面向对象编程理解

    发表于 2018-05-14 更新于 2026-06-09 分类于 Java基础 阅读次数：

    背景

    学完了Java的基础语法，终于进入了面向对象编程这块硬骨头。在此之前我一直用的是C语言写一些小项目，习惯了面向过程的思维方式——写一个函数，调用它，再写一个函数，再调用它，整个程序就是一系列函数的调用链。突然切换到面向对象，感觉脑子有点转不过弯来。

    我记得《Head First Java》里面有一个很形象的类比：说类就像是饼干的模具，而对象就是用这个模具做出来的饼干。模具本身是一个概念上的模板，真正的饼干才是实在的东西。这个类比让我开始慢慢理解”对象”到底是个什么东西。

    还特意去图书馆借了本《Java编程思想》，翻了几章感觉有点深，还是先老老实实把基础搞懂再说。

    问题

    刚开始学的时候，遇到了好多困惑：

    第一，类和对象的关系总是搞不清楚。 我知道类是用class关键字定义的，对象是用new创建出来的，但实际写代码的时候，完全不知道什么时候该定义类，一个类应该包含哪些东西。经常写着写着就把所有代码塞到一个类里面，跟写面向过程没什么区别。

    第二，封装的意义不理解。 刚接触private、public这些访问修饰符的时候，我就想：为什么要把字段设为private，然后还要写getter和setter去访问？这不脱裤子放屁吗？直接public不是更省事？

    第三，继承和组合不知道怎么选。 看了书上的例子说”猫是一种动物”可以用继承，”车有轮子”可以用组合。但实际写代码的时候，总是倾向于用继承，觉得extends一下什么都有了，方便。

    第四，多态太抽象了。 书上说”父类引用指向子类对象”，这句话我背都能背下来，但就是不知道这玩意儿到底有什么用，写代码的时候也完全想不起来用。

    第五，接口和抽象类看着差不多，不知道怎么选。 两个都不能实例化，都包含抽象方法，到底有啥区别？

    分析

    随着写了一些小例子，慢慢对这些概念有了自己的理解。

    类和对象： 类就是一个模板/蓝图，比如说”学生”这个概念，它有一些属性（姓名、学号、年龄）和行为（学习、考试）。而对象就是根据这个模板创建出来的具体实例，比如”张三”这个具体的学生。写代码的时候，应该先分析业务需求中有哪些实体，每个实体有什么属性和行为，再来定义类。


    配图说明：面向对象三大特性关系图

    封装： 现在理解了，封装的意义在于保护内部状态。如果不封装，外部代码可以随意修改对象的内部数据，可能会导致数据不一致。比如一个Student的age字段，如果直接暴露为public，外部可以给它赋一个-1这种不合理的值。通过setter方法，可以在赋值前做校验。

    继承与组合： “IS-A”关系适合用继承，”HAS-A”关系适合用组合。但继承的问题在于，父类的任何变化都会影响到所有子类，耦合度太高。现在很多书都推荐优先使用组合，组合更灵活，耦合度更低。

    多态： 多态的本质就在于父类引用指向子类对象，调用的方法却是子类重写后的版本。这样做的最大好处是：可以写通用的代码来处理不同的具体类型。比如定义一个统一的pay()方法，不管是学生交学费，还是员工发工资，都调用同一个方法名，具体怎么实现由子类自己决定。

    接口与抽象类： 接口定义的是行为契约——“你能做什么”；抽象类提供的部分实现——“你是什么”。接口强调的是能力，抽象类强调的是血缘关系。接口弥补了Java单继承的不足，一个类可以实现多个接口。

    接口示例：实现Comparable接口

    实现Comparable接口，就是告诉别人：我这个类的对象是可以比较大小的。这意味着你可以把这个类的对象放进TreeSet、用Collections.sort()排序等等。这就是面向接口编程的思想——依赖接口而不是具体实现。

    抽象类示例：Shape -> Circle / Rectangle

    抽象类Shape定义了形状该有的行为（求面积、求周长），但具体的计算方式交给子类去实现。display()方法是通用的，在抽象类里直接实现就好，子类不用重复写。

    总结

    折腾了两周，对面向对象总算有了个整体的认识。总结一下这几个星期的收获：

    1. 三大特性：封装、继承、多态。封装保护内部数据，继承实现代码复用，多态让代码更灵活。这三个东西是面向对象的基石，缺一不可。

    2. 设计思路要转变：从面向过程的”先想步骤”变成面向对象的”先找对象”。写代码之前先分析业务中有哪些实体（类），它们有什么属性和行为，它们之间有什么关系。这个思维转换确实需要时间，但慢慢练习就会习惯。

    3. 优先用组合：虽然继承用起来方便，但继承会让父类和子类耦合太紧。如果只是想要复用代码，组合往往是更好的选择。只有当确实是”IS-A”关系，并且行为需要多态时，才考虑继承。

    4. 面向接口编程：接口定义契约，实现类去遵守契约。这样写出来的代码耦合度低，扩展性好。比如排序功能依赖Comparable接口而不是具体的类，以后想换排序规则，只要改compareTo()的实现就好了。

    面向对象的路才刚刚开始，后面还有设计模式等着我。不过有了这些基础，至少看代码的时候不会再一头雾水了。继续加油！
