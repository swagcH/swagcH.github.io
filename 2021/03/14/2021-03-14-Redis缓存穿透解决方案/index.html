Redis缓存穿透解决方案

发表于 2021-03-14 更新于 2026-08-26 分类于 故障排查 阅读次数：

缓存穿透指查询一个本来就不存在的数据：Redis 每次未命中，请求继续访问数据库，数据库也返回空。只要请求使用不同的无效 ID，普通缓存几乎没有保护作用。

为了把不同方案的效果看清楚，我在隔离环境做了四轮攻防实验。压测数据均为构造数据，不针对真实线上服务。

数据库 CPU 尚未完全打满，但连接等待已经影响正常商品查询。穿透的危险不只在攻击，爬虫错误、客户端循环重试、过期链接也可能制造相同流量。

第二轮：在入口拒绝不可能的请求

第一层防护不需要 Redis。根据业务约束检查：

Controller 层只负责格式校验，用户是否有权访问某商品仍由业务层判断。不能因为引入缓存就绕过权限。

格式校验挡住了 20% 请求，数据库 QPS 降到约 1,240，但格式合法的随机 ID 仍然会穿透。

这里的 MAX_PRODUCT_ID 只能在业务编号确有稳定上界时使用。若 ID 来自分布式算法或外部系统，不应凭当前最大值拒绝未来合法数据。

第三轮：短时间缓存“确实不存在”

数据库返回空时写一个特殊标记：

空值缓存适合重复查询同一批无效 ID，例如错误链接或客户端重试。本次压测把无效 ID 集合限制在 1 万个，第二遍请求后数据库 QPS 降到 180 左右。

但如果攻击者每次生成全新 ID，空值缓存仍会不断创建新 key。还要防止 Redis 被大量无效键占满：

  • 空值 TTL 明显短于正常数据。
  • key 使用固定格式，不直接拼接任意长参数。
  • 监控空值 key 创建速率。
  • 对调用方和来源做限流。

商品创建后应主动删除对应空值缓存，否则在 TTL 到期前会得到“商品不存在”。

第四轮：布隆过滤器挡住大范围不存在 ID

布隆过滤器能快速回答“这个 ID 一定不存在”或“可能存在”。它允许少量误判存在，但不会把真实存在的 ID 判断为不存在，前提是数据同步正确。

布隆过滤器的维护比接入更难

实现时必须回答：

普通布隆过滤器不支持可靠删除。商品下线后保留为“可能存在”只会多查一次数据库，可以接受；错误删除一个仍存在的商品则可能直接返回空，不能接受。

容量估小后误判率会持续上升。重建时可以生成新版本，完成数据校验后原子切换，不要在原过滤器上边清边写。

限流保护的是最后边界

即使 Bloom 正常，也要限制异常来源。限流维度可以包括：

  • 用户或应用凭证。
  • 租户。
  • 客户端 IP，作为辅助而非唯一身份。
  • 接口和资源类型。
  • 单次批量大小。

超限时返回明确错误码和重试时间，不要让客户端立即无限重试。对于登录前公开接口，还需要网关防护和行为识别。

限流阈值根据正常峰值与容量测试确定。过低会伤害真实用户，过高则无法保护数据库。

别把缓存击穿和雪崩混进来

空值缓存和 Bloom 主要解决穿透；互斥加载或逻辑过期更适合热点击穿；随机 TTL、预热、限流和高可用用于雪崩。先分类，再选择方案。

生产落地清单

缓存穿透没有一个单点“银弹”。真正可靠的是多层减压：明显错误尽早拒绝，重复空结果短期记住，大范围不存在 ID 用概率结构过滤，异常流量在入口限速，而数据库仍保留最后的事实判断。
