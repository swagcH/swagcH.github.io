MySQL慢查询分析

发表于 2021-02-21 更新于 2026-08-26 分类于 故障排查 阅读次数：

这篇记录一次慢查询实验。目标不是看到耗时下降就结束，而是把每次改动的假设、执行计划、扫描行数和副作用放在一起比较。

测试表约 320 万行，问题接口查询某租户最近的已支付订单。文中的数据来自隔离环境，生产索引变更仍需要单独评估锁、磁盘和主从延迟。

假设 A：只强制使用租户索引

为了验证选择性，我在隔离环境使用 FORCE INDEX 做对照：

扫描从约 112 万行下降到 31 万行，平均耗时从 2.8 秒下降到 0.9 秒，但仍需要过滤和排序。

这个实验说明 tenant_id 比 status 更有选择性，不说明应该把 FORCE INDEX 写进业务 SQL。数据分布变化后，强制策略可能比优化器更差。

慢查询日志里的实际 Rows_examined 比 EXPLAIN rows 更能反映本次执行。执行计划的 rows 是估算值，两者不应混为一谈。

假设 C：把所有返回列都塞进索引

有人提出把 order_no 和 amount 也加到索引，做成覆盖索引。实验中查询确实少了回表，但收益只有几毫秒，索引体积和写入成本却继续增加。

这个接口只读取 50 行，回表 50 次并不是主要矛盾。最终没有扩大索引。

覆盖索引适合返回列少、调用频繁、扫描量明显的场景。不能为了让 Extra 出现 Using index，就把大字段和大量业务字段都加入索引。

假设 D：去掉时间条件会怎样

另一个接口复用了相同 SQL，但允许用户查询全部历史。去掉 created_at 条件后，联合索引仍能根据租户和状态定位，并按时间取前 50 条，因此首页仍然很快。

问题出现在深分页：

数据库必须跳过前 20 万条，耗时重新上升。解决方式不是继续加索引，而是改成游标：

为了让排序稳定，正式方案将 id 放到索引末尾并作为游标的一部分。仅按时间分页时，相同时间的记录可能重复或遗漏。

这次优化最有价值的并不是“加了一个联合索引”，而是验证过程：先用真实慢日志建立基线，再用单列索引实验理解选择性，最后让索引顺序匹配查询模式，并拒绝收益很小的过宽覆盖索引。
