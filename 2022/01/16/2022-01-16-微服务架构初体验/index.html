微服务架构初体验

发表于 2022-01-16 更新于 2026-08-26 分类于 架构成长 阅读次数：

写在前面：第一次接触微服务时，我也把重点放在“怎么拆”上。真正做过一轮以后才发现，拆出几个 Spring Boot 项目并不难，难的是决定边界、管理失败，以及接受一次本地调用变成网络调用之后带来的全部成本。

2022 年开始认真研究微服务，起点并不是单体应用已经完全不能运行，而是它的协作成本逐渐变高。订单、用户、库存和支付都在同一个工程里，改一个公共对象可能影响四个模块；一次发布要把所有功能一起上线；某个报表任务把内存打满，也会拖垮订单接口。

这篇更像一次架构决策记录：为什么考虑拆分、边界怎么判断，以及第一轮实践中哪些想法后来被证明太理想化。

1. 单体到底遇到了什么问题

当时的工程结构其实很清楚：

代码目录清楚，不代表业务边界清楚。几个比较明显的信号是：

  1. order 可以直接修改库存表，stock 也会反过来查询订单状态。
  2. 用户、订单和营销共用一套“万能 DTO”，新增字段以后所有模块一起回归。
  3. 一个模块的慢 SQL 会耗尽公共数据库连接池。
  4. 不相关的功能被迫一起构建、一起发布、一起回滚。
  5. 团队开始频繁解决代码冲突，而不是业务问题。

这些问题不一定要求立即微服务化。很多时候先做模块化、清理依赖方向、拆分数据库账号，就能继续支撑很长时间。真正推动拆分的，是某些业务能力已经有独立迭代和独立扩缩容的需要。

这只是把技术分层变成网络分层。一次请求仍然要在多个服务之间来回跳，common-service 很快又会变成新的大单体。

后来我主要从四个维度判断边界：

维度 要问的问题
数据归属 谁创建、修改并解释这份数据
业务闭环 能否在服务内部完成主要状态流转
变化节奏 是否需要独立发布和扩容
故障影响 服务失败时能否被隔离或降级

以库存为例，库存数量、冻结量和扣减记录应该由库存服务解释。订单服务可以请求扣减库存，但不能绕过接口直接更新库存表。支付服务外部依赖多、回调状态复杂，也适合拥有独立边界。

“一个服务一个数据库”表达的是数据所有权，不一定要求物理上马上购买四套数据库。早期可以在同一个数据库实例创建独立 schema 和账号，但必须禁止跨服务直接写表，否则服务只是代码仓库分开，耦合仍然留在数据库里。

3. 先定义契约，再搬代码

本地方法可以传任意对象，远程接口必须考虑兼容性。库存扣减接口至少要有业务请求号、SKU、数量和调用方：

返回值也不能只用 boolean，否则调用方无法区分库存不足、重复请求和服务异常：

接口契约需要明确：

  • 哪些字段必填，长度和取值范围是什么。
  • 重复提交同一个 requestId 会发生什么。
  • 业务失败和系统失败分别使用什么错误码。
  • 接口超时以后，调用方如何查询最终结果。
  • 新增字段如何保证旧调用方还能正常反序列化。

如果这些问题没有答案，服务拆得越多，调用关系越难维护。

5. 同步调用不是默认答案

服务之间的通信方式要根据业务语义决定：

用户查询订单时同步读取订单服务是合理的；订单创建后发送通知，没有必要阻塞主流程。库存扣减是否同步，要看业务是否必须立即告诉用户结果。

同步链路越长，可用性越低。假设三个下游服务可用性都是 99.9%，串联后整条链路理论可用性已经低于单个服务。还要叠加网络延迟、连接池、超时和重试带来的影响。

因此每个远程调用都应该回答：

  1. 连接超时和读取超时是多少。
  2. 能不能重试，重试是否会造成重复写入。
  3. 下游失败时是降级、排队还是直接失败。
  4. 整条请求链的总超时预算是否合理。

6. 第一批服务怎么选

我不建议第一次就拆订单主链路。更稳妥的顺序是：

  1. 先整理单体内部的模块依赖，禁止反向调用。
  2. 选择只读、边界清晰的能力，例如用户信息查询。
  3. 通过防腐层封装远程调用，让业务代码不直接依赖 HTTP 细节。
  4. 补齐 traceId、接口耗时、错误码和调用日志。
  5. 做灰度路由，保留回到本地实现的开关。
  6. 运行一个完整业务周期后，再决定下一个边界。

这种方式看起来慢，但每一步都能回退。一次性拆完所有模块，出现问题时很难判断是边界错误、网络问题还是组件配置问题。

8. 哪些情况暂时不适合拆

微服务不是规模小就不能用，也不是业务复杂就必须用。我会在下面这些情况下优先保留模块化单体：

  • 团队很小，所有模块由同一组人维护。
  • 业务边界还在频繁变化，服务拆分后会不断调整接口。
  • 没有自动化部署和基本监控。
  • 当前瓶颈是慢 SQL、代码质量或产品方向，而不是单体架构。
  • 数据强一致要求很高，拆分收益不足以覆盖一致性成本。

模块化单体同样可以有清晰边界、独立模块和严格依赖方向。它不是微服务的反面，而是很多系统更合适的阶段。

9. 这一阶段最大的认识

第一次实践以后，我对微服务的理解从“多个独立应用”变成了“围绕业务边界管理复杂度”。它确实能带来独立发布、故障隔离和按需扩容，但同时把网络、数据一致性、可观测性和运维成本带进了日常开发。

判断一次拆分是否成功，不应该看服务数量，而应该看几个结果：发布是否更独立，故障是否更容易隔离，团队是否减少相互等待，业务状态是否仍然可解释。如果这些指标没有改善，只是仓库和进程变多了，那就还没有真正获得微服务的收益。
