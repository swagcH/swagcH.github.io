SpringCloud 微服务拆分：一次真实的架构演进

发表于 2026-09-20 更新于 2026-10-16 分类于 Java ， 微服务

“微服务拆分”经常被当成一个技术动作——把单体拆成几个服务，引入注册中心和网关就算完事。但实际做下来会发现，**拆分的难点从来不在技术组件，而在”边界怎么划”和”拆完之后怎么运维”**。

这篇文章以我负责的一个集团级数据大屏项目为例，记录从架构选型、服务边界划分、异构系统集成，到部署与运维的完整过程。重点写判断依据和踩过的坑，而不是组件清单。

项目背景

规模：围绕 7 大主题（集团概况、产业布局、低碳电力、生态环保、综合燃气、数智服务、专题介绍）建设，共 36 个业务板块，接入 167 家生产企业，展示 6000 余项数据。

复杂度来源：需要与大数据平台、SIS（厂级监控信息系统）等 9 个异构系统做数据集成，对外提供 580 个指标。

约束：只有 4 台服务器，且要保证大屏展示的高可用（大屏是给领导看的，宕机影响面大）。

一、架构选型：为什么是 SpringCloud

候选方案对比

方案 优势 代价
单体 + 模块化 部署简单、无网络开销、事务简单 一处改动全量发布、无法按模块扩容
SpringCloud 生态成熟、团队熟悉、组件可选 运维复杂度上升（注册中心、网关、配置中心）
SpringCloud Alibaba 自带 Nacos/Sentinel，国内生态好 与 SpringCloud 有版本对齐成本
Dubbo RPC 性能好 偏 RPC 调用，服务治理组件需自行补齐

最终选 SpringCloud + Nacos，理由是：

  1. 团队熟悉度优先。技术选型要考虑团队能不能 hold 住，而不只是”哪个更先进”
  2. Nacos 一个组件同时解决注册中心和配置中心，比 Eureka + Config 两套更省运维
  3. 生态和文档成熟，出问题容易找到资料
  4. **数据大屏本质是”多数据源聚合 + 展示”**，对 RPC 性能要求不高，Dubbo 的性能优势用不上

拆几个服务？按什么拆？

这是最容易做错的决策。 我见过两种极端：

  • 拆太细：一个业务拆七八个服务，一个请求跨五六个服务，排查问题要开一堆日志窗口
  • 拆太粗：只有两个服务（”前端服务”和”后台服务”），等于没拆

我的拆分依据（按优先级）：

1. 按变化频率拆

变化快的模块独立出来，避免每次小改动都要全量发布。比如”专题介绍”这类内容型板块，运营经常要调整，独立成服务后可以单独发布。

2. 按数据源拆

不同数据来源的模块分开，隔离故障。这个项目里有 9 个外部系统，如果全部塞在一个服务里，任何一个上游慢都会拖垮整个服务。

3. 按性能特征拆

读多写少和写多读少分开；实时查询和离线统计分开。大屏的”实时指标”和”历史趋势”承担的负载完全不同，拆开后可以独立扩容。

4. 按团队边界拆（如果有多个团队）

康威定律：系统架构会趋同于组织结构。如果有明确的团队边界，按团队拆能减少协作成本。

最终拆成了 6 个服务：

服务 职责 拆分依据
gateway 统一入口、路由、鉴权、限流 基础设施
auth-service 认证授权、菜单权限 变化频率低但被所有服务依赖
metric-service 指标数据的接入与统一 数据源最多、最复杂
board-service 大屏各板块的数据组装 读多写少、变化频繁
screen-service 监控画面相关 数据源独立、性能特征不同
system-service 系统管理、字典、日志 通用能力

注意 metric-service 单独拆出来的原因：它是整个项目最复杂的部分——要把 9 个来源、格式各异的数据统一成 580 个指标的标准模型。把它独立出来，一方面隔离了”上游系统不稳定”的风险，另一方面它的迭代节奏和其他服务完全不同。

二、异构系统集成：最花时间的部分

9 个系统、580 个指标，这部分工作量远超预期。

难点在哪

1. 接口协议各不相同

有的提供 REST API，有的是数据库直连，有的是消息推送（Kafka/MQ），还有的只能通过文件交换。没有统一的接入方式。

应对：设计统一接入层，每种协议实现一个适配器，向上暴露统一接口。

业务代码只依赖 MetricSourceAdapter，不关心具体来源。新增一个来源系统，只需实现一个适配器。

2. 指标口径不一致

同一个指标（比如”发电量”）在不同系统里的定义、单位、统计周期可能不同。这是最容易被低估的坑——不做统一，大屏上会出现”同一个指标在不同板块数字不一样”。

应对：建立指标字典，作为唯一数据源。

关键点：

  • 指标编码全局唯一，所有服务都通过 metric_code 取数，不直接引用上游字段
  • 转换逻辑配置化（transform_expr），口径调整不用改代码
  • 更新周期分开配置，实时指标和高频统计不用同样的刷新频率

3. 更新频率差异大

有的数据秒级更新，有的是天级批量。如果统一按最高频率拉取，会造成大量无效请求。

应对：按指标配置更新周期 + 分层缓存。

数据一致性

跨系统取数存在时序差异：A 系统的数据已更新，B 系统还是旧的，聚合结果会不一致。

应对：

  • 单个指标内保证一致（同一个指标只从一个系统取）
  • 跨指标聚合时记录数据时间戳，大屏上展示”数据更新时间”，让使用者知道数据的新鲜度
  • 不做跨系统的强一致——这在异构集成的场景下成本过高且收益有限

服务间调用：Feign + 超时与熔断

必须配置熔断降级：

为什么大屏项目一定要有降级：大屏是多个板块拼起来的，如果”综合燃气”板块的服务挂了，不应该导致整个大屏白屏。局部降级 + 提示比整体不可用体验好得多。

配置中心：Nacos

为什么需要：服务多起来之后，改一个配置（比如超时时间）要重启所有服务是不可接受的。

实践建议：

  • 公共配置和服务配置分开：数据库、Redis 这类所有服务都要用的放公共配置
  • 敏感信息用环境变量注入，不要明文写在配置中心（至少要用加密配置）
  • 开启 refresh: true 但要注意范围：不是所有配置都能热更新（比如数据库连接池的核心参数）

高可用部署：只有 4 台服务器怎么办

约束：4 台服务器，要跑 6 个服务 + Nacos + Redis + MySQL + Nginx，还要保证大屏不挂。

方案：

关键判断：哪些必须高可用，哪些可以单点？

组件 是否高可用 理由
Nacos ✅ 必须 注册中心挂了，所有服务无法互相发现
网关 ✅ 必须 单点挂了整个系统不可访问
核心业务服务 ✅ 关键服务双实例 大屏主板块不能挂
Redis ⚠️ 主从 + 哨兵 缓存挂了可以降级到数据库，但不能长时间挂
MySQL ⚠️ 主从 主库挂了只读可用，写入中断
非核心服务 ❌ 可单点 系统管理、日志服务挂了不影响大屏展示

这是资源受限下的务实做法：不是所有组件都做高可用（成本不允许），而是按影响面排序，把资源投在最关键的地方。

数据库分片

数据量增长后（指标数据是持续写入的时序数据），单表查询变慢。使用 ShardingSphere 按企业维度分片。

详细的分片设计见：ShardingSphere 分库分表实践：从选型到踩坑

这里补充一点分片在微服务架构下的特殊考虑：

  • 分片规则要配置在所有访问该表的服务里（ShardingSphere-JDBC 模式），服务越多，规则同步越容易出问题
  • 如果服务数量继续增加，应该考虑改用 ShardingSphere-Proxy，把分片规则集中到代理层
  • 跨服务的分片键必须统一，否则 A 服务按 tenant_id 分片、B 服务按 device_id 分片，联表查询会变成全路由

四、踩过的坑

坑 1：服务拆分过细导致排查困难

现象：初期把一个板块拆成了 4 个服务，结果一个页面加载要调 6 个服务，某次线上问题排查花了很久——因为日志分散在多个服务里，无法串起来。

解决：

  • 引入链路追踪（SkyWalking / Sleuth + Zipkin），给每个请求分配 TraceId，日志里带上它
  • 合并过细的服务。把”强相关、总是一起变化”的服务合并回去
  • 教训：拆分的粒度应该按”变化频率”和”数据边界”，不是按”功能数量”

坑 2：Nacos 配置的命名空间混用

现象：测试环境的服务连到了生产环境的配置，导致测试时改了生产的参数。

原因：Nacos 的 namespace / group / data-id 三层没有规划好，不同环境用同一个 namespace。

解决：按环境划分 namespace，且用 CI/CD 注入，不允许手工配置。

坑 3：Feign 调用没有传递认证信息

现象：网关鉴权通过后，服务内部通过 Feign 调用其他服务时丢了用户上下文，导致下游服务拿不到用户信息。

解决：用 RequestInterceptor 把认证信息透传下去。

注意：这只是内部调用的上下文透传，下游服务仍要校验，不能信任上游传过来的身份（零信任原则）。

坑 4：大屏接口响应慢，实际是串行调用

现象：大屏首页要展示十几个板块，响应时间超过 3 秒。

原因：代码里十几个板块的数据是串行获取的。

解决：改成并行 + 统一超时。

两个关键点：

  • 单个板块超时后降级为空，不影响其他板块（大屏部分数据缺失比整个页面加载失败好）
  • 用独立的线程池（boardExecutor），不要用默认的 ForkJoinPool.commonPool()——被阻塞的任务会拖垮整个应用的其他并行操作

优化后响应时间从 3 秒降到 800ms 左右。

五、架构演进的经验总结

关于拆分

  1. 先单体，后拆分。项目初期业务边界不清晰，过早拆分会导致频繁调整。我们的做法是先按模块化单体开发，明确边界后再拆
  2. 拆分依据按优先级：变化频率 > 数据源 > 性能特征 > 团队边界
  3. **拆完要能说清”为什么这么拆”**。如果只能说”按业务拆的”，说明还没想清楚

关于治理

  1. 超时和熔断必须在第一版就有。后期补的代价是”已经出过故障”
  2. 链路追踪不是可选项。服务超过 3 个，没有 TraceId 排查就是大海捞针
  3. 降级方案要有明确的触发条件和预期行为（比如”指标服务不可用时返回缓存数据，并在大屏上标注数据延迟”）

关于资源受限的现实

不是所有组件都要高可用。 4 台服务器的约束下，正确的做法是：

  1. 列出所有组件
  2. 按”挂了的影响面”排序
  3. 把有限的资源投在前几名

这个排序本身就是架构能力的体现——能说清”为什么 Nacos 必须双节点，而日志服务可以单点”，比笼统地说”我们做了高可用”更有说服力。

落地检查清单

  • 服务拆分有明确依据（能说清每个服务为什么独立）
  • 拆分的粒度合理（没有”一个请求跨 5 个服务”的情况）
  • 有统一入口网关（路由、鉴权、限流）
  • 注册中心高可用（至少 2 节点）
  • 配置中心按环境隔离 namespace
  • 服务间调用配置了超时（不用默认值）
  • 关键调用有熔断降级，且降级行为明确
  • 认证信息在服务间正确透传，且下游仍做校验
  • 引入链路追踪，日志带 TraceId
  • 异构数据源有统一接入层，新增来源不改业务代码
  • 指标/字段有统一字典，口径问题在字典层解决
  • 按影响面确定高可用范围，重点资源投在关键组件
  • 大屏/首页类接口做并行聚合 + 单点超时降级
  • 独立线程池隔离不同业务，不共用默认池

小结

微服务架构的价值不是”用了多少组件”，而是能不能按业务的真实边界把系统切开，并让每个部分独立演进、独立扩缩容、故障隔离。

回顾这个项目，我认为最有价值的三个决策是：

  1. 先模块化单体，边界清晰后再拆——避免了初期反复调整服务划分
  2. 把最复杂的指标接入独立成服务——隔离了”上游 9 个系统不稳定”这个最大风险源
  3. 按影响面分配高可用资源——在 4 台服务器的约束下做了务实的取舍

而最该早点做的是链路追踪——服务一多，没有它排查问题会非常痛苦。

MySQL 慢查询优化：从执行计划到索引设计

发表于 2026-07-08 更新于 2026-10-16 分类于 数据库 ， 性能优化

“加个索引”是解决慢查询最常见也最容易用错的建议。加错索引不但不解决问题，还会拖慢写入、占额外空间，甚至让优化器选错执行路径。

这篇文章按实际排查顺序组织：怎么定位慢查询 → 怎么读执行计划 → 怎么设计索引 → 哪些写法会让索引失效。最后给一份可以照着走的检查清单。

第一步：先定位，不要猜

优化最容易犯的错是”凭感觉猜哪个 SQL 慢”。先把慢的找出来。

慢查询日志

注意 long_query_time 的单位是秒，可以设小数（比如 0.5）。很多线上问题的 SQL 执行时间是几百毫秒，按默认 10 秒根本抓不到。

用 mysqldumpslow 或 pt-query-digest 聚合分析，按总耗时排序而不是单次耗时——一条 50ms 但每秒执行 1000 次的 SQL，比一条 2 秒但每小时执行一次的 SQL 危害大得多。

performance_schema

关键看 rows_examined 和 rows_sent 的比例。如果扫描了几十万行只返回 10 行，说明索引没用好。

第二步：读懂 EXPLAIN

EXPLAIN 是排查的核心工具。重点看这四列：

type：访问类型（最重要的列）

从好到坏：

type 含义 说明
system 表只有一行 极少见
const 主键或唯一索引等值查询 最优
eq_ref 联表时用主键/唯一索引 联表场景最优
ref 非唯一索引等值查询 常规业务的目标
range 索引范围扫描 可接受（BETWEEN、>、IN）
index 扫全索引树 比 ALL 好一点，仍需警惕
ALL 全表扫描 必须处理

判断标准：核心业务 SQL 至少要达到 ref 或 range。出现 ALL 或 index 就要具体分析。

key 与 key_len

  • key：实际使用的索引。如果 possible_keys 有值但 key 是 NULL，说明优化器认为走索引不划算（通常是索引选择性太差）
  • key_len：使用到的索引长度（字节）。可以用来判断联合索引用到了几列

key_len 的计算（以 InnoDB、utf8mb4 为例）：

类型 长度
INT 4 字节（允许 NULL 则 +1）
BIGINT 8 字节
VARCHAR(n) 4n + 2（utf8mb4 每字符最多 4 字节，+2 存长度）
CHAR(n) 4n
索引列允许 NULL 额外 +1

举例：联合索引 idx(user_id, status, create_time)，其中 user_id BIGINT NOT NULL、status TINYINT NOT NULL。

这是验证”联合索引到底用了几列”最直接的方法，比猜靠谱。

rows 与 filtered

  • rows：预估需要扫描的行数。这是优化器基于统计信息的估算，不一定准，但数量级有参考价值
  • filtered：扫描后满足条件的行占比（百分比）。**rows × filtered% 才是真正参与后续操作的行数**

如果 rows 是 100 万但 filtered 是 0.01%，说明索引只起到了部分过滤作用，剩下大量行是在 Server 层过滤掉的。

Extra：一定要看的提示

Extra 含义 处理
Using index 覆盖索引，不需要回表 ✅ 好
Using where Server 层还要过滤 结合 filtered 判断
Using filesort 需要额外排序，无法用索引顺序 ⚠️ 大结果集时是问题
Using temporary 用了临时表（常见于 GROUP BY / DISTINCT） ⚠️ 尽量消除
Using index condition 索引下推（ICP）生效 ✅ 好

Using filesort 是最常见的性能杀手。它不一定走磁盘，但需要在内存里排序，结果集大时会占用大量内存甚至落盘。

第三步：索引设计

原则一：最左前缀

联合索引 idx(a, b, c) 能支持的查询：

记住一条：范围查询（>、<、BETWEEN、LIKE）会让它后面的列无法使用索引。

原则二：把选择性高的列放前面

选择性 = 不重复值数量 / 总行数。越接近 1 越好。

status 只有几个值，选择性极低，单独建索引基本没用（优化器会直接放弃）。但放在联合索引里作为第二列是可以的——它能在 user_id 筛选后进一步缩小范围。

例外：如果某个低选择性列是高频等值查询条件，且能和其他列组成联合索引，仍然有价值。

原则三：覆盖索引

如果查询需要的列都在索引里，就不需要回表（Using index）。

这是最有效的优化手段之一，尤其对高频查询。代价是索引变宽、占用更多空间、写入稍慢。

注意：SELECT * 几乎不可能被覆盖，这也是”不要用 SELECT *“的实际原因之一。

原则四：索引下推（ICP）

MySQL 5.6+ 默认开启。作用是把 WHERE 中能用索引判断的条件下推到存储引擎层，减少回表次数。

没有 ICP 时：先用 user_id 找到主键 → 回表 → 再判断 name。
有 ICP 时：在索引上就判断 name，只有满足的才回表。

表现是 Extra 里出现 Using index condition。

第四步：这些写法会让索引失效

即使建了索引，下面这些写法仍会导致全表扫描：

1. 在索引列上做运算或函数

2. 隐式类型转换

这个坑很隐蔽：WHERE varchar_col = 123 会触发隐式转换，MySQL 把字符串转成数字比较，索引失效。反过来的情况（数字列传字符串）通常不会失效，因为数字列会优先转成数字。

3. 前导模糊匹配

4. OR 连接不同列

5. != / NOT IN / NOT EXISTS

这类”否定条件”通常无法有效利用索引（因为要扫描的范围太大）。但要注意：这不绝对 —— 如果 != 能排除掉绝大部分数据，优化器可能仍会走索引。用 EXPLAIN 验证，不要背结论。

6. 字符集/排序规则不一致的联表

统一字符集（现在推荐全部 utf8mb4）。

几个典型场景

深分页

方案二能生效的前提是子查询能走覆盖索引（只取 id）。

大表加索引 / 改表结构

MySQL 5.6+ 的 ALGORITHM=INPLACE 支持在线加索引（不阻塞 DML），但仍需注意：

**生产环境建议用 gh-ost 或 pt-online-schema-change**，它们通过建影子表 + 增量同步的方式，把风险控制得更小，且可暂停/回滚。

COUNT(*) 很慢

InnoDB 不保存精确行数（因为 MVCC），COUNT(*) 需要扫描。优化方向：

  • 用覆盖索引扫描（选最小的索引）
  • 业务上接受近似值（用 EXPLAIN 的 rows 估算）
  • 维护计数表（用触发器或应用层增量更新）

子查询 vs JOIN

MySQL 5.6 之前子查询性能很差（相关子查询会逐行执行）。5.6+ 优化器会把很多子查询改写成 JOIN，但不是所有都能优化。

建议：能用 JOIN 就用 JOIN，尤其是 IN (SELECT ...) 这种写法。用 EXPLAIN 确认执行计划符合预期。

优化检查清单

  • 慢查询日志已开启，long_query_time 设到合理值（不要用默认 10 秒）
  • 用 pt-query-digest 按总耗时排序找 TOP SQL，而不是按单次耗时
  • 检查 rows_examined 与 rows_sent 的比例（比例过大说明索引没用好）
  • 核心 SQL 的 type 达到 ref / range，没有 ALL
  • Extra 里没有大结果集的 Using filesort / Using temporary
  • 联合索引符合最左前缀，且高选择性列在前
  • 高频查询考虑覆盖索引（Using index），避免 SELECT *
  • 确认没有在索引列上做函数运算、隐式类型转换、前导模糊
  • 联表的字符集一致
  • 深分页已改为游标分页或延迟关联
  • 大表 DDL 走 gh-ost / pt-osc，不在业务高峰执行
  • 索引不是越多越好：定期用 sys.schema_unused_indexes 清理无用索引

小结

慢查询优化有一条稳定的顺序：

先量出来（慢日志 + performance_schema）→ 再看执行计划（EXPLAIN）→ 再改索引或 SQL → 最后验证效果。

跳过前两步直接”加索引”，很容易加出无用甚至有害的索引。

另外两点经验：

  1. 索引不是越多越好。每个索引都要在写入时维护，也会占用缓冲池空间。定期清理无用索引
  2. EXPLAIN 是唯一的裁判。上面列的那些”索引失效规则”都有例外，最终要看执行计划，不要背结论

RabbitMQ 在微服务解耦中的正确用法

发表于 2026-06-15 更新于 2026-10-16 分类于 Java ， 微服务

用消息队列”解耦”是最常见的说法，但真正落地时，大部分问题都出在可靠性上：消息发出去没到、到了但消费者处理失败、处理成功了但重复消费了两次。

这篇文章不讲 API 怎么调，而是讲清楚三件事：什么场景该用 MQ、怎么保证消息不丢、为什么消费端必须做幂等。

先明确：什么时候不该用 MQ

MQ 引入了新的故障点（Broker 挂了、消息积压、重复消费），所以先排除不该用的场景：

不该用的场景：

  • 需要同步返回结果的调用。比如”下单后立即返回库存扣减结果”——这种用 RPC 更直接，硬套 MQ 会让调用方需要额外等待回执
  • 强一致性要求。MQ 是最终一致的工具，跨服务强一致要靠分布式事务，不是 MQ 能解决的
  • 逻辑本来就简单。两个服务之间的简单调用，引入 MQ 后需要处理幂等、重试、死信，复杂度反而上升
  • 低延迟要求极高。多一跳 Broker 就多一次网络往返

适合用的场景：

  • 异步处理：主流程不需要等结果（发短信、生成报表、推送通知）
  • 流量削峰：瞬时高并发写请求先入队，消费者按自己的节奏处理
  • 系统解耦：一个事件需要多个下游响应，且下游可能随时增减
  • 最终一致：跨服务的状态同步，允许短暂延迟

我在项目里的实际场景：医院通行证系统中，人员服务（负责权限校验）和设备模块（负责闸机控制）原本是同步调用——设备模块响应慢或重启时，人员服务会跟着超时。改成 MQ 后，人员服务只负责”发布通行事件”，设备模块按自己的节奏消费，一方故障不再影响另一方。

选型：RabbitMQ 适合什么

中间件 定位 适合
RabbitMQ 传统消息队列，路由灵活 业务消息、需要复杂路由、消息量中等（万级 QPS）
Kafka 分布式流平台 日志采集、事件流、超高吞吐（十万级+）
RocketMQ 阿里开源，兼顾两者 电商交易、需要事务消息

选 RabbitMQ 的理由（我们的场景）：

  1. 路由能力强：Exchange + Routing Key 的组合能表达复杂的投递规则（比如”只发给某个院区的设备”）
  2. 消息量匹配：医院场景是万级 QPS，Kafka 的吞吐优势用不上，反而运维更重
  3. 有死信队列：处理失败的消息有天然的去处
  4. 延迟低：相比 Kafka 的批量设计，RabbitMQ 的单条投递延迟更低

如果消息量到十万级 QPS，或者需要消息回放（重新消费历史消息），就该选 Kafka。

交换机类型：路由能力的差异

RabbitMQ 的路由能力来自 Exchange + Routing Key 的组合，三种常用类型：

类型 路由规则 适用场景
direct 精确匹配 Routing Key 点对点业务指令
topic 通配符匹配（* 一个词，# 多个词） 按维度订阅（院区、设备类型）
fanout 忽略 Routing Key，广播到所有绑定队列 一个事件多个下游响应

routing key 就是契约。 路由能力越强，命名约定越要提前定清楚，否则后期会变成一堆含义不明的字符串。

我们在通行证系统里的用法：设备控制指令用 direct（精确投递到目标设备类型的队列）；通行事件用 topic（pass.{院区}.{设备类型}，方便按院区或按设备类型订阅）；系统通知用 fanout（短信、统计、日志三个下游各一个队列，新增下游不用改生产端）。

可靠投递：三个环节都可能丢消息

这是本文的核心。 消息从生产者到消费者，中间有三个可能丢失的环节：

三个环节都要处理，缺一个都不算可靠。

环节①：生产者 → Broker

问题：消息发出去了，但 Broker 没收到（网络抖动、Broker 重启）。

方案：发布者确认（Publisher Confirm）

注意：Confirm 只保证消息到了交换机，不保证进了队列。路由不到队列的情况要用 Returns 捕获。

方案二：事务（不推荐）

channel.txSelect() 也能保证，但性能下降严重（每次提交都要等 Broker 响应）。生产环境用 Confirm，不用事务。

环节②：Broker 内部

问题：Broker 收到了消息，但还没落盘就宕机了。

方案：三个都要持久化

三者缺一不可：交换机不持久化，重启后路由规则丢失；队列不持久化，重启后队列和消息一起没了。

代价：持久化会降低吞吐（要写磁盘）。对可靠性要求不高的场景（比如日志推送），可以不持久化换取性能。

环节③：消费者处理

问题：消息投递给了消费者，但处理过程中抛异常/服务重启，消息被丢弃。

方案：手动 ACK

关键点：

  • 默认的 auto 模式是坑：方法返回就 ACK，抛异常也 ACK（因为 Spring 捕获了），消息就丢了
  • 区分业务异常和系统异常：业务异常重试多少次都失败，应该记录后丢弃；系统异常（网络、超时）才值得重试
  • basicNack(requeue=true) 有风险：如果失败是必然的（比如数据格式错），会无限重试打满 CPU。应该配合重试次数限制 + 死信队列

消费端必须做幂等

这是最容易被忽略、也最容易出线上问题的一点。

为什么必须幂等

RabbitMQ（以及绝大多数 MQ）只能保证 at-least-once（至少一次），不能保证 exactly-once。原因是：

这个窗口无法消除，因为”处理”和”ACK”是两个动作，不可能原子。所以：

消费端必须假设”同一条消息可能被投递多次”，并保证重复处理的结果与处理一次相同。

实现方案

方案一：唯一 ID + 去重表（最通用）

关键：去重记录的插入和业务逻辑必须在同一个事务里，否则可能出现”去重记录写了但业务没执行”。

方案二：状态机（适合有明确状态流转的业务）

UPDATE ... WHERE 旧状态 的影响行数如果是 0，说明已经处理过了。

方案三：Redis 去重（适合高并发、可接受少量丢失）

注意：Redis 不是持久的，宕机或过期后去重失效。只适合对重复不敏感的场景。

方案四：业务天然幂等

最理想的情况是业务操作本身幂等，不需要额外机制。比如：

  • SET status = 'X'（赋值操作，执行多次结果相同）
  • 插入前先判断存在性

但这需要业务设计配合，不是所有场景都能做到。

我的选择

唯一 ID + 去重表，因为：

  • 通用，不依赖业务逻辑的特殊设计
  • 去重记录可查，出问题能追溯
  • 代价是一张表和一个唯一索引（可定期清理历史记录）

在项目里，通行记录和设备指令都用了这个方案。

顺序性

RabbitMQ 不保证全局顺序，但可以保证单队列内的顺序（单消费者时）。

如果需要顺序：

  1. 按业务键路由到同一队列。比如按 userId 取模路由，保证同一个用户的消息进同一个队列
  2. 单队列单消费者（并发度受限，需要权衡）

注意：即使这样，重试仍可能打乱顺序（失败的消息重回队列会排到末尾）。对顺序要求极高的场景（比如资金流水），需要在业务层做版本号校验。

死信队列与重试

死信（Dead Letter） 是指无法被正常消费的消息，进入死信的条件：

  1. 消息被 basicNack / basicReject 且 requeue=false
  2. 消息 TTL 过期
  3. 队列达到最大长度

消息积压

积压的常见原因：

  • 消费者处理太慢（业务逻辑重、有同步远程调用）
  • 消费者实例不够
  • 消费者出故障（一直重试失败的消息）

处理方式：

情况 处理
消费者处理慢 优化业务逻辑，或增加消费者实例
消费者数量不够 水平扩容（注意：队列的消费者数不能超过队列分片能力）
消息一直失败重试 定位根因；临时把失败消息转移到”待人工处理”队列
突发流量 加临时消费者快速消费，或按业务降级

关键：积压要有监控。rabbitmqctl list_queues name messages 或者通过管理插件看队列深度，超过阈值告警。

落地检查清单

  • 确认场景适合用 MQ（不需要同步返回、能接受最终一致）
  • 生产者开启 publisher-confirm，并处理未确认的消息（落库补偿）
  • 生产者开启 publisher-returns，处理路由失败
  • 交换机、队列、消息三者都持久化
  • 消费者用手动 ACK（不用默认的 auto）
  • 区分业务异常（不重试，记录后 ACK）和系统异常（重试）
  • 消费端实现幂等（唯一 ID + 去重表 / 状态机）
  • 需要顺序时，按业务键路由到同一队列
  • 配置死信队列，且死信有告警
  • 重试有次数上限，不是无限重回队列
  • 队列深度有监控和告警
  • 消息体不要太大（大对象放对象存储，消息里只传引用）

小结

MQ 的价值在于解耦和削峰，但代价是引入了最终一致性和重复消费的问题。用之前先想清楚：

  1. 这个调用真的需要异步吗？ 同步能解决就别上 MQ
  2. 消息丢了能接受吗？ 不能接受就必须做三个环节的可靠投递
  3. 重复消费会出问题吗？ 会出问题就必须做幂等

最后一点最重要：很多团队把 MQ 接进去就以为”解耦完成了”，但没有做幂等，结果上线后出现重复扣款、重复发短信、重复记录。这类问题的根因不是 MQ 不可靠，而是**消费端假设了”只会收到一次”**。

Redis 缓存设计：穿透、击穿、雪崩的实际处理

发表于 2026-05-24 更新于 2026-10-16 分类于 Java ， 数据库

“缓存穿透、击穿、雪崩”这三个词几乎每份面经都会出现，但实际项目里出问题的往往不是概念本身，而是方案选型时的取舍没想清楚：加布隆过滤器要不要考虑误判？互斥锁会不会把可用性问题变成响应时间问题？先删缓存还是先更数据库？

这篇文章按”现象 → 方案 → 代价”的方式整理一遍，最后给出我在项目里的实际做法。

先把三个概念分清

三者经常被混着说，但触发条件完全不同：

问题 触发条件 直接后果
穿透 查询根本不存在的数据 请求绕过缓存，每次都打到数据库
击穿 单个热点 key 过期瞬间 大量并发同时去数据库重建同一个 key
雪崩 大量 key 同时失效，或 Redis 整体不可用 数据库瞬间承接全部流量

一句话区分：穿透是”数据不存在”，击穿是”一个热点没了”，雪崩是”一大片同时没了”。

缓存穿透

现象

请求查询一个数据库里也不存在的 key（比如不存在的用户 ID、被删除的商品），缓存不会命中，请求直接落到数据库。

正常业务流量下这不是问题，但如果有人恶意用随机 ID 刷接口，每次都能绕过缓存，数据库就成了第一道防线。

方案与代价

方案一：缓存空对象

查不到也往缓存里写一个空值（或特殊标记），并设置较短的过期时间。

代价：如果攻击者用大量不同的随机 ID 刷，每个都会写入一个空值，内存会被打满。所以过期时间必须短，且最好配合下面的方案。

方案二：布隆过滤器

在缓存之前加一层布隆过滤器，把数据库里存在的 key 预先写进去。查询时先问布隆过滤器”这个 key 可能存在吗”，不存在就直接返回。

代价（这三个必须知道）：

  1. 有误判率：说”可能存在”时可能是误判（实际不存在），所以布隆过滤器只能挡住”确定不存在”的请求，不能替代真实查询
  2. 不支持删除：标准布隆过滤器删不掉元素。数据删除后过滤器里还在，会导致”明明删了却还被放行”。可以用计数布隆过滤器，或者定期重建
  3. 需要预热和同步：新增数据时要同步写入，否则新数据会被误挡

方案三：入口参数校验

最便宜的一层：ID 格式不对、超出范围、必填参数缺失的请求，在 Controller 层就拒掉，连缓存都不查。

我的实际做法

参数校验 + 缓存空值（短过期），没用布隆过滤器。原因：

  • 我们的 key 空间是可枚举的（用户 ID、设备 ID），攻击者能构造的”不存在 key”数量有限
  • 引入布隆过滤器需要额外的预热和同步逻辑，收益不匹配
  • 如果以后出现大规模随机 key 攻击，再上布隆过滤器

这不是”布隆过滤器不好”，而是”当前场景用不上”。 面试时被问到，说清楚这个判断过程比背方案更有说服力。

缓存击穿

现象

某个热点 key（比如首页配置、秒杀商品）过期的那一瞬间，大量并发请求同时发现缓存没了，一起去数据库查询并重建缓存。

注意：**击穿的前提是”热点”**。一个普通 key 过期，就算有几十个请求同时打过来，数据库也扛得住。

方案与代价

方案一：互斥锁重建

只让一个线程去查数据库并回填缓存，其他线程等待后重试。

代价：

  • 响应时间变长：没抢到锁的请求要等待。热点 key 重建如果本身很慢（比如要聚合多个服务），等待会很明显
  • 有死锁风险：必须给锁设过期时间，且要考虑业务执行超过锁时间的情况
  • 重试逻辑要防雪崩：如果重试太密集，等待的线程会形成新的压力

方案二：逻辑过期（不阻塞读）

缓存里存的 value 带一个过期时间字段，Redis 层面不设过期。读到发现逻辑过期时，返回旧值，同时异步触发一个线程去更新。

代价：

  • 会返回旧数据：业务必须能接受短暂的数据延迟（大部分场景可以，涉及金额的不行）
  • 实现更复杂：需要额外的线程池和锁管理
  • 缓存不会自动清理：逻辑过期不会删除 key，需要额外的清理策略

怎么选

场景 建议
数据一致性要求高，能接受短暂等待 互斥锁重建
响应时间敏感，能接受短暂旧数据 逻辑过期
key 极少且几乎不变 干脆不设过期，变更时主动更新

缓存雪崩

雪崩有两种成因，处理方式完全不同。

成因一：大量 key 同时过期

常见于”凌晨批量刷新缓存”的实现——如果所有 key 都设 expire = 3600，那么一小时后它们会同时失效。

方案：过期时间加随机偏移

这是成本最低、收益最高的一条，几乎零成本就能避免大部分雪崩。

成因二：Redis 整体不可用

单实例 Redis 宕机或网络分区，所有请求同时落到数据库。

方案（分层防御）：

  1. 高可用部署：哨兵（主从自动切换）或集群（分片 + 高可用）。这是基础，不是可选项
  2. 多级缓存：本地缓存（Caffeine）作为一级，Redis 作为二级。Redis 挂了本地还能挡一部分
  3. 熔断降级：检测到 Redis 不可用时，直接返回降级数据（默认值、静态兜底、友好提示），而不是让请求穿透到数据库
  4. 限流：对数据库的访问做并发限制，宁可拒绝部分请求，也不让数据库被打死

关键认知：数据库是最后的防线，任何方案的目标都是”不要让数据库裸奔”。

缓存与数据库的一致性

这是比”三兄弟”更容易出问题的地方。

Cache Aside（最常用）

  • 读：先读缓存，命中返回；未命中读数据库，然后写回缓存
  • 写：先更新数据库，再删除缓存（不是更新缓存）

为什么是”删除”而不是”更新”？

更新缓存有两个问题：

  1. 如果缓存值需要复杂计算，每次写都更新会浪费（很多写操作后根本没人读）
  2. 并发写时，两个线程的更新顺序可能和数据库提交顺序不一致，导致缓存里是旧值

删除更简单：下次读的时候自然会加载最新值。

为什么是”先更库再删缓存”？

反过来（先删缓存再更库）的问题：删除后、更新前，如果有读请求进来，会把旧值重新加载进缓存，然后数据库才更新——缓存里留下的是旧值，且不会自动纠正。

先更库再删缓存的不一致窗口更小（只在”更新完成、删除前”有极短时间）。

延迟双删

即使先更库再删缓存，仍有极小概率不一致。延迟双删的思路是：更新数据库后删一次缓存，延迟一段时间再删一次，把中间可能被写回的旧值清掉。

代价：延迟时间不好定（太短没用，太长影响一致性），且引入了异步任务。

更彻底的方案：订阅 binlog

用 Canal 之类的工具订阅 MySQL binlog，数据变更时异步删除对应缓存。

优点：业务代码完全不用管缓存，一致性由数据变更事件驱动
代价：引入额外组件和运维成本

我的选择：普通业务用 Cache Aside + 短过期时间。短过期是最后的兜底——即使中间出现不一致，最长一个过期周期后也会自动恢复。

几个容易被忽略的点

大 key

单个 key 的 value 过大（比如几 MB 的列表），会导致：

  • 读取时网络传输慢，阻塞其他命令
  • 删除时阻塞（Redis 单线程）

处理：拆分 key、控制集合大小、用 SCAN 分批处理而不是一次性取全部。

热 key

单个 key 的 QPS 过高，单实例 CPU 会成为瓶颈。

处理：本地缓存挡住大部分读、key 加随机后缀分散到多个实例（读时聚合）。

缓存预热

服务发布后缓存是空的，第一波流量会全打到数据库。

处理：发布后异步预热核心数据，或者用灰度发布控制流量爬升速度。

监控指标

光有方案不够，得能看到问题：

  • 缓存命中率（低说明 key 设计或过期策略有问题）
  • 慢查询（slowlog）
  • 内存使用与淘汰情况
  • 连接数与超时

落地检查清单

  • 缓存穿透：有参数校验；对不存在的 key 缓存空值（短过期）或使用布隆过滤器
  • 缓存击穿：热点 key 有互斥重建或逻辑过期方案
  • 缓存雪崩：过期时间已加随机偏移（最低成本的一条）
  • Redis 高可用：哨兵或集群，且验证过故障切换
  • 降级方案：Redis 不可用时有兜底数据，而不是直接打数据库
  • 一致性策略明确：Cache Aside 顺序正确（先更库再删缓存）
  • 有短过期时间兜底，不依赖”永远一致”
  • 大 key / 热 key 有监控和拆分方案
  • 发布后有预热策略
  • 监控覆盖命中率、慢查询、内存、连接数

小结

缓存问题的核心不是”背下几个方案”，而是知道每个方案的代价，并判断当前场景能不能接受：

  • 缓存空值 → 代价是内存（用短过期控制）
  • 布隆过滤器 → 代价是误判和运维复杂度
  • 互斥锁 → 代价是响应时间
  • 逻辑过期 → 代价是短暂旧数据
  • 延迟双删 → 代价是时间窗口不好定

我现在的默认组合是：参数校验 + 短过期兜底 + 过期时间加随机 + Redis 高可用 + 明确的降级策略。这几条覆盖了绝大多数问题，剩下的按具体场景再加。

自建 LLM 网关：统一 4 家供应商的架构设计

发表于 2026-05-16 更新于 2026-10-16 分类于 AI ， 架构设计

当项目开始接入第二个、第三个大模型供应商时，问题就不再是”调哪个 API”，而是：

  • 每家鉴权方式、请求格式、错误码都不一样，业务代码要写四套适配
  • 某家服务抖动或限流，业务直接失败
  • 调用量上去后，无法知道钱花在哪、哪个模型最慢
  • 换模型要改代码、重新发布

这篇文章记录我用网关统一 4 家供应商的完整设计——重点不是用了什么工具，而是每个决策背后的取舍。

一、先明确：为什么需要网关

不建网关会怎样（这是我实际遇到的情况）：

四个具体问题：

  1. 重复适配：每个业务模块都要处理 4 家的差异
  2. 无容错：A 家挂了不能自动切 B 家
  3. 无法观测：不知道哪家慢、哪家贵、用量多少
  4. 变更成本高：换模型要改代码 + 重新发布

网关要解决的核心问题：把”N 家供应商”收敛成”一个统一接口”。

二、架构设计

整体结构

关键设计：对外只暴露一种协议（OpenAI 兼容）。

这是最重要的决策。理由：

  • 几乎所有客户端都支持 OpenAI 格式（LangChain、各类 SDK、自研脚本）
  • 切换成本为零：业务方只改 base_url 和 api_key
  • 不用为每家写适配

为什么选 LiteLLM

方案 优势 代价
自己写网关 完全可控 要处理几十家供应商的格式差异，工作量大
LiteLLM 支持 100+ 供应商、配置驱动、有 fallback 需要容器化部署，性能依赖其实现
OneAPI / NewAPI 国内生态、有 Web 管理界面 功能偏”多租户管理”，配置灵活性一般
云厂商网关 免运维 被厂商绑定，跨供应商能力有限

选 LiteLLM 的理由：

  1. 配置驱动：新增供应商只改 YAML，不写代码
  2. 原生支持 fallback 链：这是最需要的容错能力
  3. Python 生态：出问题能读源码定位（我用这个能力排查过超时问题）
  4. 性能够用：网关本身是 IO 密集型的转发层，不是计算瓶颈

三、核心设计点

1. 模型命名：解决”同一模型多家都有”

问题：DeepSeek V4 Flash 在 4 家供应商都能调，直接叫 deepseek-v4-flash 无法区分来源。

方案：前缀区分 + 通用别名

为什么要两套：

  • 调试/对比时用前缀：明确指定某家，看它的延迟和输出质量
  • 生产用别名：不关心具体哪家，只要能用就行，挂了自动切换

这是”可控”和”省事”的分工，不是二选一。

2. 降级链（fallback）：容错的核心

这是网关最有价值的能力。

关键理解：fallback 只在可重试的错误上触发。

为什么这个区分重要：如果参数错误也降级，会在 4 家之间白跑一圈，最后返回的还是那个参数错误，但延迟翻了 4 倍。

踩过的坑：某次调用一直报”密钥无效”，排查发现是某家供应商临时故障返回 403。403 默认不触发降级，导致请求直接失败。后来针对这种情况加了配置，让该供应商的 403 也进入降级链。

3. 超时控制

这是最容易出问题的地方。

为什么是 240 秒：推理模型的输出可能很长，实测长回答（1000+ 字）需要 15-25 秒，深度推理场景可能超过 60 秒。设太短会导致复杂问题被截断。

但要理解分层的超时：

实践建议：业务侧超时要比网关略长（比如 300s），否则会出现”业务已返回超时，但上游还在计费”的浪费。

4. 各供应商的特殊处理

这是接 4 家必然遇到的现实问题，每家都有坑：

供应商 问题 解决
CommandCode 请求被 Cloudflare 拦截（error code: 1010） 伪装浏览器 User-Agent
数智魔方 baseURL 必须带 /v1，否则拼错路径 配置时显式写全
火山方舟 Coding Plan 有 5 小时用量配额 配额耗尽时降级到其他家
通用 Cloudflare 会拦 Python urllib 的 UA 统一用 curl 或设浏览器 UA

这些坑的共同点：它们不是”配置错了”，而是上游的安全策略。接入新供应商时，如果遇到 403/1010 这类错误，先怀疑 UA 和路径，而不是密钥。

四、可观测性

没有观测的网关等于没有网关。

该统计什么

降级触发次数为什么最重要：它直接反映了”链路健康度”。如果某家供应商的降级次数突然上升，说明它在出问题，应该主动排查而不是等业务反馈。

监控告警

我们的做法是接入已有的运维告警通道：

注意区分两类检查：

  • liveliness（存活）：进程是否还在，网关自身的健康
  • 上游可用性：真实调用一次模型，看链路是否通

这两个必须分开：网关进程活着不等于上游能用。我们踩过”网关健康检查全绿，但实际调用全失败”的情况（上游供应商故障）。

五、部署与运维

容器化

几个实践点：

  1. 只监听 127.0.0.1：对外通过 Cloudflare 隧道暴露，不在主机上直接开公网端口
  2. 密钥走环境变量（.env 权限 600），不进配置文件（配置文件可能会被备份、提交、查看）
  3. 设内存上限：防止内存泄漏拖垮宿主机（实测运行 39 小时后内存从 511MB 涨到 661MB，需要留意）
  4. **restart: unless-stopped**：进程崩溃自动恢复

密钥轮换与多环境

建议：

  • 网关的 master key 和上游的 key 分开管理
  • 上游 key 泄漏时只影响一家，不会波及整个网关
  • 定期轮换，尤其是暴露给多方的 key

六、踩过的坑

坑 1：超时配置过短导致功能”形同虚设”

现象：某个基于网关的功能总是”失败后回退到默认行为”，但看网关日志一切正常。

根因：客户端超时设了 12 秒，而网关真实调用需要 20 秒左右。客户端先超时了，网关还在正常处理，但结果没人接收。

教训：超时时间必须端到端对齐。客户端超时要 ≥ 网关超时 ≥ 上游实际耗时。排查这类问题，先看客户端和网关的超时配置是否匹配。

坑 2：DeepSeek 类模型的 reasoning_content 字段

现象：某些推理模型返回的内容不在 content 字段里，而在 reasoning_content 里，导致业务取到空字符串。

原因：推理模型把”思考过程”和”最终答案”分成两个字段，不同供应商的实现不一致。

处理：网关层统一归一化，业务侧只读 content。

这是网关的另一个价值：把上游的差异（包括这种字段不一致）挡在网关之内，业务侧面对的是稳定接口。

坑 3：Docker Hub 拉不动

现象：国内服务器 docker pull ghcr.io/... 卡住或失败。

解决：用镜像加速源（实测 ghcr.nju.edu.cn 可用），或在能连通的机器上拉取后 docker save / load。

这是个纯粹的国内网络问题，但会阻塞整个部署流程，建议提前准备好可用的镜像源。

七、这套设计带来的收益

对业务方

对运维

一个具体例子

某次某家供应商出现临时故障（连续 403），因为配置了降级链，业务侧完全没有感知，只是调用延迟略有上升。事后看降级统计才发现。

这是网关从”方便”变成”必需”的转折点——它不只是在省事，而是在提供业务连续性保障。

落地检查清单

  • 对外暴露统一协议（OpenAI 兼容），业务方只改 base_url/key
  • 供应商差异挡在网关内（鉴权、UA、路径、字段归一化）
  • 模型命名有明确规则（前缀区分来源 + 别名用于生产）
  • 配置降级链，且理解哪些错误会触发降级
  • 有全局兜底模型（default_fallbacks）
  • 超时端到端对齐（客户端 ≥ 网关 ≥ 上游）
  • 密钥走环境变量，文件权限 600，不进代码库
  • 网关只监听 127.0.0.1，对外走隧道/网关
  • 设内存上限 + restart: unless-stopped
  • 区分”网关存活检查”和”上游可用性检查”（两者不是一回事）
  • 统计调用量/失败率/延迟/降级次数，其中降级次数是核心健康指标
  • 有告警通道，异常时主动通知而非等业务反馈

小结

自建 LLM 网关的价值，不在于”统一 API”这个表面能力，而在于它提供的一致性、可观测性和业务连续性。

回顾这套设计的三个关键决策：

  1. 对外只暴露一种协议——把复杂度收敛到网关内部，业务方零适配成本
  2. 降级链 + 全局兜底——从”某家挂了业务就失败”变成”业务无感知”
  3. 端到端超时对齐——这个最容易被忽略，但直接影响功能是否真的可用

如果重来一次，我会更早接入用量与成本统计。因为随着调用量增长，”哪个模型性价比最高”这个问题会越来越重要，而它需要历史数据才能回答。

分库分表最容易被当成一个”数据量大了就上”的开关，但它实际上会改变事务边界、查询方式和运维复杂度。我在两个项目里用过 ShardingSphere（医院通行证系统、能源大屏），这篇文章记录选型依据、分片键的设计过程，以及分片之后被迫重新考虑的那些事。

先说结论：什么时候不该分

很多团队把分库分表当成性能问题的第一选择，但它的代价经常被低估。先排除掉不该分的场景，能省掉大量返工。

优先做这些，而不是分片：

  • 加索引、改写慢 SQL。很多”数据量大导致的慢查询”，实际是全表扫描或缺索引
  • 冷热分离。历史数据归档到独立的归档表或冷存储，热表自然瘦身
  • 读写分离。读多写少的场景，加从库比拆分简单得多
  • 加缓存。字典、配置、热点数据放 Redis，减少落到数据库的查询
  • 升级硬件或调参数。在单表千万级以内，这通常够用

真正需要分片的信号：

  • 单表数据量到了千万级以上，且索引优化后写入或查询仍然明显变慢
  • 写入量已经超过单实例的处理能力（不只是慢，是撑不住）
  • 数据有明确的、稳定的拆分维度（比如按时间、按租户、按用户 ID）
  • 业务能接受分片带来的限制（下面会讲这些限制是什么）

最后一条最关键。如果找不到一个高基数、且几乎所有查询都会带上的分片键，分片会带来比收益更大的麻烦。

选型：为什么用 ShardingSphere

当时对比了几个方向：

方案 特点 适合的场景
ShardingSphere-JDBC 以 jar 包形式嵌入应用，走 JDBC 层，无额外部署 Java 应用，希望零额外运维成本
ShardingSphere-Proxy 独立进程，对应用透明（像连一个 MySQL） 多语言技术栈，或希望不改应用代码
MyCat 独立代理，社区活跃度下降 存量系统
自己写路由 完全可控 分片逻辑极简单且团队有能力维护
云厂商中间件 托管，省运维 已绑定云生态

我们选 ShardingSphere-JDBC，理由很直接：

  1. 技术栈是纯 Java，没有跨语言代理的需求
  2. 不想为分片额外部署和运维一个中间件进程
  3. JDBC 层接入对业务代码侵入小，SQL 写法基本不用改

代价是：分片规则在应用侧，每个需要访问分片表的服务都要引入依赖并配置规则。如果服务很多，规则同步会成为一个维护点。这种情况 Proxy 更合适。

分片键怎么选

这是整个分片方案里最重要、也最容易做错的一步。分片键选错，后面所有优化都是在补救。

选择原则：

1. 高基数

分片键的取值要足够分散，否则数据会倾斜到少数分片。用状态字段（只有几个值）做分片键是典型错误。

2. 查询必带

理想情况是”绝大多数查询都会带上这个字段”。因为不带分片键的查询会路由到所有分片，然后由中间件归并结果——这比单表查询更慢。

3. 数据分布均匀

自增 ID 做分片键会有写入热点（新数据总是落在最后一个分片）；用户 ID、租户 ID 这类天然离散的字段更好。

4. 业务上不会变

分片键一旦确定，改它的成本极高（等于全量数据重新分布）。

我们的实际选择：

医院通行证系统的通行记录有两类主要查询：按人查历史、按时间段查。

  • 选 user_id 做分片键 → 按人查能精确定位，但按时间查要扫全部分片
  • 选 create_time 做分片键 → 按时间查快，但按人查要扫全部
  • 最终选 user_id，因为”查某个人的通行历史”是高频操作，时间范围查询可以通过额外的查询条件缩小范围

能源大屏的指标数据则是另一种情况：查询几乎总是带设备/企业维度，所以分片键选企业维度，保证按企业查询能路由到单片。

这一步没有标准答案，只能按真实查询模式来定。 建议先统计线上 SQL 的执行频率，再决定。

分片之后必须重新考虑的五件事

分片不是”配置好就完事”。下面每一项都会在分片后变成新问题。

1. 本地事务失效

跨分片的写入无法用本地事务保证。这是最容易出事的地方。

分片后 fromUserId 和 toUserId 可能落在不同库，本地事务只能保证其中一边。

应对策略，按推荐顺序：

  • 优先改设计：让需要保证一致的数据落在同一个分片。比如把”账户变更”和”流水记录”用同一个分片键，保证同库
  • 柔性事务：接受最终一致，用本地消息表 + 定时补偿
  • 分布式事务框架：Seata 等。能保证强一致，但性能损耗和运维复杂度都要评估

我们的选择是改设计 + 柔性事务。跨分片的强一致场景尽量在设计阶段就消除掉。

2. 跨片查询与全路由

没有分片键的查询会变成全路由。比如按手机号查通行记录，而分片键是 user_id，就只能查所有分片再归并。

应对：

  • 给常用查询建映射表（手机号 → user_id），先查映射再路由
  • 或者用 ElasticSearch 承载多维度检索，数据库只负责按主键取详情（我们在通行证系统里就是这么做的：ES 负责查询，MySQL 负责存储）

3. 深分页

分片后每个分片都要取出前 100020 条，再在内存里归并排序取最后 20 条。页数越深，内存和耗时增长越快。

应对：

  • 游标分页（推荐）：用上一页最后一条的 create_time 作为下一页的起点，避免大 offset
  • 限制最大页数：产品上接受”最多翻到第 N 页”，深翻走导出或检索
  • 禁止跨片排序：如果业务允许，把排序维度也纳入分片键

5. 关联查询与笛卡尔积

分片表之间的 JOIN，如果分片规则不一致，会退化成笛卡尔积（每个分片互相 JOIN）。

应对：

  • 绑定表：把分片规则完全一致的表配成绑定表，JOIN 时能按分片对齐，避免笛卡尔积
  • 广播表：字典、配置这类小表，每个库都存一份，JOIN 时无需跨片
  • 避免跨片 JOIN：能在应用层组装就在应用层做

几个具体踩坑

坑 1：分片键为 null 的写入

写入时如果分片键没值，ShardingSphere 无法计算路由，会直接报错或落到默认分片。我们在数据接入层加了校验，分片键为 null 的数据直接拒绝入库，避免脏数据分散在各处。

坑 2：COUNT(*) 变慢

分片后 COUNT(*) 需要在所有分片上执行再求和。数据量大时，这个操作会显著变慢。

应对：维护计数表（增量更新），或者接受近似值，或者从检索系统（ES）取统计。

坑 3：扩容没有想象中简单

MOD 分片算法（取模）在扩容时需要重新分布几乎所有数据。如果预期会扩容，一开始就考虑：

  • 一致性哈希：扩容时只迁移部分数据
  • 预分片：一开始就分足够的片（比如 64 片），扩的是物理库而不是逻辑片数
  • 双倍扩容：4 库扩到 8 库时，每个旧库拆一半到新库，迁移量可控

我们用的是预分片思路——按较细的粒度规划逻辑分片，前期映射到较少的物理库，扩容时只改映射。

坑 4：分片规则改了但数据没迁

改分片配置不会自动迁移已有数据。规则变更必须配套数据迁移脚本和校验，否则会出现”按新规则查不到老数据”。这类问题往往在线上才暴露。

落地检查清单

如果你正在评估或实施分库分表，可以按这个顺序确认：

  • 已排除加索引、冷热分离、读写分离、加缓存这些更简单的方案
  • 分片键基数足够高，且大部分查询会带上它
  • 统计过线上 SQL 的执行频率，确认分片键选择有依据
  • 跨分片事务有明确策略（优先改设计消除，其次柔性事务）
  • 深分页有方案（游标分页优先）
  • 全局 ID 生成方案确定，时钟回拨有处理
  • 关联查询用绑定表/广播表处理，或改为应用层组装
  • 扩容方案想清楚（一致性哈希 / 预分片 / 双倍扩容）
  • 分片规则变更的迁移与校验流程已就位
  • 监控覆盖：各分片数据量是否均衡、慢查询、路由命中情况

小结

分库分表解决的是单实例处理能力的上限问题，不是”查询慢”的通用解法。它把问题从”一台机器扛不住”转换成”分布式带来的一致性、查询与运维复杂度”。

我现在的判断顺序是：先优化 SQL 和索引，再考虑缓存和读写分离，最后才动分片。真到了必须分片的时候，把时间花在分片键选择和事务边界设计上，比花在配置调优上回报高得多。
