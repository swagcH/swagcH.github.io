从单体到微服务总结

发表于 2022-12-25 分类于 架构成长

背景

为什么会研究这个问题

回看 2022 年，从单体应用到微服务架构，我最大的变化不是学会了更多组件，而是开始理解架构演进的代价。单体并不落后，微服务也不天然先进。架构选择必须服务于团队规模、业务复杂度、交付频率和稳定性要求。

问题

遇到了什么情况

这一年遇到的典型问题包括：服务拆分后调用链变长，排查问题更困难；配置项分散，环境差异变大；消息队列、缓存、注册中心都引入了新的故障点；原来一个事务能保证的逻辑，现在要考虑最终一致性。微服务解决了一部分单体问题，同时也引入了新的复杂度。

排查过程

如果基础设施没有跟上，微服务会把复杂度直接暴露给业务开发。

解决方案

具体操作

总结

经验沉淀

从单体到微服务，本质上是从代码架构走向工程体系。服务拆分只是表象，真正重要的是边界治理、稳定性建设、自动化部署和可观测性。我的经验是：不要为了微服务而微服务，当单体还能支撑业务时，先做好模块化和工程规范；当协作、发布和稳定性成为瓶颈时，再逐步演进。

Prometheus监控部署

发表于 2022-11-20 分类于 架构成长

背景

为什么会研究这个问题

日志能回答“发生了什么”，但不能很好回答“系统现在是否健康”。为了补齐监控能力，我开始研究 Prometheus。相比传统监控，Prometheus 更适合以指标为中心观察服务状态，比如 QPS、响应耗时、错误率、线程池队列、JVM 内存等。

问题

遇到了什么情况

刚开始部署时，最容易忽略的是指标设计。Prometheus 能抓到很多默认指标，但如果没有业务指标，排查时仍然不够。比如接口错误率升高，只知道 HTTP 500 变多，却不知道是哪个业务动作失败。另一个问题是标签设计不当，label 维度过多会导致时间序列爆炸。

分析

排查过程

监控指标需要分层：基础资源、JVM、接口、数据库连接池、业务指标。只看 CPU 和内存，无法支撑复杂业务排查。

具体操作

总结

经验沉淀

Prometheus 的价值不只是画图，而是建立系统健康度指标。好的监控应该能提前暴露趋势，而不是等用户反馈后才看。日志、指标、告警和复盘结合起来，才算完整的可观测性建设。

ELK日志平台搭建

发表于 2022-10-23 分类于 架构成长

背景

为什么会研究这个问题

服务数量增加后，登录服务器看日志的方式开始变得低效。一次请求可能经过网关、订单服务、库存服务和消息消费者，如果每个服务都登录机器 grep 日志，排查效率会很低。因此我开始搭建 ELK 日志平台，把分散日志集中采集、存储和检索。

问题

遇到了什么情况

搭建过程中主要遇到三个问题：日志格式不统一，导致字段无法检索；Logstash 解析规则写得太随意，数据进 Elasticsearch 后结构混乱；日志量上来后磁盘增长很快，如果不设置索引生命周期，很容易把机器打满。

排查过程

日志平台不是简单收集文本，而是要让日志结构化。只有字段固定，才能按 traceId、service、level、bizId 快速过滤。

具体操作

总结

经验沉淀

ELK 的核心价值是让日志可检索、可关联、可追溯。平台搭起来只是第一步，更重要的是日志规范。没有 traceId、业务 id 和统一字段，ELK 也只能变成一个更大的文本搜索框。

Docker基础部署，Docker Compose实践

发表于 2022-08-14 分类于 架构成长

背景

为什么会研究这个问题

在多服务项目越来越多之后，本地环境和测试环境的差异变得明显。以前部署一个 Java 应用只需要 JDK、配置文件和启动脚本，现在还要依赖 MySQL、Redis、RabbitMQ、Nginx 等组件。为了减少环境搭建成本，我开始研究 Docker 和 Docker Compose。

问题

遇到了什么情况

最开始遇到的问题是容器能启动，但服务之间连不上。比如应用容器访问 localhost:3306，结果连接的是容器内部而不是宿主机；数据卷没有挂载，容器删除后数据也没了；端口映射冲突，导致服务无法启动。这些问题说明，Docker 部署不能只记命令，要理解镜像、容器、网络、数据卷之间的关系。

排查过程

Docker Compose 的价值在于把多个容器的启动方式写成声明式配置，避免每次手写一堆 docker run 命令。

具体操作

总结

经验沉淀

Docker 带来的最大收益是环境一致性。Docker Compose 则进一步把多组件依赖固化下来。我的经验是：开发环境可以用 Compose 提效，但生产环境还需要考虑镜像版本、日志收集、健康检查、资源限制和安全配置。

Redis高可用架构

发表于 2022-07-24 分类于 架构成长

背景

为什么会研究这个问题

Redis 从单机缓存进入核心链路后，高可用就必须认真考虑。最初使用 Redis 只是为了缓存热点数据，服务挂了最多回源数据库。但随着登录态、限流、库存预扣等场景进入 Redis，单点故障的影响范围明显扩大，所以需要研究 Redis 高可用架构。

问题

遇到了什么情况

单机 Redis 最大的问题是故障恢复依赖人工。Redis 进程挂掉、机器重启、内存打满都会导致业务抖动。如果没有主从、哨兵或集群方案，应用只能等待人工处理。另一个问题是，很多人以为主从复制就等于高可用，但主节点故障后如果不能自动切换，仍然无法支撑线上稳定性。

分析

排查过程

排查高可用时，重点看三个问题：主从复制是否正常，Sentinel 是否能判断主观下线，故障转移后客户端是否能感知新主节点。

解决方案

具体操作

对于缓存场景，我会同时配合过期时间随机化、本地缓存和降级策略，避免 Redis 故障时所有流量瞬间压到数据库。

总结

经验沉淀

Redis 高可用不能只看 Redis 本身，还要看客户端、业务降级和数据库保护。Sentinel 解决主从切换问题，但不解决缓存击穿、雪崩和热点 key 问题。真正可靠的缓存架构，需要高可用、限流、降级和监控一起设计。

RabbitMQ可靠性设计

发表于 2022-06-19 分类于 架构成长

背景

为什么会研究这个问题

随着系统拆分，很多原本同步完成的操作开始改成异步。比如订单创建后发积分、发通知、写操作日志，这些逻辑不应该阻塞主流程，于是 RabbitMQ 就进入了架构设计范围。研究可靠性设计，是因为消息队列一旦使用不当，很容易出现“主流程成功了，但后续动作丢了”的问题。

问题

遇到了什么情况

最典型的问题是消息丢失和重复消费。生产者以为消息发出去了，但交换机没有正确接收；队列没有持久化，服务重启后消息消失；消费者处理成功但 ack 失败，导致消息重复投递。如果没有可靠性设计，问题往往发生在线上，而且不容易第一时间发现。

分析

排查过程

排查消息可靠性时，我会把链路拆成四段：生产确认、路由确认、队列持久化、消费确认。任何一段缺失，都可能导致数据不一致。

具体操作

总结

经验沉淀

RabbitMQ 可靠性不是一个配置能解决的，而是一组机制共同保证。生产确认保证消息发出去，持久化保证消息不因重启丢失，手动 ack 保证消费结果可控，幂等设计保证重复投递不会破坏数据。

Nacos,Gateway,OpenFeign实操

发表于 2022-03-27 分类于 架构成长

背景

为什么会研究这个问题

在 Spring Cloud 的基础概念跑通之后，我把重点放到 Nacos、Gateway 和 OpenFeign 三个组件上。原因很简单：它们覆盖了微服务最基础的一条链路——服务注册、统一入口和服务间调用。只要这三块稳定，至少能搭出一个可运行的微服务骨架。

问题

遇到了什么情况

实操中遇到的问题主要集中在配置和路径上。服务已经启动，但 Nacos 控制台看不到实例；Gateway 能访问，但路由匹配不到目标服务；OpenFeign 调用时出现 404 或超时。很多问题不是代码逻辑错，而是服务名、路径前缀、配置层级和依赖版本不一致导致的。

分析

排查过程

如果 StripPrefix 配错，请求到后端服务的路径就会变化。排查时要同时看 Gateway 日志和后端 Controller 的映射。

解决方案

具体操作

通过清单逐项排查，比直接看异常堆栈更稳定。

总结

经验沉淀

Nacos、Gateway、OpenFeign 组合起来并不复杂，复杂的是路径、服务名和配置之间的细节一致性。我的经验是：每新增一个服务，先验证注册，再验证网关，再验证 Feign，不要一次性把所有配置都写完再排查。

Spring Cloud学习笔记

发表于 2022-02-20 分类于 架构成长

背景

为什么会研究这个问题

在理解了微服务的基本拆分思路之后，我开始系统学习 Spring Cloud。相比单个 Spring Boot 应用，Spring Cloud 更像是一组微服务治理工具箱，覆盖注册发现、配置管理、网关路由、服务调用、熔断限流等能力。研究它的原因也很明确：当服务数量超过两三个之后，手写服务地址、手动维护配置、靠人肉检查调用链会变得非常不可靠。

问题

遇到了什么情况

刚开始学习时，最大的问题是概念很多但边界不清。注册中心、配置中心、网关、Feign、负载均衡这些组件看起来都能跑 Demo，但真正放到项目里，会发现不知道每个组件负责什么。比如服务调用失败到底是注册中心没发现服务，还是网关路由错了，还是 Feign 超时时间太短。组件之间的关系如果没有先画清楚，排查问题时会非常被动。

分析

排查过程

排查时我会先确认服务是否注册，再确认配置是否加载，最后确认调用链是否正常。顺序不能乱，否则容易被表面异常误导。

解决方案

具体操作

我把每个组件都拆成最小可运行样例，再逐步组合。这样做虽然慢一点，但能清楚知道问题出现在哪一层。

总结

经验沉淀

Spring Cloud 的学习重点不是背组件名，而是理解服务治理的分层。注册中心解决服务在哪里，配置中心解决配置怎么统一，网关解决入口怎么收口，Feign 解决服务之间怎么调用。只有把这些问题放回真实架构场景里，组件才有意义。

微服务架构初体验

发表于 2022-01-16 分类于 架构成长

背景

为什么会研究这个问题

2022 年开始接触微服务时，我最直接的感受是：它不是把一个系统拆成多个服务那么简单。过去做单体应用，所有模块在一个进程里，调用方式直接、事务边界清楚、部署也简单。但当业务模块逐渐增多，订单、用户、库存、支付之间的代码耦合越来越明显，每次改一个功能都要回归一大片逻辑，发布窗口也越来越长。正是在这种背景下，我开始研究微服务架构。最初的目标并不是追求架构先进，而是想弄清楚系统拆分之后，团队协作、独立部署、故障隔离到底能解决哪些真实问题。

问题

遇到了什么情况

第一次拆服务时遇到的情况比较典型：模块拆出去了，但调用关系反而更复杂；原来一次本地方法调用，现在变成了网络请求；原来一个数据库事务能覆盖的流程，现在要考虑分布式事务或最终一致性。尤其是订单创建这个流程，涉及用户校验、库存扣减、优惠计算和支付记录，拆开之后每一步都可能失败。如果只按代码包结构拆服务，很容易变成“物理拆分、逻辑仍然耦合”。

分析

排查过程

排查拆分边界时，我主要看三个维度：数据归属、业务闭环、变更频率。用户资料和订单生命周期明显不是同一类数据；库存服务变更频率不高，但对一致性要求高；支付服务外部依赖多，需要单独隔离。由此可以判断，服务拆分应该围绕业务能力，而不是围绕代码目录。

解决方案

具体操作

实际落地时，我没有一次性把所有模块拆开，而是先从边界相对清晰的库存查询、用户信息查询开始。这样即使出现问题，也不会直接影响订单主流程。等到接口、日志、异常处理逐渐稳定后，再考虑更核心的链路。

总结

经验沉淀

微服务带来的不是天然简单，而是把原来隐藏在进程内部的问题显性化。网络延迟、接口契约、数据一致性、服务监控都会成为必须面对的工程问题。我的经验是：如果团队还没有稳定的部署流程、日志规范和接口文档，过早拆微服务只会放大混乱。微服务不是目标，降低复杂度、提升交付效率和故障隔离能力才是目标。
