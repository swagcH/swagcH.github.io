Redis 缓存设计：穿透、击穿、雪崩的实际处理

发表于 2026-10-16 更新于 2026-10-15 分类于 Java ， 数据库

“缓存穿透、击穿、雪崩”这三个词几乎每份面经都会出现，但实际项目里出问题的往往不是概念本身，而是方案选型时的取舍没想清楚：加布隆过滤器要不要考虑误判？互斥锁会不会把可用性问题变成响应时间问题？先删缓存还是先更数据库？

这篇文章按”现象 → 方案 → 代价”的方式整理一遍，最后给出我在项目里的实际做法。

先把三个概念分清

三者经常被混着说，但触发条件完全不同：

问题 触发条件 直接后果
穿透 查询根本不存在的数据 请求绕过缓存，每次都打到数据库
击穿 单个热点 key 过期瞬间 大量并发同时去数据库重建同一个 key
雪崩 大量 key 同时失效，或 Redis 整体不可用 数据库瞬间承接全部流量

一句话区分：穿透是”数据不存在”，击穿是”一个热点没了”，雪崩是”一大片同时没了”。

缓存穿透

现象

请求查询一个数据库里也不存在的 key（比如不存在的用户 ID、被删除的商品），缓存不会命中，请求直接落到数据库。

正常业务流量下这不是问题，但如果有人恶意用随机 ID 刷接口，每次都能绕过缓存，数据库就成了第一道防线。

方案与代价

方案一：缓存空对象

查不到也往缓存里写一个空值（或特殊标记），并设置较短的过期时间。

代价：如果攻击者用大量不同的随机 ID 刷，每个都会写入一个空值，内存会被打满。所以过期时间必须短，且最好配合下面的方案。

方案二：布隆过滤器

在缓存之前加一层布隆过滤器，把数据库里存在的 key 预先写进去。查询时先问布隆过滤器”这个 key 可能存在吗”，不存在就直接返回。

代价（这三个必须知道）：

  1. 有误判率：说”可能存在”时可能是误判（实际不存在），所以布隆过滤器只能挡住”确定不存在”的请求，不能替代真实查询
  2. 不支持删除：标准布隆过滤器删不掉元素。数据删除后过滤器里还在，会导致”明明删了却还被放行”。可以用计数布隆过滤器，或者定期重建
  3. 需要预热和同步：新增数据时要同步写入，否则新数据会被误挡

方案三：入口参数校验

最便宜的一层：ID 格式不对、超出范围、必填参数缺失的请求，在 Controller 层就拒掉，连缓存都不查。

我的实际做法

参数校验 + 缓存空值（短过期），没用布隆过滤器。原因：

  • 我们的 key 空间是可枚举的（用户 ID、设备 ID），攻击者能构造的”不存在 key”数量有限
  • 引入布隆过滤器需要额外的预热和同步逻辑，收益不匹配
  • 如果以后出现大规模随机 key 攻击，再上布隆过滤器

这不是”布隆过滤器不好”，而是”当前场景用不上”。 面试时被问到，说清楚这个判断过程比背方案更有说服力。

缓存击穿

现象

某个热点 key（比如首页配置、秒杀商品）过期的那一瞬间，大量并发请求同时发现缓存没了，一起去数据库查询并重建缓存。

注意：**击穿的前提是”热点”**。一个普通 key 过期，就算有几十个请求同时打过来，数据库也扛得住。

方案与代价

方案一：互斥锁重建

只让一个线程去查数据库并回填缓存，其他线程等待后重试。

代价：

  • 响应时间变长：没抢到锁的请求要等待。热点 key 重建如果本身很慢（比如要聚合多个服务），等待会很明显
  • 有死锁风险：必须给锁设过期时间，且要考虑业务执行超过锁时间的情况
  • 重试逻辑要防雪崩：如果重试太密集，等待的线程会形成新的压力

方案二：逻辑过期（不阻塞读）

缓存里存的 value 带一个过期时间字段，Redis 层面不设过期。读到发现逻辑过期时，返回旧值，同时异步触发一个线程去更新。

代价：

  • 会返回旧数据：业务必须能接受短暂的数据延迟（大部分场景可以，涉及金额的不行）
  • 实现更复杂：需要额外的线程池和锁管理
  • 缓存不会自动清理：逻辑过期不会删除 key，需要额外的清理策略

怎么选

场景 建议
数据一致性要求高，能接受短暂等待 互斥锁重建
响应时间敏感，能接受短暂旧数据 逻辑过期
key 极少且几乎不变 干脆不设过期，变更时主动更新

缓存雪崩

雪崩有两种成因，处理方式完全不同。

成因一：大量 key 同时过期

常见于”凌晨批量刷新缓存”的实现——如果所有 key 都设 expire = 3600，那么一小时后它们会同时失效。

方案：过期时间加随机偏移

这是成本最低、收益最高的一条，几乎零成本就能避免大部分雪崩。

成因二：Redis 整体不可用

单实例 Redis 宕机或网络分区，所有请求同时落到数据库。

方案（分层防御）：

  1. 高可用部署：哨兵（主从自动切换）或集群（分片 + 高可用）。这是基础，不是可选项
  2. 多级缓存：本地缓存（Caffeine）作为一级，Redis 作为二级。Redis 挂了本地还能挡一部分
  3. 熔断降级：检测到 Redis 不可用时，直接返回降级数据（默认值、静态兜底、友好提示），而不是让请求穿透到数据库
  4. 限流：对数据库的访问做并发限制，宁可拒绝部分请求，也不让数据库被打死

关键认知：数据库是最后的防线，任何方案的目标都是”不要让数据库裸奔”。

缓存与数据库的一致性

这是比”三兄弟”更容易出问题的地方。

Cache Aside（最常用）

  • 读：先读缓存，命中返回；未命中读数据库，然后写回缓存
  • 写：先更新数据库，再删除缓存（不是更新缓存）

为什么是”删除”而不是”更新”？

更新缓存有两个问题：

  1. 如果缓存值需要复杂计算，每次写都更新会浪费（很多写操作后根本没人读）
  2. 并发写时，两个线程的更新顺序可能和数据库提交顺序不一致，导致缓存里是旧值

删除更简单：下次读的时候自然会加载最新值。

为什么是”先更库再删缓存”？

反过来（先删缓存再更库）的问题：删除后、更新前，如果有读请求进来，会把旧值重新加载进缓存，然后数据库才更新——缓存里留下的是旧值，且不会自动纠正。

先更库再删缓存的不一致窗口更小（只在”更新完成、删除前”有极短时间）。

延迟双删

即使先更库再删缓存，仍有极小概率不一致。延迟双删的思路是：更新数据库后删一次缓存，延迟一段时间再删一次，把中间可能被写回的旧值清掉。

代价：延迟时间不好定（太短没用，太长影响一致性），且引入了异步任务。

更彻底的方案：订阅 binlog

用 Canal 之类的工具订阅 MySQL binlog，数据变更时异步删除对应缓存。

优点：业务代码完全不用管缓存，一致性由数据变更事件驱动
代价：引入额外组件和运维成本

我的选择：普通业务用 Cache Aside + 短过期时间。短过期是最后的兜底——即使中间出现不一致，最长一个过期周期后也会自动恢复。

几个容易被忽略的点

大 key

单个 key 的 value 过大（比如几 MB 的列表），会导致：

  • 读取时网络传输慢，阻塞其他命令
  • 删除时阻塞（Redis 单线程）

处理：拆分 key、控制集合大小、用 SCAN 分批处理而不是一次性取全部。

热 key

单个 key 的 QPS 过高，单实例 CPU 会成为瓶颈。

处理：本地缓存挡住大部分读、key 加随机后缀分散到多个实例（读时聚合）。

缓存预热

服务发布后缓存是空的，第一波流量会全打到数据库。

处理：发布后异步预热核心数据，或者用灰度发布控制流量爬升速度。

监控指标

光有方案不够，得能看到问题：

  • 缓存命中率（低说明 key 设计或过期策略有问题）
  • 慢查询（slowlog）
  • 内存使用与淘汰情况
  • 连接数与超时

落地检查清单

  • 缓存穿透：有参数校验；对不存在的 key 缓存空值（短过期）或使用布隆过滤器
  • 缓存击穿：热点 key 有互斥重建或逻辑过期方案
  • 缓存雪崩：过期时间已加随机偏移（最低成本的一条）
  • Redis 高可用：哨兵或集群，且验证过故障切换
  • 降级方案：Redis 不可用时有兜底数据，而不是直接打数据库
  • 一致性策略明确：Cache Aside 顺序正确（先更库再删缓存）
  • 有短过期时间兜底，不依赖”永远一致”
  • 大 key / 热 key 有监控和拆分方案
  • 发布后有预热策略
  • 监控覆盖命中率、慢查询、内存、连接数

小结

缓存问题的核心不是”背下几个方案”，而是知道每个方案的代价，并判断当前场景能不能接受：

  • 缓存空值 → 代价是内存（用短过期控制）
  • 布隆过滤器 → 代价是误判和运维复杂度
  • 互斥锁 → 代价是响应时间
  • 逻辑过期 → 代价是短暂旧数据
  • 延迟双删 → 代价是时间窗口不好定

我现在的默认组合是：参数校验 + 短过期兜底 + 过期时间加随机 + Redis 高可用 + 明确的降级策略。这几条覆盖了绝大多数问题，剩下的按具体场景再加。

ShardingSphere 分库分表实践：从选型到踩坑

发表于 2026-10-15 分类于 Java ， 数据库

分库分表最容易被当成一个”数据量大了就上”的开关，但它实际上会改变事务边界、查询方式和运维复杂度。我在两个项目里用过 ShardingSphere（医院通行证系统、能源大屏），这篇文章记录选型依据、分片键的设计过程，以及分片之后被迫重新考虑的那些事。

先说结论：什么时候不该分

很多团队把分库分表当成性能问题的第一选择，但它的代价经常被低估。先排除掉不该分的场景，能省掉大量返工。

优先做这些，而不是分片：

  • 加索引、改写慢 SQL。很多”数据量大导致的慢查询”，实际是全表扫描或缺索引
  • 冷热分离。历史数据归档到独立的归档表或冷存储，热表自然瘦身
  • 读写分离。读多写少的场景，加从库比拆分简单得多
  • 加缓存。字典、配置、热点数据放 Redis，减少落到数据库的查询
  • 升级硬件或调参数。在单表千万级以内，这通常够用

真正需要分片的信号：

  • 单表数据量到了千万级以上，且索引优化后写入或查询仍然明显变慢
  • 写入量已经超过单实例的处理能力（不只是慢，是撑不住）
  • 数据有明确的、稳定的拆分维度（比如按时间、按租户、按用户 ID）
  • 业务能接受分片带来的限制（下面会讲这些限制是什么）

最后一条最关键。如果找不到一个高基数、且几乎所有查询都会带上的分片键，分片会带来比收益更大的麻烦。

选型：为什么用 ShardingSphere

当时对比了几个方向：

方案 特点 适合的场景
ShardingSphere-JDBC 以 jar 包形式嵌入应用，走 JDBC 层，无额外部署 Java 应用，希望零额外运维成本
ShardingSphere-Proxy 独立进程，对应用透明（像连一个 MySQL） 多语言技术栈，或希望不改应用代码
MyCat 独立代理，社区活跃度下降 存量系统
自己写路由 完全可控 分片逻辑极简单且团队有能力维护
云厂商中间件 托管，省运维 已绑定云生态

我们选 ShardingSphere-JDBC，理由很直接：

  1. 技术栈是纯 Java，没有跨语言代理的需求
  2. 不想为分片额外部署和运维一个中间件进程
  3. JDBC 层接入对业务代码侵入小，SQL 写法基本不用改

代价是：分片规则在应用侧，每个需要访问分片表的服务都要引入依赖并配置规则。如果服务很多，规则同步会成为一个维护点。这种情况 Proxy 更合适。

分片键怎么选

这是整个分片方案里最重要、也最容易做错的一步。分片键选错，后面所有优化都是在补救。

选择原则：

1. 高基数

分片键的取值要足够分散，否则数据会倾斜到少数分片。用状态字段（只有几个值）做分片键是典型错误。

2. 查询必带

理想情况是”绝大多数查询都会带上这个字段”。因为不带分片键的查询会路由到所有分片，然后由中间件归并结果——这比单表查询更慢。

3. 数据分布均匀

自增 ID 做分片键会有写入热点（新数据总是落在最后一个分片）；用户 ID、租户 ID 这类天然离散的字段更好。

4. 业务上不会变

分片键一旦确定，改它的成本极高（等于全量数据重新分布）。

我们的实际选择：

医院通行证系统的通行记录有两类主要查询：按人查历史、按时间段查。

  • 选 user_id 做分片键 → 按人查能精确定位，但按时间查要扫全部分片
  • 选 create_time 做分片键 → 按时间查快，但按人查要扫全部
  • 最终选 user_id，因为”查某个人的通行历史”是高频操作，时间范围查询可以通过额外的查询条件缩小范围

能源大屏的指标数据则是另一种情况：查询几乎总是带设备/企业维度，所以分片键选企业维度，保证按企业查询能路由到单片。

这一步没有标准答案，只能按真实查询模式来定。 建议先统计线上 SQL 的执行频率，再决定。

分片之后必须重新考虑的五件事

分片不是”配置好就完事”。下面每一项都会在分片后变成新问题。

1. 本地事务失效

跨分片的写入无法用本地事务保证。这是最容易出事的地方。

分片后 fromUserId 和 toUserId 可能落在不同库，本地事务只能保证其中一边。

应对策略，按推荐顺序：

  • 优先改设计：让需要保证一致的数据落在同一个分片。比如把”账户变更”和”流水记录”用同一个分片键，保证同库
  • 柔性事务：接受最终一致，用本地消息表 + 定时补偿
  • 分布式事务框架：Seata 等。能保证强一致，但性能损耗和运维复杂度都要评估

我们的选择是改设计 + 柔性事务。跨分片的强一致场景尽量在设计阶段就消除掉。

2. 跨片查询与全路由

没有分片键的查询会变成全路由。比如按手机号查通行记录，而分片键是 user_id，就只能查所有分片再归并。

应对：

  • 给常用查询建映射表（手机号 → user_id），先查映射再路由
  • 或者用 ElasticSearch 承载多维度检索，数据库只负责按主键取详情（我们在通行证系统里就是这么做的：ES 负责查询，MySQL 负责存储）

3. 深分页

分片后每个分片都要取出前 100020 条，再在内存里归并排序取最后 20 条。页数越深，内存和耗时增长越快。

应对：

  • 游标分页（推荐）：用上一页最后一条的 create_time 作为下一页的起点，避免大 offset
  • 限制最大页数：产品上接受”最多翻到第 N 页”，深翻走导出或检索
  • 禁止跨片排序：如果业务允许，把排序维度也纳入分片键

4. 全局唯一 ID

分片后自增主键不再全局唯一。ShardingSphere 内置了雪花算法：

雪花 ID 是有序的，对索引友好，但要注意时钟回拨问题（机器时间回退会生成重复 ID，ShardingSphere 有处理但需要关注）。

5. 关联查询与笛卡尔积

分片表之间的 JOIN，如果分片规则不一致，会退化成笛卡尔积（每个分片互相 JOIN）。

应对：

  • 绑定表：把分片规则完全一致的表配成绑定表，JOIN 时能按分片对齐，避免笛卡尔积
  • 广播表：字典、配置这类小表，每个库都存一份，JOIN 时无需跨片
  • 避免跨片 JOIN：能在应用层组装就在应用层做

几个具体踩坑

坑 1：分片键为 null 的写入

写入时如果分片键没值，ShardingSphere 无法计算路由，会直接报错或落到默认分片。我们在数据接入层加了校验，分片键为 null 的数据直接拒绝入库，避免脏数据分散在各处。

坑 2：COUNT(*) 变慢

分片后 COUNT(*) 需要在所有分片上执行再求和。数据量大时，这个操作会显著变慢。

应对：维护计数表（增量更新），或者接受近似值，或者从检索系统（ES）取统计。

坑 3：扩容没有想象中简单

MOD 分片算法（取模）在扩容时需要重新分布几乎所有数据。如果预期会扩容，一开始就考虑：

  • 一致性哈希：扩容时只迁移部分数据
  • 预分片：一开始就分足够的片（比如 64 片），扩的是物理库而不是逻辑片数
  • 双倍扩容：4 库扩到 8 库时，每个旧库拆一半到新库，迁移量可控

我们用的是预分片思路——按较细的粒度规划逻辑分片，前期映射到较少的物理库，扩容时只改映射。

坑 4：分片规则改了但数据没迁

改分片配置不会自动迁移已有数据。规则变更必须配套数据迁移脚本和校验，否则会出现”按新规则查不到老数据”。这类问题往往在线上才暴露。

落地检查清单

如果你正在评估或实施分库分表，可以按这个顺序确认：

  • 已排除加索引、冷热分离、读写分离、加缓存这些更简单的方案
  • 分片键基数足够高，且大部分查询会带上它
  • 统计过线上 SQL 的执行频率，确认分片键选择有依据
  • 跨分片事务有明确策略（优先改设计消除，其次柔性事务）
  • 深分页有方案（游标分页优先）
  • 全局 ID 生成方案确定，时钟回拨有处理
  • 关联查询用绑定表/广播表处理，或改为应用层组装
  • 扩容方案想清楚（一致性哈希 / 预分片 / 双倍扩容）
  • 分片规则变更的迁移与校验流程已就位
  • 监控覆盖：各分片数据量是否均衡、慢查询、路由命中情况

小结

分库分表解决的是单实例处理能力的上限问题，不是”查询慢”的通用解法。它把问题从”一台机器扛不住”转换成”分布式带来的一致性、查询与运维复杂度”。

我现在的判断顺序是：先优化 SQL 和索引，再考虑缓存和读写分离，最后才动分片。真到了必须分片的时候，把时间花在分片键选择和事务边界设计上，比花在配置调优上回报高得多。
