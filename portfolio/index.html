生产系统交付

深圳能源大屏

后端技术负责人

2024.05 - 2026.03

面向集团级经营与生产监控的数据大屏。围绕集团概况、产业布局、低碳电力、生态环保、综合燃气、数智服务、专题介绍 7 大主题建设，共 36 个业务板块，接入 167 家生产企业，展示 6000 余项数据与各厂监控画面。

技术栈
SpringCloud · ShardingSphere · MinIO · Redis · Nginx · MySQL
我的职责
主导后端技术选型与架构设计；负责与大数据平台、SIS 等 9 个异构系统的数据集成；配置维护 4 台服务器并部署 Nginx 负载均衡；引入 MinIO 作为对象存储方案
技术难点
9 个来源系统的数据模型、更新频率、接口协议各不相同，需要统一成一致的指标口径对外提供；单表数据量增长后查询变慢，采用 ShardingSphere 分片提升可扩展性
量化规模
36 个业务板块 · 167 家生产企业 · 9 个系统集成 · 580 个指标 · 4 台服务器

医院电子通行证系统

后端主程

2022.03 - 2024.04

面向医院出入人员管理并与门禁闸机联动的系统，支持通行记录采集与分析、实时访客管理、门禁授权管理。采用 5 模块微服务架构，已被十余家医院采购并投入使用。

技术栈
SpringCloud · RabbitMQ · ShardingSphere · ElasticSearch · Redis · MQTT（设备通信）· HL7（医疗数据交换）· MySQL · Oracle · Nginx
我的职责
独立负责出入记录、门禁管理、访客管理等核心模块的设计与开发；主导设备侧对接，基于 MQTT 实现人员服务与门禁闸机的异步解耦，支持多厂商设备接入；对接医院信息系统，基于 HL7 协议接收患者信息实现院内数据打通；主导数据库优化并推进项目整体落地
技术难点
多厂商设备接入：不同门禁设备的通信协议不一致。通过 MQTT 统一设备通信层，新增厂商只需实现对应适配，不改业务代码
与医院既有系统集成：医院侧使用 HL7 医疗数据交换标准，基于 HAPI 实现消息解析与转换，把标准协议数据映射到本系统数据模型
高频写入瓶颈：通行记录是高频写入 + 按时间范围检索场景，单表迅速到达瓶颈，采用 ShardingSphere 分库分表，分片键兼顾"按人查"与"按时间查"两类主要查询
服务耦合：人员服务与设备模块原先强耦合，一方异常影响另一方，引入 RabbitMQ 异步解耦
量化规模
1067 个 Java 文件 · 5 个微服务模块 · 36 个 Controller · 约 389 个 REST 接口 · 265 个数据实体 · 十余家医院在用

病案无纸化管理系统

后端主程

2022.03 - 2024.04

基于电子签名技术实现无纸化归档的电子病案管理系统。整合各临床信息系统的数据形成完整电子病案卷宗，使病案可脱离原系统独立展示与查阅。功能覆盖数据采集、归档、打印、借阅、封存、质控、召回等完整生命周期。

技术栈
SpringBoot · MySQL · Redis · MinIO · 电子签名
我的职责
核心需求分析与项目进度把控；独立负责病案借阅、封存解封模块的设计、开发与维护；使用 MinIO 承担病案文档的对象存储；基于 Redis 对用户下载次数做监控；对接微信公众号、阿里云短信实现消息推送与预警
技术难点
多来源文档整合：一份完整病案由住院病案首页、入院记录、手术知情同意书、护理记录单、各类检查报告等十余种文档构成，来源系统各异。需要把分散在各临床信息系统的数据汇聚成可独立展示的完整卷宗
大文件存储与并发：病案文档体积大、数量多，本地文件系统在并发上传下载时表现不佳。改用 MinIO 对象存储，把文件读写从应用服务器剥离
数据安全与合规：病案属敏感数据，借阅场景存在恶意重复下载风险。基于 Redis 记录并限制用户下载次数，同时保证正常业务不受影响
量化规模
覆盖借阅 / 封存解封 / 打印召回 / 查询 / 质控 等完整模块 · 整合十余类临床文档 · 十余家医院在用

稳定性治理与自动化

自建 AI 基础设施与运维自动化

独立设计与实现

2025 - 至今

为多个个人项目统一接入大模型能力，并把这套基础设施的部署、监控、故障恢复做成自动化流程，减少人工介入。

核心组件
统一 LLM 网关（聚合 4 家供应商、40+ 模型条目，配置 35 条 fallback 链与默认兜底模型）
双服务器架构（Cloudflare 命名隧道对外暴露 6 个域名，主机防火墙做来源白名单）
定时任务体系（模型清单扫描、服务健康检查、内容抓取与早报推送）
告警通道（异常直接推送至飞书）
我解决的问题
供应商差异：4 家平台的鉴权方式、接口协议、限流策略各不相同，通过网关统一为一种调用方式
链路可用性：单模型故障时按 fallback 链自动降级，避免业务中断
动态 IP 断连：公网 IP 漂移会导致运维通道整体失联，实现"从防火墙拦截日志自动识别来源 + 可信网段校验 + 自动放行 + 审计留痕"的闭环
服务自愈：关键服务配置健康检查与自动重启，异常时主动告警而非静默失败
量化规模
4 家模型供应商 · 40+ 模型条目 · 35 条降级链 · 6 个对外域名 · 7 个定时任务

一次跨层排障：远程桌面服务客户端持续"未就绪"

独立排查

2026.10

自建远程桌面服务端后，客户端始终显示"未就绪"。服务端进程正常、端口全通、健康检查毫秒级返回，但客户端无法完成注册。

排查路径
① 分层验证：先确认服务端自身健康（容器状态、资源占用、监听端口）
② 网络层抓包：发现 TCP 三次握手正常，但客户端建连后未发送任何数据即关闭，排除服务端拒绝的可能
③ 日志比对：服务端注册计数恒为 0，客户端却在反复请求一个服务端文档中并不存在的端口
④ 源码级确认：对照客户端源码中的响应分支，确认该版本依赖服务端管理端能力，而开源版不提供
结论与处理
定位为客户端版本与服务端的能力依赖不匹配，属于上游兼容性缺口，非配置问题。停止继续投入，回退方案并完整清理已部署组件，恢复防火墙策略与访问白名单，验证外部端口全部关闭。
体现的能力
分层排除法 · 抓包取证 · 日志关联分析 · 源码验证 · 及时止损的判断
