Java异常处理机制

发表于 2018-08-19 分类于 Java基础

背景

最近写 Java 小项目的时候，我经常会遇到各种报错。有些错误是编译阶段就提示的，比如文件找不到、方法必须抛出异常；有些错误是程序运行到一半才出现的，比如空指针、数组越界、类型转换失败。

一开始我对异常的理解比较简单：报错了就 try-catch 一下，能运行就行。但是写得多了之后发现，异常处理并不是把代码包起来这么简单。如果处理方式不对，程序表面上不报错了，真正的问题反而被藏起来了。

尤其是这段时间，我经常看到代码里有 catch (Exception e)，但 catch 里面只打印一句话，甚至什么都不写。这样虽然编译能通过，但以后排查问题会非常痛苦。

所以我打算在 2018 年 8 月这个阶段，把 Java 异常处理机制系统梳理一遍，弄清楚异常体系、try-catch-finally 执行顺序、什么时候应该抛异常、什么时候应该捕获异常。

问题

我目前遇到的困惑主要有这几个：

  • Checked异常和Unchecked异常分不清
  • finally 中的 return 会覆盖 try 中的返回值
  • 习惯性 catch (Exception e)，但 catch 之后不知道怎么处理
  • 空的 catch 块会吞掉异常，导致排查问题很困难
  • 不知道什么时候应该向上抛异常，什么时候应该自己 catch

其中最让我印象深的是 finally 里的 return。以前我以为 try 里面已经 return 了，方法就结束了。后来才发现，只要有 finally，它仍然会执行；如果 finally 里面也写了 return，还会把 try 或 catch 里的返回值覆盖掉。

另外，空 catch 块也很危险。异常发生了，但是代码没有任何日志、没有任何提示，就像什么都没发生一样。这种写法短期看起来“安静”，长期看就是在给自己埋雷。

分析

Java 的异常可以先从 Throwable 这个顶层父类看起。它下面主要有两个分支：Error 和 Exception。

Error 通常表示比较严重的问题，比如 JVM 内存不足、栈溢出等，一般不是业务代码应该捕获处理的重点。我们平时写业务代码更多关注的是 Exception。

Exception 又可以分成两类：Checked异常和Unchecked异常。

Checked异常是编译期检查异常。也就是说，如果方法可能抛出这类异常，编译器会要求我们必须处理：要么使用 try-catch 捕获，要么在方法上使用 throws 声明继续向上抛。

Unchecked异常主要指 RuntimeException 以及它的子类，比如 NullPointerException、IllegalArgumentException、IndexOutOfBoundsException 等。这类异常编译器不会强制要求处理，但它们仍然会在运行时导致程序出错。

简单理解可以这样记：

类型 是否编译期强制处理 常见例子 处理思路
Checked异常 是 IOException、SQLException 捕获后处理，或向上抛出
Unchecked异常 否 NullPointerException、IllegalArgumentException 优先通过代码逻辑避免
Error 否 OutOfMemoryError、StackOverflowError 通常不在业务代码中捕获

finally 的规则也要特别注意：无论 try 中是否发生异常，只要 JVM 没有直接退出，finally 通常都会执行。它适合用来释放资源，比如关闭文件流、数据库连接等。

但是不要在 finally 中写 return。因为 finally 的 return 会覆盖 try 或 catch 中已经准备返回的结果，也可能覆盖正在抛出的异常，让问题变得非常隐蔽。

从代码结构上看，比较合理的异常处理思路是：底层代码只负责发现问题并抛出带上下文的异常，上层代码统一捕获并处理，比如返回错误提示、记录日志、回滚事务等。这样职责会更清晰，也更容易排查问题。

异常处理最佳实践清单

经过这次整理，我觉得写异常处理时可以按下面这份清单检查：

  • 不要写空 catch 块，至少要记录日志或给出明确处理
  • 不要只写 catch (Exception e)，除非这一层确实是统一异常处理入口
  • 不要在 finally 中写 return
  • 异常信息要带上下文，比如订单号、用户ID、文件名
  • 能用代码判断避免的 RuntimeException，就不要依赖 try-catch
  • 底层异常如果无法处理，就向上抛出，不要假装处理了
  • 上层统一处理异常，负责日志、提示、事务回滚等
  • 包装异常时保留原始 cause，避免丢失根因
  • 关闭资源优先使用 try-with-resources
  • 自定义异常命名要清晰，比如 BusinessException、OrderStatusException

总结

这次系统梳理 Java 异常处理机制之后，我最大的感受是：异常处理不是为了“让程序不报错”，而是为了让错误在合适的位置被发现、被记录、被处理。

我的阶段性总结是：

  • 不要吞异常，空 catch 块是非常危险的写法
  • 异常信息要带上下文，不然排查问题会很困难
  • 底层无法处理的异常应该向上抛，上层再统一 catch
  • finally 适合释放资源，但不要在里面写 return
  • 关闭文件流、网络连接等资源时，优先使用 try-with-resources

以后写代码时，我会尽量避免为了“消除红线”而随便 try-catch。真正好的异常处理，应该能帮助我更快定位问题，而不是把问题藏起来。

HashMap基础学习

发表于 2018-07-22 分类于 Java集合

背景

2018 年 7 月，最近把 List 相关的内容过了一遍，接下来开始学习 Map。和 List 按顺序存储元素不同，Map 更像是一张“键值对表”，通过 key 可以快速找到对应的 value。

在 Java 集合框架里，HashMap 应该是工作中最常用的数据结构之一。比如根据用户 id 查用户信息、根据配置名查配置值、统计某个字段出现次数等，都很容易想到用 HashMap。

刚开始看 HashMap 的时候，我觉得它只是“根据 key 存取 value”的工具类。但继续往下学才发现，里面涉及哈希算法、数组、链表、扩容、线程安全、hashCode 和 equals 等一系列知识点。也难怪它经常出现在面试题里。

问题

学习过程中，我主要遇到了下面几个疑问：

  1. key 为 null 时，HashMap 到底怎么处理？
  2. 以前听说 HashMap 不是线程安全的，实际会出什么问题？
  3. 如果两个不同的 key 算出来的 hashCode 一样，数据会不会被覆盖？
  4. 遍历 HashMap 的方式太多，到底该用哪一种？
  5. HashMap 和 Hashtable 有什么区别？

这些问题如果只停留在“会用 API”的层面，其实很容易混淆。所以我打算先从常用操作入手，再慢慢分析它的底层原理。

分析

1. HashMap 可以存 null 吗？

HashMap 允许一个 null key，也允许多个 null value。

需要注意的是，key 是唯一的，所以 null key 只能有一个。如果重复放入 null key，后面的值会覆盖前面的值。

2. HashMap 为什么不是线程安全的？

HashMap 的大多数操作都没有加锁。如果多个线程同时修改同一个 HashMap，就可能出现问题。

在 JDK7 中，HashMap 扩容时采用头插法迁移链表节点，在并发 put 的情况下，链表可能形成环，最终导致查询时死循环。

在 JDK8 中，虽然扩容迁移逻辑有所调整，降低了死循环风险，但 HashMap 依然不是线程安全的。多个线程同时 put 时，仍然可能出现数据覆盖、数据丢失、扩容状态不一致等问题。

所以结论很明确：如果是多线程写入场景，不要直接使用普通 HashMap。

3. hashCode 相同怎么办？

HashMap 根据 key 的哈希值计算数组下标。不同的 key 可能被计算到同一个数组位置，这种情况叫哈希冲突。

JDK7 中，哈希冲突主要通过“数组 + 链表”解决：多个元素落到同一个桶时，会挂在同一条链表上。

JDK8 中，底层结构变成“数组 + 链表 + 红黑树”。当链表长度达到一定阈值，并且数组容量也达到要求后，链表会转成红黑树，减少极端情况下的查询时间。

因此，两个 key 的 hashCode 相同，并不代表一定会互相覆盖。HashMap 还会继续通过 equals 判断 key 是否真正相等。

4. 遍历方式应该选哪个？

HashMap 的遍历方式很多，比如遍历 keySet、遍历 entrySet、只遍历 value，或者使用 Iterator。

日常开发里，如果同时需要 key 和 value，我更推荐使用 entrySet。因为 entrySet 可以一次拿到 key 和 value，避免通过 key 再执行一次 get 查询。

5. HashMap 和 Hashtable 区别

Hashtable 是比较早期的集合类，HashMap 是后来集合框架中的常用实现。两者主要区别如下：

对比项 HashMap Hashtable
线程安全 非线程安全 方法使用 synchronized，线程安全
null 支持 允许一个 null key 和多个 null value 不允许 null key 和 null value
性能 单线程下通常更好 加锁开销较大
推荐程度 日常开发常用 现在较少使用
替代方案 多线程场景用 ConcurrentHashMap 通常不推荐新代码使用

5. 多线程场景使用 ConcurrentHashMap

如果多个线程会同时读写 Map，可以考虑使用 ConcurrentHashMap。

需要注意的是，ConcurrentHashMap 不是简单地给所有方法都加一把大锁。它内部做了更细粒度的并发控制，所以在并发场景下通常比 Hashtable 更合适。

不过，复合操作仍然要小心。例如“先判断再放入”不是天然原子的，可以优先使用 putIfAbsent。

总结

这次学习 HashMap，我最大的感受是：它看起来简单，但底层并不简单。

HashMap 是面试高频题，也是实际开发中非常常用的集合类。只会 put 和 get 当然可以完成很多需求，但如果不了解底层原理，就容易在哈希冲突、扩容、线程安全、自定义 key 等问题上踩坑。

我给自己总结了几条使用原则：

  1. HashMap 允许一个 null key 和多个 null value。
  2. 两个 key 的 hashCode 相同不会直接覆盖，还要继续比较 equals。
  3. 同时需要 key 和 value 时，优先使用 entrySet 遍历。
  4. 能预估数据量时，可以设置合适的初始容量，减少扩容。
  5. 多线程写入场景不要直接使用 HashMap，可以考虑 ConcurrentHashMap。
  6. 自定义对象作为 key 时，重写 equals 必须重写 hashCode。

学完这些内容后，我再看 HashMap 就不只是一个“键值对容器”了，而是能联想到数组、链表、红黑树、哈希冲突和并发安全等知识点。理解底层原理，才能真正把这个常用工具用好。

1. 90% 的场景用 ArrayList 就对了

日常开发里，大部分场景都是读多写少、随机访问、尾部追加。ArrayList 底层数组内存连续，访问速度快，CPU 缓存命中率也更友好，所以它应该作为默认选择。

2. 频繁头插再考虑 LinkedList

面向对象编程理解

发表于 2018-05-14 分类于 Java基础

背景

学完了Java的基础语法，终于进入了面向对象编程这块硬骨头。在此之前我一直用的是C语言写一些小项目，习惯了面向过程的思维方式——写一个函数，调用它，再写一个函数，再调用它，整个程序就是一系列函数的调用链。突然切换到面向对象，感觉脑子有点转不过弯来。

我记得《Head First Java》里面有一个很形象的类比：说类就像是饼干的模具，而对象就是用这个模具做出来的饼干。模具本身是一个概念上的模板，真正的饼干才是实在的东西。这个类比让我开始慢慢理解”对象”到底是个什么东西。

还特意去图书馆借了本《Java编程思想》，翻了几章感觉有点深，还是先老老实实把基础搞懂再说。

问题

刚开始学的时候，遇到了好多困惑：

第一，类和对象的关系总是搞不清楚。 我知道类是用class关键字定义的，对象是用new创建出来的，但实际写代码的时候，完全不知道什么时候该定义类，一个类应该包含哪些东西。经常写着写着就把所有代码塞到一个类里面，跟写面向过程没什么区别。

第二，封装的意义不理解。 刚接触private、public这些访问修饰符的时候，我就想：为什么要把字段设为private，然后还要写getter和setter去访问？这不脱裤子放屁吗？直接public不是更省事？

第三，继承和组合不知道怎么选。 看了书上的例子说”猫是一种动物”可以用继承，”车有轮子”可以用组合。但实际写代码的时候，总是倾向于用继承，觉得extends一下什么都有了，方便。

第四，多态太抽象了。 书上说”父类引用指向子类对象”，这句话我背都能背下来，但就是不知道这玩意儿到底有什么用，写代码的时候也完全想不起来用。

第五，接口和抽象类看着差不多，不知道怎么选。 两个都不能实例化，都包含抽象方法，到底有啥区别？

分析

随着写了一些小例子，慢慢对这些概念有了自己的理解。

类和对象： 类就是一个模板/蓝图，比如说”学生”这个概念，它有一些属性（姓名、学号、年龄）和行为（学习、考试）。而对象就是根据这个模板创建出来的具体实例，比如”张三”这个具体的学生。写代码的时候，应该先分析业务需求中有哪些实体，每个实体有什么属性和行为，再来定义类。

封装： 现在理解了，封装的意义在于保护内部状态。如果不封装，外部代码可以随意修改对象的内部数据，可能会导致数据不一致。比如一个Student的age字段，如果直接暴露为public，外部可以给它赋一个-1这种不合理的值。通过setter方法，可以在赋值前做校验。

继承与组合： “IS-A”关系适合用继承，”HAS-A”关系适合用组合。但继承的问题在于，父类的任何变化都会影响到所有子类，耦合度太高。现在很多书都推荐优先使用组合，组合更灵活，耦合度更低。

多态： 多态的本质就在于父类引用指向子类对象，调用的方法却是子类重写后的版本。这样做的最大好处是：可以写通用的代码来处理不同的具体类型。比如定义一个统一的pay()方法，不管是学生交学费，还是员工发工资，都调用同一个方法名，具体怎么实现由子类自己决定。

接口与抽象类： 接口定义的是行为契约——“你能做什么”；抽象类提供的部分实现——“你是什么”。接口强调的是能力，抽象类强调的是血缘关系。接口弥补了Java单继承的不足，一个类可以实现多个接口。

总结

折腾了两周，对面向对象总算有了个整体的认识。总结一下这几个星期的收获：

  1. 三大特性：封装、继承、多态。封装保护内部数据，继承实现代码复用，多态让代码更灵活。这三个东西是面向对象的基石，缺一不可。

  2. 设计思路要转变：从面向过程的”先想步骤”变成面向对象的”先找对象”。写代码之前先分析业务中有哪些实体（类），它们有什么属性和行为，它们之间有什么关系。这个思维转换确实需要时间，但慢慢练习就会习惯。

  3. 优先用组合：虽然继承用起来方便，但继承会让父类和子类耦合太紧。如果只是想要复用代码，组合往往是更好的选择。只有当确实是”IS-A”关系，并且行为需要多态时，才考虑继承。

  4. 面向接口编程：接口定义契约，实现类去遵守契约。这样写出来的代码耦合度低，扩展性好。比如排序功能依赖Comparable接口而不是具体的类，以后想换排序规则，只要改compareTo()的实现就好了。

面向对象的路才刚刚开始，后面还有设计模式等着我。不过有了这些基础，至少看代码的时候不会再一头雾水了。继续加油！

Java数据类型学习笔记

发表于 2018-04-08 分类于 Java基础

背景

学完第一个 Hello World 之后，我开始系统学习 Java 的基础语法。刚开始觉得数据类型应该不难，因为之前学 C 语言的时候也接触过 int、char、float 这些类型。

但是真正写 Java 代码时，我发现 Java 的类型系统比 C 语言更严格。变量必须先声明类型，类型之间不能随便混用，很多转换都需要明确写出来。

这几天练习的时候，我还遇到了两个很容易忽略的问题：一个是 int 运算溢出，另一个是 float 和 double 做小数计算时出现精度丢失。看起来只是基础知识，但如果不弄清楚，以后写业务代码肯定会踩坑。

问题

我目前遇到的问题主要有这几个：

  • 整数运算结果和预期不符（int溢出）
  • float和double计算金额时精度丢失
  • int和Integer傻傻分不清
  • 自动类型转换和强制类型转换的规则记不住

其中最让我困惑的是：明明代码没有报错，运行结果却是错的。比如两个很大的 int 相加，结果可能变成负数；两个小数相加，结果也可能不是我以为的 0.3。

分析

Java 里常用的整数类型是 int，但是 int 的范围并不是无限大，它的范围大约是 ±21 亿，也就是 -2147483648 到 2147483647。如果超过这个范围，就会发生溢出。大数运算应该使用 long，如果数字特别大，还需要使用 BigInteger。

浮点数的问题也比较典型。float 和 double 采用 IEEE 754 标准，它们在底层是用二进制表示小数的，所以无法精确表示某些十进制小数，比如 0.1、0.2。因此金额计算不能使用 float 或 double，应该使用 BigDecimal。

另外，int 是基本类型，而 Integer 是包装类。基本类型保存的是具体的数值，包装类是对象。Java 5 以后支持自动装箱和自动拆箱，所以平时写代码时它们看起来可以互相转换，但本质上不是一回事。

类型转换的规则可以简单理解为：小类型自动转大类型，大类型转小类型需要强制转换，而且可能丢失精度。

解决方案

Java开发环境搭建记录

发表于 2018-02-13 分类于 Java基础

背景

2018 年春节回来，我下定决心从 C 语言转向 Java 后端开发。上学时学过一点 C 语言，顶多写过一些控制台排序算法，对”企业级开发”完全没概念。周围同学有搞 PHP 的，有搞 Python 的，选 Java 主要是看中了它的就业面广、生态成熟。

当时手头参考资料主要是两样：廖雪峰的 Java 教程（在线版）和 《Head First Java》 这本经典入门书。廖雪峰的教程偏实战，直接讲 Eclipse 怎么配、Maven 怎么用，而 Head First 用大量插图讲面向对象思想，两本搭配着看效果不错。

因为之前只用过 Code::Blocks 写 C 语言，对 JDK、JRE、IDE 这些概念完全分不清，所以第一步搭建环境就折腾了好几天。

分析

回过头来分析这几个问题，其实都不复杂，但对新手来说每个都是拦路虎。

JDK 版本

JDK 9 引入了模块化系统（Jigsaw），算是一次比较大的架构变动。虽然新特性很吸引人，但 LTS 版本更稳妥这个道理现在懂了。JDK 8 一直到 2018 年初都还是绝对的主流，公司项目基本都在用，遇到问题网上也更容易找到解决方案。

环境变量问题

仔细排查后发现是犯了两个低级错误：

  1. 路径多了尾部斜杠：配置 JAVA_HOME 时写成了 C:\Program Files\Java\jdk1.8.0_161\（多了反斜杠），导致 %JAVA_HOME%\bin 解析出来变成了 C:\Program Files\Java\jdk1.8.0_161\\bin，双斜杠导致路径无效。

  2. 配置后没重新打开命令行：环境变量改了之后，已经打开的命令行窗口不会自动刷新，需要关掉重新打开。

总结

这次搭建环境的经历让我这个 Java 新手学到了不少东西：

  1. JDK 选择 LTS 版本最稳妥。JDK 9 虽然新，但 JDK 8 作为 LTS 版本在企业中广泛使用，遇到问题更容易找到解决方案。对于初学者来说，稳定压倒一切。

  2. 环境变量配置要仔细检查路径。多一个斜杠、少一个分号都可能导致配置不生效。配置完一定要重新打开命令行窗口再测试，这个坑后来再也没踩过。

  3. IDE 的 JVM 参数要根据机器配置调整。Eclipse 默认的 JVM 参数是为配置较高的机器准备的，2018 年主流笔记本还是 4GB~8GB 内存，默认的 1024m 对低配机器来说偏大。eclipse.ini 里的 -Xmx 参数控制最大堆内存，根据自己电脑的内存大小酌情调整就好。后来的 IntelliJ IDEA 也有类似问题，idea64.exe.vmoptions 里面的参数同样需要根据机器配置手动调整。

  4. 建议新手先熟悉命令行编译运行再依赖 IDE。虽然 Eclipse 很方便，但用命令行编译运行能让人更好理解 Java 的编译原理——Java 源代码通过 javac 编译成字节码（.class 文件），再由 JVM 解释执行。理解了这套流程，后面学 Maven、Gradle 这些构建工具也会轻松很多。
