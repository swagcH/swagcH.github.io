Tomcat部署项目

发表于 2019-05-19 分类于 项目实践

背景

把项目从本地 IDE 跑到 Tomcat 服务器上，是我第一次真正感受到部署这件事。

2019 年对我来说和 2018 年明显不一样。2018 年更多是在补 Java 基础，到了 2019 年，我开始把零散知识往项目里放。很多以前看起来懂了的概念，只要一放进真实项目流程里，马上就会暴露问题。

这篇文章记录的是我在 2019-05 前后学习和实践 Tomcat部署项目 时的理解。内容不会写得像官方文档，更像是一份踩坑记录：当时为什么学、遇到了哪些问题、怎么排查，最后沉淀出哪些可以复用的经验。

问题

刚开始实践时，我主要卡在下面几个点：

  1. IDE 能跑，部署到 Tomcat 就 404
  2. war 包路径和 context path 搞混
  3. 端口 8080 被占用

这些问题单独看都不算复杂，但放在项目里就很容易连锁反应。比如配置错了，表面上看到的是页面打不开，实际原因可能是路径、依赖、运行环境或者请求流程中的某个环节出了问题。

分析

部署失败多数不是代码问题，而是路径、端口、依赖、配置和运行环境不一致。

我后来发现，学项目实践类技术时，不能只背 API。更重要的是把它放到一条完整链路里看：

只要能说清楚它在这条链路里的位置，就不会完全靠记忆去使用。

解决方案

我的处理方式是先把最小可运行例子跑通，再逐步放到项目中验证。下面是当时整理下来的关键操作和代码片段。

实践过程中我还给自己定了一个小规则：每次遇到问题，不只记录最终命令，还要记录“为什么这么做”。否则下次换一个环境，很容易又从头查一遍。

总结

这次学习给我的最大感受是：项目实践里的知识点，真正难的不是单个语法，而是上下文。

对 Tomcat部署项目 的理解，我最后沉淀成几条经验：

  • 先理解它解决什么问题，再记具体用法；
  • 先跑通最小 Demo，再接入完整项目；
  • 配置类问题要从路径、依赖、版本、环境四个方向排查；
  • 代码示例要自己敲一遍，复制能跑不代表真的理解；
  • 每次踩坑最好留下记录，后面会节省大量时间。

2019 年的学习明显比 2018 年更贴近真实开发。很多概念，比如 Servlet、Spring、MyBatis、接口设计、权限管理，都是在一次次“跑不起来”和“终于跑通了”的过程中慢慢理解的。

2018年度学习总结

发表于 2018-12-30 分类于 随笔

现在是 2018 年 12 月 30 日深夜，窗外很安静，桌面上摊着几本书、一杯凉掉的咖啡、开着 IDE 的屏幕。刚刚跑通了一个 Spring 的小 Demo，不算什么了不起的东西，但我盯着控制台里那几行日志，愣是坐了好一会儿。

总觉得该写点什么，为这一年。

回头看，2018 年是我真正踏进编程世界的第一年。从连编辑器都不会配，到能用 Java 写点能跑的东西，这三百多天走得七拐八拐，中间有好几次差点放弃。趁着跨年前这个安静的夜晚，把这一年的路好好捋一捋。

背景

2018 年 1 月，我坐在电脑前打开了一本 C 语言的电子书，那是我和编程的第一次正式见面。

在此之前，我对编程的全部认知大概就是——很酷、很复杂、不适合我。高考报志愿时阴差阳错进了计算机相关专业，大一上学期懵懵懂懂地过了，真正开始认真对待，就是从 2018 年开始的。

最开始学的是 C 语言，指针、内存管理、结构体——说实话，学得挺痛苦的。尤其是指针，绕来绕去，debug 的时候经常对着一个段错误发呆半小时。但也正因为 C 的硬核，让我对内存、对程序的底层运行有了一点感觉。

到了三四月份，我开始纠结一个问题：C 语言当然好，但它适合作为长期深耕的方向吗？当时打听了不少学长，也刷了很多帖子，结论是——Java 在后端领域生态成熟、岗位多、学习路径清晰。于是我做了一个重要的决定：转学 Java。

这个决定，基本定义了我整个 2018 年剩下的路。

问题

目标定下来之后，真正走起来才发现，问题一个接一个。

1. 学习路线不清晰，走了不少弯路

网上关于 Java 学习的资料和路线图很多，但信息多到让人不知道该信谁。今天看到一个博客说先学 Java SE，明天又有人说直接上手 Spring Boot。我是那种喜欢把”所有前置知识”都学完再做事情的人，结果就是在基础语法阶段兜兜转转了太久。

2. 光看不练，眼高手低

这是我这一年最大的毛病。

看书的时候觉得自己都懂了——不就是面向对象吗，不就是集合框架吗，有什么难的。但是合上书，打开 IDE，写一个简单的增删改查都要查半天 API。印象最深的是学完 HashMap 原理之后，自己试着实现一个简化版本，写到一半发现根本不知道从哪里下手。这才意识到，”看懂”和”会写”之间隔着十万行代码的距离。

3. 遇到问题不敢问

当时加了一些技术群，也在论坛上潜水。遇到问题第一反应不是去问，而是反复怀疑自己是不是太笨了——这么基础的东西都不懂。于是经常一个人卡在一个小 bug 上几个小时，浪费大量时间。后来才明白，每个经历过自学的人都是从这些坑里爬出来的，问问题不是丢人的事。

4. 博客看得多，写得少

我的浏览器书签里收藏了上百篇文章，从 HashMap 源码分析到 JVM 内存模型，应有尽有。每天刷好几篇，刷完觉得充实。但一个月后回头看，脑子里能留下的印象很模糊。因为光看不写，知识的留存率太低了。

5. 时间管理不好，经常拖延

“今天太累了，明天再看吧”——这句话几乎是我上半年的口头禅。没有固定的学习时间，没有计划，全凭热情驱动。热情高的时候一天学八个小时，没状态的时候一周都不碰代码。这种节奏非常低效。

分析

后来我慢慢想明白了这些问题的根因，也在下半年做了一些调整。

学习规划的重要性

没有规划的学习就像没有地图的旅行。知识海洋是无限的，但个人的时间和精力是有限的。后来我给自己定了一条原则：选定一个方向，找到一条被验证过的路线，先踏踏实实走完，不要中途反复切换赛道。

编程是手艺活

我越来越理解一个道理：编程像学游泳，你看再多教学视频，不下水就永远学不会。代码必须亲手敲，bug 必须亲自查，项目必须亲手做。任何一个你”觉得”懂了但写不出来的知识点，都说明你还没真正掌握它。

后来我强迫自己每学一个新知识点，就写一段代码验证它，哪怕只是一个十行的小 demo。

社区和交流的价值

下半年我开始尝试在群里发言，偶尔回答一些别人提的问题。我发现教是最好的学——为了回答一个问题，你往往需要把那个知识点重新梳理一遍，这个过程本身就是一次高质量复习。而且当你发现别人也会犯和你一样的错误时，那种”只有我不行”的焦虑感会少很多。

写作是深度学习的加速器

十月份开始写博客之后，我明显感觉到自己对知识的理解深了一层。因为要把一个东西讲清楚，你必须先把它真正搞懂。写作强迫你梳理逻辑、查漏补缺、用自己的语言重新表达。这个过程比单纯地读十篇文章都有效。

固定学习节奏

下半年我开始用番茄工作法，每 25 分钟专注学习，然后休息 5 分钟。同时给自己定了规矩：每天晚上 8 点到 10 点是固定学习时间，雷打不动。效果比”等我有时间了再学”好太多。

解决方案

Linux常用命令整理

发表于 2018-11-18 分类于 Linux运维

背景

2018年双十一刚过，项目终于要部署上线了。公司买了两台阿里云ECS服务器，操作系统是CentOS 7.4。作为一个从大学到现在一直在Windows环境下写代码的.NET程序员，听到”部署到Linux服务器”这几个字时，内心是拒绝的。

之前对Linux的印象停留在”黑乎乎的命令行窗口，一堆看不懂的英文字母”。但项目不等人，硬着头皮上吧。花了大概两周时间边查边练，把日常运维常用的Linux命令过了一遍，这篇文章就是这段时间的学习笔记。

问题

刚接手Linux服务器时，遇到了一堆”小白问题”，说来有点丢人但确实很真实：

1. 文件权限看不懂

ls -l 输出了一堆 drwxr-xr-x 这样的东西，完全不知道什么意思。想给文件加执行权限，百度了半天才找到 chmod 777，但到底什么是”777”也说不清楚。

2. vim编辑器不会用

用 vi 打开文件后，发现打不了字，想退出却退不出来，最后直接关了终端。后来才知道 vim 有三种模式，退出要用 :q。

3. 进程查不到

程序跑起来后不知道在哪看，Windows 有任务管理器，Linux 呢？程序挂了也不知道为什么挂的。

4. 磁盘满了不知道清哪里

有一天数据库写不进去了，排查半天发现是磁盘满了。但日志文件、临时文件散落在各个目录，不知道从哪里开始清理。

5. 日志文件太大查看困难

Java 应用的日志文件动辄几百兆甚至几个G，用记事本打开直接卡死。想查最新的报错信息，总不能把整个文件拖下来吧。

6. 端口被占用不知道怎么查

Tomcat 启动报错 Address already in use，知道是端口被占了，但不知道被哪个程序占了，也不知道怎么杀掉它。

分析

遇到这些问题后，我花了一些时间理解了 Linux 的几个核心概念，这些概念是后续学习命令的基础。

Linux 一切皆文件

这是 Linux 最核心的设计哲学。普通文件是文件，目录是文件，设备是文件，甚至是进程信息、网络连接都被抽象成了文件。理解了这一点，就能理解为什么 Linux 有那么多文件操作命令了。

权限的 rwx 表示法

rwx 分别代表：

  • r（read）：读取权限，值为 4
  • w（write）：写入权限，值为 2
  • x（execute）：执行权限，值为 1

权限分三组，每组三个字符：所有者/所属组/其他人。所以 rwxr-xr-x 表示：所有者可读写执行，所属组可读执行，其他人可读执行。

而 chmod 755 中的 755，就是用数字表示的权限：

  • 7 = 4+2+1 = rwx（所有者）
  • 5 = 4+0+1 = r-x（所属组）
  • 5 = 4+0+1 = r-x（其他人）

vim 的三种模式

刚接触 vim 时觉得这编辑器反人类，理解了三种模式后就豁然开朗了：

  • 命令模式：刚进入 vim 时的模式，可以复制粘贴删除，但不能输入文字
  • 插入模式：按 i 进入，这个模式才能正常打字
  • 末行模式：按 : 进入，用来保存退出、搜索替换

三种模式切换搞明白后，vim 就好用多了。

进程管理思路

Linux 的进程管理不像 Windows 那样可视化，但命令行的方式其实更灵活：

  • ps 查看静态进程快照
  • top 查看动态进程信息（相当于任务管理器）
  • kill 发送信号给进程

磁盘查看思路

  • df 从宏观角度查看磁盘整体使用情况
  • du 从微观角度查看具体目录/文件占用空间

日志查看三板斧

大文件用编辑器打开是不现实的，Linux 提供了三个利器：

  • tail：从尾部看，适合看最新的日志
  • grep：按关键字过滤，适合搜索特定错误
  • less：分页查看，适合在文件中上下翻阅

端口查看思路

  • netstat：查看网络连接状态
  • lsof：查看打开的文件（一切皆文件，网络连接也是文件）

MySQL基础增删改查

发表于 2018-10-28 分类于 数据库

背景

学完JDBC之后，我意识到一个很严重的问题——我一直在“照着写”SQL，却从来没有真正理解过每条SQL背后的含义。JDBC教会了我怎么用Java连接数据库、怎么执行SQL、怎么处理ResultSet，但SQL本身呢？我只会照猫画虎地写几句SELECT和INSERT，稍微复杂一点的查询就抓瞎。

这段时间我决定从头系统地学习SQL，从最基础的建表开始，到增删改查，再到多表关联、聚合函数、索引优化，一步一步把每个知识点搞清楚。这篇文章就是我在2018年10月学习MySQL基础CRUD的完整记录。

问题

在实际写SQL的过程中，我遇到了好几个一直没搞明白的问题：

  1. DELETE和TRUNCATE到底有什么区别？ 之前一直以为都是删数据，随便用哪个都行，结果有一次用TRUNCATE删完数据发现回不去了。
  2. GROUP BY和HAVING总是写错，经常把过滤条件写在WHERE里，结果报错，搞不清什么时候该用WHERE、什么时候该用HAVING。
  3. 多表JOIN搞不清关系，INNER JOIN、LEFT JOIN、RIGHT JOIN到底返回什么数据，每次都要画图才能想明白。
  4. 索引加了但查询还是很慢，以为建了索引就万事大吉，结果有些查询根本没走索引。
  5. 不知道什么时候该建索引，哪些列该建、哪些不该建，完全没有概念。

分析

DELETE和TRUNCATE的区别

这两个看起来都是“删数据”，但底层机制完全不同：

对比点 DELETE TRUNCATE
删除方式 逐行删除 清空并重建表结构
SQL类型 DML DDL
是否可回滚 在事务中可回滚 通常不可回滚
是否支持WHERE 支持 不支持
自增ID 一般不重置 通常会重置
执行速度 数据量大时较慢 通常更快

简单理解：DELETE是一行一行删，可以配合WHERE精确删除，也可以在事务中回滚；TRUNCATE更像是把表清空后重新整理，速度快，但风险也更高。

JOIN类型的区别

JOIN最核心的不是语法，而是先搞清楚两张表之间的关系：

  • INNER JOIN：只返回两边都匹配的数据。
  • LEFT JOIN：左表全部保留，右表匹配不到的地方用NULL补齐。
  • RIGHT JOIN：右表全部保留，左表匹配不到的地方用NULL补齐。

实际开发中我感觉LEFT JOIN用得更多，因为很多时候我们会以一张主表为中心，再去关联其它明细表。

索引不是万能的

索引像书的目录，可以帮助数据库快速定位数据。但它不是万能药，加了索引并不代表一定快：

  • 表数据量很小时，全表扫描可能更快。
  • 查询返回的数据太多时，走索引反而不划算。
  • 在索引列上使用函数，可能导致索引失效。
  • LIKE以%开头时，通常无法利用普通索引。
  • 字段发生隐式类型转换时，也可能导致索引失效。

索引应该建在什么列上

比较适合建索引的列：

  • 区分度高的列，比如学生ID、手机号、身份证号。
  • 经常出现在WHERE条件里的列。
  • 经常用于JOIN关联的外键列。
  • 经常用于ORDER BY或GROUP BY的列。

不太适合建索引的列：

  • 区分度很低的列，比如性别。
  • 经常更新的列，因为维护索引也有成本。
  • 很少参与查询条件的列。

总结

这次系统整理MySQL基础增删改查之后，我最大的感受是：SQL真的是后端开发的基本功。以前写JDBC时，我只关心Java代码能不能跑通，现在才发现SQL本身才是和数据库沟通的核心。

我需要牢记的几个点：

  1. 理解SQL执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY。只有知道SQL先做什么、后做什么，才能写出正确的分组查询。
  2. DELETE和TRUNCATE不能混用：DELETE适合按条件删除，也更容易配合事务；TRUNCATE适合清空整张表，但风险更高。
  3. JOIN要先想清楚主表和关系：INNER JOIN看匹配，LEFT JOIN保留左表，RIGHT JOIN保留右表。
  4. 索引要合理使用：索引应该建在区分度高、经常查询、经常关联的列上，不是越多越好。
  5. 用EXPLAIN验证SQL：查询慢的时候，不要靠猜，要看执行计划。

背景

2018 年 9 月，我刚把 Java 基础和 MySQL 的常用语法系统学完。前面写 Java 时，大多是在控制台里打印结果；学 MySQL 时，也主要是在命令行或者图形化工具里执行 SQL。到了这个阶段，一个很自然的问题出现了：能不能用 Java 代码直接操作 MySQL 数据库？

答案就是 JDBC。

JDBC，全称是 Java Database Connectivity，它是 Java 提供的一套数据库访问规范。简单理解，JDBC 就像 Java 程序和数据库之间的一座桥：Java 代码通过 JDBC API 发送 SQL，数据库执行后再把结果返回给 Java 程序。

我当时的目标很明确：

  • 用 Java 连接 MySQL；
  • 用 Java 执行增删改查；
  • 理解 Connection、PreparedStatement、ResultSet 这些核心对象；
  • 避免连接泄漏、SQL 注入、中文乱码这些常见坑。

4. ResultSet 取值顺序混乱

ResultSet 不是一次性把所有数据都变成 Java 对象，而是一个游标。刚拿到 ResultSet 时，游标在第一行之前，必须先调用 next()，再读取当前行的数据。

如果忘记 next()，或者列名、列下标混着用，很容易出现取值混乱。

5. 资源忘记关闭导致连接泄漏

JDBC 里最容易忽略的一点是资源释放。Connection、Statement、ResultSet 都持有数据库或网络资源，用完不关闭，就可能导致连接越来越多，最后数据库拒绝新的连接。

6. 中文数据存入乱码

如果数据库、表、连接 URL 的编码不一致，中文数据就可能变成问号或者乱码。尤其是早期 MySQL 项目里，连接参数里没有指定 characterEncoding=UTF-8 时很容易遇到。

总结

这次 JDBC 连接 MySQL 的实践，让我把 Java 基础、SQL 语法和数据库连接机制串了起来。以前只是在数据库工具里执行 SQL，现在可以通过 Java 代码完成完整的 CRUD 操作，感觉 Java 程序终于可以真正和数据打交道了。

我给自己总结了几条规则：

  1. 永远优先使用 PreparedStatement，不要用字符串拼接 SQL；
  2. ResultSet 是游标模式，读取前先 next()；
  3. Connection、Statement、ResultSet 用完必须关闭；
  4. 资源关闭要放在 finally 中，或者使用 try-with-resources；
  5. 中文数据要注意数据库编码和 JDBC URL 中的 characterEncoding=UTF-8；
  6. 涉及多条 SQL 的一致性操作时，要明确事务边界；
  7. 生产环境不要直接频繁创建连接，应该使用连接池，比如 Druid。

JDBC 的代码确实比较模板化，但它非常适合用来理解数据库访问的底层过程。后面再学习 DBUtils、JdbcTemplate、MyBatis 这些框架时，就会更容易明白它们到底帮我们封装了什么。
