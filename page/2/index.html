Prometheus监控部署

发表于 2022-11-20 分类于 架构成长

日志适合解释一次具体失败，指标适合回答系统是否正在变坏。Prometheus 建起来不难，难的是决定采集什么、标签怎么设计，以及什么情况值得在半夜叫醒值班人员。

这篇按“指标、查询、面板、告警、运行”五个层次整理，不把部署成功等同于监控完成。

1. 先确定要回答的问题

对于一个订单服务，我希望监控能快速回答：

这些问题可以分成两套方法：

RED：面向请求

USE：面向资源

接口使用 RED，CPU、磁盘、连接池和线程池使用 USE。两者结合，才能区分“请求变慢是业务代码问题”还是“资源已经饱和”。

2. Prometheus 链路

Prometheus 使用 Pull 模型。目标服务暴露当前累计指标，Prometheus 定期抓取并保存时间序列。应用不需要知道 Prometheus 地址，也不会因为监控端短暂不可用而阻塞业务请求。

批处理等短生命周期任务不适合机械套用 Pull，可以评估 Pushgateway，但 Pushgateway 中指标生命周期需要额外管理，不能把它当成所有业务指标的通用上报入口。

7. 四条基础 PromQL

7.1 总 QPS

Counter 必须使用 rate 或 increase 计算变化，不要直接对累计值做告警。

7.2 5xx 错误比例

使用比例比固定错误数更合理。低流量服务还要设置最小请求量条件，否则偶发一个错误就会显示 100%。

7.3 按 URI 计算 P95

只有启用了 Histogram Bucket，才能正确计算分位数。uri 应该是框架归一化后的路由模板，例如 /orders/{id}，不能是带真实订单号的 URL。

7.4 订单创建失败速率

这条业务指标可以直接看出失败原因趋势，比只统计 HTTP 500 更接近用户感知。

一个服务首页我会按排查顺序摆放：

面板变量只提供有边界的选项，例如 env、application 和 instance。默认时间范围、单位和阈值颜色要统一，避免每个面板用不同口径。

9. 告警规则要包含持续时间

for: 10m 能过滤短暂毛刺。阈值只是示例，真实值要结合 SLO、历史基线和业务时段调整。

一条可执行的告警至少包含：

  • 哪个服务、环境和症状。
  • 当前值与阈值。
  • 相关 Dashboard 和日志入口。
  • Runbook 与升级联系人。
  • 恢复通知和抑制规则。

10. 告警为什么会失效

告警太多

同一个根因触发 CPU、延迟、错误率和实例存活几十条通知，值班人员很快会忽略。Alertmanager 应按服务和故障域分组，并用抑制规则让根因告警覆盖症状告警。

没有用户影响

JVM Old 区 80% 不一定是故障，GC 后能回落就可能正常。相比单个资源阈值，持续的错误率和延迟更接近用户影响。资源告警适合作为容量预警，不一定都需要最高级别通知。

标签变化导致规则静默

框架升级后 uri、status 或指标名改变，查询可能返回空结果。规则也要测试，并对关键指标使用 absent() 检测缺失。

没有最小流量条件

凌晨只有一次请求且失败，错误率是 100%，但影响和高峰期完全不同。告警表达式需要结合请求量或使用燃烧率思路。

11. 监控系统本身也要监控

Prometheus 本地存储适合一定规模和保留周期。需要长期保存、跨集群查询或更高可用时，可以评估远程存储方案，但先解决标签治理，否则只是把高基数问题搬到更大的集群。

12. 上线检查

最后的理解

Prometheus 最有价值的地方不是收集了多少指标，而是把“系统健康”变成了可以讨论和验证的数字。QPS、错误率、延迟和饱和度形成趋势以后，很多问题会在用户反馈前出现信号。

日志、指标和链路各有职责：指标发现异常，链路缩小范围，日志解释细节。把三者通过服务名、时间和 traceId 关联起来，才是一套真正可用于故障处理的可观测体系。

ELK日志平台搭建

发表于 2022-10-23 分类于 架构成长

这篇记录一次日志平台从“能收集”到“能排查”的建设过程。严格来说，加入 Filebeat 后常被称为 Elastic Stack。组件启动只是基础，真正决定平台质量的是日志字段、索引映射、保留策略和采集链路自身的可靠性。

1. 为什么不继续登录服务器 grep

单体阶段，一台机器上的 app.log 基本能还原请求。服务拆分后，一次订单请求可能经过：

如果每个服务有三个实例，就要在十几份文件里按时间猜测。服务器滚动发布后，旧容器日志还可能已经被删除。

日志平台希望解决四件事：

  1. 集中检索，不依赖登录生产服务器。
  2. 通过 traceId 串起跨服务请求。
  3. 按服务、级别、业务编号和异常类型过滤。
  4. 对错误趋势、采集延迟和存储容量建立监控。

它不应该成为无限期保存全部文本的仓库。日志有成本，也可能包含敏感数据，必须从一开始设计范围和生命周期。

2. 组件职责

小规模场景可以让 Filebeat 直接写 Elasticsearch，减少 Logstash 成本。需要复杂字段清洗、多目标路由或统一入口时，再加入 Logstash。组件不是越齐全越专业，每增加一层都要处理它的容量和故障。

Elastic Stack 各组件尽量保持同一大版本，并核对官方兼容说明。Elasticsearch、Kibana、Logstash 和 Filebeat 跨大版本混用，常见问题包括协议、模板和安全默认值不一致。

4. 一行一个 JSON 事件

Java 异常栈天然多行，普通文本采集需要复杂的 multiline 规则。更稳定的方式是由日志框架输出单行 JSON，把异常栈作为字符串字段。

这样 Filebeat 不负责猜测一条事件从哪里开始，能减少错拼和漏拼。代价是单行会很长，因此日志框架、Filebeat 和 Elasticsearch 都要设置合理的单事件大小限制。

6. Logstash 只做必要加工

示例省略了证书路径，生产环境必须正确校验证书，不能为了连通直接关闭 TLS 校验。

应用已经输出 JSON 时，Filebeat 可以把字段展开，Logstash 不需要再对 message 做一次 JSON 解析。重复解析会增加 CPU，也容易产生字段覆盖。

复杂 Grok 正则要谨慎。一个低效表达式在日志量升高时可能打满 Logstash CPU。能在应用端结构化的字段，不要留到采集端猜。

7. 映射决定日志是否可用

Elasticsearch 动态映射很方便，也很危险。不同服务把同一个字段 cost 分别写成字符串和数字，会造成映射冲突；动态业务键会制造大量字段。

按天索引容易理解，但日志量变化后会出现两个问题：小服务产生大量小索引，大服务单日索引又可能过大。

11. 上线前的日志规范

建设后的变化

ELK 搭建完成后，最大的变化不是“搜索速度更快”，而是排查过程开始有统一入口。开发不再先问日志在哪台机器，而是先拿到时间、业务编号和 traceId。

但平台不会自动产生好日志。字段随意、异常栈缺失、敏感信息失控时，集中存储只会把问题放大。应用日志规范、采集可靠性和生命周期管理三者一起落地，日志平台才从一个大搜索框变成真正的故障分析工具。

Docker基础部署，Docker Compose实践

发表于 2022-08-14 分类于 架构成长

这篇做一个可以实际运行的部署练习：把 JDK 8 的 Spring Boot 应用构建成镜像，再使用 Docker Compose 启动应用、MySQL 和 Redis。重点不只是 up -d，还包括网络、健康检查、数据卷、日志和排障。

0. 最终目录

Docker Compose V2 推荐使用 docker compose 命令。旧环境可能仍然使用独立的 docker-compose。新版 Compose 文件可以省略顶层 version，旧项目中的 version: "3.8" 仍然常见，但不要把它和 Docker Engine 版本混为一谈。

1. 先理解四个对象

容器不是轻量虚拟机。一个容器通常运行一个主要前台进程，进程退出，容器也会停止。容器内写入层可以保存临时文件，但删除容器后数据会消失，因此 MySQL 数据必须放在 Volume。

2. 为 Spring Boot 编写 Dockerfile

使用多阶段构建，第一阶段通过 Maven 打包，第二阶段只保留 JRE 和 Jar：

这里有几个目的：

  1. 构建环境和运行环境分开，运行镜像不包含 Maven 缓存和源代码。
  2. 先复制 pom.xml 下载依赖，依赖不变时可以复用构建缓存。
  3. 应用使用非 root 用户运行。
  4. Jar 名称在镜像中固定为 app.jar，启动命令不依赖版本号。

基础镜像标签应该固定到经过验证的版本或 digest。示例标签用于说明结构，正式项目需要经过漏洞扫描和升级流程。

如果项目打包目录里可能有多个 Jar，target/*.jar 会匹配多个文件并导致构建失败。可以在 Maven 中固定 finalName，或者在构建脚本中明确选择可执行 Jar。

Docker 构建会把上下文发送给 daemon。忽略 target、日志和本地环境文件可以提升速度，也能避免把密钥误打进镜像层。

4. 编写 Compose

.env.example 只保留变量名和示例值，真实 .env 不提交：

compose.yaml：

示例没有把 MySQL 和 Redis 端口映射到宿主机，因为只有应用容器需要访问它们。减少端口暴露可以降低误访问风险。本地确实需要客户端连接时，再显式增加 127.0.0.1:3306:3306，避免监听所有网卡。

depends_on 的健康条件需要较新的 Compose 实现。旧版本可能只保证启动顺序，不等待服务真正可用，因此应用自身仍应有有限重试和明确的启动失败日志。

-XX:+ExitOnOutOfMemoryError 需要较新的 JDK 8 update，使用前要通过实际基础镜像验证。JVM 堆也不能等于容器全部内存，还要给 Metaspace、线程栈和堆外内存留空间。

8. 五个常见故障

8.1 容器反复重启

先看退出码和最后一段日志。restart: unless-stopped 会不断拉起失败进程，容易让真正的首次异常滚出日志窗口。

8.2 MySQL 一直不健康

检查密码变量是否正确展开、数据目录权限、旧数据卷与新版本是否兼容。MySQL 初始化只在空数据目录执行，修改环境变量不会自动修改已有数据库用户密码。

8.3 应用能解析服务名但连不上

检查服务是否在同一个网络、目标进程是否监听 0.0.0.0，以及端口使用的是容器端口还是宿主机映射端口。

8.4 磁盘被日志写满

Docker json-file 默认可能持续增长。Compose 中已经限制单文件和数量，仍要监控 Docker 根目录和应用自身文件日志，避免两套日志重复写盘。

8.5 镜像在另一台机器无法运行

确认 CPU 架构、镜像是否成功推送、私有仓库认证和配置文件来源。Apple Silicon 本地构建的镜像部署到 x86 服务器时，尤其要检查目标平台。

9. 配置和密钥

Compose 环境变量适合本地练习，但生产环境不能把密码直接写进仓库。至少做到：

  • .env 加入 .gitignore。
  • 使用独立的应用数据库账号，不使用 root。
  • 密钥通过受控平台、挂载文件或 Secrets 管理。
  • 日志禁止打印数据库 URL 中的密码和 Token。
  • 配置变更有审计和回滚版本。

Docker 镜像应当只包含通用应用，不把某个环境的 application-prod.yml 和密钥烘焙进去。

10. Compose 的适用边界

Compose 很适合本地开发、自动化测试和单机多容器部署。它能把依赖关系固化成代码，也方便复现环境。

生产环境还需要考虑：

这些问题不是再写几行 Compose 就能全部解决的。是否进入 Kubernetes 等平台，要根据服务规模和运维能力决定。

收尾命令

这次实践真正解决的不是“会用 Docker 命令”，而是把构建、网络、配置、依赖和数据生命周期写成了一个可以重复执行的环境。能够在另一台干净机器上用同一份配置启动并验证，才是容器化带来的环境一致性。

Redis高可用架构

发表于 2022-07-24 分类于 架构成长

这篇不从安装命令开始，而是先比较方案，再记录一次 Sentinel 故障转移演练。因为 Redis 高可用最容易被误解的地方，是把“有副本”当成“不会中断”，或者把“自动切主”当成“不会丢数据”。

1. Redis 在系统里承担什么角色

同样是 Redis，不同用途对应的恢复目标完全不同：

架构设计前先定义两个指标：

  • RTO：故障后允许多久恢复服务。
  • RPO：允许丢失多长时间窗口的数据。

如果业务要求数据绝不丢失、强一致写入，Redis 主从加 Sentinel 并不能天然满足，需要重新评估数据模型和存储选择。

2. 四种常见形态

形态 解决的问题 没解决的问题
单机 简单缓存 单点故障、容量上限
主从复制 读副本、数据冗余 自动选主、异步复制丢失窗口
Sentinel 监控和自动故障转移 水平分片、绝对零数据丢失
Redis Cluster 分片、扩容、自动切换 跨槽操作限制、客户端复杂度

本文选择一主两从加三个 Sentinel，适合数据量仍能放在单个主节点、但需要自动故障转移的场景。

三个 Sentinel 应部署在相互独立的故障域，全部放在同一台机器只能演示流程，不能抵抗机器故障。

4. Sentinel 配置含义

三个 Sentinel 使用相同的监控名称：

monitor 最后的 2 是 quorum。至少两个 Sentinel 同意主节点客观下线，才会进入故障转移判断。它不是 Sentinel 总数，也不是副本数量。

down-after-milliseconds=5000 代表单个 Sentinel 多久无法得到有效响应后认为主观下线。设置太短会因瞬时抖动频繁切换，太长则增加恢复时间。

parallel-syncs=1 控制故障转移后同时向新主同步的副本数。同步期间副本可能不可用，值越大恢复越快，但新主节点网络和磁盘压力也更大。

7. 网络分区与“脑裂”风险

假设旧主节点与 Sentinel 失联，但仍能接收部分客户端写入。Sentinel 会提升一个副本为新主，网络恢复后旧主被降级，它隔离期间接受的写入可能丢失。

降低风险的方法包括：

  • 合理设置 min-replicas-to-write 和最大复制延迟。
  • 客户端不要绕过 Sentinel 固定连接旧主。
  • Redis 节点、Sentinel 和应用之间使用一致的网络访问策略。
  • 对关键数据保留数据库事实来源和业务对账。

这些措施是在一致性和可用性之间做选择，不可能让异步复制同时获得所有保证。

8. Redis 故障时应用怎么保护数据库

即使切换只需要十几秒，缓存未命中和连接错误也可能让流量直接打向数据库。

我会准备三层保护：

  1. 热点只读数据使用短时间本地缓存。
  2. 回源数据库前做并发合并或互斥重建，避免同一 key 同时查询。
  3. 数据库入口设置限流和降级，宁可返回可解释的繁忙提示，也不要拖垮主库。

9. 持久化和备份不能缺席

Sentinel 管理高可用，不等同于备份。误删除、错误写入会复制到所有副本。

需要根据恢复目标选择 RDB、AOF 和独立备份：

备份必须定期做恢复验证。只有生成文件、从未恢复过的备份不能算可靠。

10. 日常监控

高可用演练的结果也要进入记录：切换用了多久、丢了多少请求、有没有数据缺口、客户端多久恢复、数据库是否被回源流量冲击。

结论

Sentinel 解决的是主节点故障后的自动发现和切换，它没有消除异步复制的数据窗口，也没有替应用处理缓存击穿和数据库保护。真正的高可用是 Redis、客户端、业务降级、监控和备份共同形成的恢复能力。

架构是否可靠，不看正常情况下有几个节点，而看故障发生以后：能不能自动恢复、恢复用了多久、数据损失是否在承诺范围内，以及应用有没有把压力转移成下一场数据库故障。

RabbitMQ可靠性设计

发表于 2022-06-19 分类于 架构成长

写在前面：消息队列最麻烦的故障不是完全不可用，而是“看起来发成功了，业务却没有完成”。生产者、交换机、队列、消费者和业务数据库之间任何一步都可能失败，可靠性必须按链路逐段设计。

一次典型的消息故障

订单接口返回成功以后，积分服务没有增加积分。补发消息后积分又加了两次。把日志按 orderId 串起来，看到的是：

这里同时出现了两个问题：生产端没有证据证明消息进入 Broker；消费端业务已经成功，但 ack 没有到达 Broker，消息被再次投递。RabbitMQ 默认提供的是“至少一次”方向的能力，重复消息不是异常情况，消费者必须能够承受。

1. 先画出完整失败链路

每个箭头都要回答两个问题：

  1. 失败以后谁能发现。
  2. 发现以后如何重试，并且不会产生重复副作用。

只配置手动 ack，不能解决生产者消息丢失；只开启 Confirm，也不能保证消费者业务执行成功。

2. Producer Confirm 证明 Broker 收到了消息

Spring Boot 配置：

Confirm 表示消息是否到达 Exchange，Return 表示消息到达 Exchange 后是否因为路由失败而被退回。两者解决的不是同一个问题。

不同 Spring AMQP 版本的 Return Callback API 名称有差异，旧版本常见 setReturnCallback。升级时应根据实际依赖调整，而不是同时注册两套。

Confirm 成功只代表 Broker 接受了消息，不代表消息已经持久化到磁盘，更不代表消费者处理成功。关键消息要保存 messageId、业务主键、发送状态和重试次数，不能只写一行普通日志。

数据库事务提交后，进程可能在消息发送前崩溃；也可能消息已经发出，数据库事务却回滚。普通本地事务无法同时覆盖 MySQL 和 RabbitMQ。

一种相对容易落地的方式是本地消息表，也叫 Transactional Outbox：

订单和待发送消息在同一个数据库事务里保存：

独立任务扫描 INIT 和可重试记录，发送到 RabbitMQ；Confirm 成功后更新为 SENT。如果任务进程崩溃，下一轮仍会继续发送，因此消费者必须幂等。

扫描任务还要考虑并发抢占、批次大小和失败退避，不能每秒全表扫描。数据量大时可以进一步使用 CDC 读取 Outbox 变更，但复杂度也会增加。

4. Exchange、Queue 和消息都要持久化

交换机和队列设置 durable，只保证定义在 Broker 重启后仍存在。消息本身也需要持久化。Spring AMQP 常规转换器默认会发送持久化消息，但自定义 MessageProperties 时要确认 delivery mode。

即使消息持久化，Broker 异常时仍可能存在数据损失窗口。对高可靠要求场景，需要结合镜像队列或 Quorum Queue、磁盘和集群策略评估，不能把“durable=true”理解成绝对不丢。

5. 消费者使用手动 Ack

消费代码：

原来的 basicNack(tag, false, true) 会把异常消息立即放回队列。如果错误一直存在，消费者会高速重复读取同一条消息，CPU、日志和下游压力都会升高。更稳妥的方式是有限次数重试、逐步退避，超过次数后进入死信队列。

6. 幂等是消费端的核心

积分增加属于有副作用操作。同一个 messageId 再来一次，不能再次增加积分。

消费记录和业务更新放在同一个本地事务：

不能先在 Redis 判断“是否消费过”，再更新 MySQL。判断和业务写入不在同一个事务里，中间失败仍会产生不一致。Redis 可以做快速过滤，但数据库唯一约束才是最后防线。

业务本身有天然唯一键时，也可以使用业务表约束，例如一个订单只能生成一条积分流水。幂等键要和业务动作绑定，而不是简单使用时间戳。

7. 重试要区分错误类型

建议的重试节奏可以是 10 秒、1 分钟、5 分钟，而不是立即连续三次。具体间隔要结合业务时效。死信消息至少保存：messageId、原交换机、原路由键、异常、失败次数和首次失败时间。

恢复死信时不能直接把整个队列一次性重投。先修复根因，抽样验证，再限速回放，同时继续检查幂等记录和下游容量。

8. 顺序消息不要只依赖队列顺序

单队列、单消费者可以保持较强的消费顺序，但吞吐和可用性会受限制。多消费者、重试、死信回放都会打乱业务事件顺序。

对同一个订单的状态事件，可以：

  • 使用订单 ID 做分片键，让同一订单进入同一分片队列。
  • 在消费者校验业务版本号，只接受期望的状态迁移。
  • 对乱序事件暂存或丢弃，并记录告警。

最终仍要靠业务状态机保护，不能只相信消息到达顺序。

9. 监控哪些指标

只监控 RabbitMQ 进程存活不够。Ready 持续增长说明消费者跟不上，Unacked 很高可能是处理慢、prefetch 过大或消费者卡住。

10. 一次可靠性演练

上线前可以按顺序做小范围演练：

  1. 使用错误 Routing Key，验证 Return 和发送记录。
  2. 暂停消费者，验证队列持久化和积压告警。
  3. 消费业务成功后，在 ack 前主动抛错，验证幂等。
  4. 制造永久异常，确认不会无限 requeue。
  5. 修复后限速回放死信，核对业务结果。

演练只能在隔离环境或得到授权的窗口执行，不能为了验证可靠性直接终止生产 Broker。

复盘结论

消息可靠性不是“绝不重复、绝不丢失”的一句承诺，而是一条可验证的证据链：生产端有 Outbox 和 Confirm，Broker 有持久化与监控，消费端有事务、幂等、有限重试和死信，业务侧还有对账。

系统允许重复投递，但不能允许重复产生业务结果；系统允许短暂延迟，但不能让失败消息永远不可见。做到这两点，消息队列才真正承担了异步解耦，而不是把故障藏到了另一个进程里。

7. 五类高频问题

7.1 Nacos 看不到服务

按下面顺序检查：

不要只看最后一行启动日志，向上搜索 Nacos 客户端连接异常。

7.2 网关返回 503

lb://order-service 找不到健康实例时，通常返回 503。先看 Nacos 实例，再确认网关与订单服务是否使用同一个 namespace。注册了容器内部 IP 时，还要从网关容器内实际测试连通性。

7.3 网关返回 404

记录四个值：请求原路径、Path 谓词、过滤后路径、Controller 映射。临时打开 Gateway 路由日志可以辅助判断，但调试日志量较大，用完应恢复。

7.4 Feign 报 404 或参数缺失

对比 Feign 声明和服务端 Controller：HTTP 方法、路径、参数位置、参数名、Content-Type 必须一致。接口改动后只更新服务端，没有同步客户端契约，也会造成运行时错误。

7.5 Feign 超时

先直接请求库存接口，再通过订单服务请求。如果直连也慢，问题在库存服务；直连正常而 Feign 慢，再检查服务发现地址、连接池、DNS、负载均衡和超时配置。

写操作不要默认重试。调用方超时不代表服务端没有成功，重试可能重复扣库存，必须先设计业务幂等键。

3. 注册中心解决“服务在哪里”

单体应用可以把下游地址写在配置里：

实例扩容、迁移或重启以后，固定地址会变得难以维护。注册发现把实例列表交给注册中心：

服务名是治理体系里的稳定标识。order-service 注册后，调用方通过服务名获取实例列表，再由客户端负载均衡选择一个实例。

排查注册问题时依次确认：

  1. 应用是否真正启动成功。
  2. spring.application.name 是否符合约定。
  3. Nacos 地址、namespace、group 和认证是否一致。
  4. 控制台是否能看到实例，实例 IP 和端口是否可达。
  5. 服务是否被标记为不健康。

控制台“有实例”只代表注册成功，不代表调用方一定能连通。注册进去一个容器内部 IP，也会出现发现成功、调用超时。

4. 配置中心解决“配置怎么管理”

注册中心和配置中心可能由同一个 Nacos 提供，但它们是两条不同链路。注册正常不代表配置一定加载成功。

配置中心适合管理：

不适合把所有配置都动态刷新。数据库连接、线程池大小等参数修改后是否能安全生效，取决于组件实现。核心参数变更仍然需要评审、灰度和回滚记录。

Spring Boot 2.4 以后配置加载机制发生过变化，部分版本使用 spring.config.import，旧项目常通过 bootstrap.yml 加载。实际项目要先确认 Spring Boot、Spring Cloud 和 Alibaba 版本，再决定配置写法，不能把两套机制混在一起。

排查配置时记录三件事：

  • 最终加载的是哪个 Data ID、group 和 namespace。
  • 本地配置、环境变量和远程配置谁的优先级更高。
  • 配置变更以后 Bean 是否真的支持刷新。

5. OpenFeign 解决“服务怎么调用”

OpenFeign 把 HTTP 契约声明成 Java 接口：

它减少了重复的 HTTP 客户端代码，但远程调用的本质没有改变：仍然可能连接失败、超时、返回非预期状态码，也可能被重复调用。

接口设计要明确：

  1. URL、HTTP 方法和参数序列化方式。
  2. 连接超时和读取超时。
  3. 错误码如何映射，不能把所有失败都转成 null。
  4. 是否允许重试，写操作是否幂等。
  5. 调用日志是否包含 traceId、目标服务和耗时。

7. 稳定性组件不是错误吞掉器

熔断、限流和降级解决的是故障扩散问题，不是让异常消失。

8. 我的学习顺序

相比一次启动十个组件，下面的顺序更容易建立确定性：

  1. 两个普通 Spring Boot 服务分别启动，先用固定 URL 调通。
  2. 接入注册中心，验证服务名调用和实例切换。
  3. 使用 OpenFeign，补齐超时、错误码和调用日志。
  4. 增加 Gateway，逐条验证路由和过滤器。
  5. 接入配置中心，验证配置来源和刷新边界。
  6. 人工制造超时和实例下线，观察客户端行为。
  7. 最后接入指标、日志和链路追踪。

每一步都保留一个最小测试：健康检查、查询接口、写接口和超时接口。组件增加以后，先重复旧测试，再验证新能力。

10. 这份笔记最后留下什么

Spring Cloud 的价值不是提供一套固定架构，而是把微服务常见问题抽象成可替换的能力。理解“注册发现、配置、调用、入口、稳定性、可观测性”这些层次以后，即使以后替换 Nacos、Feign 或 Gateway，排查思路仍然有效。

学习组件时，我更关心三个问题：它解决什么故障，它自己会引入什么故障，以及没有它时有没有更简单的办法。能回答这三个问题，才算真正把组件放进了架构里。

微服务架构初体验

发表于 2022-01-16 分类于 架构成长

写在前面：第一次接触微服务时，我也把重点放在“怎么拆”上。真正做过一轮以后才发现，拆出几个 Spring Boot 项目并不难，难的是决定边界、管理失败，以及接受一次本地调用变成网络调用之后带来的全部成本。

2022 年开始认真研究微服务，起点并不是单体应用已经完全不能运行，而是它的协作成本逐渐变高。订单、用户、库存和支付都在同一个工程里，改一个公共对象可能影响四个模块；一次发布要把所有功能一起上线；某个报表任务把内存打满，也会拖垮订单接口。

这篇更像一次架构决策记录：为什么考虑拆分、边界怎么判断，以及第一轮实践中哪些想法后来被证明太理想化。

1. 单体到底遇到了什么问题

当时的工程结构其实很清楚：

代码目录清楚，不代表业务边界清楚。几个比较明显的信号是：

  1. order 可以直接修改库存表，stock 也会反过来查询订单状态。
  2. 用户、订单和营销共用一套“万能 DTO”，新增字段以后所有模块一起回归。
  3. 一个模块的慢 SQL 会耗尽公共数据库连接池。
  4. 不相关的功能被迫一起构建、一起发布、一起回滚。
  5. 团队开始频繁解决代码冲突，而不是业务问题。

这些问题不一定要求立即微服务化。很多时候先做模块化、清理依赖方向、拆分数据库账号，就能继续支撑很长时间。真正推动拆分的，是某些业务能力已经有独立迭代和独立扩缩容的需要。

2. 不能按照 Controller 数量拆服务

第一版拆分很容易写成下面这样：

这只是把技术分层变成网络分层。一次请求仍然要在多个服务之间来回跳，common-service 很快又会变成新的大单体。

后来我主要从四个维度判断边界：

维度 要问的问题
数据归属 谁创建、修改并解释这份数据
业务闭环 能否在服务内部完成主要状态流转
变化节奏 是否需要独立发布和扩容
故障影响 服务失败时能否被隔离或降级

以库存为例，库存数量、冻结量和扣减记录应该由库存服务解释。订单服务可以请求扣减库存，但不能绕过接口直接更新库存表。支付服务外部依赖多、回调状态复杂，也适合拥有独立边界。

“一个服务一个数据库”表达的是数据所有权，不一定要求物理上马上购买四套数据库。早期可以在同一个数据库实例创建独立 schema 和账号，但必须禁止跨服务直接写表，否则服务只是代码仓库分开，耦合仍然留在数据库里。

3. 先定义契约，再搬代码

本地方法可以传任意对象，远程接口必须考虑兼容性。库存扣减接口至少要有业务请求号、SKU、数量和调用方：

返回值也不能只用 boolean，否则调用方无法区分库存不足、重复请求和服务异常：

接口契约需要明确：

  • 哪些字段必填，长度和取值范围是什么。
  • 重复提交同一个 requestId 会发生什么。
  • 业务失败和系统失败分别使用什么错误码。
  • 接口超时以后，调用方如何查询最终结果。
  • 新增字段如何保证旧调用方还能正常反序列化。

如果这些问题没有答案，服务拆得越多，调用关系越难维护。

5. 同步调用不是默认答案

服务之间的通信方式要根据业务语义决定：

用户查询订单时同步读取订单服务是合理的；订单创建后发送通知，没有必要阻塞主流程。库存扣减是否同步，要看业务是否必须立即告诉用户结果。

同步链路越长，可用性越低。假设三个下游服务可用性都是 99.9%，串联后整条链路理论可用性已经低于单个服务。还要叠加网络延迟、连接池、超时和重试带来的影响。

因此每个远程调用都应该回答：

  1. 连接超时和读取超时是多少。
  2. 能不能重试，重试是否会造成重复写入。
  3. 下游失败时是降级、排队还是直接失败。
  4. 整条请求链的总超时预算是否合理。

6. 第一批服务怎么选

我不建议第一次就拆订单主链路。更稳妥的顺序是：

  1. 先整理单体内部的模块依赖，禁止反向调用。
  2. 选择只读、边界清晰的能力，例如用户信息查询。
  3. 通过防腐层封装远程调用，让业务代码不直接依赖 HTTP 细节。
  4. 补齐 traceId、接口耗时、错误码和调用日志。
  5. 做灰度路由，保留回到本地实现的开关。
  6. 运行一个完整业务周期后，再决定下一个边界。

这种方式看起来慢，但每一步都能回退。一次性拆完所有模块，出现问题时很难判断是边界错误、网络问题还是组件配置问题。

7. 微服务之前需要哪些基础能力

服务数量增加以后，下面这些能力会从“加分项”变成必需品：

如果发布一个服务仍然依赖人工登录服务器改配置，拆成十个服务只会制造十倍的操作机会。团队的工程能力要和服务数量一起增长。

8. 哪些情况暂时不适合拆

微服务不是规模小就不能用，也不是业务复杂就必须用。我会在下面这些情况下优先保留模块化单体：

  • 团队很小，所有模块由同一组人维护。
  • 业务边界还在频繁变化，服务拆分后会不断调整接口。
  • 没有自动化部署和基本监控。
  • 当前瓶颈是慢 SQL、代码质量或产品方向，而不是单体架构。
  • 数据强一致要求很高，拆分收益不足以覆盖一致性成本。

模块化单体同样可以有清晰边界、独立模块和严格依赖方向。它不是微服务的反面，而是很多系统更合适的阶段。

9. 这一阶段最大的认识

第一次实践以后，我对微服务的理解从“多个独立应用”变成了“围绕业务边界管理复杂度”。它确实能带来独立发布、故障隔离和按需扩容，但同时把网络、数据一致性、可观测性和运维成本带进了日常开发。

判断一次拆分是否成功，不应该看服务数量，而应该看几个结果：发布是否更独立，故障是否更容易隔离，团队是否减少相互等待，业务状态是否仍然可解释。如果这些指标没有改善，只是仓库和进程变多了，那就还没有真正获得微服务的收益。
