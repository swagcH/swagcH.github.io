Nacos,Gateway,OpenFeign实操

发表于 2022-03-27 分类于 架构成长

背景

为什么会研究这个问题

在 Spring Cloud 的基础概念跑通之后，我把重点放到 Nacos、Gateway 和 OpenFeign 三个组件上。原因很简单：它们覆盖了微服务最基础的一条链路——服务注册、统一入口和服务间调用。只要这三块稳定，至少能搭出一个可运行的微服务骨架。

问题

遇到了什么情况

实操中遇到的问题主要集中在配置和路径上。服务已经启动，但 Nacos 控制台看不到实例；Gateway 能访问，但路由匹配不到目标服务；OpenFeign 调用时出现 404 或超时。很多问题不是代码逻辑错，而是服务名、路径前缀、配置层级和依赖版本不一致导致的。

分析

排查过程

如果 StripPrefix 配错，请求到后端服务的路径就会变化。排查时要同时看 Gateway 日志和后端 Controller 的映射。

解决方案

具体操作

通过清单逐项排查，比直接看异常堆栈更稳定。

总结

经验沉淀

Nacos、Gateway、OpenFeign 组合起来并不复杂，复杂的是路径、服务名和配置之间的细节一致性。我的经验是：每新增一个服务，先验证注册，再验证网关，再验证 Feign，不要一次性把所有配置都写完再排查。

Spring Cloud学习笔记

发表于 2022-02-20 分类于 架构成长

背景

为什么会研究这个问题

在理解了微服务的基本拆分思路之后，我开始系统学习 Spring Cloud。相比单个 Spring Boot 应用，Spring Cloud 更像是一组微服务治理工具箱，覆盖注册发现、配置管理、网关路由、服务调用、熔断限流等能力。研究它的原因也很明确：当服务数量超过两三个之后，手写服务地址、手动维护配置、靠人肉检查调用链会变得非常不可靠。

问题

遇到了什么情况

刚开始学习时，最大的问题是概念很多但边界不清。注册中心、配置中心、网关、Feign、负载均衡这些组件看起来都能跑 Demo，但真正放到项目里，会发现不知道每个组件负责什么。比如服务调用失败到底是注册中心没发现服务，还是网关路由错了，还是 Feign 超时时间太短。组件之间的关系如果没有先画清楚，排查问题时会非常被动。

分析

排查过程

排查时我会先确认服务是否注册，再确认配置是否加载，最后确认调用链是否正常。顺序不能乱，否则容易被表面异常误导。

解决方案

具体操作

我把每个组件都拆成最小可运行样例，再逐步组合。这样做虽然慢一点，但能清楚知道问题出现在哪一层。

总结

经验沉淀

Spring Cloud 的学习重点不是背组件名，而是理解服务治理的分层。注册中心解决服务在哪里，配置中心解决配置怎么统一，网关解决入口怎么收口，Feign 解决服务之间怎么调用。只有把这些问题放回真实架构场景里，组件才有意义。

微服务架构初体验

发表于 2022-01-16 分类于 架构成长

背景

为什么会研究这个问题

2022 年开始接触微服务时，我最直接的感受是：它不是把一个系统拆成多个服务那么简单。过去做单体应用，所有模块在一个进程里，调用方式直接、事务边界清楚、部署也简单。但当业务模块逐渐增多，订单、用户、库存、支付之间的代码耦合越来越明显，每次改一个功能都要回归一大片逻辑，发布窗口也越来越长。正是在这种背景下，我开始研究微服务架构。最初的目标并不是追求架构先进，而是想弄清楚系统拆分之后，团队协作、独立部署、故障隔离到底能解决哪些真实问题。

问题

遇到了什么情况

第一次拆服务时遇到的情况比较典型：模块拆出去了，但调用关系反而更复杂；原来一次本地方法调用，现在变成了网络请求；原来一个数据库事务能覆盖的流程，现在要考虑分布式事务或最终一致性。尤其是订单创建这个流程，涉及用户校验、库存扣减、优惠计算和支付记录，拆开之后每一步都可能失败。如果只按代码包结构拆服务，很容易变成“物理拆分、逻辑仍然耦合”。

分析

排查过程

排查拆分边界时，我主要看三个维度：数据归属、业务闭环、变更频率。用户资料和订单生命周期明显不是同一类数据；库存服务变更频率不高，但对一致性要求高；支付服务外部依赖多，需要单独隔离。由此可以判断，服务拆分应该围绕业务能力，而不是围绕代码目录。

解决方案

具体操作

实际落地时，我没有一次性把所有模块拆开，而是先从边界相对清晰的库存查询、用户信息查询开始。这样即使出现问题，也不会直接影响订单主流程。等到接口、日志、异常处理逐渐稳定后，再考虑更核心的链路。

总结

经验沉淀

微服务带来的不是天然简单，而是把原来隐藏在进程内部的问题显性化。网络延迟、接口契约、数据一致性、服务监控都会成为必须面对的工程问题。我的经验是：如果团队还没有稳定的部署流程、日志规范和接口文档，过早拆微服务只会放大混乱。微服务不是目标，降低复杂度、提升交付效率和故障隔离能力才是目标。
