日志设计实践

发表于 2020-08-23 分类于 工程实践

背景

好的日志不是越多越好，而是在出问题时能准确回答“发生了什么、影响了谁、下一步查哪里”。

如果说 2019 年的重点是把项目做出来，那么 2020 年更像是开始理解“项目为什么要这样做”。很多问题表面上是技术问题，往深处看其实是规范、协作、边界和长期维护的问题。

这一年我逐渐意识到，成熟的开发不是写出更复杂的代码，而是在合适的约束下，把问题拆清楚，把风险讲明白，把结果稳定交付出去。

问题

这类问题在工作中并不少见，当时我主要遇到下面几个情况：

  1. 出问题时日志里只有“失败了”，没有上下文
  2. 日志级别混乱，INFO 和 ERROR 随意使用
  3. 敏感信息被直接打印到日志

这些问题的共同点是：短期看只是效率问题，长期看会逐渐变成质量问题。它们不会立刻让系统崩掉，但会在需求迭代、人员交接、线上排查时持续放大成本。

分析

日志设计要面向排查场景，能串起请求、用户、业务对象、异常堆栈和关键状态变化。

我后来总结出一个判断标准：凡是需要多人长期参与的事情，都不能只依赖个人经验。经验如果不能被记录、复用和检查，就很难成为团队能力。

解决方案

我的处理方式不是追求一步到位，而是先把最容易失控的部分标准化，再逐步优化细节。

具体落地时，我更倾向于采用“小步治理”的方式：先让流程可见，再让责任明确，最后再谈自动化或平台化。这样推进阻力会小很多，也更容易让团队接受。

总结

关于 日志设计实践，我这一阶段最大的收获是：成熟的工程经验往往不是某个技巧，而是一套稳定处理问题的方式。

这篇文章可以沉淀为几条原则：

  • 先明确问题边界，再讨论技术方案；
  • 能形成清单的事情，不要只靠记忆；
  • 能通过规范减少沟通的地方，就不要反复口头确认；
  • 重要结论要留痕，方便后续追溯；
  • 技术方案要服务于交付质量，而不是只追求形式上的先进。

2020 年以后，我对“经验”的理解发生了变化：经验不是踩过坑之后说一句“下次注意”，而是把坑转化为规范、流程、工具或文档，让后面的人少踩一次。

背景

从“能把项目跑起来”到“能独立改需求”，中间隔着对业务、代码结构和协作方式的系统理解。

如果说 2019 年的重点是把项目做出来，那么 2020 年更像是开始理解“项目为什么要这样做”。很多问题表面上是技术问题，往深处看其实是规范、协作、边界和长期维护的问题。

这一年我逐渐意识到，成熟的开发不是写出更复杂的代码，而是在合适的约束下，把问题拆清楚，把风险讲明白，把结果稳定交付出去。

问题

这类问题在工作中并不少见，当时我主要遇到下面几个情况：

  1. 只关注代码入口，忽略业务流程和数据流
  2. 本地环境搭建耗时过长，影响进入真实需求
  3. 遇到问题只问结论，没有沉淀排查路径

这些问题的共同点是：短期看只是效率问题，长期看会逐渐变成质量问题。它们不会立刻让系统崩掉，但会在需求迭代、人员交接、线上排查时持续放大成本。

分析

熟悉项目的关键不是把每一行代码都看懂，而是先建立业务地图、系统边界、核心链路和本地调试能力。

我后来总结出一个判断标准：凡是需要多人长期参与的事情，都不能只依赖个人经验。经验如果不能被记录、复用和检查，就很难成为团队能力。

解决方案

我的处理方式不是追求一步到位，而是先把最容易失控的部分标准化，再逐步优化细节。

具体落地时，我更倾向于采用“小步治理”的方式：先让流程可见，再让责任明确，最后再谈自动化或平台化。这样推进阻力会小很多，也更容易让团队接受。

总结

关于 新人如何快速熟悉项目，我这一阶段最大的收获是：成熟的工程经验往往不是某个技巧，而是一套稳定处理问题的方式。

这篇文章可以沉淀为几条原则：

  • 先明确问题边界，再讨论技术方案；
  • 能形成清单的事情，不要只靠记忆；
  • 能通过规范减少沟通的地方，就不要反复口头确认；
  • 重要结论要留痕，方便后续追溯；
  • 技术方案要服务于交付质量，而不是只追求形式上的先进。

2020 年以后，我对“经验”的理解发生了变化：经验不是踩过坑之后说一句“下次注意”，而是把坑转化为规范、流程、工具或文档，让后面的人少踩一次。

第一个完整项目复盘

发表于 2019-12-29 分类于 随笔

背景

2019 年的最后，我把第一个完整项目从需求、开发、部署到复盘重新梳理了一遍。

2019 年对我来说和 2018 年明显不一样。2018 年更多是在补 Java 基础，到了 2019 年，我开始把零散知识往项目里放。很多以前看起来懂了的概念，只要一放进真实项目流程里，马上就会暴露问题。

这篇文章记录的是我在 2019-12 前后学习和实践 第一个完整项目复盘 时的理解。内容不会写得像官方文档，更像是一份踩坑记录：当时为什么学、遇到了哪些问题、怎么排查，最后沉淀出哪些可以复用的经验。

问题

刚开始实践时，我主要卡在下面几个点：

  1. 需求边写边改导致返工
  2. 代码分层不清晰
  3. 部署和文档总是拖到最后

这些问题单独看都不算复杂，但放在项目里就很容易连锁反应。比如配置错了，表面上看到的是页面打不开，实际原因可能是路径、依赖、运行环境或者请求流程中的某个环节出了问题。

分析

项目复盘的价值是把“能跑”背后的过程问题暴露出来，包括需求、设计、开发、测试和部署。

只要能说清楚它在这条链路里的位置，就不会完全靠记忆去使用。

解决方案

我的处理方式是先把最小可运行例子跑通，再逐步放到项目中验证。下面是当时整理下来的关键操作和代码片段。

实践过程中我还给自己定了一个小规则：每次遇到问题，不只记录最终命令，还要记录“为什么这么做”。否则下次换一个环境，很容易又从头查一遍。

总结

这次学习给我的最大感受是：项目实践里的知识点，真正难的不是单个语法，而是上下文。

对 第一个完整项目复盘 的理解，我最后沉淀成几条经验：

  • 先理解它解决什么问题，再记具体用法；
  • 先跑通最小 Demo，再接入完整项目；
  • 配置类问题要从路径、依赖、版本、环境四个方向排查；
  • 代码示例要自己敲一遍，复制能跑不代表真的理解；
  • 每次踩坑最好留下记录，后面会节省大量时间。

2019 年的学习明显比 2018 年更贴近真实开发。很多概念，比如 Servlet、Spring、MyBatis、接口设计、权限管理，都是在一次次“跑不起来”和“终于跑通了”的过程中慢慢理解的。
