Linux磁盘爆满处理

发表于 2021-06-20 更新于 2026-08-26 分类于 故障排查

这是一段磁盘告警值班记录。表面现象是根分区 100%，但真正占用空间的文件已经被删除，因此 du 怎么找都对不上 df。

磁盘爆满时最危险的动作，是为了尽快腾空间直接删除不了解用途的大文件。值班处理应先确认挂载点和增长来源，再由对应负责人选择释放方式。

01:17，告警与业务现象

订单服务仍能处理部分查询，但日志无法写入，临时文件创建失败。我们先暂停该节点的新发布和批处理任务，并确认其他实例有足够容量承接流量。

01:24，df 与 du 的差值

df 从文件系统块使用情况统计，只要块还被占用就会计入；du 从目录树遍历可见文件。一个文件被删除后，如果进程仍持有文件描述符：

检查已删除但仍被占用的文件：

Java 进程仍持有约 20G 的已删除日志。原因已经足以解释 df 和 du 的差值。

01:27，为什么文件删了还在增长

当天有人手工删除了正在写入的 app.log，以为可以立即释放空间。Linux 删除的是文件名与 inode 的关联，进程已经打开的描述符仍指向原 inode。日志框架不知道路径消失，继续往同一个文件写。

这也是为什么不建议把 rm 当日志轮转。删除命令成功，不代表空间已经释放。

01:30，受控释放文件描述符

可选方式按优先级评估：

  1. 让日志框架主动滚动并重新打开文件。
  2. 平滑重载支持重开日志的进程。
  3. 摘流后重启单个应用实例。
  4. 极端情况下由负责人评估是否截断对应描述符。

进程退出后再次检查：

根分区使用率从 100% 降到 48%，应用健康检查和写入恢复。

如果 du 找到的就是真实大文件

不能因为“日志通常可删”就直接处理。先把候选文件按用途分类：

数据库数据、binlog、Docker 存储目录都不应通过手工删除底层文件释放空间。错误删除可能让服务无法恢复。

应急时优先处理已经确认可再生、已归档、不会影响运行的文件，并记录删除范围。所有破坏性操作都需要责任人和复核人。

把日志滚动交给应用

本次根因是日志没有稳定滚动，手工处理又删除了当前活跃文件。Spring Boot 使用 Logback 时，可以按日期和大小滚动：

数值要根据流量、磁盘容量、采集延迟和合规保留要求确定。配置 totalSizeCap 前，先确认当前 Logback 版本支持且 maxHistory 已设置。

如果统一使用 logrotate，应用必须配合重开文件；copytruncate 虽然不要求进程重开，但复制和截断之间可能丢少量日志，高吞吐场景要评估。不要让应用滚动和系统滚动同时管理同一个文件。

告警不能等到 100%

磁盘容量以增长速度而不是单一百分比判断更有意义：

同时监控：

  • inode 使用率。
  • 每小时增长量和预计耗尽时间。
  • 日志写入速率。
  • 已删除文件占用。
  • 容器层和宿主机各自容量。

阈值需要按文件系统用途设置。一个 2TB 数据盘的 90% 剩余空间，与 20G 根分区的 90% 完全不同。

值班记录最后写下什么

这次经历让我记住：磁盘满时，df 回答文件系统还剩多少，du 回答目录树里什么可见，两者对不上本身就是重要证据。先解释差值，再释放空间，比从最大的目录开始盲删可靠得多。

Nginx 出现 502 或 404 时，我以前习惯先打开配置文件改 proxy_pass。后来发现，状态码相同并不代表原因相同：502 可能是上游端口没监听、连接被拒绝或响应头非法；404 既可能由 Nginx 返回，也可能是后端正常返回。

如果 Nginx 没有 access log，请先查 DNS、负载均衡、TLS 或请求是否到了另一台机器，不要急着改后端。

502 分支一：Connection refused

典型错误：

它表示 Nginx 已经找到目标 IP，但对应端口没有接受连接。按顺序检查：

常见原因：

  • 后端进程没有启动或启动后退出。
  • 服务实际监听 8081，Nginx 配成 8080。
  • 服务只监听特定网卡。

验证至少包含：

最短决策表

现象 先看 典型方向
无 access log DNS、LB、TLS 请求未到当前 Nginx
502 + refused 监听端口、进程 上游未启动或端口错误
502 + connect timeout 路由、网络策略 Nginx 到上游不可达

404 + upstream=- location、静态规则 Nginx 返回

Nginx 排查最有效的方式不是记住更多配置项，而是始终回答两个问题：请求目前到哪一层，最后一次成功动作是什么。access log、error log、直连上游和生效配置一旦能够互相印证，502 与 404 就不再是只能靠试改配置解决的黑盒。

Redis缓存雪崩实践

发表于 2021-04-18 更新于 2026-08-26 分类于 故障排查

缓存雪崩不是某一个 key 没命中，而是大量缓存同时失效，或者 Redis 整体不可用，流量在短时间内全部落到数据库。数据库一旦变慢，应用线程和连接池继续堆积，故障会从缓存层扩散到整个调用链。

为了验证系统能否扛过这种变化，我们做了一次隔离环境演练。所有流量和故障注入都只在压测集群执行，禁止用生产 Redis 做“断开看看”之类试验。

演练目标

演练前先确认停止条件：数据库 CPU 超过 75%、连接池等待超过 20 或错误率超过 5% 时立即停止注入。压测环境也需要保护，避免影响共享测试服务。

场景 A：统一 TTL 在整点集中到期

旧的缓存预热任务每天 09:30 批量写入商品，所有 key 都使用 30 分钟 TTL：

结果几乎可以按秒观察：

时间 缓存命中率 DB QPS DB 连接等待 接口错误率
09:59:55 96% 120 0 0
10:00:01 41% 1,720 18 1.2%
10:00:04 8% 2,640 54 17%
10:00:08 13% 1,980 61 24%

数据库安全容量只有 800 QPS，却瞬间承接两千多查询。查询变慢后连接释放更慢，进一步放大等待。

第一层改造：让过期时间分散

基础 TTL 上增加随机抖动：

随机范围要结合基础 TTL 和业务新鲜度。30 秒缓存增加 10 分钟抖动显然不合理；30 分钟缓存增加 0 到 10 分钟通常更平滑。

第二轮演练中，过期分散到十分钟，数据库 QPS 峰值降到 480，没有超过安全容量。

随机 TTL 能解决“同时到期”，不能解决缓存节点整体不可用。

第二层改造：热点 key 只允许一个请求回源

即使过期时间分散，单个热点商品到期时也可能有数百个并发请求。读取逻辑增加短锁：

锁必须有较短过期时间，释放时校验持有者标识，避免误删其他线程后来获得的锁。不要让所有请求长时间阻塞等待同一把锁。

对于允许短暂旧数据的商品详情，我们采用逻辑过期：

逻辑过期后，第一个请求异步刷新，其他请求在短窗口继续读取旧值。价格、库存等强一致字段不能直接套用这个策略，应按业务容忍度拆分。

第三层改造：限制回源总量

如果 10 万个不同 key 同时失效，每个 key 一把锁仍可能产生 10 万次数据库查询。应用还需要全局回源预算：

超过预算时：

  • 核心商品读取短期旧值。
  • 非核心推荐模块返回空集合或默认结果。
  • 后台报表暂停刷新。
  • 用户请求收到明确的繁忙响应，而不是无限等待。

降级结果要在产品层面提前确认。返回旧价格可能造成资损，就不能为了可用性随意降级。

场景 B：Redis 整体不可用 60 秒

我们在压测集群通过网络故障注入让应用无法连接 Redis。初始版本每次缓存失败后都会立即查库，并重试 Redis 三次：

不仅数据库流量上涨，每个请求还先浪费约 600ms。错误日志以每秒数千条增长，磁盘 IO 也受到影响。

改造后的策略是：

  1. Redis 连续失败达到阈值后快速熔断。
  2. 熔断期间不为每个请求重复等待连接超时。
  3. 只有核心查询在回源预算内访问数据库。
  4. 本地只保留极少量、短时间、可接受旧值的热点数据。
  5. 半开状态使用少量请求探测 Redis 恢复。

Redis 恢复后不能立即让全部实例同时重建缓存。每个实例使用随机延迟进入半开，并由预热任务按优先级恢复热点。

高可用不能代替应用保护

Redis Sentinel 或 Cluster 能降低单节点故障时间，但故障转移仍有检测、选主、连接重建和数据同步窗口。客户端配置不正确时，高可用集群也可能表现为整体不可用。

需要演练：

缓存高可用解决“尽快恢复缓存”，应用限流和降级解决“恢复前数据库不要被冲垮”，两者缺一不可。

预热应该按业务热度执行

全量数据同时预热既慢，又容易再次制造统一 TTL。我们按访问热度分层：

预热任务本身要有限速、断点和幂等能力。执行结果包括成功数、失败数、耗时和缓存版本，不能只打印“预热完成”。

第二次演练结果

场景 初始版本 改造后
集中过期 DB QPS 峰值 2,640 480
Redis 故障 DB QPS 峰值 2,780 690
Redis 故障接口错误率 31% 3.4%

改造后没有追求所有请求成功。非核心推荐被降级，一部分请求快速失败，但数据库和订单核心链路保持在安全水位。可控失败比整个系统排队到崩溃更有价值。

演练后保留的检查项

缓存雪崩治理不是简单给 TTL 加一个随机数。真正要保护的是整条链路：过期时间分散，热点重建合并，数据库回源有上限，缓存故障时快速降级，恢复时也避免第二次流量冲击。

Redis缓存穿透解决方案

发表于 2021-03-14 更新于 2026-08-26 分类于 故障排查

缓存穿透指查询一个本来就不存在的数据：Redis 每次未命中，请求继续访问数据库，数据库也返回空。只要请求使用不同的无效 ID，普通缓存几乎没有保护作用。

第三轮：短时间缓存“确实不存在”

数据库返回空时写一个特殊标记：

空值缓存适合重复查询同一批无效 ID，例如错误链接或客户端重试。本次压测把无效 ID 集合限制在 1 万个，第二遍请求后数据库 QPS 降到 180 左右。

但如果攻击者每次生成全新 ID，空值缓存仍会不断创建新 key。还要防止 Redis 被大量无效键占满：

  • 空值 TTL 明显短于正常数据。
  • key 使用固定格式，不直接拼接任意长参数。
  • 监控空值 key 创建速率。
  • 对调用方和来源做限流。

商品创建后应主动删除对应空值缓存，否则在 TTL 到期前会得到“商品不存在”。

第四轮：布隆过滤器挡住大范围不存在 ID

布隆过滤器能快速回答“这个 ID 一定不存在”或“可能存在”。它允许少量误判存在，但不会把真实存在的 ID 判断为不存在，前提是数据同步正确。

“多层防护”包含参数校验、调用方限流、Bloom 和空值缓存。数据库 QPS 接近正常基线，但仍保留少量误判和真实数据查询。

布隆过滤器的维护比接入更难

实现时必须回答：

普通布隆过滤器不支持可靠删除。商品下线后保留为“可能存在”只会多查一次数据库，可以接受；错误删除一个仍存在的商品则可能直接返回空，不能接受。

容量估小后误判率会持续上升。重建时可以生成新版本，完成数据校验后原子切换，不要在原过滤器上边清边写。

限流保护的是最后边界

即使 Bloom 正常，也要限制异常来源。限流维度可以包括：

  • 用户或应用凭证。
  • 租户。
  • 客户端 IP，作为辅助而非唯一身份。
  • 接口和资源类型。
  • 单次批量大小。

超限时返回明确错误码和重试时间，不要让客户端立即无限重试。对于登录前公开接口，还需要网关防护和行为识别。

限流阈值根据正常峰值与容量测试确定。过低会伤害真实用户，过高则无法保护数据库。

别把缓存击穿和雪崩混进来

空值缓存和 Bloom 主要解决穿透；互斥加载或逻辑过期更适合热点击穿；随机 TTL、预热、限流和高可用用于雪崩。先分类，再选择方案。

生产落地清单

缓存穿透没有一个单点“银弹”。真正可靠的是多层减压：明显错误尽早拒绝，重复空结果短期记住，大范围不存在 ID 用概率结构过滤，异常流量在入口限速，而数据库仍保留最后的事实判断。

三种超时不是一个概念

HTTP 客户端至少要区分：

超时 等待的事情 本次是否命中
连接池获取超时 等待一条可用连接 是
建立连接超时 TCP 与目标地址建连 否
读取超时 连接建立后等待响应数据 否

旧配置只设置了读取超时 8 秒，没有限制连接池等待。请求可以先排队 6 秒，再等待下游 8 秒，整体时间远超网关的 5 秒。

连接池配置改为：

没有把单路由上限直接设成 100。连接数会同时消耗本机文件描述符、下游接入能力和网络资源，需要结合峰值并发与下游容量确定。

工作第一年总结

发表于 2020-12-27 更新于 2026-08-26 分类于 随笔

写下这篇总结时，我工作的第一年快结束了。回头看年初的自己，最明显的特点是着急：着急听懂会议里的每个词，着急把需求做完，着急证明自己能独立解决问题。

一年后，我会的框架确实多了一些，但更重要的变化是开始接受一件事：工程能力不只是写代码的速度，它还包括理解问题、确认边界、留下证据，以及让别人能够接着自己的工作继续走。

刚开始，所有问题看起来都像代码问题

第一次接需求时，我拿到一句“增加订单筛选”，立即打开 Controller。写到一半才发现，筛选时间按创建时间还是支付时间没有确认，导出和页面是否共用条件也没有结论。

那次需求反复改了几轮。代码并不难，真正浪费时间的是我把模糊内容当成了确定输入。

后来每次开始前，我会先写几行：

这些问题没有让开发变慢，反而减少了返工。程序员不是接收一句话就输出代码的转换器，澄清本身就是工作的一部分。

第一次独立上线，让我认识“完成”的含义

在本地看到接口返回成功时，我曾经觉得任务已经完成。真正上线后才知道，一个改动还需要回答很多问题：

  • 测试环境和生产配置是否一致。
  • 数据库变更能否兼容旧版本。
  • 日志能不能定位一笔失败请求。
  • 监控是否能发现错误率上升。
  • 如果回退，新增数据怎么办。

第一次参与发布时，我大部分时间都在等别人确认。不是因为没有权限，而是我说不清变更影响和验证方式。

从那以后，我开始在提测和发布前准备清单。最初只是怕遗漏，后来才意识到，清单更大的价值是把脑中的隐性判断交给团队。别人不必相信“我都测过了”，可以直接看到测了什么、结果是什么。

一次线上故障，比十篇教程更具体

今年遇到过连接池耗尽的问题。告警响起时，我第一反应是最近发布的代码肯定有 Bug，随后又怀疑数据库。真正开始排查后，团队先看影响范围，再保存日志和线程现场，最后才定位到导出任务把远程调用放进长事务。

那次经历让我记住了几个顺序：

过去遇到错误，我习惯立刻搜索异常文本；现在我会先问系统发生了什么变化、影响哪些请求、哪一层指标出现异常。搜索能力仍然重要，但没有正确问题，搜到的答案很容易只是相似而不是适用。

Code Review 也改变了

年初 Review 别人的代码，我主要看格式、空指针和命名。别人 Review 我的代码时，我也常把评论理解成对个人能力的评价。

合作久了以后，我逐渐看到 Review 的真正价值：作者最熟悉实现，Reviewer 更容易发现被作者默认的前提。一次有效讨论应该围绕：

我也学会让评论更具体。与其写“这里不太好”，不如说明“外部调用放在事务中会延长连接占用，建议先提交本地状态，再通过任务重试通知”。

评论对代码，不对人；结论最好有风险和替代方案。这件事说起来普通，真正做到以后，协作成本低了很多。

从“问答案”到“带着排查结果提问”

刚入职时我害怕问得太多，有时又会在卡住后直接把错误截图发给同事。两种方式都不理想：前者浪费时间，后者把全部定位工作转给了对方。

现在我会先准备：

这样的提问通常更快得到答案，也方便对方指出我在哪一步理解错了。能够求助不是能力不足，关键是让求助成为协作，而不是任务转移。

今年真正掌握的是一组小习惯

如果只列技术名词，这一年可以写 Spring Boot、MySQL、Redis、Git、Linux。但让我日常工作发生变化的，是更细小的习惯：

  1. 修改前先复现，保存基线。
  2. 提交前完整阅读自己的 diff。
  3. 复杂逻辑先写一张状态表。
  4. 日志带业务编号和 traceId，不打印敏感信息。
  5. 大改动拆成可以验证的小提交。
  6. 故障恢复后补行动项，并确认负责人。
  7. 解决一次问题后留下文档或自动测试。

这些动作单独看都不难，坚持下来却能降低很多重复成本。

也有一些没有做好的地方

今年仍然有几个明显不足。

首先是业务理解还不够主动。有时只关注当前接口，没有继续追问这个字段最终影响报表、结算还是客户操作。

其次是对底层原理的学习容易断续。遇到问题时会集中看资料，问题过去后又缺少系统整理，知识之间没有形成连接。

还有一个问题是估时偏乐观。我常按“编码完成”估算，漏掉联调、数据准备、回归和发布观察。后来开始把任务拆成可见步骤，估时才逐渐接近真实。

这些不足不会靠一份年度计划自动消失，需要放进下一年的日常动作。

给第二年的三个目标

我不打算列一长串框架，先保留三个方向。

把一个领域理解深。 不只知道接口和表，还能说明核心流程、状态变化、异常补偿和业务指标。

把排查过程系统化。 继续练习从现象到系统、进程、线程和代码的证据链，减少依靠经验猜测。

做能被团队复用的产出。 可能是一套测试、一份 Runbook、一个脚本，也可能只是把一次故障写清楚。

第一年结束时，我没有一种“已经入门完成”的感觉，反而更清楚系统里有多少自己不知道的东西。但这并不让人沮丧。与年初相比，我至少知道遇到陌生问题时该从哪里开始，知道怎样把不确定性一点点变成事实。

成长可能就是这样：写代码依旧重要，但不再把代码当成全部答案。

技术债治理思考

发表于 2020-11-28 更新于 2026-08-26 分类于 经验沉淀

“这块代码太乱，应该重构”很容易获得技术上的认同，却很难获得真实排期。原因是这句话只表达了开发感受，没有说明它正在造成什么损失、何时会放大，以及投入以后怎样判断有效。

我逐渐把技术债当成一个投资组合来管理：有些债可以继续持有，有些要在下一次需求中顺手偿还，有些已经变成稳定性风险，必须立刻处理。治理的关键不是清零，而是让有限时间优先花在利息最高的地方。

技术债不等于所有不完美

以下情况经常被混在一起：

类型 示例 是否一定要处理
审美差异 命名风格不完全一致 否
工具欠账 格式检查未进入 CI 视重复成本而定
设计欠账 一个类承担订单、支付、通知 需求频繁时优先
质量欠账 核心规则没有自动测试 风险较高
架构欠账 同步链路无法承受增长 结合容量计划
安全欠账 密钥入库、越权路径 立即处理

一段代码不够优雅，但多年不改、运行稳定，也没有明显安全和维护成本，优先级可能很低。相反，一个只有几十行的重复支付逻辑如果每月引发故障，就是高利息债务。

先建立债务台账

台账不写“代码很乱”，而写可以验证的事实：

台账让讨论从“要不要重构”变成“是否愿意继续承担这些成本”。

用利息判断优先级

我会从五个维度粗略评分，每项 1 到 5 分：

安全和数据风险不应被低频掩盖。即使只发生一次，后果不可接受，也要提高优先级。

四种治理策略

立即偿还

适用于安全漏洞、数据一致性风险、频繁故障和已经阻塞交付的问题。处理时要冻结范围，避免以紧急治理为名重写整个系统。

随需求偿还

当下一次需求正好进入该模块，可以把必要重构放进同一方案。先建立测试，再调整结构，最后实现需求。这样上下文、测试和业务价值都在场。

隔离利息

暂时无法重构时，用边界减少扩散：

隔离不是偿还，但能阻止新需求继续复制问题。

接受并观察

对于低频、低风险、即将下线的模块，明确接受可能比重构更合理。记录接受期限和触发条件，避免它永久处于“以后再说”。

重构任务也要小步交付

一次可控治理通常按以下顺序：

结构调整与业务行为修改尽量分成不同提交。这样 Review 能看清，出现问题也更容易判断应该回退哪一步。

例如统一订单状态时，先把散落判断迁移到 OrderStateMachine，不同时新增售后状态；结构稳定并通过测试后，再单独做新需求。

没有测试的重构先买保险

核心链路缺少测试时，不应该因为“无法保证”而永远不动，也不应该直接大改。可以按风险补三类保护：

  1. 特征测试：锁定输入、输出和异常。
  2. 数据校验：对比新旧路径的计算结果。
  3. 运行观测：灰度期间记录差异但不影响用户。

如果新旧实现可以短期并行，可以让旧结果继续生效，只记录两者差异。确认样本稳定后再切换。对有副作用的写操作不能简单双跑，需要使用影子数据或只对纯计算部分对比。

治理也可能制造新债

这些信号说明项目正在失控：

  • 目标从解决具体问题变成“顺便统一所有模块”。
  • 新抽象只有一个实现，却引入五层接口。
  • 重构分支持续数月，无法合并主线。
  • 没有行为基线，只能靠人工判断是否一致。
  • 新框架引入后，团队缺少维护能力。
  • 旧代码未删除，新旧两套长期并存。

此时应该暂停扩张，重新收缩到可验证结果。治理不是技术展示，新增复杂度也要支付利息。

每季度做一次组合盘点

技术债永远不会归零，因为系统和业务都在变化。成熟的治理不是发起一次大扫除，而是持续知道债务在哪里、正在支付多少利息，以及下一笔工程投入为什么值得。

开发与测试协作经验

发表于 2020-11-15 更新于 2026-08-26 分类于 项目协作

有一次测试提了一个缺陷：“优惠券使用失败。”开发看完回复：“我这里正常，无法复现。”两句话都是真的，但没有推动问题前进一步。测试看到的是某组环境和数据下的失败，开发验证的是另一组条件下的成功。

后来回看，这不是谁描述得不认真，而是双方没有共享同一套上下文。开发与测试的协作，核心不是把缺陷在系统里来回指派，而是共同缩小“预期”和“实际”之间的差异。

边界表能让双方在提测前对齐重点，也减少低成本问题进入测试队列。

测试不是最后一站

协作应该从需求评审开始。测试在评审阶段提出“金额等于门槛怎么算”“支付失败后券是否释放”，通常比代码完成后发现便宜得多。

我习惯把工作拆成四个交接点：

测试也不必理解所有代码，但知道数据状态和系统边界后，能够设计出比页面点击更有效的场景。

发现缺陷后先做分诊

不是每个失败都立刻归为代码 Bug。先判断属于哪类：

类型 证据 下一步
需求歧义 验收标准没有定义边界 产品确认并更新需求
代码缺陷 行为与已确认规则不符 开发修复并补测试
环境问题 版本、配置或依赖异常 恢复环境并记录差异
数据问题 测试前置状态不成立 修复数据构造方式
自动化问题 用例假设过期或不稳定 更新脚本并定位波动

分诊不是推卸，而是找到真正应该改变的地方。把配置错误改成一段业务兼容代码，短期能过测试，长期会让问题更隐蔽。

优先级也要基于影响：

“我提的 Bug 必须最高”会让优先级失去意义。由产品影响、用户范围、恢复成本和上线时间共同决定。

修复不能只让原步骤通过

修复完成后至少做三层验证：

  1. 原失败步骤已经恢复。
  2. 相邻边界没有被破坏。
  3. 相同规则的其他入口保持一致。

优惠券可能在下单、购物车试算和运营后台预览中分别计算。如果只改下单接口，用户会在页面看到“可用”，提交时又失败，或者相反。

开发应补自动测试锁定规则；测试根据影响范围回归。两者不是重复工作：自动测试保护以后每次构建，探索性测试继续寻找未被想到的组合。

对环境争议建立统一答案

“我本地正常”通常说明环境缺少可比性。团队应让每次测试都能确认：

服务提供版本接口，部署系统展示变更历史，测试数据使用脚本创建。这样环境问题不再依赖逐个人询问。

一次缺陷的关闭标准

开发和测试并不是前后两个工位。一个更关注系统如何实现，一个更关注系统如何失败，这两种视角本来就应该互相补充。当双方用版本、数据、traceId 和边界条件说话时，讨论会从“在我这里是否正常”变成“在哪个条件下不符合共同确认的规则”。

@Transactional 覆盖了查询、数千次远程调用和文件生成。查询结束后，事务连接并没有立即归还；当多个导出并发执行时，连接池很快被占满。

20:22，先止血

恢复顺序是：

  1. 在网关临时关闭订单导出入口，只影响新增导出。
  2. 摘除两个异常实例，不再接收新请求。
  3. 等待和终止已确认无业务写入的导出任务。
  4. 逐个重启异常实例并完成健康检查。
  5. 每次只恢复一个实例的流量，观察连接池和错误率。

终止任务、摘流和重启都可能影响业务，必须由当班负责人授权，并先确认导出操作无写入副作用。不能看到线程多就直接杀进程。

后续行动

我们把行动分成三档，避免复盘结束后留下十几条无人处理的建议。

一周内

  • 导出改为异步分页任务。
  • 设置导出并发上限和单用户频率限制。
  • 补充 1 万条数据的集成测试。
  • 连接池等待数进入告警。

一个月内

  • 建立外部调用统一超时配置。
  • Review 清单增加“事务中是否包含远程调用”。
  • 发布看板增加连接池、线程池和下游耗时。
  • 为大批量任务建立独立执行资源。

持续观察

  • 导出任务平均和最大处理时间。
  • 每批数据大小是否需要调整。
  • 客户批量接口的失败和限流情况。

每项都记录负责人、截止时间和验证标准。“加强监控”“提高意识”没有可验收结果，不算行动项。
