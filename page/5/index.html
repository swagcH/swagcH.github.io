项目部署标准化流程

发表于 2020-10-18 更新于 2026-08-26 分类于 项目部署

早期上线常见的场景是：开发把 Jar 发给运维，附上一句“替换后重启就行”。顺利时看不出问题，一旦启动失败，大家才开始确认配置改没改、数据库脚本跑没跑、旧包放在哪里。

部署标准化不是增加一堆表格，而是把一次上线变成可重复执行的 Runbook。即使换一个人值班，也能知道前置条件、执行顺序、验证标准和回退边界。

发布单先于操作

没有发布单，不开始生产操作。最小发布单包含：

标题相同的 Jar 不等于同一个版本。发布单必须能对应到唯一 Git 提交和构建产物。

0. 确认变更冻结

发布窗口开始前，确认待发布提交不再变化：

校验值应由 CI 生成，并在目标服务器再次核对。不要在服务器上临时修改 Jar、class 或配置后仍沿用原版本号，这会让后续节点无法复现。

需要一起冻结的还有：

  • 数据库脚本内容和执行顺序。
  • 配置版本。
  • 依赖服务版本。
  • 灰度节点范围。
  • 验证用例和测试数据。

“保留旧 Jar”不是完整回退方案。如果新代码已经写入旧版本无法识别的数据，应用回退仍可能失败。

最终 Runbook

标准化发布的意义，是把原本藏在个人经验里的判断变成团队可以执行和复核的步骤。流程不一定让上线更快，却能让每一次快和慢都有证据，让故障发生时不用从“这次到底改了什么”开始查起。

配置管理经验

发表于 2020-09-29 更新于 2026-08-26 分类于 工程实践

配置问题有一个很迷惑的特点：代码、测试和构建都可能完全正常，只有到了某个环境才失败。更麻烦的是，临时在服务器上改一个值通常很快见效，却会让下次发布、扩容和故障回溯失去依据。

我后来把配置看成代码之外的另一套运行逻辑。它也需要类型、边界、变更记录和回退方案，而不只是若干散落的 YAML。

先把配置分成四类

不同配置应该由不同位置管理：

类型 示例 建议归属
代码默认值 分页上限、批次大小 代码或公共配置
环境差异 域名、数据库地址、日志级别 部署平台或环境配置
敏感信息 密码、Token、私钥 密钥管理系统
运行开关 灰度比例、功能开关 有审计的动态配置

如果一个值在所有环境都一样，而且改变它必须重新测试，通常更适合作为代码常量；如果它随部署环境变化，才属于外部配置。

不要为了“灵活”把每个数字都做成配置。无边界配置会让系统组合状态急剧增加，测试无法覆盖。

仓库里的配置只放可公开内容

一个比较清晰的 Spring Boot 结构是：

仓库里不提交：

  • 真实数据库密码。
  • 云服务访问密钥。
  • 生产域名白名单和内部凭据。
  • 从服务器复制回来的完整配置。
  • 以注释方式“临时保留”的旧密码。

即使仓库是私有的，提交历史、CI 日志和开发机副本都会扩大泄露范围。已经进入 Git 历史的密钥不能只删除当前行，必须立即轮换。

用占位符表达依赖

application.yml 可以声明来源和安全默认值：

地址和账号没有默认值，是为了缺失时尽早失败；超时可以给出经过验证的默认值。生产配置里不要使用 localhost 作为兜底，否则依赖漏配后，应用可能启动成功却一直请求自己。

我会在部署记录里保存“配置键、来源、版本”，而不是把值全部打印到日志。对于敏感项，只记录是否存在和更新时间。

环境隔离不是复制四份文件

测试、预发、生产环境应该保持结构一致，只让必要值不同：

如果测试环境使用内存数据库、关闭鉴权、同步执行，而生产使用 MySQL、真实鉴权、异步消息，那么测试通过只能说明另一套系统可用。

本地环境可以提供简单依赖，但不能让代码依赖某位开发的绝对路径或个人账号。

配置变更也走一次发布流程

一次完整变更至少包含：

先在测试或单实例验证，再逐步扩大。改变连接池、线程池、超时和重试参数时，不能只看应用是否启动，还要观察下游压力、错误率、排队和资源使用。

配置变更速度快，所以更容易绕过 Review。正因为快，才更需要审计。

动态刷新不是免费能力

配置中心允许运行时刷新，但不是所有 Bean 和配置都适合热更新：

  • 数据源连接池可能需要重建。
  • 线程池大小变化要考虑正在执行的任务。
  • 多实例接收配置存在时间差。
  • 一组相关配置分次生效可能产生非法组合。
  • 回调过程中读取两次配置可能得到不同值。

对于必须原子变化的一组值，应使用一个版本对象整体发布；业务处理开始时读取一次快照，不在同一请求中反复读取。

核心连接、序列化协议、数据结构等高风险配置，我更倾向于随版本发布并重启，让行为边界明确。

功能开关要有生命周期

功能开关适合灰度和紧急关闭，但每个开关必须记录：

长期不清理的开关会在代码中形成大量分支。一次需求结束后，要么删除旧路径和开关，要么将它升级为正式业务规则并补齐测试。

权限也要控制。能修改“是否校验支付金额”的配置，比修改普通日志级别风险高得多，不应使用同一审批级别。

启动和运行时分别验证

启动时检查：

运行时则通过健康检查和指标确认配置效果，例如连接池等待时间、外部调用超时率、线程池队列和降级次数。配置正确加载不代表参数适合当前流量。

日志中可以输出脱敏摘要：

不要直接打印完整 URL 查询参数、用户名或密钥。

我的配置检查表

配置管理真正要解决的不是“值放在哪里”，而是任何环境下都能回答：当前使用什么、为什么是这个值、谁改过、怎样验证、失败后如何恢复。做到这一点，环境差异才不会继续成为只能靠经验处理的黑盒。

不要让 Controller 接收一个无边界的 Map。订单查询可以使用明确的请求对象：

DTO 只描述接口契约，不直接复用数据库实体。否则表字段变化可能意外改变接口，调用方也可能提交本不允许修改的字段。

Controller 只做协议转换

Controller 不编写 SQL，不决定事务，也不捕获所有异常后返回 200。它负责 HTTP 参数、认证上下文和响应状态，业务规则放进应用服务或领域对象。

构造器注入能让依赖显式，也便于测试；相比字段注入，不需要通过反射才能创建对象。

业务服务守住事务边界

事务放在公共 Service 方法上，并保持范围尽可能小。不要在数据库事务中执行耗时 HTTP 调用；数据库锁会一直占用，失败语义也更难处理。

示例中的分页偏移需要防止超大页码。数据量增加后，可以改成基于 id 或创建时间的游标分页，而不是无限增大的 OFFSET。

早期工程使用 NamedParameterJdbcTemplate 已经足够：

参数必须绑定，不能拼接用户输入。SQL 字段显式列出，不使用 SELECT *。当查询逐渐复杂，再决定是否引入 MyBatis 等框架，不必为了一个接口提前增加整套抽象。

错误响应要稳定

接口错误至少包含业务码、可读消息、traceId 和时间。不要把 Java 异常类名直接暴露给调用方：

业务异常还应单独映射合适的 HTTP 状态和业务码。前端可以根据稳定的业务码决定提示或重试，不依赖容易变化的中文消息。

健康检查不等于进程存在

生产环境不要默认暴露全部管理端点，尤其是环境变量、Bean 和线程信息。管理端点应走内部网络并有访问控制。

健康检查也要区分：

  • 存活：进程是否需要重启。
  • 就绪：是否能够接收新流量。

第一个接口完成后的骨架验收

Spring Boot 的价值不只是少写配置，而是让团队用约定快速建立一致基线。一个合格骨架不需要塞满技术名词，它应该让新增业务代码有位置、失败能够被看见、环境差异可控制，并且任何人都能用同一条命令得到相同产物。

日志设计实践

发表于 2020-08-23 更新于 2026-08-26 分类于 工程实践

我曾经排查过一个支付回调问题，日志里有几千行“处理失败”，却没有订单号、阶段和异常堆栈。日志数量不少，但没有一行能够把请求和业务结果连起来。

从那以后，我判断一条日志是否有价值，不再看它写了多少内容，而是看它能不能回答：发生了什么、影响哪个对象、进行到哪一步、结果是什么、下一步去哪里查。

反例一：只写一句“操作失败”

这段日志有三个问题：

  1. 没有业务标识，无法找到受影响订单。
  2. 没有异常对象，丢失类型和调用栈。
  3. 捕获后没有继续抛出，调用方可能收到成功结果。

改造时先明确异常策略，再记录必要上下文：

业务拒绝是可预期结果，使用 WARN 并记录原因码；未知异常使用 ERROR 和完整堆栈。不要在每一层重复打印同一个异常，通常由最了解业务上下文的一层记录一次，再由统一异常处理转换响应。

反例二：把对象整体序列化

看起来省事，实际上可能把密码、手机号、Token 和大段请求体写入日志。对象增加字段后，日志风险还会悄悄扩大。

更稳妥的方式是使用字段白名单：

默认不记录这些内容：

确需定位单个对象时，可以记录不可逆摘要或内部业务编号，不要用敏感原文换取短期便利。

先定义一条业务事件

自由文本很适合阅读，但不利于检索和统计。我会让关键日志具备相对稳定的字段：

例如：

event 表示稳定事件名，result 表示结果，reasonCode 表示可分类原因。人可以读懂，日志平台也能按成功率和耗时聚合。

字段命名要统一。一个服务写 orderNo，另一个写 order_id，第三个放进一段中文消息，跨服务查询会非常痛苦。

级别是一种处置约定

我用“谁需要行动”来判断级别：

级别 含义 示例
ERROR 当前请求失败，通常需要排查或告警 数据库不可用、未知异常
WARN 可恢复或可预期异常，需要观察趋势 限流、降级、业务拒绝
INFO 关键生命周期和业务结果 服务启动、订单创建完成
DEBUG 开发排查细节，生产默认关闭 分支判断、中间结果
TRACE 高频且极细粒度信息 循环内部或协议细节

用户密码错误不应每次都打 ERROR；数据库连接失败也不该只打 INFO。级别混乱会让告警失真，最终大家只能忽略日志。

也不要既在 Repository、Service、Controller 各打一遍相同堆栈，又让全局异常处理再打一遍。重复日志会放大存储量，还会让一次故障看起来像四次。

日志本身也有成本

高并发接口每次打印大对象，会消耗序列化 CPU、磁盘 IO 和网络带宽。需要关注：

  1. 热路径是否有高频 INFO。
  2. 参数构造是否在日志关闭时仍会执行。
  3. 单行是否过大，多行堆栈是否失控。
  4. 日志文件是否按大小和日期滚动。
  5. 保留周期是否符合排障与合规要求。

对高频成功事件，可以用指标统计总量，仅对失败和采样请求保留详细日志。日志、指标和链路追踪各有职责，不应让日志承担全部可观测性。

Git协作开发流程

发表于 2020-07-12 更新于 2026-08-26 分类于 工程规范

一个人使用 Git，记住 add、commit、push 基本够用；多人协作以后，难点变成了什么时候开分支、如何保持改动足够小、冲突由谁处理，以及线上版本怎样准确追溯。

下面是我逐步整理出来的一份团队运行手册。它不追求复杂的分支模型，目标只有三个：主分支随时可发布、每次改动可以审查、出现问题能够回退。

分支只承担清晰职责

小团队可以从三类分支开始：

分支 来源 生命周期 用途
main 受保护分支 长期 已验证、可发布代码
feature/* main 数小时到数天 单个需求或技术任务
hotfix/* 线上 Tag 尽可能短 生产紧急修复

如果团队有固定测试窗口，可以增加 release/*；如果没有明确收益，不必照搬完整 Git Flow。分支越多，版本流转和补丁同步成本越高。

分支名要能直接关联工作：

tmp、new、test2 之类名称会让几周后的清理和追溯变得困难。

开始任务前

先确认工作区干净，并从最新主分支创建任务分支：

--ff-only 可以阻止 pull 在本地悄悄生成一次合并提交。如果当前 Git 版本不支持 switch，可以使用 checkout 完成相同操作。

冲突处理不是选择“我的”或“他的”

处理步骤：

  1. 阅读当前分支和主分支对应提交。
  2. 确认两边修改解决的业务问题。
  3. 手工合成最终行为，而不是直接选择一侧。
  4. 删除冲突标记，重新编译并运行相关测试。
  5. git add 已解决文件，再继续 rebase 或 commit。

如果方向不对，可以执行 git rebase --abort 或 git merge --abort 回到操作前。中止比带着不确定结果继续提交更可靠。

主分支的合并规则

主分支至少应有这些保护：

  • 禁止直接 push。
  • 必须通过合并请求。
  • CI 检查通过后才能合并。
  • 至少一位非作者 Review。
  • 禁止提交密钥和生成物。
  • 合并后自动删除短期分支。

是否使用 merge commit、squash 或 rebase merge，可以按团队追溯习惯选择：

方式 优点 适合场景
Merge commit 保留完整分支上下文 大功能、需要保留阶段提交
Squash 主线简洁，一个任务一个提交 小而频繁的功能分支
Rebase merge 线性历史且保留提交 提交本身已经整理良好

不要在同一个仓库随意切换策略，否则查找版本和回退时会增加认知成本。

发布必须能对应到提交

每次生产发布都创建不可变 Tag：

发布记录至少包含 Tag、构建编号、数据库变更、配置版本和负责人。只有“周日晚上那一版”无法支持故障定位。

回退前要先区分代码回退和数据回退。应用可以回到旧 Tag，但已执行的不可逆 DDL、已写入的新状态、已发送的消息不会自动恢复。

Hotfix 的最短闭环

线上紧急修复从实际生产 Tag 创建，而不是从开发中的某个分支猜：

修复发布后，还要把对应提交合回主开发线，避免下一次发布重新带回缺陷。

关于强制推送和历史修改

git push --force 可能覆盖远端他人的提交，受保护分支应直接禁止。确需更新自己的未合并分支时，也优先使用：

--force-with-lease 会在远端已被他人更新时拒绝覆盖，但它仍然是重写历史操作，执行前必须确认分支所有者和影响范围。

同样，不把 reset --hard 当日常清理命令。未提交文件可能永久丢失；先查看 status、保存必要改动，再决定恢复方式。

一套流程最后解决的是沟通

这套手册执行一段时间后，最明显的变化并不是提交图更漂亮，而是问题更容易回答：某行代码为什么改、谁审过、对应哪个版本、怎样验证、能否回退。

Git 协作的核心不是命令数量，而是把一次改动变成边界清楚、证据完整、可被团队接住的交付单元。

如何阅读遗留代码

发表于 2020-06-20 更新于 2026-08-26 分类于 经验沉淀

接手老项目时，我最初做过一件效率很低的事：从包结构第一行开始逐个打开类，看到命名不顺眼就记一条“待重构”。两天后记了几十条问题，却仍然回答不了一个简单问题：用户提交订单后，系统到底经过哪些步骤？

后来我把阅读遗留代码当成一次代码侦查。目的不是把每个类都看懂，而是在有限时间里建立一张可靠地图，知道入口在哪里、数据怎样变化、异常会停在哪里，以及这次修改会碰到什么。

先写一张侦查任务卡

没有具体问题，阅读很容易变成漫游。开始前先把任务压缩成一张卡：

任务卡会迫使我围绕一个可验证问题前进。读到与目标无关的工具类时，只做标记，不立刻钻进去。

第一条路线：先让系统可观察

能运行的项目比静态目录更诚实。第一步不是修改配置，而是记录当前基线：

  1. 确认 JDK、Maven、数据库和中间件版本。
  2. 使用项目已有的本地配置启动，不复制生产配置。
  3. 找到健康检查、启动日志和一条最小请求。
  4. 记录启动命令、端口、依赖和失败信息。
  5. 在任何改动前执行现有测试，保存通过和失败数量。

如果项目暂时跑不起来，也要区分“代码缺陷”和“环境缺口”。例如缺少测试库、内部依赖无法下载、初始化脚本过期，应该记录为环境事实，不能凭此判断业务代码不可用。

我会先看这些文件，但不逐行精读：

这一步得到的是边界，不是结论。

第二条路线：从入口跟一条请求

阅读调用链时，我会从用户可见入口向内收缩，而不是从底层工具类向外猜。

每经过一层只回答三个问题：

  • 输入在这里增加或丢失了什么信息？
  • 哪个条件会改变正常路径？
  • 失败后由谁捕获、转换或重试？

例如 Controller 只出现一个 cancel(orderId) 调用，我不会立刻打开 Service 中的所有公共方法，而是继续搜索这个方法、订单状态枚举和对应 SQL：

搜索结果要按“生产入口、定时任务、消息消费、测试”分类。同一个方法可能不只被 HTTP 调用，遗漏后台入口是遗留系统修改中常见的风险。

第三条路线：跟踪数据，而不是只跟方法

方法调用只能说明代码经过哪里，数据变化才能解释业务发生了什么。我会为核心对象画一条简化状态线：

时点 数据状态 写入位置 约束
创建后 CREATED 订单服务 订单号唯一
支付后 PAID 支付回调 回调可能重复
取消后 CANCELLED 取消接口 仅未发货可取消
发货后 SHIPPED 消息消费者 必须校验当前状态

接着检查四类细节：

  1. 状态是由 Java 判断，还是直接写在 SQL 条件里。
  2. 一个事务覆盖哪些写操作，外部调用是否夹在事务中间。
  3. 缓存什么时候失效，失败后是否会读到旧状态。
  4. 并发更新有没有版本号、条件更新或唯一约束保护。

假设取消使用 UPDATE order_info SET status = 'CANCELLED' WHERE id = ?，而发货也不带旧状态条件，那么问题不一定在某个 if，而在数据库没有守住状态迁移。此时重命名几个方法不会降低风险。

第四条路线：用历史解释奇怪代码

遗留代码里看似多余的判断，可能是一次事故留下的护栏。遇到不理解的逻辑，我会按下面顺序查历史：

git blame 不是为了找责任人，而是为了找到提交上下文。提交说明、关联需求和同期测试往往能回答“为什么这里不能合并”“为什么失败也返回成功”。

历史只能提供线索，不能自动证明今天仍然正确。最后仍要回到现有业务规则、线上数据和测试结果。

建立事实、推测和问题三栏笔记

阅读过程中最危险的是把猜测写成事实。我使用三栏笔记强制区分：

类型 示例
已验证事实 发货消费者会调用 ship()，SQL 没有旧状态条件
当前推测 重复消息可能覆盖取消状态
待确认问题 消息是否保证同一订单有序，历史数据是否存在该情况

每个推测后面都补一个验证动作，例如查询脱敏数据、补测试、查看消息配置或询问业务负责人。这样即使当天没有定位完成，下一位接手的人也能沿着证据继续走。

修改前先写特征测试

老代码没有单元测试时，直接重构很难判断行为是否变化。特征测试先记录当前可观察行为，即使这个行为并不完美。

对于难以隔离的代码，可以先做接口级测试或固定输入输出的集成测试。测试颗粒度不是越小越好，关键是覆盖这次修改最可能破坏的行为。

画出影响半径

找到修改点后，我会再向外搜索一次：

尤其要注意字符串形式的绑定。方法名搜索不到，不代表它没有被 XML、配置或任务调度平台引用。

什么时候才适合重构

我给自己设置了四个前置条件：

  1. 能用一句话说明当前行为和目标行为。
  2. 已经找到主要入口、数据变化和异常路径。
  3. 有测试或可重复验证步骤保护关键行为。
  4. 改动可以拆成小提交，并且具备回退方式。

如果只是命名较差但近期没有修改需求，可以先记录；如果一个十行改动要同时碰八个模块，说明真正的技术债可能是职责分散，应先缩小边界。重写通常是最后的方案，因为旧系统中最昂贵的部分不是代码行数，而是没有写下来的业务规则。

一页代码地图就是阶段成果

很多“开发延期”和“测试漏测”，根因在代码开始前就已经出现：目标不清、边界没讨论、异常流程无人负责。需求评审不是听产品讲一遍页面，而是把模糊描述转换成可以实现和验收的共同结论。

1. 先问“为什么做”

评审前先确认目标：

  • 当前用户痛点是什么。
  • 成功以后用什么指标判断有效。
  • 为什么必须在这个版本完成。
  • 是否有更小范围的方案。

后端代码两天前新增了 reasonCode，文档没有更新，测试用例只验证了旧参数。三方花了半小时确认，真正修复只有一行字段说明。

这类浪费说明接口管理要覆盖设计、实现、测试、变更和下线，而不只是生成一个 Swagger 页面。

1. 一份完整契约包含什么

只给一个请求 JSON 不够。调用方还需要知道字段为空、重复提交、权限不足和下游超时时会发生什么。

2. 先写契约再实现

订单查询示例：

评审阶段先确认契约，前端可以基于 Mock 开发，测试可以提前编写用例，后端实现也有清晰边界。

OpenAPI 文件应进入版本库，和代码一起 Review。只存在运行时页面中的文档无法比较历史，也很难在 CI 中检查破坏性变更。

3. Schema 要复用但不能万能化

公共分页结构、错误结构可以复用，但不要建立一个包含所有业务字段的 CommonResponseData。过度复用会让一个字段修改影响大量无关接口。

金额是否用字符串或数字需要团队统一。JSON Number 没有十进制精度语义，跨语言调用时尤其要谨慎。

4. 错误码必须可行动

错误码表至少说明：

错误码 含义 HTTP 状态 调用方动作
ORDER_NOT_FOUND 订单不存在或无权查看 404 提示并停止重试
ORDER_STATUS_CONFLICT 当前状态不允许操作 409 刷新订单状态
RATE_LIMITED 请求过于频繁 429 按 Retry-After 重试

不要所有业务失败都返回 HTTP 200，也不要所有异常都返回 500。HTTP 状态表达协议层结果，业务错误码提供领域细节。

错误信息不能泄露 SQL、内部 IP 和完整异常栈。traceId 用于关联服务端日志。

5. 分页语义要写清楚

响应需要说明总数是否精确、排序是否稳定、同一时间新增数据是否影响翻页。大数据量使用游标分页时，游标是否过期、能否反向翻页也属于契约。

6. 写接口说明幂等

订单创建可以要求幂等头：

文档明确：

  • 同一个用户和 Key 在多久内有效。
  • 请求体不同时是否返回冲突。
  • 首次请求处理中再次提交返回什么。
  • 原请求成功后是否返回同一结果。

只写“接口支持幂等”没有可执行意义。

7. 认证和权限不是一句“需要 Token”

上传接口还要说明文件类型、大小、病毒扫描和存储时限。Webhook 要说明签名算法、防重放时间窗口和重试策略。

示例中不能放真实 Token、手机号或客户数据。

8. 文档和代码如何保持一致

两种常见方式：

Code First

通过 Spring 注解从实现生成 OpenAPI。优点是靠近代码，缺点是设计容易滞后到实现阶段，复杂说明仍需人工维护。

Design First

先维护 OpenAPI，再生成服务端接口或客户端。优点是契约先行，缺点是需要处理生成代码和业务实现边界。

无论选择哪种，都应该在 CI 中：

文档生成失败不能被静默忽略，否则线上页面可能一直停留在旧版本。

9. 变更分类

通常兼容的变化：

  • 新增可选请求字段。
  • 新增响应字段，前提是调用方能忽略未知字段。
  • 新增错误码并有默认处理。

通常破坏兼容的变化：

  • 删除或重命名字段。
  • 修改字段类型、单位或含义。
  • 可选字段改为必填。
  • 修改枚举值语义。
  • 改变分页、排序或幂等行为。

破坏性变更应通过新版本、双写兼容或迁移窗口发布，不能只在群里通知。

10. 文档的生命周期

每个接口要有负责人。没有负责人时，文档问题、兼容问题和调用咨询都会变成公共群里的随机响应。

11. Review 清单

接口文档的最终价值不是页面好看，而是减少口头确认，让实现、测试和调用方对同一个行为达成一致。当契约可以被 Review、测试和自动比较时，文档才从附属材料变成工程资产。

数据库设计经验总结

发表于 2020-03-14 更新于 2026-08-26 分类于 数据库

数据库结构承载的是业务事实。代码写错可以快速回滚，错误表结构一旦积累大量数据，修改会同时影响迁移、兼容、性能和历史报表。这篇用一次订单表评审整理设计时真正需要问的问题。

先从业务事实开始

设计订单表前，不急着列字段，先确认：

“用户可以买商品”不足以支撑表设计。金额是否允许调整、订单是否拆单、退款能否部分发生，都会改变数据模型。

1. 主键和业务编号分开

id 是数据库内部主键，适合聚簇索引和关联；order_no 是稳定的业务编号，可以暴露给外部。不要把自增 ID 直接当公开订单号，也不要让一个过长随机字符串承担所有关联主键成本。

业务编号生成要考虑全局唯一、趋势性、时钟回拨和信息泄露。使用雪花算法、号段或数据库序列都可以，但要明确失败和重复检测方式。

2. 数据类型按语义选择

金额

使用 DECIMAL 或最小货币单位整数，不使用浮点数：

同时记录币种时，金额精度不能假设永远是两位小数。跨币种系统需要专门的 Money 设计。

时间

团队必须约定数据库时区和应用转换方式。TIMESTAMP 与 DATETIME 的范围、时区行为不同，不能只因为示例常见就随意选择。

状态

TINYINT 节省空间，但数据库里看到 3 不直观。需要在代码、文档和数据字典中维护同一映射：

给状态值留间隔，后续可以插入中间状态。不要复用已经废弃的数字表示新含义，否则历史数据会被重新解释。

文本

字段长度来自业务约束，而不是统一写 VARCHAR(255)。手机号、订单号、外部流水号的长度和字符集不同。超长正文放 TEXT 时，也要考虑是否真的需要频繁查询和索引。

3. NULL 和默认值要表达真实含义

NULL 应该表示“未知或不存在”，不是“开发暂时没想好”。

把所有字符串默认成空串，会让“未填写”和“明确为空”无法区分。反过来，所有字段都允许 NULL 也会把校验压力推给每个查询。

4. 订单明细单独建表

不要把商品列表保存成逗号字符串：

sku_name 和成交单价是下单时快照。商品后来改名或改价，历史订单仍应保持当时事实。是否同时保存规格、图片和税费，要根据展示和对账需求决定。

5. 索引从查询模式出发

先列高频查询：

对应索引 (user_id, created_at) 和 (status, created_at)。索引字段顺序要匹配过滤和排序，不是简单把区分度最高的字段放最前面。

每个二级索引都会保存主键，并增加写入、存储和维护成本。下面几类索引需要重点检查：

  • 被联合索引前缀覆盖的重复索引。
  • 低区分度单列索引。
  • 为一次临时报表增加、长期无人使用的索引。
  • 包含过多长字符串的“万能覆盖索引”。

上线前使用真实数据量查看执行计划，不能只在几十行测试数据上验证。

6. 唯一约束是业务防线

应用先查询“订单号是否存在”再插入，在并发下仍可能重复。数据库唯一索引提供最终保证：

幂等请求也可以建立唯一约束：

捕获唯一键冲突后，要查询并返回原业务结果，而不是统一转换成“系统异常”。

7. 外键是否使用

外键能保护引用完整性，但会增加迁移、写入和跨表操作约束。单体且表关系稳定时可以使用；高并发、分库分表或跨服务数据所有权场景通常由应用和对账保证。

无论是否创建数据库外键，关系都必须明确：删除用户后订单如何保留，删除商品后订单快照是否还可展示。没有外键不代表没有约束。

8. 逻辑删除不能滥用

逻辑删除方便恢复和审计，但会影响唯一索引、所有查询条件和数据量。订单通常不是“删除”，而是取消或关闭；用业务状态表达比统一 deleted=1 更准确。

真正需要删除的临时数据，应有明确生命周期和归档任务。不要让所有表永久增长。

9. 乐观锁和并发更新

订单状态更新可以带版本号：

检查受影响行数，零行表示状态已变化或版本冲突。这样比先查后改更能保护合法状态流转。

乐观锁不适合所有高冲突场景。冲突频繁时要重新审视业务串行化、队列或数据库锁策略。

10. 表结构变更要可回退

开发环境能瞬间执行的 DDL，在线上大表可能锁表、占满磁盘或造成复制延迟。

变更前确认：

新增字段优先做到新旧代码都能运行：先加可兼容字段，再发布写入，再迁移历史数据，最后切换读取。不要把表变更和代码行为切换压在同一秒完成。

11. 评审清单

好的数据库设计不是一次把未来所有字段都猜出来，而是准确表达当前业务事实，同时为常见演进保留空间。表结构越接近业务语言，后续查询、接口和故障排查就越少依赖口头解释。

统一 IDEA 格式配置并放入仓库，避免每个人手工争论空格和换行。CI 检查失败要给出明确修复命令，不能只留下一个红色任务。

8. Review 看什么

我会按这个顺序 Review：

  1. 需求是否被正确理解，边界条件有没有遗漏。
  2. 数据和接口是否兼容，失败后状态是否可解释。
  3. 是否存在重复、过长方法、多层嵌套和不清晰命名。
  4. 异常、日志和事务边界是否合理。
  5. 并发、性能和安全风险是否被考虑。
  6. 测试是否覆盖主要分支。
  7. 最后才是格式问题，通常应由工具解决。

最后看质量

规范的目标不是让所有代码看起来像一个人写的，而是让任何团队成员都能更快理解、修改和验证。真正有效的规范会减少 Review 往返、降低缺陷率、缩短新人上手时间，并让线上日志更容易使用。

当团队开始讨论业务边界和失败语义，而不是反复争论括号位置，代码规范才真正发挥作用。
