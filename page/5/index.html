数据库设计经验总结

发表于 2020-03-14 分类于 数据库

数据库结构承载的是业务事实。代码写错可以快速回滚，错误表结构一旦积累大量数据，修改会同时影响迁移、兼容、性能和历史报表。这篇用一次订单表评审整理设计时真正需要问的问题。

先从业务事实开始

设计订单表前，不急着列字段，先确认：

“用户可以买商品”不足以支撑表设计。金额是否允许调整、订单是否拆单、退款能否部分发生，都会改变数据模型。

1. 主键和业务编号分开

id 是数据库内部主键，适合聚簇索引和关联；order_no 是稳定的业务编号，可以暴露给外部。不要把自增 ID 直接当公开订单号，也不要让一个过长随机字符串承担所有关联主键成本。

业务编号生成要考虑全局唯一、趋势性、时钟回拨和信息泄露。使用雪花算法、号段或数据库序列都可以，但要明确失败和重复检测方式。

2. 数据类型按语义选择

金额

使用 DECIMAL 或最小货币单位整数，不使用浮点数：

同时记录币种时，金额精度不能假设永远是两位小数。跨币种系统需要专门的 Money 设计。

时间

团队必须约定数据库时区和应用转换方式。TIMESTAMP 与 DATETIME 的范围、时区行为不同，不能只因为示例常见就随意选择。

状态

TINYINT 节省空间，但数据库里看到 3 不直观。需要在代码、文档和数据字典中维护同一映射：

给状态值留间隔，后续可以插入中间状态。不要复用已经废弃的数字表示新含义，否则历史数据会被重新解释。

文本

字段长度来自业务约束，而不是统一写 VARCHAR(255)。手机号、订单号、外部流水号的长度和字符集不同。超长正文放 TEXT 时，也要考虑是否真的需要频繁查询和索引。

3. NULL 和默认值要表达真实含义

NULL 应该表示“未知或不存在”，不是“开发暂时没想好”。

把所有字符串默认成空串，会让“未填写”和“明确为空”无法区分。反过来，所有字段都允许 NULL 也会把校验压力推给每个查询。

4. 订单明细单独建表

不要把商品列表保存成逗号字符串：

sku_name 和成交单价是下单时快照。商品后来改名或改价，历史订单仍应保持当时事实。是否同时保存规格、图片和税费，要根据展示和对账需求决定。

5. 索引从查询模式出发

先列高频查询：

对应索引 (user_id, created_at) 和 (status, created_at)。索引字段顺序要匹配过滤和排序，不是简单把区分度最高的字段放最前面。

每个二级索引都会保存主键，并增加写入、存储和维护成本。下面几类索引需要重点检查：

  • 被联合索引前缀覆盖的重复索引。
  • 低区分度单列索引。
  • 为一次临时报表增加、长期无人使用的索引。
  • 包含过多长字符串的“万能覆盖索引”。

上线前使用真实数据量查看执行计划，不能只在几十行测试数据上验证。

6. 唯一约束是业务防线

应用先查询“订单号是否存在”再插入，在并发下仍可能重复。数据库唯一索引提供最终保证：

幂等请求也可以建立唯一约束：

捕获唯一键冲突后，要查询并返回原业务结果，而不是统一转换成“系统异常”。

7. 外键是否使用

外键能保护引用完整性，但会增加迁移、写入和跨表操作约束。单体且表关系稳定时可以使用；高并发、分库分表或跨服务数据所有权场景通常由应用和对账保证。

无论是否创建数据库外键，关系都必须明确：删除用户后订单如何保留，删除商品后订单快照是否还可展示。没有外键不代表没有约束。

8. 逻辑删除不能滥用

逻辑删除方便恢复和审计，但会影响唯一索引、所有查询条件和数据量。订单通常不是“删除”，而是取消或关闭；用业务状态表达比统一 deleted=1 更准确。

真正需要删除的临时数据，应有明确生命周期和归档任务。不要让所有表永久增长。

9. 乐观锁和并发更新

订单状态更新可以带版本号：

检查受影响行数，零行表示状态已变化或版本冲突。这样比先查后改更能保护合法状态流转。

乐观锁不适合所有高冲突场景。冲突频繁时要重新审视业务串行化、队列或数据库锁策略。

10. 表结构变更要可回退

开发环境能瞬间执行的 DDL，在线上大表可能锁表、占满磁盘或造成复制延迟。

变更前确认：

新增字段优先做到新旧代码都能运行：先加可兼容字段，再发布写入，再迁移历史数据，最后切换读取。不要把表变更和代码行为切换压在同一秒完成。

11. 评审清单

好的数据库设计不是一次把未来所有字段都猜出来，而是准确表达当前业务事实，同时为常见演进保留空间。表结构越接近业务语言，后续查询、接口和故障排查就越少依赖口头解释。

1. 命名是最便宜的设计

7. 可以自动化的全部交给工具

统一 IDEA 格式配置并放入仓库，避免每个人手工争论空格和换行。CI 检查失败要给出明确修复命令，不能只留下一个红色任务。

自动化规则不要一次开启几百条并要求全量旧代码立即通过。可以先对新增和修改代码生效，再逐步治理存量。

8. Review 看什么

我会按这个顺序 Review：

  1. 需求是否被正确理解，边界条件有没有遗漏。
  2. 数据和接口是否兼容，失败后状态是否可解释。
  3. 是否存在重复、过长方法、多层嵌套和不清晰命名。
  4. 异常、日志和事务边界是否合理。
  5. 并发、性能和安全风险是否被考虑。
  6. 测试是否覆盖主要分支。
  7. 最后才是格式问题，通常应由工具解决。

最后看质量

规范的目标不是让所有代码看起来像一个人写的，而是让任何团队成员都能更快理解、修改和验证。真正有效的规范会减少 Review 往返、降低缺陷率、缩短新人上手时间，并让线上日志更容易使用。

当团队开始讨论业务边界和失败语义，而不是反复争论括号位置，代码规范才真正发挥作用。

新人如何快速熟悉项目

发表于 2020-01-11 分类于 经验沉淀

刚进入一个项目时，最容易走两个极端：从第一行源码开始读，几天后仍然没有全局概念；或者只等别人分配任务，能改代码却解释不清请求为什么这样流转。比较有效的方法，是用一周建立一张“可以工作的项目地图”。

第 0 天：先约定上手目标

第 1 天：把项目可靠地跑起来

先读这些文件，而不是立即搜索业务类：

记录本地依赖和版本：JDK、Maven、MySQL、Redis、消息队列，以及必须申请的配置或账号。敏感值只记录获取方式，不复制到个人笔记。

启动完成后，不以“控制台没有报错”为标准，而要验证：

把启动过程中遇到的缺失配置、端口冲突和初始化步骤补回团队文档。新人遇到的问题往往也是下一位新人会遇到的问题。

第 2 天：画业务地图，不急着画类图

先问产品或同事三个问题：

  1. 系统最重要的用户是谁。
  2. 哪三个流程最影响业务结果。
  3. 哪些状态一旦错误最难修复。

最容易浪费时间的做法

  1. 从工具类开始逐行阅读，没有业务问题作为线索。
  2. 复制同事配置却不知道来源和权限边界。
  3. 一上来重构公共代码，尚未理解兼容原因。
  4. 只记录结论，不记录命令、现象和判断过程。
  5. 遇到问题立即问人，从不先搜索日志和历史提交。

一个月后的验收

第一周建立地图，第一个月应该逐步做到：

  • 能独立完成一个中等需求。
  • 能解释核心链路的事务和失败分支。
  • 能处理常见环境和数据问题。
  • 能在 Review 中发现业务影响，不只看格式。
  • 至少补齐一份团队可复用的文档或测试。

快速熟悉项目不是记住最多类名，而是形成定位问题的坐标系。知道业务目标、数据边界、调用入口和协作流程后，陌生代码会从一片文件变成可以逐步验证的系统。

第一个完整项目复盘

发表于 2019-12-29 分类于 随笔

背景

2019 年的最后，我把第一个完整项目从需求、开发、部署到复盘重新梳理了一遍。

2019 年对我来说和 2018 年明显不一样。2018 年更多是在补 Java 基础，到了 2019 年，我开始把零散知识往项目里放。很多以前看起来懂了的概念，只要一放进真实项目流程里，马上就会暴露问题。

这篇文章记录的是我在 2019-12 前后学习和实践 第一个完整项目复盘 时的理解。内容不会写得像官方文档，更像是一份踩坑记录：当时为什么学、遇到了哪些问题、怎么排查，最后沉淀出哪些可以复用的经验。

问题

刚开始实践时，我主要卡在下面几个点：

  1. 需求边写边改导致返工
  2. 代码分层不清晰
  3. 部署和文档总是拖到最后

这些问题单独看都不算复杂，但放在项目里就很容易连锁反应。比如配置错了，表面上看到的是页面打不开，实际原因可能是路径、依赖、运行环境或者请求流程中的某个环节出了问题。

分析

项目复盘的价值是把“能跑”背后的过程问题暴露出来，包括需求、设计、开发、测试和部署。

我后来发现，学项目实践类技术时，不能只背 API。更重要的是把它放到一条完整链路里看：

只要能说清楚它在这条链路里的位置，就不会完全靠记忆去使用。

解决方案

我的处理方式是先把最小可运行例子跑通，再逐步放到项目中验证。下面是当时整理下来的关键操作和代码片段。

实践过程中我还给自己定了一个小规则：每次遇到问题，不只记录最终命令，还要记录“为什么这么做”。否则下次换一个环境，很容易又从头查一遍。

总结

这次学习给我的最大感受是：项目实践里的知识点，真正难的不是单个语法，而是上下文。

对 第一个完整项目复盘 的理解，我最后沉淀成几条经验：

  • 先理解它解决什么问题，再记具体用法；
  • 先跑通最小 Demo，再接入完整项目；
  • 配置类问题要从路径、依赖、版本、环境四个方向排查；
  • 代码示例要自己敲一遍，复制能跑不代表真的理解；
  • 每次踩坑最好留下记录，后面会节省大量时间。

2019 年的学习明显比 2018 年更贴近真实开发。很多概念，比如 Servlet、Spring、MyBatis、接口设计、权限管理，都是在一次次“跑不起来”和“终于跑通了”的过程中慢慢理解的。

项目上线前检查清单

发表于 2019-12-08 分类于 项目实践

背景

第一次准备上线项目时，我才发现代码写完并不等于项目完成。

2019 年对我来说和 2018 年明显不一样。2018 年更多是在补 Java 基础，到了 2019 年，我开始把零散知识往项目里放。很多以前看起来懂了的概念，只要一放进真实项目流程里，马上就会暴露问题。

这篇文章记录的是我在 2019-12 前后学习和实践 项目上线前检查清单 时的理解。内容不会写得像官方文档，更像是一份踩坑记录：当时为什么学、遇到了哪些问题、怎么排查，最后沉淀出哪些可以复用的经验。

问题

刚开始实践时，我主要卡在下面几个点：

  1. 本地能跑不代表线上能跑
