工作第一年总结

发表于 2020-12-27 分类于 随笔

背景

工作第一年的成长，不只是学会更多框架，而是开始理解工程、业务和协作之间的关系。

如果说 2019 年的重点是把项目做出来，那么 2020 年更像是开始理解“项目为什么要这样做”。很多问题表面上是技术问题，往深处看其实是规范、协作、边界和长期维护的问题。

这一年我逐渐意识到，成熟的开发不是写出更复杂的代码，而是在合适的约束下，把问题拆清楚，把风险讲明白，把结果稳定交付出去。

问题

这类问题在工作中并不少见，当时我主要遇到下面几个情况：

  1. 只关注完成需求，没有主动理解业务价值
  2. 遇到问题时容易陷入局部技术细节
  3. 对协作、沟通、质量的理解不够系统

这些问题的共同点是：短期看只是效率问题，长期看会逐渐变成质量问题。它们不会立刻让系统崩掉，但会在需求迭代、人员交接、线上排查时持续放大成本。

分析

第一年的成长是从“把功能做完”转向“把事情做稳”，开始关注可维护性、协作效率和交付质量。

我后来总结出一个判断标准：凡是需要多人长期参与的事情，都不能只依赖个人经验。经验如果不能被记录、复用和检查，就很难成为团队能力。

解决方案

我的处理方式不是追求一步到位，而是先把最容易失控的部分标准化，再逐步优化细节。

具体落地时，我更倾向于采用“小步治理”的方式：先让流程可见，再让责任明确，最后再谈自动化或平台化。这样推进阻力会小很多，也更容易让团队接受。

总结

关于 工作第一年总结，我这一阶段最大的收获是：成熟的工程经验往往不是某个技巧，而是一套稳定处理问题的方式。

这篇文章可以沉淀为几条原则：

  • 先明确问题边界，再讨论技术方案；
  • 能形成清单的事情，不要只靠记忆；
  • 能通过规范减少沟通的地方，就不要反复口头确认；
  • 重要结论要留痕，方便后续追溯；
  • 技术方案要服务于交付质量，而不是只追求形式上的先进。

2020 年以后，我对“经验”的理解发生了变化：经验不是踩过坑之后说一句“下次注意”，而是把坑转化为规范、流程、工具或文档，让后面的人少踩一次。

背景

好的日志不是越多越好，而是在出问题时能准确回答“发生了什么、影响了谁、下一步查哪里”。

如果说 2019 年的重点是把项目做出来，那么 2020 年更像是开始理解“项目为什么要这样做”。很多问题表面上是技术问题，往深处看其实是规范、协作、边界和长期维护的问题。

这一年我逐渐意识到，成熟的开发不是写出更复杂的代码，而是在合适的约束下，把问题拆清楚，把风险讲明白，把结果稳定交付出去。

问题

这类问题在工作中并不少见，当时我主要遇到下面几个情况：

  1. 出问题时日志里只有“失败了”，没有上下文
  2. 日志级别混乱，INFO 和 ERROR 随意使用
  3. 敏感信息被直接打印到日志

这些问题的共同点是：短期看只是效率问题，长期看会逐渐变成质量问题。它们不会立刻让系统崩掉，但会在需求迭代、人员交接、线上排查时持续放大成本。

分析

日志设计要面向排查场景，能串起请求、用户、业务对象、异常堆栈和关键状态变化。

我后来总结出一个判断标准：凡是需要多人长期参与的事情，都不能只依赖个人经验。经验如果不能被记录、复用和检查，就很难成为团队能力。

解决方案

我的处理方式不是追求一步到位，而是先把最容易失控的部分标准化，再逐步优化细节。

具体落地时，我更倾向于采用“小步治理”的方式：先让流程可见，再让责任明确，最后再谈自动化或平台化。这样推进阻力会小很多，也更容易让团队接受。

总结

关于 日志设计实践，我这一阶段最大的收获是：成熟的工程经验往往不是某个技巧，而是一套稳定处理问题的方式。

这篇文章可以沉淀为几条原则：

  • 先明确问题边界，再讨论技术方案；
  • 能形成清单的事情，不要只靠记忆；
  • 能通过规范减少沟通的地方，就不要反复口头确认；
  • 重要结论要留痕，方便后续追溯；
  • 技术方案要服务于交付质量，而不是只追求形式上的先进。

2020 年以后，我对“经验”的理解发生了变化：经验不是踩过坑之后说一句“下次注意”，而是把坑转化为规范、流程、工具或文档，让后面的人少踩一次。
