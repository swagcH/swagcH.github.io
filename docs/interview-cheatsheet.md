## 一、分库分表（对应：能源大屏 / 医院通行证）

### 高频追问

| 面试官会问 | 我要答的 |
|---|---|
| **什么时候该分？** | 先排除：加索引改 SQL → 冷热分离 → 读写分离 → 加缓存。**只有"单实例写入撑不住 + 存在高基数且查询必带的分片键"才分** |
| **分片键怎么选？** | 四原则：①高基数 ②查询必带 ③分布均匀 ④业务不变。<br>通行证系统选 `user_id`（因为"查某人历史"是高频操作）；能源大屏选企业维度 |
| **跨分片事务怎么办？** | 优先**改设计消除**（让需一致的数据同分片）→ 其次柔性事务（本地消息表+定时补偿）→ 最后才是 Seata 这类框架 |
| **不带分片键的查询？** | 会**路由到所有分片再归并，比单表更慢**。应对：建映射表（手机号→user_id）或让 ES 承载多维度检索 |
| **深分页问题？** | 每个分片都取前 N 条再内存归并。应对：**游标分页**（用上页最后一条的时间做起点）或延迟关联 |
| **全局 ID？** | 雪花算法（有序、对索引友好），注意时钟回拨 |
| **扩容怎么做？** | 取模算法扩容要重分布几乎所有数据。应对：**预分片**（一开始分足够的逻辑片）、一致性哈希、双倍扩容 |
| **分片规则改了数据没迁？** | 会"按新规则查不到老数据"。**规则变更必须配迁移脚本与校验** |

### 关键认知（要能说出来）

```
分库分表解决的是"单实例处理能力上限"，不是"查询慢"的通用解法。
它把问题从"一台机器扛不住"转换成"分布式带来的一致性、查询与运维复杂度"。
索引不是越多越好——每个索引都要在写入时维护，也占缓冲池。
```

## 二、Redis 缓存（对应：全部项目）

### 高频追问

| 面试官会问 | 我要答的 |
|---|---|
| **三者怎么区分？** | **穿透=数据不存在**（每次绕过缓存打库）；**击穿=单个热点 key 失效**（并发重建）；**雪崩=一大片同时失效或 Redis 挂了** |
| **穿透怎么防？** | ①参数校验（最便宜）②缓存空值（**必须短过期**，否则内存被打满）③布隆过滤器（代价：有误判、不支持删除、需预热同步） |
| **击穿怎么防？** | ①互斥锁重建（代价：响应时间变长、有死锁风险）②**逻辑过期**（返回旧值+异步更新，代价：短暂脏数据） |
| **雪崩怎么防？** | ①**过期时间加随机偏移**（成本最低收益最高）②高可用部署 ③多级缓存 ④熔断降级 ⑤限流 |
| **为什么删缓存不更新缓存？** | 更新缓存浪费（写后可能没人读）；并发写时更新顺序可能与库不一致，导致缓存留旧值 |
| **为什么先更库再删缓存？** | 反过来（先删后更）时，删除到更新之间若有读请求，会把**旧值**重新加载进缓存且不会自动纠正 |
| **延迟双删？** | 更库后删一次，延迟再删一次清掉"更新期间被读请求写回的旧值"。代价：延迟时间不好定 |
| **最终兜底？** | **短过期时间**——即使中间不一致，最长一个过期周期后自动恢复 |

### 我实际的选择（要能说出取舍）

```
参数校验 + 缓存空值（短过期），没用布隆过滤器。
理由：key 空间可枚举（用户 ID、设备 ID），攻击者能构造的不存在 key 有限；
      引入布隆过滤器需要额外预热和同步逻辑，收益不匹配。
这才是面试官想听的——不是"我知道布隆过滤器"，而是"我知道什么时候不用它"。
```

## 三、MySQL 慢查询（对应：全部项目）

### 高频追问

| 面试官会问 | 我要答的 |
|---|---|
| **怎么定位慢 SQL？** | 慢日志（`long_query_time` **单位是秒**，要设小数）；`pt-query-digest` **按总耗时排序**（不是单次耗时）；`performance_schema` 看 `rows_examined/rows_sent` 比例 |
| **EXPLAIN 看什么？** | ①`type`（核心 SQL 至少 `ref`/`range`，不能 `ALL`）②`key_len`（**验证联合索引用了几列**）③`rows × filtered%` ④`Extra` |
| **`key_len` 怎么算？** | `BIGINT`=8、`TINYINT`=1、`INT`=4，允许 NULL 再 +1；`VARCHAR(n)` = 4n+2（utf8mb4） |
| **`Extra` 里哪两个要警惕？** | `Using filesort`（额外排序）、`Using temporary`（临时表）；`Using index` 是好的（覆盖索引） |
| **哪些写法让索引失效？** | ①索引列上做函数运算 ②**隐式类型转换**（`WHERE varchar_col = 123`）③前导模糊 `LIKE '%x'` ④`OR` 跨列 |
| **`!=` 会让索引失效吗？** | **不绝对**。如果 `!=` 能排除绝大部分数据，优化器可能仍走索引。**用 EXPLAIN 验证，不要背结论** |
| **深分页怎么优化？** | ①游标分页 ②延迟关联（先用覆盖索引取主键再回表） |
| **大表加索引？** | MySQL 5.6+ 支持 `ALGORITHM=INPLACE`，但生产建议 **gh-ost / pt-osc**（可暂停、可回滚） |

## 四、RabbitMQ（对应：医院通行证）

### 高频追问

| 面试官会问 | 我要答的 |
|---|---|
| **什么时候不该用 MQ？** | 需同步返回结果、强一致、逻辑本来就简单、延迟要求极高 |
| **消息丢失的三个环节？** | ①生产者→Broker（网络抖动）②Broker 内部（未落盘宕机）③消费者处理（失败/ACK 丢失） |
| **分别怎么解决？** | ①`publisher-confirm` + `publisher-returns`（**Confirm 只保证到交换机**，路由失败要用 Returns 捕获）②**交换机、队列、消息三者都持久化** ③**手动 ACK** + 区分业务/系统异常 |
| **为什么不能用默认 auto ACK？** | auto 模式下方法返回就 ACK，**抛异常也会 ACK**，消息就丢了 |
| **业务异常和系统异常怎么区分？** | 业务异常（参数错、状态不符）重试多少次都失败 → 记录后 ACK；系统异常（网络、超时）→ `basicNack(requeue=true)` 重试 |
| **为什么必须做幂等？** | RabbitMQ 只能保证 **at-least-once**。"处理成功"和"ACK"是两个动作，不可能原子，所以**同一条消息可能被投递多次** |
| **幂等怎么实现？** | ①**唯一 ID + 去重表**（去重记录与业务**必须同事务**）②状态机（`UPDATE ... WHERE 旧状态`）③Redis 去重（不持久，只适合不敏感场景）④业务天然幂等 |
| **哪些错误会触发降级/重试？** | 429 限流、5xx、超时、连接失败会；400 参数错、401 鉴权、内容审核不会 |

## 五、SpringCloud 微服务拆分（对应：能源大屏）

### 高频追问

| 面试官会问 | 我要答的 |
|---|---|
| **服务按什么拆？** | 优先级：**变化频率 > 数据源 > 性能特征 > 团队边界**（康威定律） |
| **拆太细/太粗各有什么问题？** | 太细：一个页面调 6 个服务，日志分散无法串联；太粗：等于没拆，无法按模块扩容 |
| **为什么单独拆出 metric-service？** | 隔离"**上游 9 个系统不稳定**"这个最大风险源，且它的迭代节奏与其他服务完全不同 |
| **异构系统怎么集成？** | **适配器模式**统一接入层（REST/DB直连/MQ订阅各实现一个 adapter），业务代码只依赖接口 |
| **指标口径不一致怎么办？** | 建**指标字典**：全局唯一 `metric_code` + 配置化转换表达式（口径调整不改代码）+ 分层更新周期（秒级/分钟级/小时级/天级） |
| **4 台服务器怎么做高可用？** | **按影响面排序**：Nacos/网关必须双节点（挂了全系统不可用）；Redis/MySQL 主从；非核心服务可单点。**不是所有组件都冗余** |
| **大屏响应慢怎么优化？** | 之前是**串行**获取十几个板块（3 秒）→ 改 `CompletableFuture` 并行 + **单板块超时降级**（2s）+ **独立线程池**（不用 commonPool）→ 800ms |
| **服务间调用要注意什么？** | ①必须配超时（不用默认值）②必须配熔断降级（大屏局部降级优于整体白屏）③认证信息用 `RequestInterceptor` 透传，**下游仍要校验** |

## 六、LLM 网关（对应：AI 基础设施，差异化亮点）

### 高频追问

| 面试官会问 | 我要答的 |
|---|---|
| **为什么要建网关？** | 四类问题：重复适配、无容错、无法观测、变更成本高。网关把"N 家供应商"**收敛成一个统一接口** |
| **核心设计是什么？** | 对外只暴露 **OpenAI 兼容协议**——不用为每家写适配，切换成本为零（业务方只改 `base_url` 和 `api_key`） |
| **模型命名怎么处理？** | **双轨制**：前缀（`ark-`/`r4-`/`cc-`）明确指定供应商用于调试对比；通用别名（`deepseek-v4-flash`）用于生产走降级链 |
| **降级链的关键是什么？** | **理解哪些错误才触发降级**：429/5xx/超时/连接失败会；400/401/内容审核不会。<br>参数错误若也降级，会在 4 家白跑一圈，延迟翻 4 倍还是同一个错 |
| **最容易忽略的坑？** | **超时端到端对齐**（客户端 ≥ 网关 240s ≥ 上游）。踩过：客户端 12s 但真实需要 20s，客户端先超时、网关还在处理但结果没人接收 → **功能形同虚设，看日志还一切正常** |
| **上游差异怎么处理？** | 挡在网关内：CommandCode 被 CF 拦需伪装 UA、数智魔方 baseURL 必须带 `/v1`、推理模型的 `reasoning_content` 字段归一化 |
| **怎么监控？** | 调用量/失败率/延迟/**降级次数**。 **降级次数是核心健康指标**，它直接反映链路健康度，比失败率更早暴露问题 |
