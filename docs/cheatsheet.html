一、分库分表

面试官会问我要答的
什么时候该分？先排除：加索引改 SQL → 冷热分离 → 读写分离 → 加缓存。只有"单实例写入撑不住 + 有高基数且查询必带的分片键"才分
分片键怎么选？四原则：①高基数 ②查询必带 ③分布均匀 ④业务不变。通行证选 user_id（查某人历史是高频）；能源大屏选企业维度
跨分片事务？优先改设计消除（需一致的数据同分片）→ 柔性事务（本地消息表+补偿）→ 最后才 Seata
不带分片键的查询？会路由到所有分片再归并，比单表更慢。应对：建映射表，或让 ES 承载多维度检索
深分页？每分片取前 N 条再内存归并。游标分页或延迟关联
全局 ID？雪花算法（有序、对索引友好），注意时钟回拨
扩容？取模扩容要重分布几乎所有数据。应对：预分片、一致性哈希、双倍扩容
关键认知：分库分表解决的是"单实例处理能力上限"，不是"查询慢"的通用解法。它把问题从"一台机器扛不住"转换成"分布式带来的一致性、查询与运维复杂度"。

二、Redis 缓存

面试官会问我要答的
三者怎么区分？穿透=数据不存在（每次绕过缓存打库）；击穿=单个热点 key 失效（并发重建）；雪崩=一大片同时失效或 Redis 挂了
穿透怎么防？①参数校验（最便宜）②缓存空值（必须短过期，否则内存被打满）③布隆过滤器（代价：有误判、不支持删除、需预热同步）
击穿怎么防？①互斥锁重建（代价：响应时间变长、有死锁风险）②逻辑过期（返回旧值+异步更新，代价：短暂脏数据）
雪崩怎么防？①过期时间加随机偏移（成本最低收益最高）②高可用 ③多级缓存 ④熔断降级 ⑤限流
为什么删缓存不更新缓存？更新浪费（写后可能没人读）；并发写时更新顺序可能与库不一致，导致缓存留旧值
为什么先更库再删缓存？反过来时，删除到更新之间若有读请求，会把旧值重新加载进缓存且不会自动纠正
最终兜底？短过期时间——即使中间不一致，最长一个过期周期后自动恢复
我实际的选择（要能说取舍）：参数校验 + 缓存空值（短过期），没用布隆过滤器。理由：key 空间可枚举（用户 ID、设备 ID），攻击者能构造的不存在 key 有限；引入布隆过滤器需要额外预热和同步逻辑，收益不匹配。
面试官想听的不是"我知道布隆过滤器"，而是"我知道什么时候不用它"。

三、MySQL 慢查询

面试官会问我要答的
怎么定位慢 SQL？慢日志（long_query_time 单位是秒，要设小数）；pt-query-digest 按总耗时排序；performance_schema 看 rows_examined/rows_sent 比例
EXPLAIN 看什么？①type（核心 SQL 至少 ref/range，不能 ALL）②key_len（验证联合索引用了几列）③rows × filtered% ④Extra
key_len 怎么算？BIGINT=8、TINYINT=1、INT=4，允许 NULL 再 +1；VARCHAR(n) = 4n+2（utf8mb4）
Extra 哪两个要警惕？Using filesort（额外排序）、Using temporary（临时表）；Using index 是好的（覆盖索引）
哪些写法让索引失效？①索引列上做函数运算 ②隐式类型转换（WHERE varchar_col = 123）③前导模糊 LIKE '%x' ④OR 跨列
!= 会让索引失效吗？不绝对。如果能排除绝大部分数据，优化器可能仍走索引。用 EXPLAIN 验证，不要背结论
深分页怎么优化？①游标分页 ②延迟关联（先用覆盖索引取主键再回表）

四、RabbitMQ

面试官会问我要答的
什么时候不该用 MQ？需同步返回结果、强一致、逻辑本来就简单、延迟要求极高
消息丢失的三个环节？①生产者→Broker（网络抖动）②Broker 内部（未落盘宕机）③消费者处理（失败/ACK 丢失）
分别怎么解决？①publisher-confirm + publisher-returns（Confirm 只保证到交换机，路由失败要用 Returns）②交换机、队列、消息三者都持久化 ③手动 ACK + 区分业务/系统异常
为什么不能用默认 auto ACK？auto 模式下方法返回就 ACK，抛异常也会 ACK，消息就丢了
业务异常和系统异常？业务异常（参数错、状态不符）重试多少次都失败 → 记录后 ACK；系统异常（网络、超时）→ basicNack(requeue=true) 重试
为什么必须做幂等？RabbitMQ 只能保证 at-least-once。"处理成功"和"ACK"是两个动作不可能原子，所以同一条消息可能被投递多次
幂等怎么实现？①唯一 ID + 去重表（去重记录与业务必须同事务）②状态机（UPDATE ... WHERE 旧状态）③Redis 去重（不持久）④业务天然幂等

五、SpringCloud 微服务拆分

面试官会问我要答的
服务按什么拆？优先级：变化频率 > 数据源 > 性能特征 > 团队边界（康威定律）
拆太细/太粗的问题？太细：一个页面调 6 个服务，日志分散无法串联；太粗：等于没拆，无法按模块扩容
为什么单独拆 metric-service？隔离"上游 9 个系统不稳定"这个最大风险源，且它的迭代节奏与其他服务完全不同
异构系统怎么集成？适配器模式统一接入层（REST/DB直连/MQ订阅各实现一个 adapter），业务只依赖接口
指标口径不一致？建指标字典：全局唯一 metric_code + 配置化转换表达式 + 分层更新周期（秒/分钟/小时/天级）
4 台服务器做高可用？按影响面排序：Nacos/网关必须双节点（挂了全系统不可用）；Redis/MySQL 主从；非核心服务可单点。不是所有组件都冗余
大屏响应慢怎么优化？原串行获取十几个板块（3 秒）→ CompletableFuture 并行 + 单板块超时降级（2s）+ 独立线程池（不用 commonPool）→ 800ms

六、LLM 网关（差异化亮点）

面试官会问我要答的
为什么要建网关？四类问题：重复适配、无容错、无法观测、变更成本高。网关把"N 家供应商"收敛成一个统一接口
核心设计？对外只暴露 OpenAI 兼容协议——不用为每家写适配，切换成本为零（业务方只改 base_url 和 api_key）
模型命名？双轨制：前缀（ark-/r4-/cc-）指定供应商用于调试对比；通用别名用于生产走降级链
降级链的关键？理解哪些错误才触发降级：429/5xx/超时/连接失败会；400/401/内容审核不会。
参数错误若也降级，会在 4 家白跑一圈，延迟翻 4 倍还是同一个错
最容易忽略的坑？超时端到端对齐（客户端 ≥ 网关 240s ≥ 上游）。踩过：客户端 12s 但真实需要 20s，客户端先超时、网关还在处理但结果没人接收 → 功能形同虚设，看日志还一切正常
上游差异怎么处理？挡在网关内：CommandCode 被 CF 拦需伪装 UA、数智魔方 baseURL 必须带 /v1、reasoning_content 字段归一化
怎么监控？调用量/失败率/延迟/降级次数。降级次数是核心健康指标，比失败率更早暴露问题
