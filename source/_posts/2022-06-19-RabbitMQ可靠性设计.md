# 背景

为什么会研究这个问题

随着系统拆分，很多原本同步完成的操作开始改成异步。比如订单创建后发积分、发通知、写操作日志，这些逻辑不应该阻塞主流程，于是 RabbitMQ 就进入了架构设计范围。研究可靠性设计，是因为消息队列一旦使用不当，很容易出现“主流程成功了，但后续动作丢了”的问题。

# 问题

遇到了什么情况

最典型的问题是消息丢失和重复消费。生产者以为消息发出去了，但交换机没有正确接收；队列没有持久化，服务重启后消息消失；消费者处理成功但 ack 失败，导致消息重复投递。如果没有可靠性设计，问题往往发生在线上，而且不容易第一时间发现。

# 分析

排查过程

```text
可靠投递链路：
Producer
  -> Exchange
  -> Queue
  -> Consumer
  -> Ack
```

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    listener:
      simple:
        acknowledge-mode: manual
```

排查消息可靠性时，我会把链路拆成四段：生产确认、路由确认、队列持久化、消费确认。任何一段缺失，都可能导致数据不一致。

# 解决方案

具体操作

```java
rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) {
        log.error("message send failed, id={}, cause={}", correlationData.getId(), cause);
    }
});
```

```java
@RabbitListener(queues = "order.point.queue")
public void consume(Message message, Channel channel) throws IOException {
    long tag = message.getMessageProperties().getDeliveryTag();
    try {
        handle(message);
        channel.basicAck(tag, false);
    } catch (Exception e) {
        channel.basicNack(tag, false, true);
    }
}
```

```text
设计补充：
- 业务表增加 message_id 去重
- 失败消息进入死信队列
- 消费失败次数需要监控
- 关键消息保留发送记录
```


# 总结

经验沉淀

RabbitMQ 可靠性不是一个配置能解决的，而是一组机制共同保证。生产确认保证消息发出去，持久化保证消息不因重启丢失，手动 ack 保证消费结果可控，幂等设计保证重复投递不会破坏数据。
