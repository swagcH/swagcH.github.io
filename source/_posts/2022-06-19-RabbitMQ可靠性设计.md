> 写在前面：消息队列最麻烦的故障不是完全不可用，而是“看起来发成功了，业务却没有完成”。生产者、交换机、队列、消费者和业务数据库之间任何一步都可能失败，可靠性必须按链路逐段设计。

## 一次典型的消息故障

订单接口返回成功以后，积分服务没有增加积分。补发消息后积分又加了两次。把日志按 `orderId` 串起来，看到的是：

```text
10:02:11 order created, orderId=20220619001
10:02:11 publish points event, messageId=msg-8f21
10:02:11 no publish confirm log

10:15:32 manual republish, messageId=msg-91a0
10:15:33 consumer success
10:15:33 consumer channel closed before ack
10:15:35 consumer receives message again
```

这里同时出现了两个问题：生产端没有证据证明消息进入 Broker；消费端业务已经成功，但 ack 没有到达 Broker，消息被再次投递。RabbitMQ 默认提供的是“至少一次”方向的能力，重复消息不是异常情况，消费者必须能够承受。

## 1. 先画出完整失败链路

```text
订单数据库事务
  -> Producer 发送
  -> Exchange 接收
  -> Routing Key 匹配 Queue
  -> Queue 保存消息
  -> Consumer 获取消息
  -> 消费者业务数据库事务
  -> Ack 返回 Broker
```

每个箭头都要回答两个问题：

1. 失败以后谁能发现。
2. 发现以后如何重试，并且不会产生重复副作用。

只配置手动 ack，不能解决生产者消息丢失；只开启 Confirm，也不能保证消费者业务执行成功。

## 2. Producer Confirm 证明 Broker 收到了消息

Spring Boot 配置：

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
```

`Confirm` 表示消息是否到达 Exchange，`Return` 表示消息到达 Exchange 后是否因为路由失败而被退回。两者解决的不是同一个问题。

```java
@Component
public class RabbitPublishCallback {

    public RabbitPublishCallback(RabbitTemplate rabbitTemplate) {
        rabbitTemplate.setConfirmCallback((data, ack, cause) -> {
            String messageId = data == null ? "unknown" : data.getId();
            if (ack) {
                log.info("消息到达交换机, messageId={}", messageId);
                return;
            }
            log.error("消息未到达交换机, messageId={}, cause={}", messageId, cause);
        });

        rabbitTemplate.setReturnsCallback(returned ->
            log.error("消息路由失败, replyText={}, exchange={}, routingKey={}",
                returned.getReplyText(), returned.getExchange(), returned.getRoutingKey()));
    }
}
```

不同 Spring AMQP 版本的 Return Callback API 名称有差异，旧版本常见 `setReturnCallback`。升级时应根据实际依赖调整，而不是同时注册两套。

Confirm 成功只代表 Broker 接受了消息，不代表消息已经持久化到磁盘，更不代表消费者处理成功。关键消息要保存 `messageId`、业务主键、发送状态和重试次数，不能只写一行普通日志。

## 3. 数据库成功、消息发送失败怎么办

下面的代码存在事务缝隙：

```java
@Transactional
public void createOrder(CreateOrderCommand command) {
    orderRepository.save(command);
    rabbitTemplate.convertAndSend("order.exchange", "order.created", command);
}
```

数据库事务提交后，进程可能在消息发送前崩溃；也可能消息已经发出，数据库事务却回滚。普通本地事务无法同时覆盖 MySQL 和 RabbitMQ。

一种相对容易落地的方式是本地消息表，也叫 Transactional Outbox：

```sql
CREATE TABLE mq_outbox (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    message_id VARCHAR(64) NOT NULL,
    topic VARCHAR(128) NOT NULL,
    business_key VARCHAR(128) NOT NULL,
    payload TEXT NOT NULL,
    status VARCHAR(20) NOT NULL,
    retry_count INT NOT NULL DEFAULT 0,
    next_retry_time DATETIME NULL,
    created_at DATETIME NOT NULL,
    UNIQUE KEY uk_message_id (message_id),
    KEY idx_status_retry (status, next_retry_time)
);
```

订单和待发送消息在同一个数据库事务里保存：

```text
事务开始
  -> 写 order
  -> 写 mq_outbox，状态 INIT
事务提交
```

独立任务扫描 `INIT` 和可重试记录，发送到 RabbitMQ；Confirm 成功后更新为 `SENT`。如果任务进程崩溃，下一轮仍会继续发送，因此消费者必须幂等。

扫描任务还要考虑并发抢占、批次大小和失败退避，不能每秒全表扫描。数据量大时可以进一步使用 CDC 读取 Outbox 变更，但复杂度也会增加。

## 4. Exchange、Queue 和消息都要持久化

```java
@Bean
public DirectExchange orderExchange() {
    return new DirectExchange("order.exchange", true, false);
}

@Bean
public Queue pointsQueue() {
    return QueueBuilder.durable("order.points.queue")
        .deadLetterExchange("order.dlx")
        .deadLetterRoutingKey("order.points.dead")
        .build();
}
```

交换机和队列设置 durable，只保证定义在 Broker 重启后仍存在。消息本身也需要持久化。Spring AMQP 常规转换器默认会发送持久化消息，但自定义 `MessageProperties` 时要确认 delivery mode。

即使消息持久化，Broker 异常时仍可能存在数据损失窗口。对高可靠要求场景，需要结合镜像队列或 Quorum Queue、磁盘和集群策略评估，不能把“durable=true”理解成绝对不丢。

## 5. 消费者使用手动 Ack

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        prefetch: 20
        concurrency: 2
        max-concurrency: 8
```

消费代码：

```java
@RabbitListener(queues = "order.points.queue")
public void consume(Message message, Channel channel) throws IOException {
    long deliveryTag = message.getMessageProperties().getDeliveryTag();
    String messageId = message.getMessageProperties().getMessageId();
    try {
        pointsService.handle(messageId, message.getBody());
        channel.basicAck(deliveryTag, false);
    } catch (IllegalArgumentException ex) {
        // 参数永久错误，不再放回原队列，交给死信队列处理
        channel.basicNack(deliveryTag, false, false);
    } catch (Exception ex) {
        // 是否重回队列应由统一重试策略决定，避免无限快速重投
        channel.basicNack(deliveryTag, false, false);
    }
}
```

原来的 `basicNack(tag, false, true)` 会把异常消息立即放回队列。如果错误一直存在，消费者会高速重复读取同一条消息，CPU、日志和下游压力都会升高。更稳妥的方式是有限次数重试、逐步退避，超过次数后进入死信队列。

## 6. 幂等是消费端的核心

积分增加属于有副作用操作。同一个 `messageId` 再来一次，不能再次增加积分。

```sql
CREATE TABLE mq_consume_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    consumer_name VARCHAR(64) NOT NULL,
    message_id VARCHAR(64) NOT NULL,
    business_key VARCHAR(128) NOT NULL,
    consumed_at DATETIME NOT NULL,
    UNIQUE KEY uk_consumer_message (consumer_name, message_id)
);
```

消费记录和业务更新放在同一个本地事务：

```text
事务开始
  -> 插入消费记录
  -> 唯一键冲突：说明已处理，直接返回成功
  -> 增加积分
事务提交
  -> Ack
```

不能先在 Redis 判断“是否消费过”，再更新 MySQL。判断和业务写入不在同一个事务里，中间失败仍会产生不一致。Redis 可以做快速过滤，但数据库唯一约束才是最后防线。

业务本身有天然唯一键时，也可以使用业务表约束，例如一个订单只能生成一条积分流水。幂等键要和业务动作绑定，而不是简单使用时间戳。

## 7. 重试要区分错误类型

```text
瞬时错误：网络抖动、数据库短暂不可用，可以有限重试
永久错误：参数错误、业务对象不存在，重试没有意义
未知错误：进入人工可观察队列，保留上下文
```

建议的重试节奏可以是 10 秒、1 分钟、5 分钟，而不是立即连续三次。具体间隔要结合业务时效。死信消息至少保存：messageId、原交换机、原路由键、异常、失败次数和首次失败时间。

恢复死信时不能直接把整个队列一次性重投。先修复根因，抽样验证，再限速回放，同时继续检查幂等记录和下游容量。

## 8. 顺序消息不要只依赖队列顺序

单队列、单消费者可以保持较强的消费顺序，但吞吐和可用性会受限制。多消费者、重试、死信回放都会打乱业务事件顺序。

对同一个订单的状态事件，可以：

- 使用订单 ID 做分片键，让同一订单进入同一分片队列。
- 在消费者校验业务版本号，只接受期望的状态迁移。
- 对乱序事件暂存或丢弃，并记录告警。

最终仍要靠业务状态机保护，不能只相信消息到达顺序。

## 9. 监控哪些指标

```text
生产端：发送量、Confirm 失败、Return 数量、Outbox 积压和重试次数
Broker：连接数、Channel、磁盘、内存、Queue Ready、Unacked
消费端：成功率、处理耗时、重试数、死信数、幂等命中数
业务端：订单成功但积分缺失等对账差异
```

只监控 RabbitMQ 进程存活不够。`Ready` 持续增长说明消费者跟不上，`Unacked` 很高可能是处理慢、prefetch 过大或消费者卡住。

## 10. 一次可靠性演练

上线前可以按顺序做小范围演练：

1. 使用错误 Routing Key，验证 Return 和发送记录。
2. 暂停消费者，验证队列持久化和积压告警。
3. 消费业务成功后，在 ack 前主动抛错，验证幂等。
4. 制造永久异常，确认不会无限 requeue。
5. 修复后限速回放死信，核对业务结果。

演练只能在隔离环境或得到授权的窗口执行，不能为了验证可靠性直接终止生产 Broker。

## 复盘结论

消息可靠性不是“绝不重复、绝不丢失”的一句承诺，而是一条可验证的证据链：生产端有 Outbox 和 Confirm，Broker 有持久化与监控，消费端有事务、幂等、有限重试和死信，业务侧还有对账。

系统允许重复投递，但不能允许重复产生业务结果；系统允许短暂延迟，但不能让失败消息永远不可见。做到这两点，消息队列才真正承担了异步解耦，而不是把故障藏到了另一个进程里。
