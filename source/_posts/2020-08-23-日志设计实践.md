我曾经排查过一个支付回调问题，日志里有几千行“处理失败”，却没有订单号、阶段和异常堆栈。日志数量不少，但没有一行能够把请求和业务结果连起来。

从那以后，我判断一条日志是否有价值，不再看它写了多少内容，而是看它能不能回答：发生了什么、影响哪个对象、进行到哪一步、结果是什么、下一步去哪里查。

## 反例一：只写一句“操作失败”

```java
try {
    orderService.create(request);
} catch (Exception exception) {
    log.error("创建订单失败");
}
```

这段日志有三个问题：

1. 没有业务标识，无法找到受影响订单。
2. 没有异常对象，丢失类型和调用栈。
3. 捕获后没有继续抛出，调用方可能收到成功结果。

改造时先明确异常策略，再记录必要上下文：

```java
try {
    orderService.create(request);
} catch (BusinessException exception) {
    log.warn("order_create_rejected userId={} reasonCode={}",
            request.getUserId(), exception.getCode());
    throw exception;
} catch (Exception exception) {
    log.error("order_create_failed userId={} requestId={}",
            request.getUserId(), request.getRequestId(), exception);
    throw new SystemException("ORDER_CREATE_FAILED", exception);
}
```

业务拒绝是可预期结果，使用 `WARN` 并记录原因码；未知异常使用 `ERROR` 和完整堆栈。不要在每一层重复打印同一个异常，通常由最了解业务上下文的一层记录一次，再由统一异常处理转换响应。

## 反例二：把对象整体序列化

```java
log.info("login request={}", json.toJson(loginRequest));
```

看起来省事，实际上可能把密码、手机号、Token 和大段请求体写入日志。对象增加字段后，日志风险还会悄悄扩大。

更稳妥的方式是使用字段白名单：

```java
log.info("login_attempt accountType={} tenantId={} clientIp={}",
        request.getAccountType(),
        request.getTenantId(),
        maskIp(clientIp));
```

默认不记录这些内容：

```text
密码、验证码、Cookie、Authorization
身份证号、银行卡号、完整手机号和邮箱
数据库连接密码、密钥、签名原文
文件正文、二进制内容、超长 SQL 参数
```

确需定位单个对象时，可以记录不可逆摘要或内部业务编号，不要用敏感原文换取短期便利。

## 先定义一条业务事件

自由文本很适合阅读，但不利于检索和统计。我会让关键日志具备相对稳定的字段：

```text
timestamp   level   service   env
event       traceId requestId
userId      orderId
result      reasonCode
costMs      exception
```

例如：

```text
event=order_submit
traceId=7f94c892a0d1
orderId=O202008230018
userId=10027
result=SUCCESS
costMs=84
```

`event` 表示稳定事件名，`result` 表示结果，`reasonCode` 表示可分类原因。人可以读懂，日志平台也能按成功率和耗时聚合。

字段命名要统一。一个服务写 `orderNo`，另一个写 `order_id`，第三个放进一段中文消息，跨服务查询会非常痛苦。

## 级别是一种处置约定

我用“谁需要行动”来判断级别：

| 级别 | 含义 | 示例 |
| --- | --- | --- |
| `ERROR` | 当前请求失败，通常需要排查或告警 | 数据库不可用、未知异常 |
| `WARN` | 可恢复或可预期异常，需要观察趋势 | 限流、降级、业务拒绝 |
| `INFO` | 关键生命周期和业务结果 | 服务启动、订单创建完成 |
| `DEBUG` | 开发排查细节，生产默认关闭 | 分支判断、中间结果 |
| `TRACE` | 高频且极细粒度信息 | 循环内部或协议细节 |

用户密码错误不应每次都打 `ERROR`；数据库连接失败也不该只打 `INFO`。级别混乱会让告警失真，最终大家只能忽略日志。

## 在入口建立 traceId

一条请求经过多个类甚至多个服务时，需要一个共同标识。Spring Boot 项目可以在过滤器中放入 MDC：

```java
public class TraceIdFilter extends OncePerRequestFilter {

    private static final String TRACE_ID = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {
        String traceId = request.getHeader("X-Trace-Id");
        if (traceId == null || traceId.trim().isEmpty()) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }

        try {
            // 放入 MDC 后，日志格式可以自动输出 traceId
            MDC.put(TRACE_ID, traceId);
            response.setHeader("X-Trace-Id", traceId);
            filterChain.doFilter(request, response);
        } finally {
            // 线程会被容器复用，必须清理，避免串到下一次请求
            MDC.remove(TRACE_ID);
        }
    }
}
```

日志格式中加入 `%X{traceId}` 后，同一请求的日志就能串起来。调用下游服务、发送消息时还要显式传递这个标识；仅在当前线程生成，并不能自动穿过 HTTP、MQ 和异步线程池。

## 异步任务容易丢上下文

MDC 基于线程上下文，提交到线程池后通常不会自动复制。可以在任务包装器中保存和恢复：

```java
public Runnable withMdc(Runnable task) {
    Map<String, String> context = MDC.getCopyOfContextMap();
    return () -> {
        try {
            if (context != null) {
                MDC.setContextMap(context);
            }
            task.run();
        } finally {
            MDC.clear();
        }
    };
}
```

这段写法兼容 JDK 8。实际项目中可以放进统一的 `TaskDecorator` 或线程池封装，避免每个业务方法自行复制。

## 记录入口和出口，但控制粒度

不是每个方法都需要“开始、结束”两条日志。适合记录的边界包括：

- 外部 HTTP 请求进入和完成。
- 消息生产、投递确认、消费和确认。
- 定时任务开始、处理数量和结束。
- 重要状态迁移。
- 外部依赖调用的结果与耗时。

一个请求结束日志可以同时承担访问审计和性能观察：

```text
event=http_request_completed
method=POST
path=/api/orders
status=201
costMs=126
traceId=7f94c892a0d1
```

路径应使用模板 `/api/orders/{id}`，而不是把每个具体 ID 当成新维度，否则统计维度会无限增长。

## 异常日志保留最有用的上下文

异常堆栈说明“代码在哪里失败”，业务字段说明“谁失败”。两者缺一不可，但上下文要有限：

```java
log.error(
        "payment_callback_failed paymentNo={} orderId={} callbackType={}",
        paymentNo,
        orderId,
        callbackType,
        exception
);
```

不要通过字符串拼接输出异常：

```java
// 错误：通常只得到 exception.toString()，没有完整调用栈
log.error("callback failed: " + exception);
```

也不要既在 Repository、Service、Controller 各打一遍相同堆栈，又让全局异常处理再打一遍。重复日志会放大存储量，还会让一次故障看起来像四次。

## 日志本身也有成本

高并发接口每次打印大对象，会消耗序列化 CPU、磁盘 IO 和网络带宽。需要关注：

1. 热路径是否有高频 `INFO`。
2. 参数构造是否在日志关闭时仍会执行。
3. 单行是否过大，多行堆栈是否失控。
4. 日志文件是否按大小和日期滚动。
5. 保留周期是否符合排障与合规要求。

对高频成功事件，可以用指标统计总量，仅对失败和采样请求保留详细日志。日志、指标和链路追踪各有职责，不应让日志承担全部可观测性。

## 用反例驱动一次日志 Review

每次评审我会抽查下面几项：

```text
[ ] 关键事件能否按 traceId 和业务编号检索
[ ] 事件名、字段名和结果码是否稳定
[ ] 异常是否只在合适层级记录一次
[ ] ERROR 是否真的需要行动
[ ] 是否泄露敏感字段或完整请求体
[ ] 异步和跨服务场景是否传递上下文
[ ] 高频日志是否影响性能和存储
[ ] 滚动、保留和告警规则是否匹配
```

一条好日志应该像交接给值班同事的一句完整说明：哪件事失败、影响谁、证据在哪里。只有真正出问题时还能用得上的日志，才值得在正常运行的每一分钟里被写入。
