这是一段磁盘告警值班记录。表面现象是根分区 100%，但真正占用空间的文件已经被删除，因此 `du` 怎么找都对不上 `df`。

磁盘爆满时最危险的动作，是为了尽快腾空间直接删除不了解用途的大文件。值班处理应先确认挂载点和增长来源，再由对应负责人选择释放方式。

## 01:17，告警与业务现象

```text
host: app-02
mount: /
usage: 100%
available: 0

应用错误：
java.io.IOException: No space left on device
```

订单服务仍能处理部分查询，但日志无法写入，临时文件创建失败。我们先暂停该节点的新发布和批处理任务，并确认其他实例有足够容量承接流量。

## 01:20，先确认是哪一种“满”

```bash
df -hT
df -ih
```

结果：

```text
Filesystem  Type  Size  Used Avail Use% Mounted on
/dev/vda1   xfs    40G   40G     0 100% /

Filesystem  Inodes IUsed IFree IUse% Mounted on
/dev/vda1     20M  210K 19.8M    2% /
```

容量用完，inode 很充足，因此不是海量小文件。后续查找始终限制在根文件系统，避免进入其他挂载点：

```bash
du -xhd1 / 2>/dev/null | sort -h
du -xhd1 /var 2>/dev/null | sort -h
```

`du` 合计只有约 14G，而 `df` 显示已用 40G，差了 20 多 G。此时继续向下找目录意义不大，应该解释两种统计为什么不同。

## 01:24，df 与 du 的差值

`df` 从文件系统块使用情况统计，只要块还被占用就会计入；`du` 从目录树遍历可见文件。一个文件被删除后，如果进程仍持有文件描述符：

```text
目录项已经消失 -> du 看不到
进程仍在写入     -> 磁盘块没有释放
进程关闭描述符   -> 空间才真正归还
```

检查已删除但仍被占用的文件：

```bash
lsof +L1
```

输出中有一条：

```text
java  1842  app  17w  REG  253,1  21474836480  /var/log/order/app.log (deleted)
```

Java 进程仍持有约 20G 的已删除日志。原因已经足以解释 `df` 和 `du` 的差值。

## 01:27，为什么文件删了还在增长

当天有人手工删除了正在写入的 `app.log`，以为可以立即释放空间。Linux 删除的是文件名与 inode 的关联，进程已经打开的描述符仍指向原 inode。日志框架不知道路径消失，继续往同一个文件写。

这也是为什么不建议把 `rm` 当日志轮转。删除命令成功，不代表空间已经释放。

## 01:30，受控释放文件描述符

可选方式按优先级评估：

1. 让日志框架主动滚动并重新打开文件。
2. 平滑重载支持重开日志的进程。
3. 摘流后重启单个应用实例。
4. 极端情况下由负责人评估是否截断对应描述符。

本次 Java 应用没有可靠的重开信号，我们选择：

```text
从负载均衡摘除 app-02
等待存量请求结束
保存必要日志与进程证据
正常停止服务
确认旧描述符消失
启动服务并通过健康检查
逐步恢复流量
```

摘流和重启会改变生产容量，必须由有权限的值班人员执行，并确认其他实例健康。不要为了释放文件直接 `kill -9`；强制终止可能中断事务，也不利于保留现场。

进程退出后再次检查：

```bash
df -hT /
lsof +L1
```

根分区使用率从 100% 降到 48%，应用健康检查和写入恢复。

## 如果 du 找到的就是真实大文件

不能因为“日志通常可删”就直接处理。先把候选文件按用途分类：

```text
应用日志：确认保留周期、采集状态和当前写入文件
临时文件：确认是否被任务使用
数据库文件：必须交给数据库机制管理
容器数据：通过容器运行时清理策略处理
Core Dump：确认是否已留存排障证据
发布产物：确认当前和回退版本
```

数据库数据、binlog、Docker 存储目录都不应通过手工删除底层文件释放空间。错误删除可能让服务无法恢复。

应急时优先处理已经确认可再生、已归档、不会影响运行的文件，并记录删除范围。所有破坏性操作都需要责任人和复核人。

## 把日志滚动交给应用

本次根因是日志没有稳定滚动，手工处理又删除了当前活跃文件。Spring Boot 使用 Logback 时，可以按日期和大小滚动：

```xml
<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>/var/log/order/app.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
        <fileNamePattern>/var/log/order/app.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
        <maxFileSize>200MB</maxFileSize>
        <maxHistory>14</maxHistory>
        <totalSizeCap>8GB</totalSizeCap>
    </rollingPolicy>
    <encoder>
        <pattern>%d %-5level [%X{traceId}] %logger - %msg%n</pattern>
    </encoder>
</appender>
```

数值要根据流量、磁盘容量、采集延迟和合规保留要求确定。配置 `totalSizeCap` 前，先确认当前 Logback 版本支持且 `maxHistory` 已设置。

如果统一使用 `logrotate`，应用必须配合重开文件；`copytruncate` 虽然不要求进程重开，但复制和截断之间可能丢少量日志，高吞吐场景要评估。不要让应用滚动和系统滚动同时管理同一个文件。

## 告警不能等到 100%

磁盘容量以增长速度而不是单一百分比判断更有意义：

```text
预警：使用率 75%，检查趋势
高危：使用率 85% 或预计 24 小时内耗尽
紧急：使用率 95% 或关键写入失败
```

同时监控：

- inode 使用率。
- 每小时增长量和预计耗尽时间。
- 日志写入速率。
- 已删除文件占用。
- 容器层和宿主机各自容量。

阈值需要按文件系统用途设置。一个 2TB 数据盘的 90% 剩余空间，与 20G 根分区的 90% 完全不同。

## 值班记录最后写下什么

```text
直接原因：Java 持有已删除的 20G 日志文件
触发原因：当前日志被手工 rm，应用未重开描述符
系统缺口：无大小上限、告警过晚、缺少标准处理手册
恢复动作：单实例摘流并正常重启
验证：磁盘 48%，日志可写，订单接口正常
后续：启用滚动策略、增加趋势告警、禁止手工删除活跃日志
```

这次经历让我记住：磁盘满时，`df` 回答文件系统还剩多少，`du` 回答目录树里什么可见，两者对不上本身就是重要证据。先解释差值，再释放空间，比从最大的目录开始盲删可靠得多。
