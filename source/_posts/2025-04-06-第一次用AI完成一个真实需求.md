这是我第一次有意识地让 AI 参与一个完整需求，而不是只让它解释报错或补一个工具方法。

需求不大：在工单列表增加“最近跟进时间”筛选，并让导出接口使用相同条件。真正做下来，AI 最有价值的部分不是写代码，而是帮助我快速梳理分散的调用链；最危险的部分也不是语法错误，而是它会非常自然地替需求补上一个没有确认过的定义。

下面按当天的开发时间线还原整个过程。项目和数据均做了简化，重点是我与 AI 怎样分工，以及哪些地方发生了返工。

<!-- more -->

## 09:12，拿到一句看似明确的需求

产品描述是：

```text
工单列表增加最近跟进时间筛选，导出也要支持。
```

我本来准备直接搜索列表接口，让 AI 帮我加两个时间参数。提交之前多问了一句：“最近跟进时间是最后一条跟进记录的创建时间，还是工单表上的 `last_follow_at`？”

答案是前者，而且还有两个规则：

- 没有跟进记录的工单不命中任何时间范围；
- 开始时间包含，结束时间按次日零点之前处理。

这两个规则如果没问，AI 大概率会根据字段名使用 `last_follow_at`，本地代码仍然能编译，查询结果却会悄悄出错。

我先把需求改写成状态明确的任务卡：

```text
目标：列表与导出支持按最后一条跟进记录的 created_at 筛选。
输入：followStartDate、followEndDate，格式 yyyy-MM-dd，可单独传。
边界：开始日 00:00:00 包含；结束日转换为下一日 00:00:00，使用小于比较。
空记录：无跟进记录的工单不命中。
兼容：不传参数时，SQL 与响应保持原行为。
完成：列表和导出共用条件，Mapper 集成测试覆盖五个边界用例。
```

这是当天最值得的一步，虽然一行代码都没有产生。

## 09:35，让 AI 先找路，不要先写

我让 AI 在仓库中回答四个问题：

1. 列表接口与导出接口分别从哪里进入；
2. 两者最终是否复用同一个查询对象；
3. 工单和跟进记录通过什么字段关联；
4. 当前项目的日期范围条件通常怎样写。

它搜索后给出的调用图是：

```text
TicketController#page
  -> TicketQueryService#page
  -> TicketMapper#selectPage

TicketExportController#export
  -> TicketExportService#export
  -> TicketMapper#selectForExport

两个 Mapper 方法都接收 TicketQueryCondition
跟进表通过 ticket_id 关联
```

同时找到另一个“完成时间”筛选，项目约定在 Java 层把日期转换成左闭右开的 `LocalDateTime` 区间，再传给 Mapper。

这一步节省了我在目录中来回跳转的时间。更重要的是，它用真实代码否定了我最初的猜测：列表和导出并没有共用 SQL，只共用条件对象，因此验收范围至少涉及两个 Mapper 查询。

## 10:05，第一次计划里出现了过度设计

AI 建议：

```text
新增 FollowTimeRange 值对象
新增 TicketFollowQueryDomainService
新增 FollowRecordRepository
统一重构列表与导出查询
```

从结构上看很完整，但对于一个已有项目中的两个筛选条件，改动太大。新增领域层会让本次需求同时承担架构迁移，Review 和回归范围都被放大。

我把范围压回到四个文件：

```text
TicketQueryCondition.java
TicketQueryService.java
TicketMapper.xml
TicketMapperIntegrationTest.java
```

其中 XML 内有两个查询片段；导出服务继续复用同一个条件构造方法。原则是先完成可验证的业务变化，不借小需求清理整个项目。

## 10:32，日期边界第一次写错

AI 生成的转换逻辑是：

```java
condition.setFollowEndTime(endDate.atTime(23, 59, 59));
```

这在秒精度数据库中看起来可用，但会漏掉带毫秒或微秒的记录。项目中已有的正确约定是左闭右开：

```java
private void applyFollowTimeRange(TicketQueryCondition condition,
                                  LocalDate startDate,
                                  LocalDate endDate) {
    if (startDate != null) {
        condition.setFollowStartTime(startDate.atStartOfDay());
    }
    if (endDate != null) {
        // 使用次日零点作为排他上界，避免丢失结束日最后一秒的小数精度记录
        condition.setFollowEndExclusive(endDate.plusDays(1).atStartOfDay());
    }
}
```

对应 SQL：

```xml
<if test="followStartTime != null">
  AND latest_follow.created_at <![CDATA[>=]]> #{followStartTime}
</if>
<if test="followEndExclusive != null">
  AND latest_follow.created_at <![CDATA[<]]> #{followEndExclusive}
</if>
```

这次错误让我看到一个规律：AI 很容易给出“常见答案”，而项目已有约定才是更可靠的局部答案。让它搜索相邻实现，比在提示词中反复强调“考虑边界”有效。

## 11:10，SQL 能运行，但语义不对

第一版 SQL 使用普通关联：

```sql
LEFT JOIN ticket_follow_record follow_record
  ON follow_record.ticket_id = ticket.id
```

再对 `follow_record.created_at` 加时间条件。问题是这会匹配“任意一条在区间内的跟进”，而需求要求“最后一条跟进在区间内”。

例如一张工单有两次跟进：

```text
2025-03-01  第一次跟进
2025-04-03  最近一次跟进
```

筛选三月份时，普通关联会返回它；按需求，最近跟进发生在四月，不应该返回。

最终 SQL 先聚合每张工单的最新时间：

```sql
LEFT JOIN (
    SELECT ticket_id, MAX(created_at) AS latest_follow_at
    FROM ticket_follow_record
    WHERE deleted = 0
    GROUP BY ticket_id
) latest_follow ON latest_follow.ticket_id = ticket.id
```

筛选条件作用在 `latest_follow_at` 上。AI 随后提醒我检查执行计划，因为全表聚合可能成为新瓶颈。测试库数据量不大时，正确性会掩盖性能风险。

查看索引后，跟进表只有单列 `ticket_id` 索引。我们补充了 `(ticket_id, deleted, created_at)` 联合索引的数据库变更，并在接近生产分布的测试数据上对比执行计划。这个索引不是由 AI 一句话决定的，而是由查询模式、数据分布和执行计划共同决定。

## 13:40，测试暴露了两个遗漏

我先让 AI 根据任务卡列测试矩阵，再由它补测试数据。最终有六个用例：

| 用例 | 预期 |
| --- | --- |
| 不传时间 | 保持原列表数量 |
| 只传开始日 | 包含开始日零点后的记录 |
| 只传结束日 | 不包含次日零点记录 |
| 同时传开始和结束 | 命中闭日期范围 |
| 一张工单多条跟进 | 只按最新一条判断 |
| 无跟进记录 | 不命中时间筛选 |

第一次执行时，两个测试失败。

第一个失败来自导出。虽然 `TicketQueryCondition` 增加了字段，但导出 Controller 使用另一个请求对象，转换时漏传了两个参数。调用链分析做过一次，并不代表实现阶段不会漏掉转换边界。

第二个失败来自删除数据。最新时间子查询忘记过滤逻辑删除记录，导致一条已撤回的跟进成为“最新记录”。需求卡没有写这个规则，是项目的数据约定补全了它。

这两个失败都不是坏事。测试在上线前把“看起来完整”变成了具体反例。

## 15:20，我自己做了一轮只看差异的 Review

AI 已经解释过每个改动，但我关闭对话，只阅读版本差异。检查顺序是：

```text
有没有超出需求的文件
请求参数是否向后兼容
日期转换是否只有一处
列表和导出语义是否一致
SQL 是否处理逻辑删除
是否引入全表扫描或重复行
测试是不是在验证结果，而不是复述实现
日志里有没有敏感筛选条件
```

这一轮删除了一段 AI 主动添加的调试日志。它会打印整个查询条件，其中包含创建人手机号。日志对排查有用，但不能把请求对象直接序列化后全部输出。

我还把模型生成的 `buildCondition` 复制代码合并回已有转换方法，避免列表和导出以后再次分叉。

## 16:30，提测不是终点

提测前完成了三类验证：

1. Mapper 集成测试证明 SQL 边界；
2. Service 单元测试证明日期转换和参数传递；
3. 测试环境手工比较列表与导出结果。

发布清单增加了两项：观察慢查询中该 SQL 的扫描行数，以及确认新增索引构建不会阻塞高峰写入。数据库变更选择在低峰执行，并保留取消条件。

上线后用不传参数、单边界和完整区间各验证一次，再观察接口 P95、数据库 CPU 与慢查询。没有异常，才把任务标记完成。

## 当天的投入到底有没有变少

如果只看编码时间，AI 确实快：定位文件、生成测试骨架和整理 SQL 候选，大约节省了一到两个小时。但总交付时间没有缩短一半，因为需求确认、性能验证、数据安全和上线观察仍然必须由人完成。

我把当天的工作粗略拆开：

| 工作 | AI 的作用 | 人的责任 |
| --- | --- | --- |
| 调用链梳理 | 搜索和摘要很快 | 判断摘要是否真实 |
| 方案设计 | 提供多个候选 | 控制改动范围 |
| 代码生成 | 完成机械修改 | 检查项目约定与边界 |
| 测试 | 生成矩阵和骨架 | 确认测试能证明需求 |
| SQL 优化 | 提醒风险、辅助读计划 | 根据数据与生产约束决策 |
| 上线 | 整理清单 | 承担发布与回滚责任 |

第一次完整使用 AI 交付需求后，我没有得到“以后可以少看代码”的结论。相反，我更清楚哪些工作不能被流畅的输出跳过。

AI 把从问题到候选方案的距离缩短了，但从候选方案到可信改动，仍然需要需求边界、项目事实、自动测试和人工判断。这四样东西在场时，它是效率很高的搭档；缺任何一项，速度都可能只是更快地走向返工。
