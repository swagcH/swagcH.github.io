![Redis缓存穿透解决方案技术图](/images/posts/2021/redis-penetration-cover.svg)

缓存穿透指查询一个本来就不存在的数据：Redis 每次未命中，请求继续访问数据库，数据库也返回空。只要请求使用不同的无效 ID，普通缓存几乎没有保护作用。

为了把不同方案的效果看清楚，我在隔离环境做了四轮攻防实验。压测数据均为构造数据，不针对真实线上服务。

## 实验规则

商品查询接口：

```text
GET /api/products/{productId}
```

数据规模和请求模型：

```text
有效商品：100 万
压测流量：2000 req/s
有效 ID：20%
不存在但格式合法的 ID：60%
格式非法 ID：20%
数据库连接池上限：80
```

基础读取逻辑：

```java
public Product query(Long productId) {
    String key = "product:" + productId;
    Product cached = redisRepository.get(key);
    if (cached != null) {
        return cached;
    }

    Product product = productRepository.findById(productId);
    if (product != null) {
        redisRepository.set(key, product, Duration.ofMinutes(30));
    }
    return product;
}
```

不存在的数据不进入缓存，因此每次都会查库。

## 第一轮：没有额外防护

结果：

| 指标 | 正常基线 | 无效流量进入后 |
| --- | ---: | ---: |
| Redis 命中率 | 94% | 19% |
| 数据库 QPS | 120 | 1,640 |
| 接口 P99 | 85ms | 1.8s |
| 数据库连接等待 | 0 | 47 |

数据库 CPU 尚未完全打满，但连接等待已经影响正常商品查询。穿透的危险不只在攻击，爬虫错误、客户端循环重试、过期链接也可能制造相同流量。

## 第二轮：在入口拒绝不可能的请求

第一层防护不需要 Redis。根据业务约束检查：

```text
ID 是否为正整数
长度是否在合法范围
租户和数据范围是否有效
接口调用频率是否异常
批量查询数量是否超过上限
```

Controller 层只负责格式校验，用户是否有权访问某商品仍由业务层判断。不能因为引入缓存就绕过权限。

```java
public ProductView queryProduct(long productId, UserContext user) {
    if (productId <= 0 || productId > MAX_PRODUCT_ID) {
        throw new BusinessException("INVALID_PRODUCT_ID");
    }
    permissionService.checkTenantAccess(user);
    return productQueryService.query(productId, user.getTenantId());
}
```

格式校验挡住了 20% 请求，数据库 QPS 降到约 1,240，但格式合法的随机 ID 仍然会穿透。

这里的 `MAX_PRODUCT_ID` 只能在业务编号确有稳定上界时使用。若 ID 来自分布式算法或外部系统，不应凭当前最大值拒绝未来合法数据。

## 第三轮：短时间缓存“确实不存在”

数据库返回空时写一个特殊标记：

```java
public Product query(Long productId) {
    String key = buildKey(productId);
    String cached = redisRepository.getString(key);

    if (NULL_VALUE.equals(cached)) {
        return null;
    }
    if (cached != null) {
        return productSerializer.deserialize(cached);
    }

    Product product = productRepository.findById(productId);
    if (product == null) {
        // 空值只缓存较短时间，避免商品刚创建后长期不可见
        long ttlSeconds = 60 + ThreadLocalRandom.current().nextInt(60);
        redisRepository.setString(key, NULL_VALUE, ttlSeconds);
        return null;
    }

    redisRepository.setString(
            key,
            productSerializer.serialize(product),
            1800
    );
    return product;
}
```

空值缓存适合重复查询同一批无效 ID，例如错误链接或客户端重试。本次压测把无效 ID 集合限制在 1 万个，第二遍请求后数据库 QPS 降到 180 左右。

但如果攻击者每次生成全新 ID，空值缓存仍会不断创建新 key。还要防止 Redis 被大量无效键占满：

- 空值 TTL 明显短于正常数据。
- key 使用固定格式，不直接拼接任意长参数。
- 监控空值 key 创建速率。
- 对调用方和来源做限流。

商品创建后应主动删除对应空值缓存，否则在 TTL 到期前会得到“商品不存在”。

## 第四轮：布隆过滤器挡住大范围不存在 ID

布隆过滤器能快速回答“这个 ID 一定不存在”或“可能存在”。它允许少量误判存在，但不会把真实存在的 ID 判断为不存在，前提是数据同步正确。

查询顺序调整为：

```text
参数与权限校验
  -> Redis 查询
  -> Bloom 判断
       一定不存在：直接返回空
       可能存在：查询数据库
  -> 回填正常值或短期空值
```

为什么先查 Redis 再查 Bloom？热点数据已经在 Redis 时，直接返回最快；Bloom 主要保护缓存未命中的后续数据库路径。

示意代码：

```java
public Product queryWithBloom(Long productId) {
    ProductCacheValue cacheValue = cacheRepository.find(productId);
    if (cacheValue.isHit()) {
        return cacheValue.getProduct();
    }
    if (cacheValue.isNullMarker()) {
        return null;
    }

    if (!productBloomFilter.mightContain(productId)) {
        return null;
    }

    Product product = productRepository.findById(productId);
    cacheRepository.saveResult(productId, product);
    return product;
}
```

加入布隆过滤器后：

| 指标 | 无防护 | 参数校验 | 空值缓存 | 多层防护 |
| --- | ---: | ---: | ---: | ---: |
| 数据库 QPS | 1,640 | 1,240 | 180 | 126 |
| P99 | 1.8s | 1.3s | 120ms | 92ms |
| Redis 新增空 key/s | 0 | 0 | 43 | 3 |

“多层防护”包含参数校验、调用方限流、Bloom 和空值缓存。数据库 QPS 接近正常基线，但仍保留少量误判和真实数据查询。

## 布隆过滤器的维护比接入更难

实现时必须回答：

```text
初始数据如何加载
新商品怎样实时加入
删除商品如何处理
过滤器容量和误判率是多少
重建期间怎样切换
同步失败如何告警
```

普通布隆过滤器不支持可靠删除。商品下线后保留为“可能存在”只会多查一次数据库，可以接受；错误删除一个仍存在的商品则可能直接返回空，不能接受。

容量估小后误判率会持续上升。重建时可以生成新版本，完成数据校验后原子切换，不要在原过滤器上边清边写。

## 限流保护的是最后边界

即使 Bloom 正常，也要限制异常来源。限流维度可以包括：

- 用户或应用凭证。
- 租户。
- 客户端 IP，作为辅助而非唯一身份。
- 接口和资源类型。
- 单次批量大小。

超限时返回明确错误码和重试时间，不要让客户端立即无限重试。对于登录前公开接口，还需要网关防护和行为识别。

限流阈值根据正常峰值与容量测试确定。过低会伤害真实用户，过高则无法保护数据库。

## 别把缓存击穿和雪崩混进来

```text
穿透：查询不存在的数据，缓存和数据库都没有
击穿：一个热点 key 失效，大量请求同时回源
雪崩：大量 key 同时失效或缓存整体不可用
```

空值缓存和 Bloom 主要解决穿透；互斥加载或逻辑过期更适合热点击穿；随机 TTL、预热、限流和高可用用于雪崩。先分类，再选择方案。

## 生产落地清单

```text
[ ] 无效参数在入口提前拒绝
[ ] 权限校验不依赖缓存命中与否
[ ] 空值使用独立标记和短 TTL
[ ] 业务新增后主动失效空值缓存
[ ] Bloom 容量、误判率和重建流程明确
[ ] 同步失败有监控和降级路径
[ ] 调用方、接口和批量大小有限流
[ ] 监控缓存命中率、空值率和数据库回源 QPS
```

缓存穿透没有一个单点“银弹”。真正可靠的是多层减压：明显错误尽早拒绝，重复空结果短期记住，大范围不存在 ID 用概率结构过滤，异常流量在入口限速，而数据库仍保留最后的事实判断。
