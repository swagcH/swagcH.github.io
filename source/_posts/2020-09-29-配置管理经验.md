配置问题有一个很迷惑的特点：代码、测试和构建都可能完全正常，只有到了某个环境才失败。更麻烦的是，临时在服务器上改一个值通常很快见效，却会让下次发布、扩容和故障回溯失去依据。

我后来把配置看成代码之外的另一套运行逻辑。它也需要类型、边界、变更记录和回退方案，而不只是若干散落的 YAML。

## 先把配置分成四类

不同配置应该由不同位置管理：

| 类型 | 示例 | 建议归属 |
| --- | --- | --- |
| 代码默认值 | 分页上限、批次大小 | 代码或公共配置 |
| 环境差异 | 域名、数据库地址、日志级别 | 部署平台或环境配置 |
| 敏感信息 | 密码、Token、私钥 | 密钥管理系统 |
| 运行开关 | 灰度比例、功能开关 | 有审计的动态配置 |

如果一个值在所有环境都一样，而且改变它必须重新测试，通常更适合作为代码常量；如果它随部署环境变化，才属于外部配置。

不要为了“灵活”把每个数字都做成配置。无边界配置会让系统组合状态急剧增加，测试无法覆盖。

## 仓库里的配置只放可公开内容

一个比较清晰的 Spring Boot 结构是：

```text
application.yml          服务名、序列化等公共行为
application-local.yml    本地安全默认值
application-test.yml     自动测试专用配置
部署平台                 测试、预发、生产环境差异
密钥系统                 密码、Token 和证书
```

仓库里不提交：

- 真实数据库密码。
- 云服务访问密钥。
- 生产域名白名单和内部凭据。
- 从服务器复制回来的完整配置。
- 以注释方式“临时保留”的旧密码。

即使仓库是私有的，提交历史、CI 日志和开发机副本都会扩大泄露范围。已经进入 Git 历史的密钥不能只删除当前行，必须立即轮换。

## 用占位符表达依赖

`application.yml` 可以声明来源和安全默认值：

```yaml
spring:
  profiles:
    active: ${APP_PROFILE:local}
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

payment:
  base-url: ${PAYMENT_BASE_URL}
  connect-timeout: ${PAYMENT_CONNECT_TIMEOUT:2s}
  read-timeout: ${PAYMENT_READ_TIMEOUT:5s}
  retry-count: ${PAYMENT_RETRY_COUNT:1}
```

地址和账号没有默认值，是为了缺失时尽早失败；超时可以给出经过验证的默认值。生产配置里不要使用 `localhost` 作为兜底，否则依赖漏配后，应用可能启动成功却一直请求自己。

## 搞清楚覆盖优先级

Spring Boot 支持多种配置来源。排查“明明改了却不生效”时，要先确认最终值来自哪里。常见的高优先级来源包括：

```text
命令行参数
系统属性
操作系统环境变量
Profile 配置文件
application.yml
代码默认值
```

这里只表达常见理解，具体顺序应以项目使用的 Spring Boot 版本为准。配置中心、自定义启动脚本和容器注入还可能增加新的来源。

我会在部署记录里保存“配置键、来源、版本”，而不是把值全部打印到日志。对于敏感项，只记录是否存在和更新时间。

## 将配置绑定为有类型的对象

在业务代码里到处写 `@Value`，会让配置关系分散，也难以统一校验。相关配置可以聚合：

```java
@Validated
@ConfigurationProperties(prefix = "payment")
public class PaymentProperties {

    @NotBlank
    private String baseUrl;

    @NotNull
    private Duration connectTimeout = Duration.ofSeconds(2);

    @NotNull
    private Duration readTimeout = Duration.ofSeconds(5);

    @Min(0)
    @Max(3)
    private int retryCount = 1;

    // getter 和 setter 省略
}
```

再通过配置类显式启用：

```java
@Configuration
@EnableConfigurationProperties(PaymentProperties.class)
public class PaymentConfiguration {

    @Bean
    public PaymentClient paymentClient(PaymentProperties properties) {
        // 客户端只依赖已经校验过的配置对象
        return new PaymentClient(
                properties.getBaseUrl(),
                properties.getConnectTimeout(),
                properties.getReadTimeout(),
                properties.getRetryCount()
        );
    }
}
```

这样配置缺失、格式错误或范围越界会在启动阶段暴露。相比运行到第一笔支付才报空指针，启动失败更容易发现和回退。

## 环境隔离不是复制四份文件

测试、预发、生产环境应该保持结构一致，只让必要值不同：

```text
应该相同：配置键、认证方式、协议、超时语义
可以不同：实例地址、容量、账号、日志级别
需要说明：为了测试而关闭的安全检查或外部依赖
```

如果测试环境使用内存数据库、关闭鉴权、同步执行，而生产使用 MySQL、真实鉴权、异步消息，那么测试通过只能说明另一套系统可用。

本地环境可以提供简单依赖，但不能让代码依赖某位开发的绝对路径或个人账号。

## 配置变更也走一次发布流程

一次完整变更至少包含：

```text
变更原因
配置键与影响服务
旧值和新值（敏感值仅保留版本）
生效方式：重启、刷新或下一次请求
风险与观察指标
操作人与复核人
执行时间
回退条件与旧版本
```

先在测试或单实例验证，再逐步扩大。改变连接池、线程池、超时和重试参数时，不能只看应用是否启动，还要观察下游压力、错误率、排队和资源使用。

配置变更速度快，所以更容易绕过 Review。正因为快，才更需要审计。

## 动态刷新不是免费能力

配置中心允许运行时刷新，但不是所有 Bean 和配置都适合热更新：

- 数据源连接池可能需要重建。
- 线程池大小变化要考虑正在执行的任务。
- 多实例接收配置存在时间差。
- 一组相关配置分次生效可能产生非法组合。
- 回调过程中读取两次配置可能得到不同值。

对于必须原子变化的一组值，应使用一个版本对象整体发布；业务处理开始时读取一次快照，不在同一请求中反复读取。

核心连接、序列化协议、数据结构等高风险配置，我更倾向于随版本发布并重启，让行为边界明确。

## 功能开关要有生命周期

功能开关适合灰度和紧急关闭，但每个开关必须记录：

```text
负责人
默认值
开启条件
影响范围
计划删除日期
关闭后的行为
```

长期不清理的开关会在代码中形成大量分支。一次需求结束后，要么删除旧路径和开关，要么将它升级为正式业务规则并补齐测试。

权限也要控制。能修改“是否校验支付金额”的配置，比修改普通日志级别风险高得多，不应使用同一审批级别。

## 启动和运行时分别验证

启动时检查：

```text
必填配置是否存在
地址和数值格式是否正确
上下限关系是否合法
互斥开关是否同时开启
证书是否在有效期
```

运行时则通过健康检查和指标确认配置效果，例如连接池等待时间、外部调用超时率、线程池队列和降级次数。配置正确加载不代表参数适合当前流量。

日志中可以输出脱敏摘要：

```text
payment_config_loaded
baseUrlHost=pay.example
connectTimeoutMs=2000
readTimeoutMs=5000
retryCount=1
secretConfigured=true
configVersion=20200929-03
```

不要直接打印完整 URL 查询参数、用户名或密钥。

## 我的配置检查表

```text
[ ] 每个配置都有明确语义和负责人
[ ] 仓库不含真实凭据
[ ] 环境差异由部署层注入
[ ] 配置对象有类型、默认值和范围校验
[ ] 能说明最终值的来源与优先级
[ ] 测试环境与生产保持关键行为一致
[ ] 变更有版本、复核、观察和回退记录
[ ] 动态刷新考虑原子性和多实例时差
[ ] 功能开关有删除日期
[ ] 日志只输出脱敏摘要
```

配置管理真正要解决的不是“值放在哪里”，而是任何环境下都能回答：当前使用什么、为什么是这个值、谁改过、怎样验证、失败后如何恢复。做到这一点，环境差异才不会继续成为只能靠经验处理的黑盒。
