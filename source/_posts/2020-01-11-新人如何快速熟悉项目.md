> 刚进入一个项目时，最容易走两个极端：从第一行源码开始读，几天后仍然没有全局概念；或者只等别人分配任务，能改代码却解释不清请求为什么这样流转。比较有效的方法，是用一周建立一张“可以工作的项目地图”。

## 第 0 天：先约定上手目标

“熟悉项目”太模糊。第一周不要求掌握所有模块，我会把目标改成五个可以验证的结果：

```text
能在本地独立启动
能讲清一个核心业务流程
能找到对应接口、服务和数据表
能通过日志调试一次请求
能提交一个低风险修改并完成测试
```

同时确认联系人：业务问题问谁、环境问题问谁、数据库变更由谁审核、线上故障如何升级。提前知道责任边界，比卡住以后在群里泛问“有人知道吗”有效得多。

## 第 1 天：把项目可靠地跑起来

先读这些文件，而不是立即搜索业务类：

```text
README.md
pom.xml
application*.yml
Dockerfile / compose.yaml
数据库初始化脚本
CI 配置
启动脚本
```

记录本地依赖和版本：JDK、Maven、MySQL、Redis、消息队列，以及必须申请的配置或账号。敏感值只记录获取方式，不复制到个人笔记。

```bash
java -version
mvn -version
mvn clean test
mvn spring-boot:run -Dspring-boot.run.profiles=local
```

启动完成后，不以“控制台没有报错”为标准，而要验证：

```bash
curl http://127.0.0.1:8080/actuator/health
curl -i http://127.0.0.1:8080/api/ping
```

把启动过程中遇到的缺失配置、端口冲突和初始化步骤补回团队文档。新人遇到的问题往往也是下一位新人会遇到的问题。

## 第 2 天：画业务地图，不急着画类图

先问产品或同事三个问题：

1. 系统最重要的用户是谁。
2. 哪三个流程最影响业务结果。
3. 哪些状态一旦错误最难修复。

例如订单系统可以先画成：

```text
用户下单
  -> 价格计算
  -> 库存校验
  -> 创建订单
  -> 支付
  -> 履约
  -> 完成/退款
```

再标出每一步的入口、数据和外部依赖：

| 环节 | 接口 | 核心表 | 外部依赖 |
| --- | --- | --- | --- |
| 创建订单 | `POST /orders` | `order_info` | 库存服务 |
| 支付 | `POST /payments` | `payment_record` | 支付渠道 |
| 退款 | `POST /refunds` | `refund_record` | 支付渠道、消息队列 |

这张表不需要第一天就完全正确。它的价值是暴露未知项，让后续阅读有方向。

## 第 3 天：认识数据和状态

代码可以重构，数据库里的历史数据会长期存在。优先了解：

```text
核心表主键和业务唯一键
状态字段及合法流转
金额、时间和逻辑删除字段
读写量最大的索引
定时任务和数据修复脚本
```

不要用生产账号随意执行查询。通过只读环境或脱敏数据查看表结构：

```sql
SHOW CREATE TABLE order_info;
SHOW INDEX FROM order_info;
```

针对状态字段，写出状态机：

```text
CREATED -> PAID -> SHIPPED -> FINISHED
   |         |
   v         v
CANCELLED  REFUNDING -> REFUNDED
```

如果代码里任何状态都能改成任何状态，这是一个值得记录的风险，但新人第一周不需要立刻重构它。

## 第 4 天：跟踪一条完整请求

选择一个查询接口，从入口追到数据库：

```text
Controller
  -> Application Service
  -> Domain/Business Service
  -> Repository/Mapper
  -> SQL
  -> Response
```

常用搜索：

```bash
rg '@(Get|Post|Put|Delete)Mapping' src/main/java
rg 'orderNo|requestId' src/main/java src/main/resources
rg 'select .*order_info|from order_info' src/main/resources
```

IDEA 中用 Call Hierarchy、Find Usages 和断点确认真实调用，不能只凭类名猜。记录请求参数在哪一层校验、事务从哪里开始、异常在哪里转换、日志是否能串起全过程。

## 第 5 天：看最近修改，而不是考古所有历史

最近三个月的提交最接近当前业务重点：

```bash
git log --oneline --decorate -30
git log --since='3 months ago' --stat
git blame -L 80,130 src/main/java/com/example/order/OrderService.java
```

`git blame` 不是为了找责任人，而是找到引入这段逻辑的提交，再理解当时的上下文。结合需求单、PR 描述和测试用例，通常比猜注释更准确。

选择两个近期需求回答：

- 为什么要改。
- 改了哪些层。
- 哪些兼容逻辑被保留。
- 测试覆盖了什么。
- 上线后如何验证。

## 第 6 天：完成一个低风险闭环

合适的首个任务可以是：补充校验、修复文案、增加测试、完善日志或调整只读接口。重点不是任务大小，而是完整走一遍流程：

```text
理解需求
  -> 定位代码
  -> 修改和测试
  -> 自查影响范围
  -> 提交 PR
  -> 响应 Review
  -> 验证环境
```

提交前至少运行关联测试，不要因为任务小就跳过：

```bash
mvn -Dtest=OrderServiceTest test
git diff --check
git diff --stat
```

## 第 7 天：输出一页项目地图

我的一页总结通常包含：

```text
项目目标与核心用户
三个核心业务流程
主要模块和负责人
核心表与状态机
外部依赖和环境入口
启动、测试和发布命令
当前仍不理解的问题
```

最后一项很重要。项目复杂时，不可能一周全部掌握。把未知项显式列出，后续任务会自然补全地图。

## 怎样提一个高质量问题

不要只说“项目启动不了”，可以这样组织：

```text
目标：使用 local profile 启动 order-service
已做：JDK 8、MySQL 和 Redis 已确认；mvn test 通过
现象：启动时连接 config-service 超时
证据：异常首行、目标地址、发生时间
判断：怀疑缺少本地配置或网络权限
问题：local 环境应使用哪个配置入口？
```

这能让对方快速判断，也证明自己已经完成基础排查。

## 最容易浪费时间的做法

1. 从工具类开始逐行阅读，没有业务问题作为线索。
2. 复制同事配置却不知道来源和权限边界。
3. 一上来重构公共代码，尚未理解兼容原因。
4. 只记录结论，不记录命令、现象和判断过程。
5. 遇到问题立即问人，从不先搜索日志和历史提交。

## 一个月后的验收

第一周建立地图，第一个月应该逐步做到：

- 能独立完成一个中等需求。
- 能解释核心链路的事务和失败分支。
- 能处理常见环境和数据问题。
- 能在 Review 中发现业务影响，不只看格式。
- 至少补齐一份团队可复用的文档或测试。

快速熟悉项目不是记住最多类名，而是形成定位问题的坐标系。知道业务目标、数据边界、调用入口和协作流程后，陌生代码会从一片文件变成可以逐步验证的系统。
