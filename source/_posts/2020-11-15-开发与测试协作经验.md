有一次测试提了一个缺陷：“优惠券使用失败。”开发看完回复：“我这里正常，无法复现。”两句话都是真的，但没有推动问题前进一步。测试看到的是某组环境和数据下的失败，开发验证的是另一组条件下的成功。

后来回看，这不是谁描述得不认真，而是双方没有共享同一套上下文。开发与测试的协作，核心不是把缺陷在系统里来回指派，而是共同缩小“预期”和“实际”之间的差异。

## 同一个问题的两个视角

测试首先关心：

```text
用户做了什么
预期看到什么
实际发生什么
哪些条件下稳定复现
还可能影响哪些场景
```

开发首先关心：

```text
请求进入哪个版本和实例
参数、身份和数据状态是什么
代码走到哪个分支
日志、异常和下游返回是什么
最小改动会影响哪些调用方
```

两边并不冲突。测试提供可观察行为，开发补充内部证据，合在一起才是一份可定位的问题。

## 把“优惠券失败”补完整

一份可以直接开始排查的缺陷记录应该像这样：

```text
标题：新用户券在商品金额等于门槛时提示不可用
环境：test，order-service 1.11.3
账号：测试账号 U10027
前置数据：
- 优惠券满 100 减 20，未使用，未过期
- 商品原价 100，无其他优惠

步骤：
1. 加入商品并进入结算页
2. 选择该优惠券
3. 提交订单

预期：应抵扣 20，实付 80
实际：返回 COUPON_THRESHOLD_NOT_REACHED
时间：2020-11-15 14:32:18
traceId：b3f1078a92
频率：重复 5 次均出现
对照：商品金额 101 时可以使用
```

“100 失败、101 成功”比一张错误截图更接近根因。开发沿 traceId 查到门槛判断使用了 `amount > threshold`，而需求是大于等于。

截图可以保留界面现象，但文本字段必须可搜索、可复制。密码、Token 和真实用户信息不能作为附件上传。

## 测试开始前，开发交付什么

提测不能只有一个分支名。开发至少说明：

```text
改动目的和范围
明确未实现的内容
接口、数据库、配置变化
主流程与异常流程
自测结果
已知风险
日志和监控入口
回退方式
```

对于优惠券需求，开发自测不只验证“能用”：

| 维度 | 用例 |
| --- | --- |
| 金额 | 99.99、100、100.01 |
| 时间 | 生效前、有效期内、刚过期 |
| 状态 | 未使用、已锁定、已核销 |
| 并发 | 重复提交、超时重试 |
| 组合 | 与会员价、满减是否互斥 |
| 权限 | 是否属于当前用户 |

边界表能让双方在提测前对齐重点，也减少低成本问题进入测试队列。

## 测试不是最后一站

协作应该从需求评审开始。测试在评审阶段提出“金额等于门槛怎么算”“支付失败后券是否释放”，通常比代码完成后发现便宜得多。

我习惯把工作拆成四个交接点：

```text
需求评审：共同补边界和验收标准
方案评审：测试了解状态、依赖和风险
开发阶段：关键用例先自动化，环境提前准备
提测之后：按证据定位、验证修复并补回归
```

测试也不必理解所有代码，但知道数据状态和系统边界后，能够设计出比页面点击更有效的场景。

## 发现缺陷后先做分诊

不是每个失败都立刻归为代码 Bug。先判断属于哪类：

| 类型 | 证据 | 下一步 |
| --- | --- | --- |
| 需求歧义 | 验收标准没有定义边界 | 产品确认并更新需求 |
| 代码缺陷 | 行为与已确认规则不符 | 开发修复并补测试 |
| 环境问题 | 版本、配置或依赖异常 | 恢复环境并记录差异 |
| 数据问题 | 测试前置状态不成立 | 修复数据构造方式 |
| 自动化问题 | 用例假设过期或不稳定 | 更新脚本并定位波动 |

分诊不是推卸，而是找到真正应该改变的地方。把配置错误改成一段业务兼容代码，短期能过测试，长期会让问题更隐蔽。

优先级也要基于影响：

```text
阻塞：核心流程不可用，无替代方案
高：重要功能错误、数据或安全风险
中：局部功能错误，有明确绕行方式
低：展示、文案或低频体验问题
```

“我提的 Bug 必须最高”会让优先级失去意义。由产品影响、用户范围、恢复成本和上线时间共同决定。

## 开发收到缺陷后的回复方式

有效回复不是“不是我的问题”，而是给出当前判断和下一步：

```text
已在 test 1.11.3 复现。
定位到 CouponRule 第 48 行使用了严格大于判断。
需求确认门槛应包含等于场景。
计划补充 99.99、100、100.01 三个单元测试后修复。
预计 17:00 提供版本，影响所有满额券计算。
```

暂时无法复现时也可以明确缺什么：

```text
当前使用相同账号和版本执行 3 次未出现。
请补充失败时间或 traceId，以确认请求实例和当时配置。
我会同时检查 14:30 前后的券锁定日志。
```

这样问题仍在向前推进。

## 修复不能只让原步骤通过

修复完成后至少做三层验证：

1. 原失败步骤已经恢复。
2. 相邻边界没有被破坏。
3. 相同规则的其他入口保持一致。

优惠券可能在下单、购物车试算和运营后台预览中分别计算。如果只改下单接口，用户会在页面看到“可用”，提交时又失败，或者相反。

开发应补自动测试锁定规则；测试根据影响范围回归。两者不是重复工作：自动测试保护以后每次构建，探索性测试继续寻找未被想到的组合。

## 对环境争议建立统一答案

“我本地正常”通常说明环境缺少可比性。团队应让每次测试都能确认：

```text
前端与后端版本
Git 提交或构建号
数据库迁移版本
关键配置版本
依赖服务状态
测试数据创建方式
```

服务提供版本接口，部署系统展示变更历史，测试数据使用脚本创建。这样环境问题不再依赖逐个人询问。

## 一次缺陷的关闭标准

```text
[ ] 根因和影响范围已记录
[ ] 修复提交与部署版本可追溯
[ ] 原用例和相邻边界验证通过
[ ] 必要自动测试已补充
[ ] 临时数据、开关和调试日志已清理
[ ] 需求或接口文档同步更新
[ ] 线上观察项与负责人明确
```

开发和测试并不是前后两个工位。一个更关注系统如何实现，一个更关注系统如何失败，这两种视角本来就应该互相补充。当双方用版本、数据、traceId 和边界条件说话时，讨论会从“在我这里是否正常”变成“在哪个条件下不符合共同确认的规则”。
