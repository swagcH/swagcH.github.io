> 很多“开发延期”和“测试漏测”，根因在代码开始前就已经出现：目标不清、边界没讨论、异常流程无人负责。需求评审不是听产品讲一遍页面，而是把模糊描述转换成可以实现和验收的共同结论。

## 一个典型评审现场

需求只有一句：

```text
用户可以取消未发货订单，退款原路返回。
```

听起来很简单，继续问才发现至少有这些分支：

```text
已支付但库存未出库
部分商品已出库
优惠券是否退回
积分是否回滚
支付渠道退款失败
重复点击取消
客服和用户同时操作
订单正在状态迁移
```

如果这些问题留到开发或测试阶段才发现，接口、表结构和排期都可能重新调整。

## 1. 先问“为什么做”

评审前先确认目标：

- 当前用户痛点是什么。
- 成功以后用什么指标判断有效。
- 为什么必须在这个版本完成。
- 是否有更小范围的方案。

“增加取消按钮”是功能描述，“降低未发货订单的客服取消量”才是目标。知道目标后，才能判断是否需要自动退款、取消原因和运营后台。

## 2. 把正常流程写成状态变化

```text
PAID
  -> CANCEL_REQUESTED
  -> REFUNDING
  -> CANCELLED
```

每个箭头回答：

```text
谁触发
需要什么权限
前置状态
写哪些数据
调用哪些外部系统
失败后停在哪个状态
能否重试
```

页面流程可能只有三步，服务端状态通常更多。状态没有定义清楚时，不要急着估时。

## 3. 用边界表发现遗漏

| 维度 | 需要确认的问题 |
| --- | --- |
| 用户 | 普通用户、客服、管理员权限是否不同 |
| 时间 | 发货前、支付后多久允许取消 |
| 状态 | 哪些状态允许，处理中如何展示 |
| 数据 | 历史订单是否支持，是否需要迁移 |
| 并发 | 重复点击、多人同时操作如何处理 |
| 外部依赖 | 支付、库存、优惠券失败怎么办 |
| 通知 | 用户、商家和客服是否收到消息 |
| 审计 | 谁在什么时候因为什么取消 |

边界表不是为了把需求无限做大，而是让产品明确哪些在本期、哪些不支持。

## 4. 权限要具体到数据范围

“登录用户可以取消订单”不够，需要说明：

```text
用户只能取消自己的订单
客服需要 order:cancel 权限
客服跨租户不可操作
管理员强制取消必须填写原因
敏感操作记录操作人和来源
```

权限遗漏常常不会在正常测试中暴露，却可能造成严重数据越权。

## 5. 异常不是统一提示“失败”

支付渠道超时有多种可能：

```text
请求未到达渠道
渠道已受理但响应丢失
渠道明确拒绝
渠道退款成功但本地更新失败
```

调用超时不能直接把订单恢复原状态，因为渠道可能已经退款。需求中要定义查询、补偿和人工处理入口。

对用户展示的文案、后台状态和告警负责人也要明确，不能全部留给开发“看着处理”。

## 6. 数据变化提前说清楚

```text
是否新增表或字段
历史数据如何初始化
报表口径是否变化
搜索索引是否重建
是否产生新的个人信息
数据保留多久
```

数据迁移和回滚常常比接口开发耗时更长。评审只估页面和接口，会得到虚假的排期。

## 7. 验收标准要能测试

不清晰：

```text
取消过程要友好，退款尽快完成。
```

可测试：

```text
未发货且已支付订单允许申请取消
重复提交同一订单只创建一笔退款
渠道明确成功后订单进入 CANCELLED
渠道超时后订单保持 REFUNDING，并可由任务查询
用户能看到取消进度和失败原因分类
```

性能、权限、兼容和失败恢复也属于验收，不只是按钮能点击。

## 8. 估时不要只报编码天数

拆分为：

```text
方案设计
接口和数据变更
外部依赖联调
自动化测试
历史数据处理
灰度和监控
上线验证
风险缓冲
```

存在未确认项时，给区间和前提：

```text
支付渠道支持退款查询：预计 5 天
若不支持查询，需要增加人工对账：另评估 2 至 3 天
```

这比给一个精确但没有依据的日期更负责。

## 9. 会议结论怎么记录

```text
目标：降低未发货订单客服取消量
本期范围：已支付、未出库的普通订单
不在范围：部分出库、组合订单、跨境订单
已确认：状态机、权限、退款查询方式
待确认：优惠券退回时效，负责人产品 A，截止周二
技术风险：渠道超时后的最终状态
数据变更：新增退款请求表和取消原因
验收：12 条主流程和异常用例
```

结论应进入需求单或共享文档，不能只留在会议录音和聊天记录中。

## 10. 需求变更如何处理

变更发生时记录：

- 改了什么，为什么。
- 影响接口、数据、测试和排期哪些部分。
- 谁确认接受新的时间或范围。
- 已开发内容如何处理。

小改动积累起来同样会改变交付风险。变更记录不是为了追责，而是避免不同角色持有不同版本的需求。

## 我会带进评审的十个问题

```text
1. 用户问题和成功指标是什么？
2. 本期明确不做什么？
3. 状态如何变化？
4. 异常和超时后停在哪里？
5. 权限和数据范围是什么？
6. 重复和并发操作怎么处理？
7. 外部依赖有什么不确定性？
8. 历史数据和兼容怎么处理？
9. 如何测试并验收？
10. 上线后看什么指标，失败怎么回退？
```

好的需求评审不会消灭所有变化，但会让重要的不确定性提前出现。开发的价值也不是在会上不断说“做不了”，而是说明风险、提出更小方案，并把模糊目标转成可以交付的边界。
