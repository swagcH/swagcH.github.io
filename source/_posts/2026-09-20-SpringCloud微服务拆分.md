"微服务拆分"经常被当成一个技术动作——把单体拆成几个服务，引入注册中心和网关就算完事。但实际做下来会发现，**拆分的难点从来不在技术组件，而在"边界怎么划"和"拆完之后怎么运维"**。

这篇文章以我负责的一个集团级数据大屏项目为例，记录从架构选型、服务边界划分、异构系统集成，到部署与运维的完整过程。重点写**判断依据和踩过的坑**，而不是组件清单。

## 项目背景

**规模**：围绕 7 大主题（集团概况、产业布局、低碳电力、生态环保、综合燃气、数智服务、专题介绍）建设，共 36 个业务板块，接入 167 家生产企业，展示 6000 余项数据。

**复杂度来源**：需要与大数据平台、SIS（厂级监控信息系统）等 **9 个异构系统**做数据集成，对外提供 **580 个指标**。

**约束**：只有 4 台服务器，且要保证大屏展示的高可用（大屏是给领导看的，宕机影响面大）。

![能源大屏微服务架构总览](/images/posts/2026/springcloud-arch-overview.svg)

## 一、架构选型：为什么是 SpringCloud

### 候选方案对比

| 方案 | 优势 | 代价 |
|---|---|---|
| **单体 + 模块化** | 部署简单、无网络开销、事务简单 | 一处改动全量发布、无法按模块扩容 |
| **SpringCloud** | 生态成熟、团队熟悉、组件可选 | 运维复杂度上升（注册中心、网关、配置中心）|
| **SpringCloud Alibaba** | 自带 Nacos/Sentinel，国内生态好 | 与 SpringCloud 有版本对齐成本 |
| **Dubbo** | RPC 性能好 | 偏 RPC 调用，服务治理组件需自行补齐 |

**最终选 SpringCloud + Nacos**，理由是：

1. **团队熟悉度优先**。技术选型要考虑团队能不能 hold 住，而不只是"哪个更先进"
2. **Nacos 一个组件同时解决注册中心和配置中心**，比 Eureka + Config 两套更省运维
3. **生态和文档成熟**，出问题容易找到资料
4. **数据大屏本质是"多数据源聚合 + 展示"**，对 RPC 性能要求不高，Dubbo 的性能优势用不上

### 拆几个服务？按什么拆？

**这是最容易做错的决策。** 我见过两种极端：

- **拆太细**：一个业务拆七八个服务，一个请求跨五六个服务，排查问题要开一堆日志窗口
- **拆太粗**：只有两个服务（"前端服务"和"后台服务"），等于没拆

**我的拆分依据（按优先级）：**

**1. 按变化频率拆**

变化快的模块独立出来，避免每次小改动都要全量发布。比如"专题介绍"这类内容型板块，运营经常要调整，独立成服务后可以单独发布。

**2. 按数据源拆**

不同数据来源的模块分开，隔离故障。这个项目里有 9 个外部系统，如果全部塞在一个服务里，任何一个上游慢都会拖垮整个服务。

**3. 按性能特征拆**

读多写少和写多读少分开；实时查询和离线统计分开。大屏的"实时指标"和"历史趋势"承担的负载完全不同，拆开后可以独立扩容。

**4. 按团队边界拆**（如果有多个团队）

康威定律：系统架构会趋同于组织结构。如果有明确的团队边界，按团队拆能减少协作成本。

![服务拆分依据与 6 个服务的职责划分](/images/posts/2026/springcloud-split-criteria.svg)

**最终拆成了 6 个服务：**

| 服务 | 职责 | 拆分依据 |
|---|---|---|
| `gateway` | 统一入口、路由、鉴权、限流 | 基础设施 |
| `auth-service` | 认证授权、菜单权限 | 变化频率低但被所有服务依赖 |
| `metric-service` | 指标数据的接入与统一 | 数据源最多、最复杂 |
| `board-service` | 大屏各板块的数据组装 | 读多写少、变化频繁 |
| `screen-service` | 监控画面相关 | 数据源独立、性能特征不同 |
| `system-service` | 系统管理、字典、日志 | 通用能力 |

**注意 `metric-service` 单独拆出来的原因**：它是整个项目最复杂的部分——要把 9 个来源、格式各异的数据统一成 580 个指标的标准模型。把它独立出来，一方面隔离了"上游系统不稳定"的风险，另一方面它的迭代节奏和其他服务完全不同。

## 二、异构系统集成：最花时间的部分

**9 个系统、580 个指标，这部分工作量远超预期。**

### 难点在哪

**1. 接口协议各不相同**

有的提供 REST API，有的是数据库直连，有的是消息推送（Kafka/MQ），还有的只能通过文件交换。**没有统一的接入方式。**

**应对**：设计**统一接入层**，每种协议实现一个适配器，向上暴露统一接口。

```java
public interface MetricSourceAdapter {
    /** 该适配器支持的来源类型 */
    SourceType supportType();

    /** 拉取指标数据 */
    List<MetricData> fetch(MetricQuery query);
}

@Component
public class RestApiAdapter implements MetricSourceAdapter { /* ... */ }

@Component
public class DbDirectAdapter implements MetricSourceAdapter { /* ... */ }

@Component
public class MqSubscribeAdapter implements MetricSourceAdapter { /* ... */ }
```

业务代码只依赖 `MetricSourceAdapter`，不关心具体来源。新增一个来源系统，只需实现一个适配器。

**2. 指标口径不一致**

同一个指标（比如"发电量"）在不同系统里的定义、单位、统计周期可能不同。**这是最容易被低估的坑**——不做统一，大屏上会出现"同一个指标在不同板块数字不一样"。

**应对**：建立**指标字典**，作为唯一数据源。

```sql
CREATE TABLE metric_dict (
    metric_code    VARCHAR(64) PRIMARY KEY,   -- 指标编码，全局唯一
    metric_name    VARCHAR(128),              -- 指标名称
    unit           VARCHAR(16),               -- 标准单位
    source_type    VARCHAR(32),               -- 来源类型
    source_config  JSON,                      -- 来源配置（接口地址/表名/字段映射）
    transform_expr VARCHAR(512),              -- 转换表达式（单位换算、口径调整）
    update_period  INT,                       -- 更新周期（秒）
    enabled        TINYINT
);
```

**关键点**：

- **指标编码全局唯一**，所有服务都通过 `metric_code` 取数，不直接引用上游字段
- **转换逻辑配置化**（`transform_expr`），口径调整不用改代码
- **更新周期分开配置**，实时指标和高频统计不用同样的刷新频率

**3. 更新频率差异大**

有的数据秒级更新，有的是天级批量。如果统一按最高频率拉取，会造成大量无效请求。

**应对**：**按指标配置更新周期 + 分层缓存**。

```
秒级指标 → 直连查询（或短缓存 5s）
分钟级   → Redis 缓存 5min
小时级   → Redis 缓存 1h
天级     → 本地缓存 + 定时刷新
```

### 数据一致性

跨系统取数存在时序差异：A 系统的数据已更新，B 系统还是旧的，聚合结果会不一致。

**应对**：

- **单个指标内保证一致**（同一个指标只从一个系统取）
- **跨指标聚合时记录数据时间戳**，大屏上展示"数据更新时间"，让使用者知道数据的新鲜度
- **不做跨系统的强一致**——这在异构集成的场景下成本过高且收益有限

## 三、几个关键技术点

### 服务间调用：Feign + 超时与熔断

```java
@FeignClient(name = "metric-service", fallbackFactory = MetricFallbackFactory.class)
public interface MetricClient {

    @GetMapping("/metric/batch")
    List<MetricVO> batchQuery(@RequestParam("codes") List<String> codes);
}
```

**必须配置超时**（默认值往往过长）：

```yaml
feign:
  client:
    config:
      default:
        connectTimeout: 2000      # 连接超时 2s
        readTimeout: 5000         # 读超时 5s
```

**必须配置熔断降级**：

```java
@Component
public class MetricFallbackFactory implements FallbackFactory<MetricClient> {
    @Override
    public MetricClient create(Throwable cause) {
        return codes -> {
            log.error("指标服务调用失败: {}", cause.getMessage());
            // 降级：返回缓存数据或空值，不要让整个大屏挂掉
            return Collections.emptyList();
        };
    }
}
```

**为什么大屏项目一定要有降级**：大屏是多个板块拼起来的，如果"综合燃气"板块的服务挂了，不应该导致整个大屏白屏。**局部降级 + 提示**比整体不可用体验好得多。

### 配置中心：Nacos

**为什么需要**：服务多起来之后，改一个配置（比如超时时间）要重启所有服务是不可接受的。

```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: ${NACOS_ADDR}
        file-extension: yaml
        shared-configs:
          - data-id: common-config.yaml     # 公共配置（数据库、Redis）
            refresh: true
          - data-id: ${spring.application.name}.yaml   # 服务专属配置
```

**实践建议**：

- **公共配置和服务配置分开**：数据库、Redis 这类所有服务都要用的放公共配置
- **敏感信息用环境变量注入**，不要明文写在配置中心（至少要用加密配置）
- **开启 `refresh: true` 但要注意范围**：不是所有配置都能热更新（比如数据库连接池的核心参数）

### 高可用部署：只有 4 台服务器怎么办

**约束**：4 台服务器，要跑 6 个服务 + Nacos + Redis + MySQL + Nginx，还要保证大屏不挂。

**方案**：

```
┌─────────────┐
│   Nginx     │  负载均衡 + 静态资源（部署在 2 台）
└──────┬──────┘
       │
┌──────▼──────┐  ┌─────────────┐
│  服务实例 A  │  │  服务实例 B  │  关键服务双实例（分布在不同机器）
└──────┬──────┘  └──────┬──────┘
       │                │
┌──────▼────────────────▼──────┐
│  Nacos 集群（2 节点）          │  注册中心必须高可用
└──────────────────────────────┘
```

**关键判断：哪些必须高可用，哪些可以单点？**

| 组件 | 是否高可用 | 理由 |
|---|---|---|
| **Nacos** | ✅ 必须 | 注册中心挂了，所有服务无法互相发现 |
| **网关** | ✅ 必须 | 单点挂了整个系统不可访问 |
| **核心业务服务** | ✅ 关键服务双实例 | 大屏主板块不能挂 |
| **Redis** | ⚠️ 主从 + 哨兵 | 缓存挂了可以降级到数据库，但不能长时间挂 |
| **MySQL** | ⚠️ 主从 | 主库挂了只读可用，写入中断 |
| **非核心服务** | ❌ 可单点 | 系统管理、日志服务挂了不影响大屏展示 |

**这是资源受限下的务实做法**：不是所有组件都做高可用（成本不允许），而是**按影响面排序**，把资源投在最关键的地方。

### 数据库分片

数据量增长后（指标数据是持续写入的时序数据），单表查询变慢。使用 **ShardingSphere** 按企业维度分片。

**详细的分片设计见**：[ShardingSphere 分库分表实践：从选型到踩坑](/2026/04/12/2026-04-12-ShardingSphere分库分表实践/)

**这里补充一点分片在微服务架构下的特殊考虑**：

- **分片规则要配置在所有访问该表的服务里**（ShardingSphere-JDBC 模式），服务越多，规则同步越容易出问题
- 如果服务数量继续增加，应该考虑改用 **ShardingSphere-Proxy**，把分片规则集中到代理层
- **跨服务的分片键必须统一**，否则 A 服务按 `tenant_id` 分片、B 服务按 `device_id` 分片，联表查询会变成全路由

## 四、踩过的坑

### 坑 1：服务拆分过细导致排查困难

**现象**：初期把一个板块拆成了 4 个服务，结果一个页面加载要调 6 个服务，某次线上问题排查花了很久——因为日志分散在多个服务里，无法串起来。

**解决**：

- **引入链路追踪**（SkyWalking / Sleuth + Zipkin），给每个请求分配 TraceId，日志里带上它
- **合并过细的服务**。把"强相关、总是一起变化"的服务合并回去
- **教训**：拆分的粒度应该按"变化频率"和"数据边界"，不是按"功能数量"

### 坑 2：Nacos 配置的命名空间混用

**现象**：测试环境的服务连到了生产环境的配置，导致测试时改了生产的参数。

**原因**：Nacos 的 `namespace` / `group` / `data-id` 三层没有规划好，不同环境用同一个 namespace。

**解决**：**按环境划分 namespace**，且用 CI/CD 注入，不允许手工配置。

```
namespace: dev / test / prod
group: DEFAULT_GROUP
data-id: ${app-name}-${env}.yaml
```

### 坑 3：Feign 调用没有传递认证信息

**现象**：网关鉴权通过后，服务内部通过 Feign 调用其他服务时丢了用户上下文，导致下游服务拿不到用户信息。

**解决**：用 `RequestInterceptor` 把认证信息透传下去。

```java
@Configuration
public class FeignAuthConfig {
    @Bean
    public RequestInterceptor authInterceptor() {
        return template -> {
            // 从当前请求上下文取出 token 和用户信息，透传给下游
            RequestAttributes attrs = RequestContextHolder.getRequestAttributes();
            if (attrs instanceof ServletRequestAttributes sra) {
                String token = sra.getRequest().getHeader("Authorization");
                if (token != null) template.header("Authorization", token);
            }
        };
    }
}
```

**注意**：这只是内部调用的上下文透传，**下游服务仍要校验**，不能信任上游传过来的身份（零信任原则）。

### 坑 4：大屏接口响应慢，实际是串行调用

**现象**：大屏首页要展示十几个板块，响应时间超过 3 秒。

**原因**：代码里十几个板块的数据是**串行**获取的。

**解决**：改成并行 + 统一超时。

```java
// 用 CompletableFuture 并行获取多个板块的数据
List<CompletableFuture<BoardData>> futures = boardCodes.stream()
    .map(code -> CompletableFuture
        .supplyAsync(() -> loadBoard(code), boardExecutor)
        .orTimeout(2, TimeUnit.SECONDS)              // 单个板块超时 2s
        .exceptionally(ex -> BoardData.empty(code)))  // 失败降级为空
    .toList();

List<BoardData> results = futures.stream()
    .map(CompletableFuture::join)
    .toList();
```

**两个关键点**：

- **单个板块超时后降级为空**，不影响其他板块（大屏部分数据缺失比整个页面加载失败好）
- **用独立的线程池**（`boardExecutor`），不要用默认的 `ForkJoinPool.commonPool()`——被阻塞的任务会拖垮整个应用的其他并行操作

**优化后响应时间从 3 秒降到 800ms 左右。**

## 五、架构演进的经验总结

### 关于拆分

1. **先单体，后拆分**。项目初期业务边界不清晰，过早拆分会导致频繁调整。我们的做法是**先按模块化单体开发，明确边界后再拆**
2. **拆分依据按优先级**：变化频率 > 数据源 > 性能特征 > 团队边界
3. **拆完要能说清"为什么这么拆"**。如果只能说"按业务拆的"，说明还没想清楚

### 关于治理

1. **超时和熔断必须在第一版就有**。后期补的代价是"已经出过故障"
2. **链路追踪不是可选项**。服务超过 3 个，没有 TraceId 排查就是大海捞针
3. **降级方案要有明确的触发条件和预期行为**（比如"指标服务不可用时返回缓存数据，并在大屏上标注数据延迟"）

### 关于资源受限的现实

**不是所有组件都要高可用。** 4 台服务器的约束下，正确的做法是：

1. **列出所有组件**
2. **按"挂了的影响面"排序**
3. **把有限的资源投在前几名**

**这个排序本身就是架构能力的体现**——能说清"为什么 Nacos 必须双节点，而日志服务可以单点"，比笼统地说"我们做了高可用"更有说服力。

## 落地检查清单

- [ ] 服务拆分有明确依据（能说清每个服务为什么独立）
- [ ] 拆分的粒度合理（没有"一个请求跨 5 个服务"的情况）
- [ ] 有统一入口网关（路由、鉴权、限流）
- [ ] 注册中心高可用（至少 2 节点）
- [ ] 配置中心按环境隔离 namespace
- [ ] 服务间调用配置了超时（不用默认值）
- [ ] 关键调用有熔断降级，且降级行为明确
- [ ] 认证信息在服务间正确透传，且下游仍做校验
- [ ] 引入链路追踪，日志带 TraceId
- [ ] 异构数据源有统一接入层，新增来源不改业务代码
- [ ] 指标/字段有统一字典，口径问题在字典层解决
- [ ] 按影响面确定高可用范围，重点资源投在关键组件
- [ ] 大屏/首页类接口做并行聚合 + 单点超时降级
- [ ] 独立线程池隔离不同业务，不共用默认池

## 小结

微服务架构的价值不是"用了多少组件"，而是**能不能按业务的真实边界把系统切开，并让每个部分独立演进、独立扩缩容、故障隔离**。

回顾这个项目，我认为最有价值的三个决策是：

1. **先模块化单体，边界清晰后再拆**——避免了初期反复调整服务划分
2. **把最复杂的指标接入独立成服务**——隔离了"上游 9 个系统不稳定"这个最大风险源
3. **按影响面分配高可用资源**——在 4 台服务器的约束下做了务实的取舍

而最该早点做的是**链路追踪**——服务一多，没有它排查问题会非常痛苦。
