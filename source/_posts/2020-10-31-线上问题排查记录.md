这是我第一次完整参与线上故障处理。事后看，根因并不复杂：一个导出任务在事务中执行了慢速远程调用，持续占用数据库连接，最终把连接池耗尽。真正让我印象深刻的，是故障现场里“恢复、取证、判断、沟通”必须同时进行。

下面的时间和业务数据都做了脱敏，保留的是排查过程。

## 事故摘要

```text
时间：2020-10-31 20:07 - 20:38
影响：订单查询和创建间歇性失败
峰值错误率：约 18%
直接原因：数据库连接池无可用连接
根本原因：批量导出事务包含逐条远程调用
恢复方式：关闭导出入口，重启异常实例并逐步恢复流量
```

当晚 19:40 发布了订单导出功能。发布后最初二十分钟指标正常，因此团队完成了常规发布确认。

## 20:07，第一条告警

监控显示订单接口 P99 从 420ms 上升到 8s，随后开始出现 5xx。客服同时反馈用户“偶尔打不开订单列表”。

当时群里很快出现了几个猜测：

- 刚发布的新版本有问题。
- 数据库变慢。
- 网络波动。
- 线程池满了。

值班负责人先把内容分成事实和假设：

```text
事实：
- 只有 order-service 明显异常
- 三个实例中有两个错误率高
- CPU 约 35%，内存无明显上涨
- 数据库整体 CPU 约 42%

假设：
- 应用连接池耗尽
- 某条 SQL 变慢
- 新功能占用了公共线程或连接
```

这个动作看起来简单，却避免了团队按各自猜测同时改系统。

## 20:10，先确认影响范围

我们从网关按路径和状态码聚合：

```text
/api/orders/query      5xx 约 16%
/api/orders/create     5xx 约 11%
/api/products/query    正常
/api/users/profile     正常
```

订单读写都受影响，说明问题不太像单一查询逻辑。随后按实例查看，发现刚处理过导出请求的两个实例最严重。

日志中的共同异常是：

```text
SQLTransientConnectionException:
HikariPool-1 - Connection is not available,
request timed out after 3000ms
```

至此可以确认直接故障点是连接池，而不是把“数据库可能有问题”当最终结论。

## 20:14，保留现场

在重启前，我们从一个异常实例保存了三类证据：

```bash
# 记录进程和资源快照
ps -eo pid,%cpu,%mem,etime,cmd --sort=-%cpu | head

# 连续抓取三次线程现场，观察是否一直停在同一位置
jstack <pid> > /tmp/order-201031-2014-1.log
jstack <pid> > /tmp/order-201031-2014-2.log
jstack <pid> > /tmp/order-201031-2014-3.log

# 查看进程建立的数据库连接数量
lsof -Pan -p <pid> -iTCP | head
```

这些命令应由有服务器权限的值班人员执行，导出文件要按生产数据规范保存，不上传到个人网盘或公共聊天。

连接池指标显示：

```text
active=30
idle=0
pending=86
max=30
```

线程 dump 中，大量请求在等待 `HikariPool.getConnection`；另有 30 个导出线程停在外部客户信息接口。连接数、线程数和连接池上限正好能够对应。

## 20:18，找到连接为什么不释放

沿着导出任务的 traceId 查日志，看到一次导出包含 8,000 多条订单。代码结构可以简化成：

```java
@Transactional
public File exportOrders(OrderExportRequest request) {
    List<Order> orders = orderRepository.findForExport(request);
    for (Order order : orders) {
        Customer customer = customerClient.query(order.getCustomerId());
        order.fillCustomerName(customer.getName());
    }
    return excelWriter.write(orders);
}
```

`@Transactional` 覆盖了查询、数千次远程调用和文件生成。查询结束后，事务连接并没有立即归还；当多个导出并发执行时，连接池很快被占满。

这时还有一个关键判断：是否直接扩大连接池？结论是不扩大。数据库并未达到容量上限，但扩大连接池只会允许更多长事务并发，可能把局部问题推向数据库。

## 20:22，先止血

恢复顺序是：

1. 在网关临时关闭订单导出入口，只影响新增导出。
2. 摘除两个异常实例，不再接收新请求。
3. 等待和终止已确认无业务写入的导出任务。
4. 逐个重启异常实例并完成健康检查。
5. 每次只恢复一个实例的流量，观察连接池和错误率。

终止任务、摘流和重启都可能影响业务，必须由当班负责人授权，并先确认导出操作无写入副作用。不能看到线程多就直接杀进程。

20:28，订单接口错误率开始下降；20:33，P99 恢复到 500ms 左右；20:38，连续五分钟没有新的连接超时，故障转入观察。

## 20:45，修复方案评审

修复没有只删除 `@Transactional`，而是重新划分处理阶段：

```text
阶段一：分页读取订单，只在短事务中访问数据库
阶段二：批量查询客户信息，设置超时和并发上限
阶段三：流式写文件，避免所有结果常驻内存
阶段四：记录任务状态，用户异步下载
```

数据库查询改为每批 500 条：

```java
public void export(OrderExportTask task) {
    Long lastId = null;
    do {
        // 每批查询独立完成，不让数据库事务跨越远程调用
        List<Order> batch = orderQueryService.findNextBatch(
                task.getCondition(), lastId, 500);
        if (batch.isEmpty()) {
            break;
        }

        Map<Long, Customer> customers =
                customerBatchClient.queryByIds(extractCustomerIds(batch));
        excelWriter.append(enrich(batch, customers));
        lastId = batch.get(batch.size() - 1).getId();
    } while (true);
}
```

这里使用游标分页，避免页数增大后 `OFFSET` 扫描越来越慢。客户接口改为批量查询，并限制单实例同时执行的导出数量。

## 为什么发布检查没有发现

复盘时没有停在“开发事务写大了”，而是继续追问系统为什么允许这个问题上线：

```text
为什么连接池耗尽？
因为多个导出任务长时间持有连接。

为什么长时间持有？
因为事务覆盖远程调用和文件生成。

为什么测试没有发现？
测试数据只有 50 条，且只执行一次导出。

为什么灰度没有发现？
冒烟只验证文件能生成，没有观察连接池。

为什么影响普通接口？
导出和在线请求共享连接池，没有并发隔离。
```

这说明根因既有代码问题，也有容量测试、灰度指标和资源隔离缺口。

## 后续行动

我们把行动分成三档，避免复盘结束后留下十几条无人处理的建议。

### 一周内

- 导出改为异步分页任务。
- 设置导出并发上限和单用户频率限制。
- 补充 1 万条数据的集成测试。
- 连接池等待数进入告警。

### 一个月内

- 建立外部调用统一超时配置。
- Review 清单增加“事务中是否包含远程调用”。
- 发布看板增加连接池、线程池和下游耗时。
- 为大批量任务建立独立执行资源。

### 持续观察

- 导出任务平均和最大处理时间。
- 每批数据大小是否需要调整。
- 客户批量接口的失败和限流情况。

每项都记录负责人、截止时间和验证标准。“加强监控”“提高意识”没有可验收结果，不算行动项。

## 这次事故改变的排查习惯

第一次线上故障让我形成了一个固定顺序：

```text
先定影响范围
再区分事实与假设
保存最小现场
用指标缩小到资源
用日志和线程定位代码
按授权执行止血
恢复后再做根因与系统改进
```

故障现场最容易犯的错，是把第一个合理解释当成根因，或者为了快速恢复先清掉所有证据。真正有效的排查不是谁最先猜中，而是团队能否用同一组事实逐步收敛，并在恢复业务后让相同问题更难再次发生。
