![死锁问题定位过程技术图](/images/posts/2021/deadlock-debug-cover.svg)

一次批量任务上线后，服务没有崩溃，CPU 和内存也都正常，但部分请求一直处于 pending。重启可以短暂恢复，过一段时间又出现。

这类现象很容易被误判成下游超时。真正的证据来自线程 dump：两个线程分别持有一把锁，同时等待对方手中的锁，JVM 已经明确报告 Java 级死锁。

## 现场信息

```text
现象：批量调拨任务不再推进，相关查询逐渐超时
CPU：22%
堆内存：46%，无持续增长
GC：正常
HTTP 工作线程：大量 WAITING / BLOCKED
数据库连接池：未满
开始时间：19:17 左右
```

监控只说明资源没有明显耗尽，无法证明线程正在正常工作。重启前，我们先在一个异常实例保存现场。

## 第一步：连续抓取线程 dump

```bash
jps -l
jstack -l <pid> > /tmp/thread-1919-1.log
jstack -l <pid> > /tmp/thread-1919-2.log
jstack -l <pid> > /tmp/thread-1919-3.log
```

三次采集间隔约 10 秒。连续快照可以区分“正在执行一段较慢代码”和“始终停在同一等待点”。

生产线程 dump 可能包含类名、业务标识和内部地址，应由授权人员采集并安全保存。采集命令通常开销可控，但仍要观察繁忙进程状态，避免高频循环抓取。

先按线程状态做粗略统计：

```bash
rg 'java.lang.Thread.State' /tmp/thread-1919-1.log | sort | uniq -c
```

结果中 `BLOCKED` 数量持续增加。继续搜索 JVM 的死锁结论：

```bash
rg -n 'deadlock|waiting to lock|locked <' /tmp/thread-1919-1.log
```

文件末尾出现：

```text
Found one Java-level deadlock:
=============================
"transfer-worker-7":
  waiting to lock monitor 0x000000001
  which is held by "transfer-worker-12"

"transfer-worker-12":
  waiting to lock monitor 0x000000002
  which is held by "transfer-worker-7"
```

这已经不是“可能死锁”，而是 JVM 给出的闭环证据。

## 第二步：还原两条锁链

线程 7 的关键栈：

```text
"transfer-worker-7" BLOCKED
at com.example.stock.StockTransferService.transfer(StockTransferService.java:84)
- waiting to lock <0x00000000b> (a java.lang.Object)
- locked <0x00000000a> (a java.lang.Object)
```

线程 12：

```text
"transfer-worker-12" BLOCKED
at com.example.stock.StockTransferService.transfer(StockTransferService.java:84)
- waiting to lock <0x00000000a> (a java.lang.Object)
- locked <0x00000000b> (a java.lang.Object)
```

画成等待图：

```text
worker-7  持有仓库 A 锁 -> 等待仓库 B 锁
worker-12 持有仓库 B 锁 -> 等待仓库 A 锁
                         ^              |
                         +--------------+
```

两个线程都不会主动释放已持有锁，因此相关任务永久等待。随着更多请求等待这两个仓库，工作线程也逐渐被占满。

## 第三步：对应到代码

简化后的旧实现：

```java
public void transfer(Long sourceWarehouseId,
                     Long targetWarehouseId,
                     Long productId,
                     int quantity) {
    Object sourceLock = lockRegistry.get(sourceWarehouseId);
    Object targetLock = lockRegistry.get(targetWarehouseId);

    synchronized (sourceLock) {
        checkAndDecrease(sourceWarehouseId, productId, quantity);
        synchronized (targetLock) {
            increase(targetWarehouseId, productId, quantity);
        }
    }
}
```

请求 `A -> B` 先锁 A 后锁 B；另一个请求 `B -> A` 先锁 B 后锁 A。代码单独看没有语法问题，并发组合后形成循环等待。

还要确认 `lockRegistry` 对同一个仓库 ID 是否始终返回同一个对象。如果每次 `new Object()`，锁根本无法提供互斥；如果 registry 无界增长，又会产生内存问题。

## 临时恢复

死锁中的线程无法通过业务超时自动恢复。我们先停止批量任务入口，保存三份 dump 和相关任务号，再摘除异常实例并正常重启。

重启会打断当前任务，执行前确认：

- 调拨操作是否有事务。
- 已执行步骤能否幂等重试。
- 消息是否会重新投递。
- 是否存在需要人工核对的中间状态。

不能只看接口恢复就重新打开批量入口，否则同一组相反方向任务会再次触发。

## 修复一：所有调用使用稳定锁顺序

按仓库 ID 从小到大获取锁，与调拨方向无关：

```java
public void transfer(Long sourceWarehouseId,
                     Long targetWarehouseId,
                     Long productId,
                     int quantity) {
    if (sourceWarehouseId.equals(targetWarehouseId)) {
        throw new BusinessException("SAME_WAREHOUSE_TRANSFER");
    }

    Long firstId = Math.min(sourceWarehouseId, targetWarehouseId);
    Long secondId = Math.max(sourceWarehouseId, targetWarehouseId);
    Object firstLock = lockRegistry.get(firstId);
    Object secondLock = lockRegistry.get(secondId);

    synchronized (firstLock) {
        synchronized (secondLock) {
            // 获取顺序固定后，再按真实业务方向更新
            doTransfer(sourceWarehouseId, targetWarehouseId, productId, quantity);
        }
    }
}
```

`A -> B` 和 `B -> A` 都先获取编号较小的锁，不再形成环。

锁内只保留必要计算和本地数据更新，不执行远程调用、文件 IO 或不受控重试。持锁时间越长，吞吐越低，故障影响也越大。

## 修复二：增加有限等待和可观察性

一致顺序解决当前死锁，但线程仍可能因其他缺陷长时间等待。对于需要超时能力的场景，可以使用 `ReentrantLock.tryLock`：

```java
boolean firstAcquired = firstLock.tryLock(200, TimeUnit.MILLISECONDS);
if (!firstAcquired) {
    throw new BusinessException("TRANSFER_BUSY");
}

try {
    boolean secondAcquired = secondLock.tryLock(200, TimeUnit.MILLISECONDS);
    if (!secondAcquired) {
        throw new BusinessException("TRANSFER_BUSY");
    }
    try {
        doTransfer(sourceId, targetId, productId, quantity);
    } finally {
        secondLock.unlock();
    }
} finally {
    firstLock.unlock();
}
```

获取失败要返回可处理的业务结果或进入重试队列，不能无限紧循环重试。所有成功获取都必须在 `finally` 中释放。

实际项目将锁等待次数、等待耗时和失败仓库编号做成指标，日志只记录脱敏业务 ID，不输出完整请求对象。

## 单元测试要主动制造相反顺序

普通串行测试永远不会触发。我们使用两个线程同时执行 `A -> B` 和 `B -> A`，并设置测试超时：

```java
@Test(timeout = 3000)
public void oppositeTransfersShouldCompleteWithoutDeadlock() throws Exception {
    CountDownLatch start = new CountDownLatch(1);

    Future<?> first = executor.submit(() -> {
        await(start);
        service.transfer(1L, 2L, 100L, 1);
    });
    Future<?> second = executor.submit(() -> {
        await(start);
        service.transfer(2L, 1L, 100L, 1);
    });

    start.countDown();
    first.get(2, TimeUnit.SECONDS);
    second.get(2, TimeUnit.SECONDS);
}
```

这个测试证明当前实现不会永久等待，但并发测试仍可能受调度影响。还需要代码 Review 检查锁顺序，并在压测中重复运行更多随机组合。

## JVM 锁解决不了多实例一致性

服务部署多个实例后，实例 A 的 `synchronized` 无法阻止实例 B 同时修改相同库存。真实库存一致性最终要依赖数据库条件更新、事务、版本号或经过设计的分布式协调。

例如扣减可以让数据库原子判断：

```sql
UPDATE warehouse_stock
SET available = available - :quantity,
    version = version + 1
WHERE warehouse_id = :warehouseId
  AND product_id = :productId
  AND available >= :quantity
  AND version = :version;
```

受影响行数为 0 时重新读取并按业务决定重试或失败。不要因为修复了单 JVM 死锁，就误以为分布式并发也已解决。

## 取证报告的最终结论

```text
直接证据：JVM 报告 Java-level deadlock
线程闭环：worker-7 持 A 等 B，worker-12 持 B 等 A
代码原因：锁顺序跟随业务参数方向
触发条件：两个仓库同时发生相反方向调拨
短期恢复：停止入口、保存现场、摘流重启
长期修复：按仓库 ID 固定加锁顺序，增加有限等待与并发测试
额外风险：JVM 锁不覆盖多实例
```

这次定位过程并不依赖猜测。线程状态、对象地址、持有关系和源码行号组成了完整证据链。遇到“CPU 不高但请求不动”时，先保留线程现场，往往比反复重启更接近答案。
