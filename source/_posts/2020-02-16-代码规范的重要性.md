> 代码规范真正节省的不是敲键盘时间，而是未来每一次阅读、Review 和故障排查的时间。格式可以交给工具，命名、边界和失败语义仍然需要团队判断。

## 一次看似普通的 Review

下面的方法功能没有错，却让 Review 很难进行：

```java
public void doIt(Long id, String s, Integer t) {
    User u = userMapper.selectById(id);
    if (u != null) {
        if (t == 1) {
            u.setStatus(2);
            userMapper.updateById(u);
            log.info("ok:{}", id);
        }
    }
}
```

问题不只是缩写：

```text
doIt 不表达业务动作
s 没有被使用，调用方却必须传
数字 1、2 的含义不可见
用户不存在时静默返回
没有说明为什么允许状态变化
日志无法判断动作、旧状态和原因
```

如果团队只统一缩进，这段代码仍然难维护。规范必须覆盖业务表达和失败语义。

## 改造后的版本

```java
public void freezeAccount(Long userId, String reason) {
    User user = getExistingUser(userId);
    if (UserStatus.FROZEN.equals(user.getStatus())) {
        return;
    }
    validateCanFreeze(user, reason);
    userRepository.updateStatus(userId, UserStatus.FROZEN);
    log.info("用户账号已冻结, userId={}, previousStatus={}, reason={}",
        userId, user.getStatus(), reason);
}
```

变化包括：方法名表达动作，魔法值变成枚举，校验提取为单一职责方法，日志包含排查所需上下文。代码多了几行，却减少了调用者和维护者的猜测。

## 1. 命名是最便宜的设计

变量和方法名应该回答“它代表什么”，而不是“它是什么类型”：

```java
// 不清晰
List<Order> list;
boolean flag;
long time;

// 更具体
List<Order> pendingOrders;
boolean inventoryReserved;
long paymentDeadlineMillis;
```

命名也要保持同一业务词汇。产品文档写“冻结库存”，代码一部分叫 `lockStock`，另一部分叫 `occupyAmount`，会增加沟通成本。可以维护一份领域术语表，让接口、数据库和代码尽量使用同一语言。

避免为了短而缩写。`ctx`、`req` 在局部范围可能清楚，`ps`、`d`、`x1` 通常只对作者当时清楚。

## 2. 方法只处在一个抽象层次

业务方法里同时出现流程判断、SQL 拼装和 HTTP 细节，会很难阅读：

```text
submitOrder
  -> validateCommand
  -> calculatePrice
  -> reserveInventory
  -> createOrder
  -> publishCreatedEvent
```

顶层方法应该像流程说明，具体实现下沉到对应对象。提取方法不是为了把 100 行机械拆成十个 10 行方法，而是给不同意图命名。

过长参数列表也会暴露缺少业务对象：

```java
// 参数含义容易传错
createOrder(userId, skuId, count, addressId, couponId, source);

// 命令对象可以统一校验和演进
createOrder(CreateOrderCommand command);
```

## 3. 提前返回减少嵌套

```java
public OrderView queryOrder(String orderNo) {
    if (StringUtils.isBlank(orderNo)) {
        throw new IllegalArgumentException("订单号不能为空");
    }
    Order order = orderRepository.findByOrderNo(orderNo);
    if (order == null) {
        throw new OrderNotFoundException(orderNo);
    }
    return orderAssembler.toView(order);
}
```

参数非法和对象不存在先退出，主流程保持在较低缩进层级。提前返回不是所有地方都要使用，但对校验和异常分支很有效。

## 4. 异常要带业务上下文

下面的处理让故障变得不可追踪：

```java
try {
    paymentClient.pay(command);
} catch (Exception ex) {
    throw new RuntimeException("支付失败");
}
```

至少保留原始异常和关键业务标识：

```java
try {
    paymentClient.pay(command);
} catch (PaymentException ex) {
    throw new OrderPaymentException(
        "订单支付失败, orderNo=" + command.getOrderNo(), ex);
}
```

不要捕获 `Exception` 后返回成功，也不要同一个异常在每层重复打印完整堆栈。通常由最了解业务上下文的一层补充信息，在统一边界记录一次。

## 5. 日志规范不是多打印

有价值的日志包含动作、结果、业务主键和必要原因：

```java
log.info("库存冻结成功, orderNo={}, skuId={}, quantity={}",
    orderNo, skuId, quantity);
```

避免：

```text
进入方法
执行成功
参数={整个请求对象}
发生异常={只有 getMessage()}
```

整个请求对象可能包含密码、Token 或个人信息，也会制造大量日志。规范应明确敏感字段、日志级别和采样策略。

## 6. 注释解释为什么

```java
// 支付渠道最多查询最近 30 天记录，超过范围必须走离线对账
if (createdAt.isBefore(thirtyDaysAgo)) {
    return offlineReconciliation(orderNo);
}
```

这类注释解释业务约束，保留价值高。下面的注释只重复代码：

```java
// 用户 ID 赋值给 userId
Long userId = user.getId();
```

代码变化后，过期注释比没有注释更危险。Review 时要把注释和代码当成一个整体检查。

## 7. 可以自动化的全部交给工具

```text
格式化：IDE Formatter / Spotless
静态检查：Checkstyle / PMD / SpotBugs
依赖漏洞：依赖扫描
测试：Maven test + CI
覆盖率：JaCoCo，作为趋势而不是唯一质量指标
```

统一 IDEA 格式配置并放入仓库，避免每个人手工争论空格和换行。CI 检查失败要给出明确修复命令，不能只留下一个红色任务。

自动化规则不要一次开启几百条并要求全量旧代码立即通过。可以先对新增和修改代码生效，再逐步治理存量。

## 8. Review 看什么

我会按这个顺序 Review：

1. 需求是否被正确理解，边界条件有没有遗漏。
2. 数据和接口是否兼容，失败后状态是否可解释。
3. 是否存在重复、过长方法、多层嵌套和不清晰命名。
4. 异常、日志和事务边界是否合理。
5. 并发、性能和安全风险是否被考虑。
6. 测试是否覆盖主要分支。
7. 最后才是格式问题，通常应由工具解决。

Review 意见要说明原因和风险：

```text
不建议：这里写得不好，改一下。

建议：当前先写订单再调用库存，库存失败会留下 CREATED 状态。
请明确失败状态或补偿任务，并增加对应测试。
```

## 9. 规范如何在团队落地

一份没人看的文档不会自动改变代码。有效做法是：

```text
从高频问题中提炼 10 条核心规则
提供正反示例
格式和静态检查进入 CI
PR 模板加入业务、数据、测试和回滚项
Review 中统一引用规则编号
每季度删除无价值规则并补充新案例
```

规范也需要例外机制。性能热点、框架约束或兼容代码可能无法遵循普通写法，但例外应在代码或设计记录中解释原因。

## 最后看质量

规范的目标不是让所有代码看起来像一个人写的，而是让任何团队成员都能更快理解、修改和验证。真正有效的规范会减少 Review 往返、降低缺陷率、缩短新人上手时间，并让线上日志更容易使用。

当团队开始讨论业务边界和失败语义，而不是反复争论括号位置，代码规范才真正发挥作用。
