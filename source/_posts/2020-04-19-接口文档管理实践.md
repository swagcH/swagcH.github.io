> 接口文档不是开发完成后的说明书，而是前端、后端、测试和调用方共同依赖的契约。文档与代码分离维护时，最常见的结果不是“有人忘记更新”，而是团队没有机制证明两者一致。

## 一个联调现场

前端按照文档提交：

```json
{
  "orderNo": "202004190001",
  "reason": "地址填写错误"
}
```

接口却返回：

```json
{
  "code": 40013,
  "message": "reasonCode不能为空"
}
```

后端代码两天前新增了 `reasonCode`，文档没有更新，测试用例只验证了旧参数。三方花了半小时确认，真正修复只有一行字段说明。

这类浪费说明接口管理要覆盖设计、实现、测试、变更和下线，而不只是生成一个 Swagger 页面。

## 1. 一份完整契约包含什么

```text
用途和调用方
HTTP 方法与路径
认证和权限
请求头、路径、查询和请求体参数
字段类型、必填、长度、枚举和示例
成功响应
业务错误码和处理建议
幂等、分页、限流与超时语义
版本和变更记录
负责人
```

只给一个请求 JSON 不够。调用方还需要知道字段为空、重复提交、权限不足和下游超时时会发生什么。

## 2. 先写契约再实现

订单查询示例：

```yaml
paths:
  /api/orders/{orderNo}:
    get:
      summary: 查询订单详情
      operationId: getOrder
      parameters:
        - name: orderNo
          in: path
          required: true
          schema:
            type: string
            maxLength: 32
      responses:
        '200':
          description: 查询成功
        '404':
          description: 订单不存在或当前用户无权查看
```

评审阶段先确认契约，前端可以基于 Mock 开发，测试可以提前编写用例，后端实现也有清晰边界。

OpenAPI 文件应进入版本库，和代码一起 Review。只存在运行时页面中的文档无法比较历史，也很难在 CI 中检查破坏性变更。

## 3. Schema 要复用但不能万能化

```yaml
components:
  schemas:
    OrderSummary:
      type: object
      required: [orderNo, status, totalAmount, createdAt]
      properties:
        orderNo:
          type: string
          example: '202004190001'
        status:
          type: string
          enum: [CREATED, PAID, SHIPPED, FINISHED, CANCELLED]
        totalAmount:
          type: string
          example: '199.00'
        createdAt:
          type: string
          format: date-time
```

公共分页结构、错误结构可以复用，但不要建立一个包含所有业务字段的 `CommonResponseData`。过度复用会让一个字段修改影响大量无关接口。

金额是否用字符串或数字需要团队统一。JSON Number 没有十进制精度语义，跨语言调用时尤其要谨慎。

## 4. 错误码必须可行动

```json
{
  "code": "ORDER_NOT_FOUND",
  "message": "订单不存在",
  "traceId": "f4cc2b1d03b14d12",
  "details": null
}
```

错误码表至少说明：

| 错误码 | 含义 | HTTP 状态 | 调用方动作 |
| --- | --- | ---: | --- |
| `ORDER_NOT_FOUND` | 订单不存在或无权查看 | 404 | 提示并停止重试 |
| `ORDER_STATUS_CONFLICT` | 当前状态不允许操作 | 409 | 刷新订单状态 |
| `RATE_LIMITED` | 请求过于频繁 | 429 | 按 `Retry-After` 重试 |

不要所有业务失败都返回 HTTP 200，也不要所有异常都返回 500。HTTP 状态表达协议层结果，业务错误码提供领域细节。

错误信息不能泄露 SQL、内部 IP 和完整异常栈。`traceId` 用于关联服务端日志。

## 5. 分页语义要写清楚

```yaml
page:
  type: integer
  minimum: 1
  default: 1
size:
  type: integer
  minimum: 1
  maximum: 100
  default: 20
sort:
  type: string
  enum: [createdAt, updatedAt]
```

响应需要说明总数是否精确、排序是否稳定、同一时间新增数据是否影响翻页。大数据量使用游标分页时，游标是否过期、能否反向翻页也属于契约。

## 6. 写接口说明幂等

订单创建可以要求幂等头：

```text
Idempotency-Key: 0fcaf3a1-4d54-4d4d-9ae2-80d99df2be5d
```

文档明确：

- 同一个用户和 Key 在多久内有效。
- 请求体不同时是否返回冲突。
- 首次请求处理中再次提交返回什么。
- 原请求成功后是否返回同一结果。

只写“接口支持幂等”没有可执行意义。

## 7. 认证和权限不是一句“需要 Token”

```text
认证方式：Bearer Token
权限：order:read
数据范围：只能访问当前租户订单
Token 过期：401
权限不足：403
资源不存在或不可见：404
```

上传接口还要说明文件类型、大小、病毒扫描和存储时限。Webhook 要说明签名算法、防重放时间窗口和重试策略。

示例中不能放真实 Token、手机号或客户数据。

## 8. 文档和代码如何保持一致

两种常见方式：

### Code First

通过 Spring 注解从实现生成 OpenAPI。优点是靠近代码，缺点是设计容易滞后到实现阶段，复杂说明仍需人工维护。

### Design First

先维护 OpenAPI，再生成服务端接口或客户端。优点是契约先行，缺点是需要处理生成代码和业务实现边界。

无论选择哪种，都应该在 CI 中：

```text
生成最新 OpenAPI
与仓库基线比较
检查语法和引用
识别删除字段、修改类型等破坏性变更
发布带版本的文档
```

文档生成失败不能被静默忽略，否则线上页面可能一直停留在旧版本。

## 9. 变更分类

通常兼容的变化：

- 新增可选请求字段。
- 新增响应字段，前提是调用方能忽略未知字段。
- 新增错误码并有默认处理。

通常破坏兼容的变化：

- 删除或重命名字段。
- 修改字段类型、单位或含义。
- 可选字段改为必填。
- 修改枚举值语义。
- 改变分页、排序或幂等行为。

破坏性变更应通过新版本、双写兼容或迁移窗口发布，不能只在群里通知。

## 10. 文档的生命周期

```text
草稿：正在评审，不允许生产调用
已发布：与某个服务版本对应
已废弃：标明替代接口和停止时间
已下线：文档保留历史，但不再出现在默认入口
```

每个接口要有负责人。没有负责人时，文档问题、兼容问题和调用咨询都会变成公共群里的随机响应。

## 11. Review 清单

```text
[ ] 路径和 HTTP 方法符合语义
[ ] 请求字段包含类型、约束和示例
[ ] 成功与失败响应都有定义
[ ] 错误码能指导调用方动作
[ ] 权限、数据范围和敏感字段明确
[ ] 分页、幂等、超时和重试语义明确
[ ] 变更兼容性经过检查
[ ] 文档、Mock、测试和代码使用同一契约
[ ] 负责人和下线策略明确
```

接口文档的最终价值不是页面好看，而是减少口头确认，让实现、测试和调用方对同一个行为达成一致。当契约可以被 Review、测试和自动比较时，文档才从附属材料变成工程资产。
