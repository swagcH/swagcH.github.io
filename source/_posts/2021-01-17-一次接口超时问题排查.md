![一次接口超时问题排查技术图](/images/posts/2021/api-timeout-cover.svg)

这次问题的现象是订单提交接口偶发超时。网关在 5 秒后返回 504，订单服务却经常到第 7 秒才打印结束日志。最初大家怀疑库存服务处理慢，但库存服务自己的日志显示请求只执行了 80 多毫秒。

“调用库存耗时 6 秒”和“库存只处理 80 毫秒”看起来矛盾，最后恰恰是这个差值把问题指向了 HTTP 连接池。

## 09:41，告警给出的第一组事实

```text
接口：POST /api/orders/submit
QPS：18 -> 52
P50：210ms
P99：5.2s
网关 504：约 7%
订单服务 CPU：38%
订单服务堆内存：稳定
数据库连接池：active 12 / max 40
```

CPU、堆和数据库连接没有达到上限，说明不能直接把“服务压力大”当成结论。我们先把一次请求拆成入口、数据库、缓存和下游四段。

## 09:44，用同一个 traceId 对齐时间

网关日志：

```text
09:44:12.103 request_started
path=/api/orders/submit
traceId=adf9c0a2b1

09:44:17.105 upstream_timeout
status=504
costMs=5002
```

订单服务日志：

```text
09:44:12.109 order_submit_started traceId=adf9c0a2b1
09:44:12.151 price_calculated costMs=32
09:44:12.188 order_saved costMs=31
09:44:18.374 inventory_reserved costMs=6181
09:44:18.391 order_submit_completed costMs=6282
```

库存服务日志：

```text
09:44:18.277 reserve_started traceId=adf9c0a2b1
09:44:18.362 reserve_completed costMs=85
```

三边时间线对齐后可以看到：

```text
订单开始调用库存：09:44:12.188
库存真正收到请求：09:44:18.277
中间空白时间：约 6.1 秒
```

耗时发生在请求离开订单服务之前，而不是库存业务代码内部。

## 09:49，先排除 DNS、建连和网络

从订单服务同一运行环境执行受控探测：

```bash
getent hosts inventory.service.local
curl --connect-timeout 1 --max-time 2 -o /dev/null -s -w 'connect=%{time_connect} total=%{time_total}\n' http://inventory.service.local/actuator/health
```

连续请求的连接和总耗时都在几十毫秒。网络探测只能说明当时路径可用，不能完全排除瞬时问题，但与 6 秒稳定空白不符。

库存实例的请求量也没有异常堆积。于是排查重点回到订单进程：线程在发出请求前做了什么。

## 09:53，线程 dump 出现共同等待点

我们连续抓取三次线程现场：

```bash
jstack <order-pid> > /tmp/order-0953-1.log
jstack <order-pid> > /tmp/order-0953-2.log
jstack <order-pid> > /tmp/order-0953-3.log
```

生产线程信息可能包含业务类名和参数，应由授权人员采集并按内部规范保存。不要为了贴到公共群里直接上传完整 dump。

大量请求线程停在同一位置：

```text
"http-nio-8080-exec-37" WAITING
at java.util.concurrent.locks.LockSupport.park(...)
at org.apache.http.pool.AbstractConnPool.getPoolEntryBlocking(...)
at org.apache.http.impl.conn.PoolingHttpClientConnectionManager.requestConnection(...)
```

线程不是在等待库存响应，而是在等待从 Apache HttpClient 连接池借出一条连接。

## 09:57，配置解释了为什么只有两条连接

项目创建了共享 HttpClient，却只设置了总连接数：

```java
PoolingHttpClientConnectionManager manager =
        new PoolingHttpClientConnectionManager();
manager.setMaxTotal(100);

CloseableHttpClient httpClient = HttpClients.custom()
        .setConnectionManager(manager)
        .build();
```

`maxTotal=100` 容易让人以为每个下游都有 100 条连接，但连接池还受单路由上限控制。没有显式设置时，当前组件版本默认每个路由只有 2 条。

运行指标印证了这一点：

```text
route=inventory.service.local
leased=2
available=0
pending=61
max=2
```

库存调用平均耗时约 120ms，两条并发连接理论上每秒只能完成大约 16 次调用。订单提交上涨到每秒 50 多次后，请求开始在本地排队。业务日志把“借连接 + 网络 + 下游处理”合并成一个耗时，因此看起来像库存服务慢。

## 三种超时不是一个概念

HTTP 客户端至少要区分：

| 超时 | 等待的事情 | 本次是否命中 |
| --- | --- | --- |
| 连接池获取超时 | 等待一条可用连接 | 是 |
| 建立连接超时 | TCP 与目标地址建连 | 否 |
| 读取超时 | 连接建立后等待响应数据 | 否 |

旧配置只设置了读取超时 8 秒，没有限制连接池等待。请求可以先排队 6 秒，再等待下游 8 秒，整体时间远超网关的 5 秒。

超时应从外到内逐级收紧，并为上层留出处理时间：

```text
网关总预算             5000ms
订单服务业务预算       4500ms
库存单次调用预算       800ms
连接池获取             200ms
建立连接               300ms
读取响应               500ms
失败处理和响应预留     300ms
```

这些数字必须根据真实基线调整，不能直接复制示例。

## 10:06，先做有边界的修复

连接池配置改为：

```java
@Bean
public RestTemplate inventoryRestTemplate() {
    PoolingHttpClientConnectionManager manager =
            new PoolingHttpClientConnectionManager();
    manager.setMaxTotal(100);
    manager.setDefaultMaxPerRoute(40);

    RequestConfig requestConfig = RequestConfig.custom()
            // 等不到连接时尽快失败，避免请求无限堆积
            .setConnectionRequestTimeout(200)
            .setConnectTimeout(300)
            .setSocketTimeout(500)
            .build();

    CloseableHttpClient httpClient = HttpClients.custom()
            .setConnectionManager(manager)
            .setDefaultRequestConfig(requestConfig)
            .build();

    HttpComponentsClientHttpRequestFactory factory =
            new HttpComponentsClientHttpRequestFactory(httpClient);
    return new RestTemplate(factory);
}
```

没有把单路由上限直接设成 100。连接数会同时消耗本机文件描述符、下游接入能力和网络资源，需要结合峰值并发与下游容量确定。

同时增加：

- 连接池 `leased`、`pending`、`available` 指标。
- 库存调用的客户端排队耗时和服务端处理耗时。
- 提交接口并发限制。
- 超时后明确的订单状态与补偿任务。

失败不能盲目重试。库存预占是写操作，只有携带幂等键且下游保证重复请求不重复扣减时，才允许有限重试。

## 压测验证不是只看平均值

在隔离环境使用相同数据和下游延迟进行三轮对照：

| 并发 | 调整前 P99 | 调整后 P99 | pending 峰值 | 错误率 |
| ---: | ---: | ---: | ---: | ---: |
| 20 | 1.6s | 310ms | 8 | 0 |
| 50 | 6.4s | 480ms | 19 | 0 |
| 80 | 超过 8s | 760ms | 37 | 0.4% |

80 并发时出现少量连接获取超时，说明系统开始主动拒绝，而不是让所有请求拖到网关超时。随后根据生产峰值、实例数量和库存服务容量，将单实例并发限制设在可承受范围内。

还额外验证了：

```text
库存响应变慢到 1 秒时是否快速失败
库存完全不可用时线程是否持续增长
订单超时后的状态能否被补偿
网关断开后服务是否继续执行无意义工作
连接释放后池指标是否恢复
```

## 这条调用链最后留下的图

```text
网关 5s
  -> 参数与认证 15ms
  -> 价格计算 35ms
  -> 数据库写入 40ms
  -> HTTP 连接池排队 0~200ms
  -> 库存处理 P99 420ms
  -> 状态落库 30ms
  -> 预留异常处理时间
```

这次排查让我意识到，“某个下游调用耗时 6 秒”仍然是一个过粗的结论。客户端排队、DNS、建连、网络传输和服务端处理必须继续拆开。只有把不同系统的时钟、traceId、线程状态和连接池指标放在一起，消失的那 6 秒才真正有了位置。
