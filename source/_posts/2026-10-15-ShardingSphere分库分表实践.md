分库分表最容易被当成一个"数据量大了就上"的开关，但它实际上会改变事务边界、查询方式和运维复杂度。我在两个项目里用过 ShardingSphere（医院通行证系统、能源大屏），这篇文章记录选型依据、分片键的设计过程，以及分片之后被迫重新考虑的那些事。

## 先说结论：什么时候不该分

很多团队把分库分表当成性能问题的第一选择，但它的代价经常被低估。先排除掉不该分的场景，能省掉大量返工。

**优先做这些，而不是分片：**

- 加索引、改写慢 SQL。很多"数据量大导致的慢查询"，实际是全表扫描或缺索引
- 冷热分离。历史数据归档到独立的归档表或冷存储，热表自然瘦身
- 读写分离。读多写少的场景，加从库比拆分简单得多
- 加缓存。字典、配置、热点数据放 Redis，减少落到数据库的查询
- 升级硬件或调参数。在单表千万级以内，这通常够用

**真正需要分片的信号：**

- 单表数据量到了**千万级以上**，且索引优化后写入或查询仍然明显变慢
- 写入量已经超过单实例的处理能力（不只是慢，是撑不住）
- 数据有明确的、稳定的拆分维度（比如按时间、按租户、按用户 ID）
- 业务能接受分片带来的限制（下面会讲这些限制是什么）

最后一条最关键。**如果找不到一个高基数、且几乎所有查询都会带上的分片键，分片会带来比收益更大的麻烦。**

## 选型：为什么用 ShardingSphere

当时对比了几个方向：

| 方案 | 特点 | 适合的场景 |
|---|---|---|
| **ShardingSphere-JDBC** | 以 jar 包形式嵌入应用，走 JDBC 层，无额外部署 | Java 应用，希望零额外运维成本 |
| **ShardingSphere-Proxy** | 独立进程，对应用透明（像连一个 MySQL） | 多语言技术栈，或希望不改应用代码 |
| **MyCat** | 独立代理，社区活跃度下降 | 存量系统 |
| **自己写路由** | 完全可控 | 分片逻辑极简单且团队有能力维护 |
| **云厂商中间件** | 托管，省运维 | 已绑定云生态 |

我们选 **ShardingSphere-JDBC**，理由很直接：

1. 技术栈是纯 Java，没有跨语言代理的需求
2. 不想为分片额外部署和运维一个中间件进程
3. JDBC 层接入对业务代码侵入小，SQL 写法基本不用改

代价是：**分片规则在应用侧，每个需要访问分片表的服务都要引入依赖并配置规则**。如果服务很多，规则同步会成为一个维护点。这种情况 Proxy 更合适。

## 分片键怎么选

这是整个分片方案里最重要、也最容易做错的一步。分片键选错，后面所有优化都是在补救。

**选择原则：**

**1. 高基数**

分片键的取值要足够分散，否则数据会倾斜到少数分片。用状态字段（只有几个值）做分片键是典型错误。

**2. 查询必带**

理想情况是"绝大多数查询都会带上这个字段"。因为**不带分片键的查询会路由到所有分片**，然后由中间件归并结果——这比单表查询更慢。

**3. 数据分布均匀**

自增 ID 做分片键会有写入热点（新数据总是落在最后一个分片）；用户 ID、租户 ID 这类天然离散的字段更好。

**4. 业务上不会变**

分片键一旦确定，改它的成本极高（等于全量数据重新分布）。

**我们的实际选择：**

医院通行证系统的通行记录有两类主要查询：**按人查历史**、**按时间段查**。

- 选 `user_id` 做分片键 → 按人查能精确定位，但按时间查要扫全部分片
- 选 `create_time` 做分片键 → 按时间查快，但按人查要扫全部
- 最终选 `user_id`，因为"查某个人的通行历史"是高频操作，时间范围查询可以通过额外的查询条件缩小范围

能源大屏的指标数据则是另一种情况：查询几乎总是带**设备/企业维度**，所以分片键选企业维度，保证按企业查询能路由到单片。

**这一步没有标准答案，只能按真实查询模式来定。** 建议先统计线上 SQL 的执行频率，再决定。

## 分片之后必须重新考虑的五件事

分片不是"配置好就完事"。下面每一项都会在分片后变成新问题。

### 1. 本地事务失效

跨分片的写入无法用本地事务保证。这是最容易出事的地方。

```java
// 分片前：一个 @Transactional 就够了
@Transactional
public void transfer(Long fromUserId, Long toUserId, BigDecimal amount) {
    accountMapper.decrease(fromUserId, amount);
    accountMapper.increase(toUserId, amount);   // 分片后：可能在不同库
}
```

分片后 `fromUserId` 和 `toUserId` 可能落在不同库，本地事务只能保证其中一边。

**应对策略，按推荐顺序：**

- **优先改设计**：让需要保证一致的数据落在同一个分片。比如把"账户变更"和"流水记录"用同一个分片键，保证同库
- **柔性事务**：接受最终一致，用本地消息表 + 定时补偿
- **分布式事务框架**：Seata 等。能保证强一致，但性能损耗和运维复杂度都要评估

我们的选择是**改设计 + 柔性事务**。跨分片的强一致场景尽量在设计阶段就消除掉。

### 2. 跨片查询与全路由

没有分片键的查询会变成全路由。比如按手机号查通行记录，而分片键是 `user_id`，就只能查所有分片再归并。

**应对：**

- 给常用查询建**映射表**（手机号 → user_id），先查映射再路由
- 或者用 ElasticSearch 承载多维度检索，数据库只负责按主键取详情（我们在通行证系统里就是这么做的：ES 负责查询，MySQL 负责存储）

### 3. 深分页

```sql
-- 每页 20 条，查第 5000 页
SELECT * FROM record ORDER BY create_time DESC LIMIT 100000, 20;
```

分片后每个分片都要取出前 100020 条，再在内存里归并排序取最后 20 条。**页数越深，内存和耗时增长越快。**

**应对：**

- **游标分页**（推荐）：用上一页最后一条的 `create_time` 作为下一页的起点，避免大 offset
- **限制最大页数**：产品上接受"最多翻到第 N 页"，深翻走导出或检索
- **禁止跨片排序**：如果业务允许，把排序维度也纳入分片键

### 4. 全局唯一 ID

分片后自增主键不再全局唯一。ShardingSphere 内置了雪花算法：

```yaml
spring:
  shardingsphere:
    rules:
      sharding:
        key-generators:
          snowflake:
            type: SNOWFLAKE
```

雪花 ID 是有序的，对索引友好，但要注意**时钟回拨**问题（机器时间回退会生成重复 ID，ShardingSphere 有处理但需要关注）。

### 5. 关联查询与笛卡尔积

分片表之间的 JOIN，如果分片规则不一致，会退化成笛卡尔积（每个分片互相 JOIN）。

**应对：**

- **绑定表**：把分片规则完全一致的表配成绑定表，JOIN 时能按分片对齐，避免笛卡尔积
- **广播表**：字典、配置这类小表，每个库都存一份，JOIN 时无需跨片
- **避免跨片 JOIN**：能在应用层组装就在应用层做

## 几个具体踩坑

**坑 1：分片键为 null 的写入**

写入时如果分片键没值，ShardingSphere 无法计算路由，会直接报错或落到默认分片。我们在数据接入层加了校验，**分片键为 null 的数据直接拒绝入库**，避免脏数据分散在各处。

**坑 2：`COUNT(*)` 变慢**

分片后 `COUNT(*)` 需要在所有分片上执行再求和。数据量大时，这个操作会显著变慢。

应对：维护计数表（增量更新），或者接受近似值，或者从检索系统（ES）取统计。

**坑 3：扩容没有想象中简单**

`MOD` 分片算法（取模）在扩容时需要重新分布几乎所有数据。如果预期会扩容，一开始就考虑：

- **一致性哈希**：扩容时只迁移部分数据
- **预分片**：一开始就分足够的片（比如 64 片），扩的是物理库而不是逻辑片数
- **双倍扩容**：4 库扩到 8 库时，每个旧库拆一半到新库，迁移量可控

我们用的是**预分片**思路——按较细的粒度规划逻辑分片，前期映射到较少的物理库，扩容时只改映射。

**坑 4：分片规则改了但数据没迁**

改分片配置不会自动迁移已有数据。**规则变更必须配套数据迁移脚本和校验**，否则会出现"按新规则查不到老数据"。这类问题往往在线上才暴露。

## 落地检查清单

如果你正在评估或实施分库分表，可以按这个顺序确认：

- [ ] 已排除加索引、冷热分离、读写分离、加缓存这些更简单的方案
- [ ] 分片键基数足够高，且大部分查询会带上它
- [ ] 统计过线上 SQL 的执行频率，确认分片键选择有依据
- [ ] 跨分片事务有明确策略（优先改设计消除，其次柔性事务）
- [ ] 深分页有方案（游标分页优先）
- [ ] 全局 ID 生成方案确定，时钟回拨有处理
- [ ] 关联查询用绑定表/广播表处理，或改为应用层组装
- [ ] 扩容方案想清楚（一致性哈希 / 预分片 / 双倍扩容）
- [ ] 分片规则变更的迁移与校验流程已就位
- [ ] 监控覆盖：各分片数据量是否均衡、慢查询、路由命中情况

## 小结

分库分表解决的是**单实例处理能力的上限问题**，不是"查询慢"的通用解法。它把问题从"一台机器扛不住"转换成"分布式带来的一致性、查询与运维复杂度"。

我现在的判断顺序是：**先优化 SQL 和索引，再考虑缓存和读写分离，最后才动分片**。真到了必须分片的时候，把时间花在**分片键选择**和**事务边界设计**上，比花在配置调优上回报高得多。
