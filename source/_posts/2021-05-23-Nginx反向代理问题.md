Nginx 出现 502 或 404 时，我以前习惯先打开配置文件改 `proxy_pass`。后来发现，状态码相同并不代表原因相同：502 可能是上游端口没监听、连接被拒绝或响应头非法；404 既可能由 Nginx 返回，也可能是后端正常返回。

下面这份分支手册先判断错误来自哪一层，再进入对应路径。

## 总入口：四步确定责任边界

```text
客户端请求
  |
  +-- 1. 域名、TCP、TLS 是否成功
  |
  +-- 2. Nginx access log 是否收到请求
  |
  +-- 3. Nginx 实际匹配哪个 location
  |
  +-- 4. 从 Nginx 所在机器直连 upstream 是否正常
```

先保留一个带时间和请求 ID 的样本：

```bash
curl -v --max-time 5 -H 'X-Request-Id: nginx-debug-20210523-01' https://api.example.com/api/orders/1001
```

调试生产域名时不要在命令历史里写真实 Token。需要认证的请求使用受控测试凭证，并按安全规范处理 `-v` 输出。

同时查看：

```text
Nginx access log：请求是否进入、状态码、upstream 地址与耗时
Nginx error log：连接和代理错误
后端 access log：后端是否真正收到相同 requestId
```

如果 Nginx 没有 access log，请先查 DNS、负载均衡、TLS 或请求是否到了另一台机器，不要急着改后端。

## 502 分支一：Connection refused

典型错误：

```text
connect() failed (111: Connection refused) while connecting to upstream
upstream: "http://127.0.0.1:8080/api/orders/1001"
```

它表示 Nginx 已经找到目标 IP，但对应端口没有接受连接。按顺序检查：

```bash
ss -lntp
curl --max-time 2 http://127.0.0.1:8080/actuator/health
ps -ef | rg 'order-service'
```

常见原因：

- 后端进程没有启动或启动后退出。
- 服务实际监听 8081，Nginx 配成 8080。
- 服务只监听特定网卡。
- 容器端口与宿主机映射不一致。
- upstream 配置仍指向已下线实例。

不要看到连接拒绝就延长超时。对方没有监听，等更久也不会成功。

## 502 分支二：No route 或连接超时

错误可能是：

```text
connect() failed (113: No route to host) while connecting to upstream
upstream timed out while connecting to upstream
```

这类问题发生在建连阶段，重点是：

```text
upstream IP 是否正确
路由和安全组是否允许
容器或集群网络是否连通
目标端口是否被防火墙拦截
域名解析结果是否过期
```

从 Nginx 所在网络命名空间测试比从个人电脑测试更有意义。个人电脑能访问，不代表 Nginx 节点到上游可达。

网络策略和防火墙变更应由有权限的运维人员执行。不要为验证问题临时关闭整机防火墙。

## 502/504 分支三：上游处理太慢

错误日志：

```text
upstream timed out (110: Connection timed out)
while reading response header from upstream
```

这里 TCP 已经连接成功，Nginx 在等待响应头。检查 access log 中两个时间：

```nginx
log_format upstream_timing
  '$request_id status=$status request_time=$request_time '
  'upstream_addr=$upstream_addr '
  'upstream_status=$upstream_status '
  'connect=$upstream_connect_time '
  'header=$upstream_header_time '
  'response=$upstream_response_time';
```

`connect` 很小、`header` 很大，通常说明后端处理慢或后端内部排队。继续用 requestId 查后端日志、线程池、数据库和下游，不要只在 Nginx 增加 `proxy_read_timeout`。

超时必须符合整体预算：

```nginx
proxy_connect_timeout 300ms;
proxy_send_timeout 2s;
proxy_read_timeout 3s;
```

语法和单位应在当前 Nginx 版本验证。长文件下载、普通 API 和异步回调不一定使用同一超时。

## 502 分支四：上游响应不符合协议

如果 error log 出现：

```text
upstream sent too big header
upstream sent invalid header
upstream prematurely closed connection
```

分别考虑：

- Cookie 或响应头过大。
- 后端把非 HTTP 内容发到 HTTP 端口。
- 应用崩溃、被 OOM Kill 或主动关闭连接。
- 代理协议 HTTP/HTTPS 配反。

“响应头过大”不能立即通过无限增大 buffer 解决。先确认是异常 Cookie、重复 Header 还是确有业务需要，并评估内存成本。

应用提前断开时，查看同一时刻的应用退出日志、容器事件和系统 OOM 记录。Nginx 只能看到连接结束，无法替后端说明为什么结束。

## 404 的第一个问题：谁返回的

在 access log 同时记录 `status` 和 `upstream_status`：

```text
status=404 upstream_status=-
```

横线表示没有请求上游，404 多半由 Nginx 的静态文件或 location 规则产生。

```text
status=404 upstream_status=404
```

说明请求已经代理，后端返回 404。此时应核对后端路径、Context Path、HTTP 方法和版本。

响应页面样式只能作为线索，不能当证据。统一错误页可能覆盖后端原始响应。

## 404 分支一：location 匹配错误

配置中可能同时存在：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}

location /api/ {
    proxy_pass http://order_backend;
}
```

如果写成 `location /api` 或被正则 location 抢先处理，路径可能落入前端静态规则。排查时查看完整生效配置：

```bash
nginx -T
```

`nginx -T` 可能输出证书路径、内部域名或其他敏感配置，只在授权服务器查看，不把完整结果发到公开位置。

需要理解基本匹配：

```text
=       精确匹配
普通前缀  选择最长前缀
^~      命中后不再检查正则
~ / ~*  正则匹配
```

配置复杂时，通过一个最小测试路径验证，而不是凭肉眼猜最终 location。

## 404 分支二：proxy_pass 尾斜杠改变路径

这两个配置转发结果不同。

保留原始 URI：

```nginx
location /api/ {
    proxy_pass http://order_backend;
}
```

`/api/orders/1001` 转发为 `/api/orders/1001`。

替换匹配前缀：

```nginx
location /api/ {
    proxy_pass http://order_backend/;
}
```

`/api/orders/1001` 转发为 `/orders/1001`。

哪种正确取决于后端真实路径。修改前直接从 Nginx 节点请求 upstream 的两个候选路径，确认后再调整。

## 404 分支三：Host 和转发头不符合后端路由

部分后端按 Host、协议或前缀生成路由：

```nginx
location /api/ {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Request-Id $request_id;
    proxy_pass http://order_backend;
}
```

Header 名称和信任边界要与后端约定。后端不能无条件信任任何客户端传来的 `X-Forwarded-For`，应该只信任受控代理链。

如果 upstream 是虚拟主机，可能需要将 `Host` 设置为上游约定域名，而不是外部域名。

## 修改配置的安全闭环

每次修改按固定顺序：

```bash
# 1. 检查语法和引用文件
nginx -t

# 2. 由有权限的操作人平滑重载
nginx -s reload

# 3. 立即验证目标路径、旧路径和错误日志
```

重载会影响生产流量，应通过发布或变更流程执行。语法通过只说明配置可解析，不说明转发行为正确。

验证至少包含：

```text
目标接口成功
不存在路径仍正确返回 404
认证 Header 未丢失
请求体和文件上传正常
WebSocket 或流式接口未被普通超时影响
access log 的 upstream 地址、状态和耗时正确
```

## 最短决策表

| 现象 | 先看 | 典型方向 |
| --- | --- | --- |
| 无 access log | DNS、LB、TLS | 请求未到当前 Nginx |
| 502 + refused | 监听端口、进程 | 上游未启动或端口错误 |
| 502 + connect timeout | 路由、网络策略 | Nginx 到上游不可达 |
| 504/read timeout | upstream 时间 | 后端处理或内部排队 |
| 404 + upstream=- | location、静态规则 | Nginx 返回 |
| 404 + upstream=404 | 转发 URI、Host | 后端返回 |

Nginx 排查最有效的方式不是记住更多配置项，而是始终回答两个问题：请求目前到哪一层，最后一次成功动作是什么。access log、error log、直连上游和生效配置一旦能够互相印证，502 与 404 就不再是只能靠试改配置解决的黑盒。
