用消息队列"解耦"是最常见的说法，但真正落地时，**大部分问题都出在可靠性上**：消息发出去没到、到了但消费者处理失败、处理成功了但重复消费了两次。

这篇文章不讲 API 怎么调，而是讲清楚三件事：**什么场景该用 MQ、怎么保证消息不丢、为什么消费端必须做幂等**。

## 先明确：什么时候不该用 MQ

MQ 引入了新的故障点（Broker 挂了、消息积压、重复消费），所以先排除不该用的场景：

**不该用的场景：**

- **需要同步返回结果的调用**。比如"下单后立即返回库存扣减结果"——这种用 RPC 更直接，硬套 MQ 会让调用方需要额外等待回执
- **强一致性要求**。MQ 是最终一致的工具，跨服务强一致要靠分布式事务，不是 MQ 能解决的
- **逻辑本来就简单**。两个服务之间的简单调用，引入 MQ 后需要处理幂等、重试、死信，复杂度反而上升
- **低延迟要求极高**。多一跳 Broker 就多一次网络往返

**适合用的场景：**

- **异步处理**：主流程不需要等结果（发短信、生成报表、推送通知）
- **流量削峰**：瞬时高并发写请求先入队，消费者按自己的节奏处理
- **系统解耦**：一个事件需要多个下游响应，且下游可能随时增减
- **最终一致**：跨服务的状态同步，允许短暂延迟

**我在项目里的实际场景**：医院通行证系统中，人员服务（负责权限校验）和设备模块（负责闸机控制）原本是同步调用——设备模块响应慢或重启时，人员服务会跟着超时。改成 MQ 后，人员服务只负责"发布通行事件"，设备模块按自己的节奏消费，一方故障不再影响另一方。

## 选型：RabbitMQ 适合什么

| 中间件 | 定位 | 适合 |
|---|---|---|
| **RabbitMQ** | 传统消息队列，路由灵活 | 业务消息、需要复杂路由、消息量中等（万级 QPS）|
| **Kafka** | 分布式流平台 | 日志采集、事件流、超高吞吐（十万级+）|
| **RocketMQ** | 阿里开源，兼顾两者 | 电商交易、需要事务消息 |

**选 RabbitMQ 的理由**（我们的场景）：

1. **路由能力强**：Exchange + Routing Key 的组合能表达复杂的投递规则（比如"只发给某个院区的设备"）
2. **消息量匹配**：医院场景是万级 QPS，Kafka 的吞吐优势用不上，反而运维更重
3. **有死信队列**：处理失败的消息有天然的去处
4. **延迟低**：相比 Kafka 的批量设计，RabbitMQ 的单条投递延迟更低

**如果消息量到十万级 QPS，或者需要消息回放（重新消费历史消息），就该选 Kafka。**

## 交换机类型：路由能力的差异

RabbitMQ 的路由能力来自 **Exchange + Routing Key** 的组合，三种常用类型：

![direct / topic / fanout 三种交换机的路由能力对比](/images/posts/2026/rabbitmq-exchange-types.svg)

| 类型 | 路由规则 | 适用场景 |
|---|---|---|
| **direct** | 精确匹配 Routing Key | 点对点业务指令 |
| **topic** | 通配符匹配（`*` 一个词，`#` 多个词）| 按维度订阅（院区、设备类型）|
| **fanout** | 忽略 Routing Key，广播到所有绑定队列 | 一个事件多个下游响应 |

**routing key 就是契约。** 路由能力越强，命名约定越要提前定清楚，否则后期会变成一堆含义不明的字符串。

**我们在通行证系统里的用法**：设备控制指令用 `direct`（精确投递到目标设备类型的队列）；通行事件用 `topic`（`pass.{院区}.{设备类型}`，方便按院区或按设备类型订阅）；系统通知用 `fanout`（短信、统计、日志三个下游各一个队列，新增下游不用改生产端）。

## 可靠投递：三个环节都可能丢消息

**这是本文的核心。** 消息从生产者到消费者，中间有三个可能丢失的环节：

```
生产者 ──①──> Broker（交换机/队列） ──②──> 消费者 ──③──> 处理成功
        可能丢：网络抖动            可能丢：Broker宕机   可能丢：消费失败
```

**三个环节都要处理，缺一个都不算可靠。**

![RabbitMQ 可靠投递的三个环节与对应方案](/images/posts/2026/rabbitmq-reliability.svg)

### 环节①：生产者 → Broker

**问题**：消息发出去了，但 Broker 没收到（网络抖动、Broker 重启）。

**方案：发布者确认（Publisher Confirm）**

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated   # 开启确认回调
    publisher-returns: true              # 开启路由失败回调
```

```java
rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) {
        // Broker 未确认：需要重发或记录待补偿
        log.error("消息未确认: {}, 原因: {}", correlationData, cause);
        // 落库到"待重发表"，由定时任务补偿
    }
});

// 消息到达交换机但路由不到队列时触发
rabbitTemplate.setReturnsCallback(returned -> {
    log.error("消息路由失败: exchange={}, routingKey={}",
        returned.getExchange(), returned.getRoutingKey());
});
```

**注意**：`Confirm` 只保证消息到了**交换机**，不保证进了**队列**。路由不到队列的情况要用 `Returns` 捕获。

**方案二：事务（不推荐）**

`channel.txSelect()` 也能保证，但**性能下降严重**（每次提交都要等 Broker 响应）。**生产环境用 Confirm，不用事务。**

### 环节②：Broker 内部

**问题**：Broker 收到了消息，但还没落盘就宕机了。

**方案：三个都要持久化**

```java
// ① 交换机持久化
new DirectExchange("exchange.name", true, false);

// ② 队列持久化
new Queue("queue.name", true);

// ③ 消息持久化（默认就是持久化的，但显式声明更清晰）
MessageProperties props = MessageProperties.PERSISTENT_TEXT_PLAIN;
```

**三者缺一不可**：交换机不持久化，重启后路由规则丢失；队列不持久化，重启后队列和消息一起没了。

**代价**：持久化会降低吞吐（要写磁盘）。对可靠性要求不高的场景（比如日志推送），可以不持久化换取性能。

### 环节③：消费者处理

**问题**：消息投递给了消费者，但处理过程中抛异常/服务重启，消息被丢弃。

**方案：手动 ACK**

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual   # 默认是 auto，处理失败也会 ACK
```

```java
@RabbitListener(queues = "order.queue")
public void handle(OrderMessage message, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) long tag) {
    try {
        process(message);
        // 处理成功才 ACK
        channel.basicAck(tag, false);
    } catch (BusinessException e) {
        // 业务异常：不重试（重试也没用），记录后 ACK，走人工处理
        log.error("业务异常，不再重试: {}", message, e);
        channel.basicAck(tag, false);
    } catch (Exception e) {
        // 系统异常：拒绝并重回队列（或进死信队列）
        log.error("系统异常，稍后重试: {}", message, e);
        channel.basicNack(tag, false, true);   // requeue = true
    }
}
```

**关键点**：

- **默认的 `auto` 模式是坑**：方法返回就 ACK，抛异常也 ACK（因为 Spring 捕获了），消息就丢了
- **区分业务异常和系统异常**：业务异常重试多少次都失败，应该记录后丢弃；系统异常（网络、超时）才值得重试
- **`basicNack(requeue=true)` 有风险**：如果失败是必然的（比如数据格式错），会无限重试打满 CPU。**应该配合重试次数限制 + 死信队列**

## 消费端必须做幂等

**这是最容易被忽略、也最容易出线上问题的一点。**

### 为什么必须幂等

RabbitMQ（以及绝大多数 MQ）只能保证 **at-least-once**（至少一次），不能保证 exactly-once。原因是：

```
消费者处理成功 → 准备 ACK → 【服务重启/网络断】→ ACK 没送达
→ Broker 认为消息未消费 → 重新投递 → 消息被处理了两次
```

**这个窗口无法消除**，因为"处理"和"ACK"是两个动作，不可能原子。所以：

> **消费端必须假设"同一条消息可能被投递多次"，并保证重复处理的结果与处理一次相同。**

### 实现方案

**方案一：唯一 ID + 去重表（最通用）**

```java
@Transactional
public void handle(OrderMessage message) {
    // 消息自带唯一 ID（生产端生成）
    String msgId = message.getMsgId();

    // 利用唯一索引：插入成功说明首次处理，插入冲突说明已处理过
    try {
        dedupMapper.insert(new DedupRecord(msgId, LocalDateTime.now()));
    } catch (DuplicateKeyException e) {
        log.info("消息已处理，跳过: {}", msgId);
        return;
    }

    // 首次处理，执行业务逻辑（与去重记录在同一事务里）
    doBusiness(message);
}
```

**关键**：去重记录的插入和业务逻辑**必须在同一个事务**里，否则可能出现"去重记录写了但业务没执行"。

**方案二：状态机（适合有明确状态流转的业务）**

```sql
-- 只有当前状态是"待处理"时才更新，天然幂等
UPDATE orders SET status = 'PAID'
WHERE id = #{orderId} AND status = 'UNPAID';
```

`UPDATE ... WHERE 旧状态` 的影响行数如果是 0，说明已经处理过了。

**方案三：Redis 去重（适合高并发、可接受少量丢失）**

```java
Boolean first = redis.opsForValue().setIfAbsent("msg:" + msgId, "1", 24, TimeUnit.HOURS);
if (Boolean.FALSE.equals(first)) {
    return;   // 已处理
}
```

**注意**：Redis 不是持久的，宕机或过期后去重失效。**只适合对重复不敏感的场景**。

**方案四：业务天然幂等**

最理想的情况是业务操作本身幂等，不需要额外机制。比如：
- `SET status = 'X'`（赋值操作，执行多次结果相同）
- 插入前先判断存在性

**但这需要业务设计配合**，不是所有场景都能做到。

### 我的选择

**唯一 ID + 去重表**，因为：
- 通用，不依赖业务逻辑的特殊设计
- 去重记录可查，出问题能追溯
- 代价是一张表和一个唯一索引（可定期清理历史记录）

**在项目里，通行记录和设备指令都用了这个方案。**

## 顺序性

**RabbitMQ 不保证全局顺序**，但可以保证**单队列内的顺序**（单消费者时）。

**如果需要顺序：**

1. **按业务键路由到同一队列**。比如按 `userId` 取模路由，保证同一个用户的消息进同一个队列
2. **单队列单消费者**（并发度受限，需要权衡）

```java
// 发送时按业务键计算路由键，保证同一用户的消息进同一队列
String routingKey = "user." + (userId % 4);
rabbitTemplate.convertAndSend("exchange", routingKey, message);
```

**注意**：即使这样，**重试仍可能打乱顺序**（失败的消息重回队列会排到末尾）。对顺序要求极高的场景（比如资金流水），需要在业务层做版本号校验。

## 死信队列与重试

**死信（Dead Letter）** 是指无法被正常消费的消息，进入死信的条件：

1. 消息被 `basicNack` / `basicReject` 且 `requeue=false`
2. 消息 TTL 过期
3. 队列达到最大长度

**配置死信队列：**

```java
@Bean
public Queue businessQueue() {
    return QueueBuilder.durable("business.queue")
        .withArgument("x-dead-letter-exchange", "dlx.exchange")
        .withArgument("x-dead-letter-routing-key", "dlx.routing.key")
        .build();
}
```

**重试策略**（推荐分层）：

```
第一次失败 → 延迟 5 秒重试
第二次失败 → 延迟 30 秒重试
第三次失败 → 进入死信队列 + 告警
```

**延迟重试的实现**：用 TTL + 死信队列组合（消息过期后进入重试队列），或者用延迟插件 `rabbitmq_delayed_message_exchange`。

**死信队列必须有告警**，否则消息静静躺在那儿没人知道。我们的做法是死信队列有消息就推送告警到飞书。

## 消息积压

积压的常见原因：

- 消费者处理太慢（业务逻辑重、有同步远程调用）
- 消费者实例不够
- 消费者出故障（一直重试失败的消息）

**处理方式：**

| 情况 | 处理 |
|---|---|
| 消费者处理慢 | 优化业务逻辑，或增加消费者实例 |
| 消费者数量不够 | 水平扩容（注意：队列的消费者数不能超过队列分片能力）|
| 消息一直失败重试 | 定位根因；临时把失败消息转移到"待人工处理"队列 |
| 突发流量 | 加临时消费者快速消费，或按业务降级 |

**关键**：**积压要有监控**。`rabbitmqctl list_queues name messages` 或者通过管理插件看队列深度，超过阈值告警。

## 落地检查清单

- [ ] 确认场景适合用 MQ（不需要同步返回、能接受最终一致）
- [ ] 生产者开启 `publisher-confirm`，并处理未确认的消息（落库补偿）
- [ ] 生产者开启 `publisher-returns`，处理路由失败
- [ ] 交换机、队列、消息**三者都持久化**
- [ ] 消费者用**手动 ACK**（不用默认的 auto）
- [ ] 区分业务异常（不重试，记录后 ACK）和系统异常（重试）
- [ ] **消费端实现幂等**（唯一 ID + 去重表 / 状态机）
- [ ] 需要顺序时，按业务键路由到同一队列
- [ ] 配置死信队列，且**死信有告警**
- [ ] 重试有次数上限，不是无限重回队列
- [ ] 队列深度有监控和告警
- [ ] 消息体不要太大（大对象放对象存储，消息里只传引用）

## 小结

MQ 的价值在于**解耦和削峰**，但代价是**引入了最终一致性和重复消费的问题**。用之前先想清楚：

1. **这个调用真的需要异步吗？** 同步能解决就别上 MQ
2. **消息丢了能接受吗？** 不能接受就必须做三个环节的可靠投递
3. **重复消费会出问题吗？** 会出问题就必须做幂等

**最后一点最重要**：很多团队把 MQ 接进去就以为"解耦完成了"，但**没有做幂等**，结果上线后出现重复扣款、重复发短信、重复记录。这类问题的根因不是 MQ 不可靠，而是**消费端假设了"只会收到一次"**。
