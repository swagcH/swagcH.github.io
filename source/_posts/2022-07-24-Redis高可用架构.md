> 这篇不从安装命令开始，而是先比较方案，再记录一次 Sentinel 故障转移演练。因为 Redis 高可用最容易被误解的地方，是把“有副本”当成“不会中断”，或者把“自动切主”当成“不会丢数据”。

## 1. Redis 在系统里承担什么角色

同样是 Redis，不同用途对应的恢复目标完全不同：

```text
普通查询缓存：可以回源数据库，短暂不可用可以降级
登录会话：丢失会让用户重新登录
分布式锁：故障切换可能影响互斥语义
限流计数：短暂不一致会影响流量控制
库存预扣：数据丢失可能造成超卖
```

架构设计前先定义两个指标：

- RTO：故障后允许多久恢复服务。
- RPO：允许丢失多长时间窗口的数据。

如果业务要求数据绝不丢失、强一致写入，Redis 主从加 Sentinel 并不能天然满足，需要重新评估数据模型和存储选择。

## 2. 四种常见形态

| 形态 | 解决的问题 | 没解决的问题 |
| --- | --- | --- |
| 单机 | 简单缓存 | 单点故障、容量上限 |
| 主从复制 | 读副本、数据冗余 | 自动选主、异步复制丢失窗口 |
| Sentinel | 监控和自动故障转移 | 水平分片、绝对零数据丢失 |
| Redis Cluster | 分片、扩容、自动切换 | 跨槽操作限制、客户端复杂度 |

本文选择一主两从加三个 Sentinel，适合数据量仍能放在单个主节点、但需要自动故障转移的场景。

```text
app-1 / app-2
      |
sentinel-1  sentinel-2  sentinel-3
      |
redis-master 10.0.0.11:6379
      |-- replica-1 10.0.0.12:6379
      `-- replica-2 10.0.0.13:6379
```

三个 Sentinel 应部署在相互独立的故障域，全部放在同一台机器只能演示流程，不能抵抗机器故障。

## 3. 先保证主从复制正常

从节点配置：

```conf
replicaof 10.0.0.11 6379
masterauth <managed-secret>
replica-read-only yes
```

`<managed-secret>` 是文档占位符，需要由部署系统渲染为真实值，Redis 6.2 配置文件不能依赖 Shell 自动展开它。配置文件不应该提交真实密码。生产环境可以使用受控配置文件、权限隔离和 Redis ACL，并限制 Redis 端口只能被业务网段访问。

主节点查看复制：

```bash
redis-cli -h 10.0.0.11 -p 6379 INFO replication
```

重点输出：

```text
role:master
connected_slaves:2
slave0:ip=10.0.0.12,port=6379,state=online,offset=...,lag=0
slave1:ip=10.0.0.13,port=6379,state=online,offset=...,lag=0
```

旧版本沿用 `slave` 字段名，新版本命令和文档更多使用 `replica`。看到两个副本在线后，还要观察复制延迟和 `master_repl_offset`，不能只看连接数量。

Redis 主从复制默认是异步的。主节点回复客户端成功后，这次写入可能还没有到副本；主节点此时故障，新主节点可能缺少最后一小段数据。

可以用下面的配置减少风险：

```conf
min-replicas-to-write 1
min-replicas-max-lag 10
```

它表示没有至少一个延迟小于 10 秒的副本时拒绝写入。这样降低数据损失概率，但网络分区时会牺牲可用性，不能不分析业务就照搬。

## 4. Sentinel 配置含义

三个 Sentinel 使用相同的监控名称：

```conf
port 26379
sentinel monitor mymaster 10.0.0.11 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
sentinel auth-pass mymaster <managed-secret>
```

`monitor` 最后的 `2` 是 quorum。至少两个 Sentinel 同意主节点客观下线，才会进入故障转移判断。它不是 Sentinel 总数，也不是副本数量。

`down-after-milliseconds=5000` 代表单个 Sentinel 多久无法得到有效响应后认为主观下线。设置太短会因瞬时抖动频繁切换，太长则增加恢复时间。

`parallel-syncs=1` 控制故障转移后同时向新主同步的副本数。同步期间副本可能不可用，值越大恢复越快，但新主节点网络和磁盘压力也更大。

启动后检查：

```bash
redis-cli -h 10.0.0.21 -p 26379 SENTINEL masters
redis-cli -h 10.0.0.21 -p 26379 SENTINEL replicas mymaster
redis-cli -h 10.0.0.21 -p 26379 SENTINEL ckquorum mymaster
```

旧版本命令可能使用 `SENTINEL slaves`。`ckquorum` 能检查当前可用 Sentinel 是否足以完成故障转移，比只看 `masters` 更有价值。

## 5. Spring Boot 客户端配置

Spring Boot 2.x 示例：

```yaml
spring:
  redis:
    password: ${REDIS_PASSWORD}
    timeout: 2s
    sentinel:
      master: mymaster
      nodes:
        - 10.0.0.21:26379
        - 10.0.0.22:26379
        - 10.0.0.23:26379
    lettuce:
      pool:
        max-active: 50
        max-idle: 20
        min-idle: 5
        max-wait: 500ms
```

客户端连接的是 Sentinel 列表，不是把主节点地址写死。故障转移后，客户端从 Sentinel 获取新主地址并重连。

连接池参数要结合并发量、命令耗时和实例数量计算。`max-active` 很大并不会提升 Redis 单线程命令执行能力，反而可能在 Redis 变慢时积累更多等待请求。

## 6. 一次可控的故障转移演练

演练前准备：

```text
确认主从复制正常
确认三个 Sentinel 满足 quorum
记录当前 master_run_id 和复制 offset
准备持续读写的测试 key
打开客户端重连、错误率和延迟监控
确认演练环境和回退方式
```

先写一个带时间戳的测试值：

```bash
redis-cli -h 10.0.0.11 SET ha:drill "before-failover-20220724"
redis-cli -h 10.0.0.12 GET ha:drill
redis-cli -h 10.0.0.13 GET ha:drill
```

在隔离环境可以执行主动切换：

```bash
redis-cli -h 10.0.0.21 -p 26379 SENTINEL failover mymaster
```

这是一条会改变主从角色的命令，生产环境必须走变更流程，不能拿它做日常健康检查。

演练期间观察 Sentinel 日志：

```text
+sdown
+odown
+try-failover
+selected-slave
+promoted-slave
+switch-master
```

切换完成后检查：

```bash
redis-cli -h 10.0.0.21 -p 26379 SENTINEL get-master-addr-by-name mymaster
redis-cli -h new-master -p 6379 INFO replication
redis-cli -h new-master -p 6379 GET ha:drill
```

客户端侧记录失败请求数量和恢复时间。Sentinel 切主成功不代表应用零错误，DNS、连接池、拓扑刷新和重试策略都会影响实际 RTO。

## 7. 网络分区与“脑裂”风险

假设旧主节点与 Sentinel 失联，但仍能接收部分客户端写入。Sentinel 会提升一个副本为新主，网络恢复后旧主被降级，它隔离期间接受的写入可能丢失。

降低风险的方法包括：

- 合理设置 `min-replicas-to-write` 和最大复制延迟。
- 客户端不要绕过 Sentinel 固定连接旧主。
- Redis 节点、Sentinel 和应用之间使用一致的网络访问策略。
- 对关键数据保留数据库事实来源和业务对账。

这些措施是在一致性和可用性之间做选择，不可能让异步复制同时获得所有保证。

## 8. Redis 故障时应用怎么保护数据库

即使切换只需要十几秒，缓存未命中和连接错误也可能让流量直接打向数据库。

我会准备三层保护：

1. 热点只读数据使用短时间本地缓存。
2. 回源数据库前做并发合并或互斥重建，避免同一 key 同时查询。
3. 数据库入口设置限流和降级，宁可返回可解释的繁忙提示，也不要拖垮主库。

过期时间增加随机值可以缓解同一时刻大量 key 失效：

```java
int baseSeconds = 30 * 60;
int jitterSeconds = ThreadLocalRandom.current().nextInt(0, 5 * 60);
redisTemplate.opsForValue().set(key, value,
    baseSeconds + jitterSeconds, TimeUnit.SECONDS);
```

这只能缓解缓存雪崩，不解决 Redis 实例不可用，因此仍要有连接失败的降级路径。

## 9. 持久化和备份不能缺席

Sentinel 管理高可用，不等同于备份。误删除、错误写入会复制到所有副本。

需要根据恢复目标选择 RDB、AOF 和独立备份：

```text
RDB：恢复快，快照间隔内可能丢数据
AOF：记录更细，文件更大，需要关注重写
离线备份：防止整个集群误操作或文件损坏
```

备份必须定期做恢复验证。只有生成文件、从未恢复过的备份不能算可靠。

## 10. 日常监控

```text
实例：存活、角色、连接数、阻塞客户端、内存、淘汰 key
复制：副本在线数、复制延迟、offset 差距、全量同步次数
Sentinel：可用数量、quorum、切换次数、主观/客观下线
客户端：连接失败、命令超时、连接池等待、降级次数
业务：缓存命中率、数据库回源量、关键 key 对账
```

高可用演练的结果也要进入记录：切换用了多久、丢了多少请求、有没有数据缺口、客户端多久恢复、数据库是否被回源流量冲击。

## 结论

Sentinel 解决的是主节点故障后的自动发现和切换，它没有消除异步复制的数据窗口，也没有替应用处理缓存击穿和数据库保护。真正的高可用是 Redis、客户端、业务降级、监控和备份共同形成的恢复能力。

架构是否可靠，不看正常情况下有几个节点，而看故障发生以后：能不能自动恢复、恢复用了多久、数据损失是否在承诺范围内，以及应用有没有把压力转移成下一场数据库故障。
