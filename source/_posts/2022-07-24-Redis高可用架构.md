# 背景

为什么会研究这个问题

Redis 从单机缓存进入核心链路后，高可用就必须认真考虑。最初使用 Redis 只是为了缓存热点数据，服务挂了最多回源数据库。但随着登录态、限流、库存预扣等场景进入 Redis，单点故障的影响范围明显扩大，所以需要研究 Redis 高可用架构。

# 问题

遇到了什么情况

单机 Redis 最大的问题是故障恢复依赖人工。Redis 进程挂掉、机器重启、内存打满都会导致业务抖动。如果没有主从、哨兵或集群方案，应用只能等待人工处理。另一个问题是，很多人以为主从复制就等于高可用，但主节点故障后如果不能自动切换，仍然无法支撑线上稳定性。

# 分析

排查过程

```text
Sentinel 架构：

app
 ↓
sentinel-1 sentinel-2 sentinel-3
 ↓
redis-master
 ↓
redis-slave-1
redis-slave-2
```

```conf
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
```

排查高可用时，重点看三个问题：主从复制是否正常，Sentinel 是否能判断主观下线，故障转移后客户端是否能感知新主节点。

# 解决方案

具体操作

```yaml
spring:
  redis:
    sentinel:
      master: mymaster
      nodes:
        - 127.0.0.1:26379
        - 127.0.0.1:26380
        - 127.0.0.1:26381
```

```bash
redis-cli -p 26379 sentinel masters
redis-cli -p 26379 sentinel slaves mymaster
redis-cli -p 26379 sentinel failover mymaster
```

对于缓存场景，我会同时配合过期时间随机化、本地缓存和降级策略，避免 Redis 故障时所有流量瞬间压到数据库。

# 总结

经验沉淀

Redis 高可用不能只看 Redis 本身，还要看客户端、业务降级和数据库保护。Sentinel 解决主从切换问题，但不解决缓存击穿、雪崩和热点 key 问题。真正可靠的缓存架构，需要高可用、限流、降级和监控一起设计。
