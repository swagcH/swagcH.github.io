接手老项目时，我最初做过一件效率很低的事：从包结构第一行开始逐个打开类，看到命名不顺眼就记一条“待重构”。两天后记了几十条问题，却仍然回答不了一个简单问题：用户提交订单后，系统到底经过哪些步骤？

后来我把阅读遗留代码当成一次代码侦查。目的不是把每个类都看懂，而是在有限时间里建立一张可靠地图，知道入口在哪里、数据怎样变化、异常会停在哪里，以及这次修改会碰到什么。

## 先写一张侦查任务卡

没有具体问题，阅读很容易变成漫游。开始前先把任务压缩成一张卡：

```text
业务问题：已取消订单为什么还能被发货？
本次目标：找到取消与发货的状态校验位置
已知入口：POST /api/orders/{id}/cancel
观察样本：一条脱敏后的订单号和 traceId
时间限制：两小时先交付调用链，不立即重构
输出：状态流转图、关键代码、风险点、待确认问题
```

任务卡会迫使我围绕一个可验证问题前进。读到与目标无关的工具类时，只做标记，不立刻钻进去。

## 第一条路线：先让系统可观察

能运行的项目比静态目录更诚实。第一步不是修改配置，而是记录当前基线：

1. 确认 JDK、Maven、数据库和中间件版本。
2. 使用项目已有的本地配置启动，不复制生产配置。
3. 找到健康检查、启动日志和一条最小请求。
4. 记录启动命令、端口、依赖和失败信息。
5. 在任何改动前执行现有测试，保存通过和失败数量。

如果项目暂时跑不起来，也要区分“代码缺陷”和“环境缺口”。例如缺少测试库、内部依赖无法下载、初始化脚本过期，应该记录为环境事实，不能凭此判断业务代码不可用。

我会先看这些文件，但不逐行精读：

```text
pom.xml                    依赖、插件和 Java 版本
application*.yml           外部依赖与环境差异
启动类                     扫描范围和启动扩展
安全配置与过滤器           身份从哪里进入
数据库迁移脚本             表结构如何演进
README、部署脚本、CI        项目真实运行方式
```

这一步得到的是边界，不是结论。

## 第二条路线：从入口跟一条请求

阅读调用链时，我会从用户可见入口向内收缩，而不是从底层工具类向外猜。

```text
HTTP 请求
  -> Filter / Interceptor
  -> Controller
  -> Application Service
  -> Domain / Rule
  -> Mapper / Repository
  -> 数据库、缓存或外部服务
```

每经过一层只回答三个问题：

- 输入在这里增加或丢失了什么信息？
- 哪个条件会改变正常路径？
- 失败后由谁捕获、转换或重试？

例如 Controller 只出现一个 `cancel(orderId)` 调用，我不会立刻打开 Service 中的所有公共方法，而是继续搜索这个方法、订单状态枚举和对应 SQL：

```bash
rg "cancel\(" src/main/java
rg "CANCELLED|SHIPPED" src/main/java src/main/resources
rg "update.*order|order_info" src/main/resources
```

搜索结果要按“生产入口、定时任务、消息消费、测试”分类。同一个方法可能不只被 HTTP 调用，遗漏后台入口是遗留系统修改中常见的风险。

## 第三条路线：跟踪数据，而不是只跟方法

方法调用只能说明代码经过哪里，数据变化才能解释业务发生了什么。我会为核心对象画一条简化状态线：

| 时点 | 数据状态 | 写入位置 | 约束 |
| --- | --- | --- | --- |
| 创建后 | `CREATED` | 订单服务 | 订单号唯一 |
| 支付后 | `PAID` | 支付回调 | 回调可能重复 |
| 取消后 | `CANCELLED` | 取消接口 | 仅未发货可取消 |
| 发货后 | `SHIPPED` | 消息消费者 | 必须校验当前状态 |

接着检查四类细节：

1. 状态是由 Java 判断，还是直接写在 SQL 条件里。
2. 一个事务覆盖哪些写操作，外部调用是否夹在事务中间。
3. 缓存什么时候失效，失败后是否会读到旧状态。
4. 并发更新有没有版本号、条件更新或唯一约束保护。

假设取消使用 `UPDATE order_info SET status = 'CANCELLED' WHERE id = ?`，而发货也不带旧状态条件，那么问题不一定在某个 `if`，而在数据库没有守住状态迁移。此时重命名几个方法不会降低风险。

## 第四条路线：用历史解释奇怪代码

遗留代码里看似多余的判断，可能是一次事故留下的护栏。遇到不理解的逻辑，我会按下面顺序查历史：

```bash
git log --oneline -- src/main/java/com/example/order/OrderService.java
git blame -L 80,120 src/main/java/com/example/order/OrderService.java
git show <commit-id>
```

`git blame` 不是为了找责任人，而是为了找到提交上下文。提交说明、关联需求和同期测试往往能回答“为什么这里不能合并”“为什么失败也返回成功”。

历史只能提供线索，不能自动证明今天仍然正确。最后仍要回到现有业务规则、线上数据和测试结果。

## 建立事实、推测和问题三栏笔记

阅读过程中最危险的是把猜测写成事实。我使用三栏笔记强制区分：

| 类型 | 示例 |
| --- | --- |
| 已验证事实 | 发货消费者会调用 `ship()`，SQL 没有旧状态条件 |
| 当前推测 | 重复消息可能覆盖取消状态 |
| 待确认问题 | 消息是否保证同一订单有序，历史数据是否存在该情况 |

每个推测后面都补一个验证动作，例如查询脱敏数据、补测试、查看消息配置或询问业务负责人。这样即使当天没有定位完成，下一位接手的人也能沿着证据继续走。

## 修改前先写特征测试

老代码没有单元测试时，直接重构很难判断行为是否变化。特征测试先记录当前可观察行为，即使这个行为并不完美。

```java
@RunWith(MockitoJUnitRunner.class)
public class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;

    @InjectMocks
    private OrderService orderService;

    @Test
    public void shouldRejectCancellationWhenOrderAlreadyShipped() {
        Order shippedOrder = new Order(1001L, OrderStatus.SHIPPED);
        when(orderRepository.findById(1001L)).thenReturn(shippedOrder);

        try {
            orderService.cancel(1001L);
            fail("已发货订单不应允许取消");
        } catch (BusinessException exception) {
            // 先锁定现有业务语义，再调整内部实现
            assertEquals("ORDER_ALREADY_SHIPPED", exception.getCode());
        }

        verify(orderRepository, never()).updateStatus(anyLong(), any());
    }
}
```

对于难以隔离的代码，可以先做接口级测试或固定输入输出的集成测试。测试颗粒度不是越小越好，关键是覆盖这次修改最可能破坏的行为。

## 画出影响半径

找到修改点后，我会再向外搜索一次：

```text
直接调用者        Controller、其他 Service
隐式调用者        Spring 事件、反射、SPI、表达式
异步入口          MQ 消费者、定时任务、线程池任务
数据依赖          SQL、视图、报表、缓存 key
外部契约          API 字段、错误码、消息结构
运维依赖          配置项、告警、脚本、日志关键字
```

尤其要注意字符串形式的绑定。方法名搜索不到，不代表它没有被 XML、配置或任务调度平台引用。

## 什么时候才适合重构

我给自己设置了四个前置条件：

1. 能用一句话说明当前行为和目标行为。
2. 已经找到主要入口、数据变化和异常路径。
3. 有测试或可重复验证步骤保护关键行为。
4. 改动可以拆成小提交，并且具备回退方式。

如果只是命名较差但近期没有修改需求，可以先记录；如果一个十行改动要同时碰八个模块，说明真正的技术债可能是职责分散，应先缩小边界。重写通常是最后的方案，因为旧系统中最昂贵的部分不是代码行数，而是没有写下来的业务规则。

## 一页代码地图就是阶段成果

一次有效阅读不要求理解全部源码，但应该留下可复用结果：

```text
核心业务入口：
关键调用链：
主要数据表与状态：
外部依赖：
事务和异步边界：
已验证风险：
仍待确认的问题：
本次修改与验证方案：
```

后来再接触陌生项目时，我不再把“读完代码”当目标。沿着具体问题建立证据、用数据和历史校正判断，再用测试保护修改，这张路线图比记住多少个类更有用。
