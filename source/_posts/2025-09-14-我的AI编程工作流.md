AI 编程最浪费时间的场景，不是模型写不出代码，而是它在错误的项目理解上连续工作了半小时：改错入口、重复已有工具类、使用不兼容版本，最后生成一大份很难审查的差异。

我逐渐把使用方式从“想到什么问什么”改成了一条固定工作流。它不绑定某个模型或编辑器，核心只有一句话：**先让模型用证据还原项目，再让它在明确边界内修改。**

这篇按 Runbook 来写，可以直接拿一个小需求跟着走一遍。

## 入口：先给任务分级

不是每个任务都值得启动完整流程。我先按影响范围分三档：

| 等级 | 例子 | 工作方式 |
| --- | --- | --- |
| L1 可逆 | 改文案、补测试、调整局部样式 | 快速修改，执行局部验证 |
| L2 模块内 | 新增接口字段、修改查询、重构 Service | 先读调用链，写计划，小步提交 |
| L3 高风险 | 权限、支付、迁移、生产运维 | 人主导设计，双人审查，演练与回滚 |

风险不只看代码行数。把按钮颜色改错通常是 L1，删除脚本即使只有一行也可能是 L3。分级决定需要多少上下文、测试和人工确认。

下面的完整流程主要面向 L2。L1 可以裁剪，L3 还要叠加团队正式变更流程。

## 检查点一：把请求改写成任务说明

原始需求经常是：

```text
列表加一个状态筛选。
```

我不会直接让 AI 改代码，而是先补一张短任务卡：

```text
问题：运营无法只查看“等待回访”的客户。
目标：客户列表和导出增加 followStatus 筛选。
输入：可选枚举 PENDING、DONE；不传保持原行为。
范围：后端查询与现有前端筛选，不改数据库。
非目标：不重构客户状态模型，不增加批量处理。
验收：列表与导出结果一致；非法值返回现有参数错误码。
```

“非目标”非常重要。模型擅长顺手完善周边，如果不写边界，一个筛选需求可能变成状态模型重构。

任务卡不需要一次写对。信息缺失时，让 AI 根据现有描述列出待确认问题，我再向产品或代码事实求证。需求澄清不能由模型自问自答。

## 检查点二：只读探索仓库

第一轮明确要求不修改文件，只回答项目现状。我通常让模型查这些位置：

```text
构建文件：Java、框架、依赖版本
项目入口：模块边界和启动方式
请求入口：Controller、路由或消息消费者
数据流：Service、Mapper、外部客户端
相邻实现：项目里已经完成的类似功能
测试：当前使用的框架、夹具和断言风格
规范：README、AGENTS.md、架构决策和 CI 配置
```

探索结果必须带证据，格式可以很简单：

```text
结论：列表和导出共用 CustomerQueryCondition。
证据：CustomerPageService.java:48、CustomerExportService.java:62。

结论：项目要求 JDK 8。
证据：pom.xml 的 maven.compiler.source=1.8。

待确认：非法枚举由全局异常处理还是 Controller 转换。
```

“证据”和“待确认”能阻止猜测混进结论。若模型找不到某个类，就继续搜索或明确不存在，不根据常见命名补一个出来。

### 控制上下文预算

读仓库不是把所有文件一次塞给模型。我会沿调用链逐层加载：

```text
入口文件
  -> 它直接调用的接口
  -> 对应实现与数据对象
  -> 一个最接近的参考实现
  -> 相关测试和构建配置
```

生成目录、压缩后的前端产物、重复日志和无关模块先排除。上下文足够大时，信息选择比信息数量更重要。

## 检查点三：修改前先审计划

项目地图清楚后，让 AI 给出计划，但暂时不写代码。一个可审查的计划至少包含：

1. 实际要修改的文件；
2. 每个文件为什么要改；
3. 数据和调用路径怎样变化；
4. 空值、异常、并发与兼容边界；
5. 要新增或运行哪些测试；
6. 仍然无法确认的风险。

计划阶段最容易发现范围膨胀。例如任务只需要复用已有查询条件，计划却新建 Repository、Assembler 和通用查询框架，这时删掉比写完后再删便宜得多。

我还会要求把步骤拆到可独立验证：

```text
1. 先增加请求字段和参数校验，运行接口层测试；
2. 再增加 Mapper 条件，运行数据库测试；
3. 接入列表并验证原行为；
4. 接入导出并做结果对照；
5. 最后清理重复与更新文档。
```

一条计划如果要同时修改二十个文件才可运行，通常还没有找到合适的切分点。

## 检查点四：按小循环实施

实施阶段我使用同一条循环：

```text
修改一个职责
  -> 格式与静态检查
  -> 运行最小相关测试
  -> 阅读版本差异
  -> 记录结果
  -> 进入下一步
```

这里“阅读差异”不能省。AI 有时会在目标代码之外格式化整个文件、调整错误文案或升级依赖。测试可能照样通过，但 Review 成本和回归范围已经扩大。

每轮我会检查：

- 是否出现任务外文件；
- 是否复制了已有能力；
- 是否改变公共接口或默认值；
- 是否添加未经批准的依赖；
- 是否打印密钥、个人数据或完整请求；
- 是否使用项目版本不支持的语法；
- 注释是在解释原因，还是重复代码表面含义。

发现方向错误时，优先回到最后一个小步骤，而不是继续提示模型在错误实现上打补丁。

## 检查点五：建立验证阶梯

“已完成”需要对应证据。我把验证从便宜到昂贵排成阶梯：

```text
语法与格式
  -> 编译 / 类型检查
  -> 目标单元测试
  -> 模块测试
  -> 集成或端到端测试
  -> 构建生产产物
  -> 测试环境真实操作
  -> 监控与回滚演练
```

简单改动可以停在较低层，高风险改动必须继续向上。关键是清楚说出停在哪里，而不是把“代码看起来没问题”写成“验证通过”。

Java 项目中，一组常见命令可能是：

```bash
# 先跑目标测试，快速得到反馈
mvn -Dtest=CustomerQueryServiceTest test

# 再运行模块测试并打包，确认依赖与资源完整
mvn clean package
```

若仓库提供 Maven Wrapper，应优先使用仓库固定的 `./mvnw`。命令只是入口，真正的验收还要匹配业务，例如比较筛选前后数据、重复请求、权限用户和空记录。

### 不要让模型代替测试宣布成功

我要求执行结果分三类写：

```text
已验证：命令真实执行，附关键结果。
未验证：当前环境无法执行，并说明原因。
待观察：只能上线后从监控或真实流量确认。
```

这三类比一句“应该没问题”诚实，也方便下一位接手的人继续。

## 检查点六：提交前进行独立 Review

实现对话会让人产生路径依赖：模型已经解释了为什么这样改，我也一路看着它完成，很容易默认结论正确。

提交前，我会暂时不看对话，只从需求卡和最终差异重新审一遍：

```text
需求中的每条验收是否有对应代码和测试
没有写进需求的行为是否被意外改变
错误路径是否比正常路径更危险
数据库和外部调用是否处在合理事务边界
测试是否会在实现被删掉时失败
回滚是否只需回退代码，还是涉及数据处理
```

这相当于给自己换一个 Reviewer 视角。复杂任务还应由另一位工程师审查，不能因为代码由 AI 生成就降低门槛。

## 检查点七：把有价值的上下文留在仓库

一次任务中反复告诉模型的内容，如果下次仍然适用，应该沉淀成项目资产：

- 构建和测试方式写进 README；
- 编码约束写进项目级说明；
- 关键架构取舍写成 ADR；
- 容易回归的规则写成测试；
- 发布步骤和回滚条件写进 Runbook。

不要把对话记录当唯一文档。对话适合探索，仓库才是团队共同维护的长期上下文。

我还会在提交说明中保留三个信息：为什么改、行为怎样变、用什么验证。过几个月再看历史，不需要重新翻完整对话。

## 三种常见失控方式

### 一直追加提示，不愿回到事实

模型改错方向后，连续说“再修一下”会堆积补丁。先停止修改，重新确认入口和约束，通常更快。

### 一次交给模型整个功能

任务越大，错误越晚暴露，最终差异越难 Review。把垂直功能拆成可运行的小片段，让每一步都有反馈。

### 只检查代码，不检查环境

代码正确不等于配置、数据库、权限和部署正确。尤其是版本、环境变量和外部接口，必须用真实构建与运行证据验证。

## 一页版流程

需要快速回忆时，我只看这七行：

```text
1. 说明问题、目标、范围和验收。
2. 只读项目，用文件与日志建立事实。
3. 先审计划，删除不必要的改动。
4. 一次修改一个职责，小步看差异。
5. 从编译到真实场景逐层验证。
6. 脱离对话，按需求独立 Review。
7. 把稳定知识沉淀进文档和测试。
```

这套流程没有神奇提示词，甚至会让开始写代码的时间晚几分钟。但它减少了最昂贵的部分：在错误上下文上高速前进。

模型不需要一开始就“完全读懂项目”。它需要在每个决策点看到足够的真实信息，并及时收到构建、测试和人工判断的反馈。把这条循环设计好，AI 才会从偶尔惊艳的演示，变成可以稳定复用的开发工具。
