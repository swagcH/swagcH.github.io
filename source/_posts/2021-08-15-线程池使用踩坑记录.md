一次批量通知功能上线后，接口响应从 200ms 涨到 6s，CPU 却只有 30%。线程池监控看起来也没有报错：

```text
poolSize=32
active=32
queueSize=10000
completedTaskCount=1200
rejected=0
```

后来才明白，“没有拒绝”并不是健康信号。容量一万的队列把压力藏了起来，任务已经要排几分钟，调用方却仍然成功提交。

这篇不直接给一组万能参数，而是从任务耗时和下游容量推导线程数、队列和拒绝策略，再用压测验证。

## 先还原任务在做什么

通知任务包含：

```text
读取一条业务数据：约 20ms
调用外部通知接口：P50 700ms，P99 1.8s
更新发送结果：约 30ms
平均总耗时：约 1.2s
入口提交速度：峰值 40 tasks/s
```

这是 IO 等待为主的任务。32 个线程在理想情况下每秒处理：

```text
32 / 1.2 ≈ 26.7 tasks/s
```

入口每秒 40 个，处理每秒约 27 个，队列每秒增长约 13 个。十分钟后就是近 8,000 个任务。CPU 不高，只说明线程大部分在等待网络，不说明系统有余量。

## 第一个坑：直接使用 Executors

旧代码：

```java
private final ExecutorService executor =
        Executors.newFixedThreadPool(32);
```

`newFixedThreadPool` 内部使用近似无界的 `LinkedBlockingQueue`。任务持续堆积时：

- 排队时间没有上限。
- 请求携带的对象长期占用堆内存。
- 已经过期的任务仍然执行。
- 拒绝策略很晚才有机会生效。
- 服务关闭时需要处理大量积压。

问题不是 `Executors` 这个类不能用，而是便捷工厂隐藏了影响容量的关键参数。生产线程池应该把边界显式写出来。

## 线程数从并发需求开始估算

Little 定律可以提供一个起点：

```text
在途任务数 ≈ 到达速率 × 平均处理时间
              40/s × 1.2s
              ≈ 48
```

要在稳定状态处理 40 tasks/s，大约需要 48 个同时在途任务。但这不等于线程数直接设 48，还要问：

1. 通知服务允许我们并发多少请求。
2. 当前实例数量是多少。
3. 数据库连接池能否支撑每个任务的读写。
4. P99 耗时上升时会增加多少在途任务。
5. 机器线程栈和上下文切换成本是多少。

通知服务给出的租户并发上限是 120，订单服务有 4 个实例，因此单实例最多使用约 30 个并发。把线程池增到 48 会越过下游限制，换来 429 和更多重试。

最终决策不是“本地每秒处理 40 个”，而是入口也限制到全局可承受速度，超出部分进入可靠消息队列，而不是堆在 JVM 内存。

## 队列容量从可等待时间反推

假设单实例稳定处理能力约 25 tasks/s，业务允许任务最多在本地排队 2 秒：

```text
队列容量 ≈ 25 tasks/s × 2s = 50
```

可以预留波动，将容量设为 100，但没有理由设成 10,000。队列越大，拒绝发生越晚，用户看到的“提交成功”和真实执行时间差得越远。

如果业务允许几小时后完成，正确容器通常是持久化任务表或消息队列，不是把线程池队列调得无限大。

## 把所有关键参数写出来

```java
public final class NotificationExecutorFactory {

    private NotificationExecutorFactory() {
    }

    public static ThreadPoolExecutor create() {
        AtomicInteger sequence = new AtomicInteger(1);
        ThreadFactory threadFactory = runnable -> {
            Thread thread = new Thread(
                    runnable,
                    "notification-" + sequence.getAndIncrement()
            );
            // 未捕获异常必须进入统一日志
            thread.setUncaughtExceptionHandler((current, throwable) ->
                    log.error("notification_task_crashed thread={}",
                            current.getName(), throwable));
            return thread;
        };

        return new ThreadPoolExecutor(
                20,
                30,
                60,
                TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(100),
                threadFactory,
                new ThreadPoolExecutor.AbortPolicy()
        );
    }
}
```

参数含义：

```text
corePoolSize=20       普通流量下保留的工作线程
maximumPoolSize=30    不超过单实例下游并发预算
keepAlive=60s         波峰线程空闲后的回收时间
queue=100             本地最多约数秒缓冲
AbortPolicy           满载时明确失败，不静默丢任务
```

核心线程、最大线程和队列之间的调度顺序也要理解：

```text
线程少于 core -> 创建线程
达到 core      -> 先进入队列
队列已满       -> 继续创建到 max
达到 max       -> 执行拒绝策略
```

因此使用很大的队列时，`maximumPoolSize` 可能永远不会生效。

## 拒绝策略必须对应业务语义

JDK 自带策略：

| 策略 | 行为 | 风险 |
| --- | --- | --- |
| `AbortPolicy` | 抛出异常 | 调用方必须处理 |
| `CallerRunsPolicy` | 提交线程执行 | 可能拖慢 HTTP 或 MQ 线程 |
| `DiscardPolicy` | 静默丢弃 | 业务任务不可追溯 |
| `DiscardOldestPolicy` | 丢最旧任务后重试 | 可能丢掉更重要任务 |

通知任务需要可追踪，不能静默丢弃。我们使用 `AbortPolicy`，在提交边界捕获：

```java
public void submit(NotificationTask task) {
    try {
        executor.execute(() -> notificationService.send(task));
    } catch (RejectedExecutionException exception) {
        // JVM 已满时写入持久化补偿队列，避免任务消失
        retryTaskRepository.save(task, "LOCAL_EXECUTOR_FULL");
        meterRegistry.counter("notification.rejected").increment();
        throw new BusinessException("NOTIFICATION_BUSY", exception);
    }
}
```

持久化补偿也可能失败，需要唯一任务号、数据库约束和告警。若提交本身属于事务，要明确任务记录与业务状态的一致性，不能只在内存里重试。

`CallerRunsPolicy` 能给生产者施加反压，但如果生产者是 Tomcat 请求线程，外部调用会占住请求线程；如果是 RabbitMQ 消费线程，会拖慢确认。使用前必须验证这种反压正是想要的效果。

## 第二个坑：submit 后忽略 Future

```java
executor.submit(() -> notificationService.send(task));
```

`submit` 会把异常放进 `Future`。调用方不执行 `get()`，也没有包装任务时，异常可能没有进入预期日志。

异步边界统一包装：

```java
private Runnable observed(NotificationTask task) {
    return () -> {
        long startedAt = System.nanoTime();
        try {
            notificationService.send(task);
            metrics.recordSuccess(elapsedMillis(startedAt));
        } catch (Exception exception) {
            metrics.recordFailure(elapsedMillis(startedAt));
            log.error("notification_send_failed taskId={} receiverId={}",
                    task.getTaskId(), task.getReceiverId(), exception);
            retryTaskRepository.save(task, "SEND_FAILED");
        } finally {
            MDC.clear();
        }
    };
}
```

关键任务不能只靠日志补偿。异常结果需要写入可查询状态，并由重试任务按次数和退避策略处理。

## 上下文和资源也要跨过异步边界

线程池复用线程，ThreadLocal、MDC 和用户上下文不会自动安全传递。提交时只复制必要的 traceId 和业务编号，执行完必须清理。

不要把完整 HTTP Request 或大对象捕获进 Lambda。任务在队列等待期间，这些对象无法回收，也可能包含失效连接和敏感信息。

异步任务参数应是小而稳定的值对象：

```text
taskId
businessId
receiverId
templateCode
traceId
```

执行时根据 ID 获取所需数据，并处理数据已变化或任务已取消的情况。

## 压测对照

压测固定下游平均耗时 1.2 秒，并逐步增加入口：

| 入口速率 | 旧池队列峰值 | 新方案本地队列 | 拒绝/持久化 | P99 |
| ---: | ---: | ---: | ---: | ---: |
| 15/s | 0 | 0 | 0 | 1.9s |
| 25/s | 620 | 36 | 0 | 3.1s |
| 40/s | 4,780 | 100 | 约 15/s | 4.8s |
| 60/s | 10,000 | 100 | 约 35/s | 4.9s |

新方案在超载时不会无限增加本地等待，额外任务进入持久化补偿。下游恢复后，补偿消费者以受控速度追赶。

还要注入这些异常：

```text
下游 P99 从 1.8s 上升到 5s
连接超时持续 30 秒
数据库写结果失败
任务执行抛出运行时异常
应用接到关闭信号
```

正常流量压测只能证明吞吐，异常注入才能证明边界。

## 关闭时不要直接丢掉队列

服务停止流程：

```java
public void shutdown() {
    executor.shutdown();
    try {
        if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
            List<Runnable> notStarted = executor.shutdownNow();
            // 未开始任务必须转存，不能只打印数量
            retryTaskRepository.saveAll(convert(notStarted));
        }
    } catch (InterruptedException exception) {
        Thread.currentThread().interrupt();
        retryTaskRepository.saveAll(convert(executor.shutdownNow()));
    }
}
```

真实实现不应依赖从任意 `Runnable` 反向解析业务任务，可以使用自定义任务类型或在提交前先持久化。示例重点是：关闭超时后仍要明确处理未开始任务。

## 我现在会看这些指标

```text
active / poolSize / max
queueSize / remainingCapacity
submitted / completed / rejected
任务排队时间
任务执行时间
下游成功率与限流数
补偿任务数量与最老等待时间
```

线程池参数不是一次配置后永久有效。任务耗时、实例数量和下游容量变化时，稳定处理能力也会变化。

这次踩坑最大的收获是：线程池本质上是一套容量控制。线程决定同时做多少，队列决定愿意等多久，拒绝策略决定超载后谁承担结果。三者都没有业务边界时，所谓异步只是在把故障推迟到几分钟以后。
