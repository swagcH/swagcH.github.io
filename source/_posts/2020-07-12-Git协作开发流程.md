一个人使用 Git，记住 `add`、`commit`、`push` 基本够用；多人协作以后，难点变成了什么时候开分支、如何保持改动足够小、冲突由谁处理，以及线上版本怎样准确追溯。

下面是我逐步整理出来的一份团队运行手册。它不追求复杂的分支模型，目标只有三个：主分支随时可发布、每次改动可以审查、出现问题能够回退。

## 分支只承担清晰职责

小团队可以从三类分支开始：

| 分支 | 来源 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| `main` | 受保护分支 | 长期 | 已验证、可发布代码 |
| `feature/*` | `main` | 数小时到数天 | 单个需求或技术任务 |
| `hotfix/*` | 线上 Tag | 尽可能短 | 生产紧急修复 |

如果团队有固定测试窗口，可以增加 `release/*`；如果没有明确收益，不必照搬完整 Git Flow。分支越多，版本流转和补丁同步成本越高。

分支名要能直接关联工作：

```text
feature/order-export
fix/payment-callback-idempotency
hotfix/20200712-login-timeout
```

`tmp`、`new`、`test2` 之类名称会让几周后的清理和追溯变得困难。

## 开始任务前

先确认工作区干净，并从最新主分支创建任务分支：

```bash
git status
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/order-export
```

`--ff-only` 可以阻止 `pull` 在本地悄悄生成一次合并提交。如果当前 Git 版本不支持 `switch`，可以使用 `checkout` 完成相同操作。

开始编码前还应明确：

```text
需求或缺陷编号
本次明确包含和不包含的范围
数据库、接口、配置是否变化
验证方式
上线和回退方式
```

Git 能记录代码变化，却不能替代范围管理。

## 一个提交表达一个意图

好的提交不是“今天写了多少”，而是一个可以独立解释、审查和撤销的变化。例如：

```text
feat(order): add paid-order export endpoint
fix(payment): ignore duplicated callback
test(order): cover export permission boundary
refactor(order): extract status transition validation
```

提交前先检查实际内容：

```bash
git status --short
git diff
git diff --cached
```

不要习惯性执行 `git add .`。配置、日志、IDE 文件和临时数据很容易一起进入提交。更稳妥的方式是按文件或按代码块暂存：

```bash
git add src/main/java/com/example/order/OrderExportService.java
git add -p
git commit -m "feat(order): add paid-order export service"
```

如果一次提交同时包含格式化全项目、重命名、业务修改和依赖升级，Review 很难分辨真正变化。应把机械修改和行为修改拆开。

## 每天与主分支同步

短分支能显著降低冲突。功能开发超过一天时，我会定期同步远端：

```bash
git fetch origin
git rebase origin/main
```

适合使用 `rebase` 的前提是分支由自己维护，或者团队明确允许重写该分支历史。已经被多人共同使用的分支不要随意 rebase，否则其他人的提交基线会变化。

不允许重写历史时，使用合并：

```bash
git merge origin/main
```

团队应统一一种默认方式。混合使用并不可怕，真正麻烦的是没有约定，导致提交图无法解释。

## 冲突处理不是选择“我的”或“他的”

冲突发生时先暂停自动操作，理解两边意图：

```bash
git status
git diff --name-only --diff-filter=U
git log --oneline --left-right HEAD...origin/main
```

处理步骤：

1. 阅读当前分支和主分支对应提交。
2. 确认两边修改解决的业务问题。
3. 手工合成最终行为，而不是直接选择一侧。
4. 删除冲突标记，重新编译并运行相关测试。
5. `git add` 已解决文件，再继续 rebase 或 commit。

如果方向不对，可以执行 `git rebase --abort` 或 `git merge --abort` 回到操作前。中止比带着不确定结果继续提交更可靠。

## 提交合并请求前的自检

合并请求不是把检查工作转交给 Reviewer。提交前至少确认：

```text
[ ] 改动范围与任务一致，没有临时文件
[ ] 编译、自动测试和静态检查通过
[ ] 接口、数据库和配置变化有说明
[ ] 日志不包含密码、Token 或个人敏感信息
[ ] 新增分支和异常路径有测试
[ ] 兼容与回退方式明确
[ ] 分支已同步最新主分支
```

合并请求描述建议回答四件事：

```markdown
## 为什么改
支付回调可能重复投递，积分会重复增加。

## 怎么改
以支付流水号建立唯一约束，重复请求返回原处理结果。

## 怎么验证
单次、重复、并发回调测试均通过。

## 风险与回退
先上线约束与兼容代码；回退应用不删除约束。
```

Reviewer 应重点看业务边界、数据一致性、异常处理和测试，格式问题尽量交给自动化工具。

## 主分支的合并规则

主分支至少应有这些保护：

- 禁止直接 push。
- 必须通过合并请求。
- CI 检查通过后才能合并。
- 至少一位非作者 Review。
- 禁止提交密钥和生成物。
- 合并后自动删除短期分支。

是否使用 merge commit、squash 或 rebase merge，可以按团队追溯习惯选择：

| 方式 | 优点 | 适合场景 |
| --- | --- | --- |
| Merge commit | 保留完整分支上下文 | 大功能、需要保留阶段提交 |
| Squash | 主线简洁，一个任务一个提交 | 小而频繁的功能分支 |
| Rebase merge | 线性历史且保留提交 | 提交本身已经整理良好 |

不要在同一个仓库随意切换策略，否则查找版本和回退时会增加认知成本。

## 发布必须能对应到提交

每次生产发布都创建不可变 Tag：

```bash
git switch main
git pull --ff-only origin main
git tag -a v1.8.0 -m "release v1.8.0"
git push origin v1.8.0
```

发布记录至少包含 Tag、构建编号、数据库变更、配置版本和负责人。只有“周日晚上那一版”无法支持故障定位。

回退前要先区分代码回退和数据回退。应用可以回到旧 Tag，但已执行的不可逆 DDL、已写入的新状态、已发送的消息不会自动恢复。

## Hotfix 的最短闭环

线上紧急修复从实际生产 Tag 创建，而不是从开发中的某个分支猜：

```bash
git switch -c hotfix/20200712-login-timeout v1.8.0
# 完成最小修改、测试和 Review
git tag -a v1.8.1 -m "hotfix login timeout"
git push origin v1.8.1
```

修复发布后，还要把对应提交合回主开发线，避免下一次发布重新带回缺陷。

## 关于强制推送和历史修改

`git push --force` 可能覆盖远端他人的提交，受保护分支应直接禁止。确需更新自己的未合并分支时，也优先使用：

```bash
git push --force-with-lease
```

`--force-with-lease` 会在远端已被他人更新时拒绝覆盖，但它仍然是重写历史操作，执行前必须确认分支所有者和影响范围。

同样，不把 `reset --hard` 当日常清理命令。未提交文件可能永久丢失；先查看 `status`、保存必要改动，再决定恢复方式。

## 一套流程最后解决的是沟通

这套手册执行一段时间后，最明显的变化并不是提交图更漂亮，而是问题更容易回答：某行代码为什么改、谁审过、对应哪个版本、怎样验证、能否回退。

Git 协作的核心不是命令数量，而是把一次改动变成边界清楚、证据完整、可被团队接住的交付单元。
