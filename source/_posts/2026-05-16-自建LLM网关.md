当项目开始接入第二个、第三个大模型供应商时，问题就不再是"调哪个 API"，而是：

- 每家鉴权方式、请求格式、错误码都不一样，业务代码要写四套适配
- 某家服务抖动或限流，业务直接失败
- 调用量上去后，无法知道钱花在哪、哪个模型最慢
- 换模型要改代码、重新发布

这篇文章记录我用网关统一 4 家供应商的完整设计——**重点不是用了什么工具，而是每个决策背后的取舍**。

## 一、先明确：为什么需要网关

**不建网关会怎样**（这是我实际遇到的情况）：

```java
// 业务代码里散落着各家的调用逻辑
public String callArk(String prompt) {
    // 火山方舟的鉴权和格式
}

public String callR4(String prompt) {
    // R4coder 的鉴权和格式（伪装浏览器 UA）
}

public String callSzmf(String prompt) {
    // 数智魔方的格式（baseURL 必须带 /v1）
}
```

**四个具体问题**：

1. **重复适配**：每个业务模块都要处理 4 家的差异
2. **无容错**：A 家挂了不能自动切 B 家
3. **无法观测**：不知道哪家慢、哪家贵、用量多少
4. **变更成本高**：换模型要改代码 + 重新发布

**网关要解决的核心问题：把"N 家供应商"收敛成"一个统一接口"。**

![LLM 网关解决的四类问题](/images/posts/2026/llm-gateway-problems.svg)

## 二、架构设计

### 整体结构

```
业务应用（多个项目）
        │
        │ 统一 OpenAI 兼容协议
        ▼
┌─────────────────────────┐
│      LLM 网关            │
│  · 统一鉴权              │
│  · 模型路由 + 别名        │
│  · 降级链（fallback）     │
│  · 超时控制              │
│  · 用量与延迟统计         │
└────────┬────────────────┘
         │
    ┌────┴────┬────────┬────────┐
    ▼         ▼        ▼        ▼
  供应商 A  供应商 B  供应商 C  供应商 D
```

**关键设计：对外只暴露一种协议（OpenAI 兼容）。**

这是最重要的决策。理由：

- **几乎所有客户端都支持 OpenAI 格式**（LangChain、各类 SDK、自研脚本）
- **切换成本为零**：业务方只改 `base_url` 和 `api_key`
- **不用为每家写适配**

### 为什么选 LiteLLM

| 方案 | 优势 | 代价 |
|---|---|---|
| **自己写网关** | 完全可控 | 要处理几十家供应商的格式差异，工作量大 |
| **LiteLLM** | 支持 100+ 供应商、配置驱动、有 fallback | 需要容器化部署，性能依赖其实现 |
| **OneAPI / NewAPI** | 国内生态、有 Web 管理界面 | 功能偏"多租户管理"，配置灵活性一般 |
| **云厂商网关** | 免运维 | 被厂商绑定，跨供应商能力有限 |

**选 LiteLLM 的理由**：

1. **配置驱动**：新增供应商只改 YAML，不写代码
2. **原生支持 fallback 链**：这是最需要的容错能力
3. **Python 生态**：出问题能读源码定位（我用这个能力排查过超时问题）
4. **性能够用**：网关本身是 IO 密集型的转发层，不是计算瓶颈

## 三、核心设计点

### 1. 模型命名：解决"同一模型多家都有"

**问题**：DeepSeek V4 Flash 在 4 家供应商都能调，直接叫 `deepseek-v4-flash` 无法区分来源。

**方案：前缀区分 + 通用别名**

```
带前缀（明确指定供应商）：
  ark-deepseek-v4-flash      ← 火山方舟
  r4-deepseek-v4-flash       ← R4coder
  cc-deepseek-v4-flash       ← CommandCode
  szmf-deepseek-v4-flash     ← 数智魔方

通用别名（不关心来源，走 fallback 链）：
  deepseek-v4-flash          ← 主选 + 自动降级
```

**为什么要两套**：

- **调试/对比时用前缀**：明确指定某家，看它的延迟和输出质量
- **生产用别名**：不关心具体哪家，只要能用就行，挂了自动切换

**这是"可控"和"省事"的分工**，不是二选一。

![网关架构与降级链设计](/images/posts/2026/llm-gateway-arch.svg)

### 2. 降级链（fallback）：容错的核心

**这是网关最有价值的能力。**

```yaml
# 每个模型配置降级链
model_list:
  - model_name: deepseek-v4-flash
    litellm_params:
      model: openai/deepseek-v4-flash
      api_base: https://ark.example.com/v1
      api_key: os.environ/ARK_API_KEY

# 降级链：A 失败 → B → C
fallbacks:
  - ark-deepseek-v4-flash: ["r4-deepseek-v4-flash", "cc-deepseek-v4-flash"]
  - r4-deepseek-v4-flash:  ["ark-deepseek-v4-flash", "cc-deepseek-v4-flash"]
  # ... 共 35 条

# 全局兜底：任何模型都失败时用最稳的那个
default_fallbacks: ["deepseek-v4-flash"]
```

**关键理解**：fallback 只在**可重试的错误**上触发。

```
✅ 会触发降级：429 限流、5xx 服务端错误、超时、连接失败
❌ 不会触发降级：400 参数错误、401 鉴权失败、内容审核拒绝
```

**为什么这个区分重要**：如果参数错误也降级，会在 4 家之间白跑一圈，最后返回的还是那个参数错误，但延迟翻了 4 倍。

**踩过的坑**：某次调用一直报"密钥无效"，排查发现是某家供应商临时故障返回 403。**403 默认不触发降级**，导致请求直接失败。后来针对这种情况加了配置，让该供应商的 403 也进入降级链。

### 3. 超时控制

**这是最容易出问题的地方。**

```yaml
litellm_settings:
  request_timeout: 240        # 网关等待上游的总超时（秒）
```

**为什么是 240 秒**：推理模型的输出可能很长，实测长回答（1000+ 字）需要 15-25 秒，深度推理场景可能超过 60 秒。设太短会导致复杂问题被截断。

**但要理解分层的超时**：

```
业务侧超时     ← 应该 ≥ 网关超时（否则业务先放弃，但网关还在等）
    ↓
网关超时 240s
    ↓
上游供应商超时  ← 各家的默认值不一样
```

**实践建议**：业务侧超时要比网关略长（比如 300s），否则会出现"业务已返回超时，但上游还在计费"的浪费。

### 4. 各供应商的特殊处理

**这是接 4 家必然遇到的现实问题**，每家都有坑：

| 供应商 | 问题 | 解决 |
|---|---|---|
| **CommandCode** | 请求被 Cloudflare 拦截（`error code: 1010`）| 伪装浏览器 User-Agent |
| **数智魔方** | baseURL 必须带 `/v1`，否则拼错路径 | 配置时显式写全 |
| **火山方舟** | Coding Plan 有 5 小时用量配额 | 配额耗尽时降级到其他家 |
| **通用** | Cloudflare 会拦 Python urllib 的 UA | 统一用 curl 或设浏览器 UA |

**这些坑的共同点**：它们不是"配置错了"，而是**上游的安全策略**。接入新供应商时，如果遇到 403/1010 这类错误，先怀疑 UA 和路径，而不是密钥。

## 四、可观测性

**没有观测的网关等于没有网关。**

### 该统计什么

```
· 每个模型的调用量（次数 + token 数）
· 每家供应商的失败率
· P50 / P95 / P99 延迟
· 降级触发次数（这是最重要的健康指标）
· 各模型的成本
```

**降级触发次数为什么最重要**：它直接反映了"链路健康度"。如果某家供应商的降级次数突然上升，说明它在出问题，应该主动排查而不是等业务反馈。

### 监控告警

我们的做法是**接入已有的运维告警通道**：

```
网关健康检查（本地端口探测，毫秒级）
    ↓ 异常时
定时任务检测 + 推送告警到飞书
```

**注意区分两类检查**：

- **liveliness**（存活）：进程是否还在，网关自身的健康
- **上游可用性**：真实调用一次模型，看链路是否通

**这两个必须分开**：网关进程活着不等于上游能用。我们踩过"网关健康检查全绿，但实际调用全失败"的情况（上游供应商故障）。

## 五、部署与运维

### 容器化

```yaml
services:
  litellm:
    image: ghcr.io/berriai/litellm:main-stable
    ports:
      - "127.0.0.1:4000:4000"     # 只监听本地，对外走隧道
    volumes:
      - ./config.yaml:/app/config.yaml
      - ./data:/app/data
    env_file:
      - .env                       # 密钥用环境变量，不进配置文件
    mem_limit: 900m
    restart: unless-stopped
```

**几个实践点**：

1. **只监听 127.0.0.1**：对外通过 Cloudflare 隧道暴露，不在主机上直接开公网端口
2. **密钥走环境变量**（`.env` 权限 600），不进配置文件（配置文件可能会被备份、提交、查看）
3. **设内存上限**：防止内存泄漏拖垮宿主机（实测运行 39 小时后内存从 511MB 涨到 661MB，需要留意）
4. **`restart: unless-stopped`**：进程崩溃自动恢复

### 密钥轮换与多环境

```
.env 里按供应商分组：
  ARK_API_KEY=xxx
  R4_API_KEY=xxx
  SZMF_API_KEY=xxx
  COG_API_KEY=xxx

  LITELLM_MASTER_KEY=xxx      ← 网关自己的鉴权密钥
```

**建议**：

- 网关的 master key 和上游的 key 分开管理
- 上游 key 泄漏时只影响一家，不会波及整个网关
- 定期轮换，尤其是暴露给多方的 key

## 六、踩过的坑

### 坑 1：超时配置过短导致功能"形同虚设"

**现象**：某个基于网关的功能总是"失败后回退到默认行为"，但看网关日志一切正常。

**根因**：客户端超时设了 12 秒，而网关真实调用需要 20 秒左右。**客户端先超时了，网关还在正常处理，但结果没人接收。**

**教训**：**超时时间必须端到端对齐**。客户端超时要 ≥ 网关超时 ≥ 上游实际耗时。排查这类问题，先看客户端和网关的超时配置是否匹配。

### 坑 2：DeepSeek 类模型的 `reasoning_content` 字段

**现象**：某些推理模型返回的内容不在 `content` 字段里，而在 `reasoning_content` 里，导致业务取到空字符串。

**原因**：推理模型把"思考过程"和"最终答案"分成两个字段，不同供应商的实现不一致。

**处理**：网关层统一归一化，业务侧只读 `content`。

```python
# 伪代码：网关侧统一
content = message.get("content") or message.get("reasoning_content") or ""
```

**这是网关的另一个价值**：把上游的差异（包括这种字段不一致）挡在网关之内，业务侧面对的是稳定接口。

### 坑 3：Docker Hub 拉不动

**现象**：国内服务器 `docker pull ghcr.io/...` 卡住或失败。

**解决**：用镜像加速源（实测 `ghcr.nju.edu.cn` 可用），或在能连通的机器上拉取后 `docker save` / `load`。

**这是个纯粹的国内网络问题，但会阻塞整个部署流程**，建议提前准备好可用的镜像源。

## 七、这套设计带来的收益

### 对业务方

```
接入成本：从"读 4 家文档、写 4 套适配" → 改 base_url 和 api_key
容错能力：从"某家挂了就失败" → 自动降级到其他家
换模型：  从"改代码 + 发布" → 改一行配置
```

### 对运维

```
可观测：统一看所有模型的调用量、延迟、失败率
可控制：密钥集中管理，不散落在各业务代码里
可扩展：新增供应商只改配置
```

### 一个具体例子

某次某家供应商出现临时故障（连续 403），因为配置了降级链，**业务侧完全没有感知**，只是调用延迟略有上升。事后看降级统计才发现。

**这是网关从"方便"变成"必需"的转折点**——它不只是在省事，而是在提供**业务连续性保障**。

## 落地检查清单

- [ ] 对外暴露统一协议（OpenAI 兼容），业务方只改 base_url/key
- [ ] 供应商差异挡在网关内（鉴权、UA、路径、字段归一化）
- [ ] 模型命名有明确规则（前缀区分来源 + 别名用于生产）
- [ ] 配置降级链，且理解**哪些错误会触发降级**
- [ ] 有全局兜底模型（`default_fallbacks`）
- [ ] 超时端到端对齐（客户端 ≥ 网关 ≥ 上游）
- [ ] 密钥走环境变量，文件权限 600，不进代码库
- [ ] 网关只监听 127.0.0.1，对外走隧道/网关
- [ ] 设内存上限 + `restart: unless-stopped`
- [ ] 区分"网关存活检查"和"上游可用性检查"（两者不是一回事）
- [ ] 统计调用量/失败率/延迟/降级次数，其中**降级次数是核心健康指标**
- [ ] 有告警通道，异常时主动通知而非等业务反馈

## 小结

自建 LLM 网关的价值，**不在于"统一 API"这个表面能力，而在于它提供的一致性、可观测性和业务连续性**。

回顾这套设计的三个关键决策：

1. **对外只暴露一种协议**——把复杂度收敛到网关内部，业务方零适配成本
2. **降级链 + 全局兜底**——从"某家挂了业务就失败"变成"业务无感知"
3. **端到端超时对齐**——这个最容易被忽略，但直接影响功能是否真的可用

如果重来一次，我会**更早接入用量与成本统计**。因为随着调用量增长，"哪个模型性价比最高"这个问题会越来越重要，而它需要历史数据才能回答。
