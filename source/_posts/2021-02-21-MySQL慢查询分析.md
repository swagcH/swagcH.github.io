这篇记录一次慢查询实验。目标不是看到耗时下降就结束，而是把每次改动的假设、执行计划、扫描行数和副作用放在一起比较。

测试表约 320 万行，问题接口查询某租户最近的已支付订单。文中的数据来自隔离环境，生产索引变更仍需要单独评估锁、磁盘和主从延迟。

## 实验对象

```sql
SELECT id, order_no, amount, created_at
FROM order_info
WHERE tenant_id = 1001
  AND status = 'PAID'
  AND created_at >= '2021-01-01 00:00:00'
ORDER BY created_at DESC
LIMIT 50;
```

表上原有索引：

```sql
PRIMARY KEY (id),
KEY idx_tenant (tenant_id),
KEY idx_status (status),
KEY idx_created_at (created_at)
```

三个查询字段分别有索引，很容易产生“应该不会慢”的判断。但 MySQL 通常不会把三个单列索引自动组合成最符合过滤和排序的访问路径。

## 先固定实验方法

为了让结果可比较，我约定：

```text
数据库版本：MySQL 5.7
数据快照：同一份脱敏数据
结果数量：固定 50
每个方案：预热 2 次，记录后续 5 次
同时记录：耗时、Rows_examined、执行计划、CPU
每轮之间：不修改其他参数
```

缓存冷暖会显著影响耗时，所以不能拿第一次查询和第十次查询直接比较。生产问题还要从慢查询日志确认真实频率：

```text
# Query_time: 2.846  Lock_time: 0.000
# Rows_sent: 50  Rows_examined: 1184297
```

只返回 50 行却扫描 118 万行，是比单次 2.8 秒更稳定的信号。

慢查询日志的全局开关会影响数据库行为，应由数据库管理员按规范操作。排查人员优先读取现有平台和日志，不在生产随意执行 `SET GLOBAL`。

## 基线：执行计划在做什么

```sql
EXPLAIN
SELECT id, order_no, amount, created_at
FROM order_info
WHERE tenant_id = 1001
  AND status = 'PAID'
  AND created_at >= '2021-01-01 00:00:00'
ORDER BY created_at DESC
LIMIT 50;
```

精简后的结果：

```text
type: range
possible_keys: idx_tenant,idx_status,idx_created_at
key: idx_status
rows: 1120000
Extra: Using index condition; Using where; Using filesort
```

这里重点看四项：

1. `key`：实际选择了哪个索引。
2. `rows`：优化器估算要检查多少行。
3. `Using where`：取出索引记录后仍需过滤。
4. `Using filesort`：结果顺序无法直接由当前索引满足。

`type=range` 不代表一定高效。状态 `PAID` 在全表中占比很高，先按状态扫描仍会读取大量不属于租户 1001 的记录。

## 假设 A：只强制使用租户索引

为了验证选择性，我在隔离环境使用 `FORCE INDEX` 做对照：

```sql
EXPLAIN
SELECT id, order_no, amount, created_at
FROM order_info FORCE INDEX (idx_tenant)
WHERE tenant_id = 1001
  AND status = 'PAID'
  AND created_at >= '2021-01-01 00:00:00'
ORDER BY created_at DESC
LIMIT 50;
```

扫描从约 112 万行下降到 31 万行，平均耗时从 2.8 秒下降到 0.9 秒，但仍需要过滤和排序。

这个实验说明 `tenant_id` 比 `status` 更有选择性，不说明应该把 `FORCE INDEX` 写进业务 SQL。数据分布变化后，强制策略可能比优化器更差。

## 假设 B：建立符合查询顺序的联合索引

查询模式是：

```text
tenant_id：等值
status：等值
created_at：范围 + 倒序
```

因此实验索引为：

```sql
CREATE INDEX idx_tenant_status_created
ON order_info (tenant_id, status, created_at);
```

在生产执行该 DDL 前，必须确认数据库版本、在线 DDL 能力、表大小、额外磁盘、锁等待和复制延迟，并准备中止与回退方案。

新执行计划：

```text
type: range
key: idx_tenant_status_created
rows: 41862
Extra: Using index condition
```

`Using filesort` 消失。因为前两列是等值条件，MySQL 可以沿 `created_at` 的索引顺序取最近记录，并在满足 `LIMIT 50` 后尽早停止。

五次记录：

| 方案 | 平均耗时 | P95 | Rows_examined | filesort |
| --- | ---: | ---: | ---: | --- |
| 原始索引 | 2.81s | 3.06s | 1,184,297 | 是 |
| 强制租户索引 | 0.91s | 1.02s | 312,460 | 是 |
| 联合索引 | 43ms | 58ms | 50 | 否 |

慢查询日志里的实际 `Rows_examined` 比 `EXPLAIN rows` 更能反映本次执行。执行计划的 `rows` 是估算值，两者不应混为一谈。

## 假设 C：把所有返回列都塞进索引

有人提出把 `order_no` 和 `amount` 也加到索引，做成覆盖索引。实验中查询确实少了回表，但收益只有几毫秒，索引体积和写入成本却继续增加。

这个接口只读取 50 行，回表 50 次并不是主要矛盾。最终没有扩大索引。

覆盖索引适合返回列少、调用频繁、扫描量明显的场景。不能为了让 `Extra` 出现 `Using index`，就把大字段和大量业务字段都加入索引。

## 假设 D：去掉时间条件会怎样

另一个接口复用了相同 SQL，但允许用户查询全部历史。去掉 `created_at` 条件后，联合索引仍能根据租户和状态定位，并按时间取前 50 条，因此首页仍然很快。

问题出现在深分页：

```sql
LIMIT 200000, 50;
```

数据库必须跳过前 20 万条，耗时重新上升。解决方式不是继续加索引，而是改成游标：

```sql
SELECT id, order_no, amount, created_at
FROM order_info
WHERE tenant_id = 1001
  AND status = 'PAID'
  AND (created_at < '2021-02-20 10:00:00'
       OR (created_at = '2021-02-20 10:00:00' AND id < 2918172))
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

为了让排序稳定，正式方案将 `id` 放到索引末尾并作为游标的一部分。仅按时间分页时，相同时间的记录可能重复或遗漏。

## 索引上线前后分别验证

上线前：

```text
[ ] SQL 来自真实慢日志，不是凭印象优化
[ ] 数据分布和生产相近
[ ] 联合索引顺序匹配过滤与排序
[ ] 检查已有重复索引
[ ] 评估索引大小、写放大和复制延迟
[ ] 准备 DDL 观察与中止方案
```

上线后：

```text
[ ] 实际执行计划使用预期索引
[ ] Rows_examined 与耗时下降
[ ] 数据库 CPU 和 IO 没有异常上升
[ ] INSERT、UPDATE 延迟仍在基线内
[ ] 主从延迟正常
[ ] 一周后复核真实查询分布
```

这次优化最有价值的并不是“加了一个联合索引”，而是验证过程：先用真实慢日志建立基线，再用单列索引实验理解选择性，最后让索引顺序匹配查询模式，并拒绝收益很小的过宽覆盖索引。

执行计划不是一张及格证。只有扫描量、响应时间、写入成本和真实业务负载一起改善，这次调优才算完成。
