# 背景

最近写 Java 小项目的时候，我经常会遇到各种报错。有些错误是编译阶段就提示的，比如文件找不到、方法必须抛出异常；有些错误是程序运行到一半才出现的，比如空指针、数组越界、类型转换失败。

一开始我对异常的理解比较简单：报错了就 `try-catch` 一下，能运行就行。但是写得多了之后发现，异常处理并不是把代码包起来这么简单。如果处理方式不对，程序表面上不报错了，真正的问题反而被藏起来了。

尤其是这段时间，我经常看到代码里有 `catch (Exception e)`，但 catch 里面只打印一句话，甚至什么都不写。这样虽然编译能通过，但以后排查问题会非常痛苦。

所以我打算在 2018 年 8 月这个阶段，把 Java 异常处理机制系统梳理一遍，弄清楚异常体系、`try-catch-finally` 执行顺序、什么时候应该抛异常、什么时候应该捕获异常。

# 问题

我目前遇到的困惑主要有这几个：

- Checked异常和Unchecked异常分不清
- `finally` 中的 `return` 会覆盖 `try` 中的返回值
- 习惯性 `catch (Exception e)`，但 catch 之后不知道怎么处理
- 空的 catch 块会吞掉异常，导致排查问题很困难
- 不知道什么时候应该向上抛异常，什么时候应该自己 catch

其中最让我印象深的是 `finally` 里的 `return`。以前我以为 `try` 里面已经 `return` 了，方法就结束了。后来才发现，只要有 `finally`，它仍然会执行；如果 `finally` 里面也写了 `return`，还会把 `try` 或 `catch` 里的返回值覆盖掉。

另外，空 catch 块也很危险。异常发生了，但是代码没有任何日志、没有任何提示，就像什么都没发生一样。这种写法短期看起来“安静”，长期看就是在给自己埋雷。

# 分析

Java 的异常可以先从 `Throwable` 这个顶层父类看起。它下面主要有两个分支：`Error` 和 `Exception`。

`Error` 通常表示比较严重的问题，比如 JVM 内存不足、栈溢出等，一般不是业务代码应该捕获处理的重点。我们平时写业务代码更多关注的是 `Exception`。

`Exception` 又可以分成两类：Checked异常和Unchecked异常。

Checked异常是编译期检查异常。也就是说，如果方法可能抛出这类异常，编译器会要求我们必须处理：要么使用 `try-catch` 捕获，要么在方法上使用 `throws` 声明继续向上抛。

Unchecked异常主要指 `RuntimeException` 以及它的子类，比如 `NullPointerException`、`IllegalArgumentException`、`IndexOutOfBoundsException` 等。这类异常编译器不会强制要求处理，但它们仍然会在运行时导致程序出错。

*配图说明：Java异常体系中 Throwable、Error、Exception 和 RuntimeException 的关系*

简单理解可以这样记：

| 类型 | 是否编译期强制处理 | 常见例子 | 处理思路 |
| --- | --- | --- | --- |
| Checked异常 | 是 | IOException、SQLException | 捕获后处理，或向上抛出 |
| Unchecked异常 | 否 | NullPointerException、IllegalArgumentException | 优先通过代码逻辑避免 |
| Error | 否 | OutOfMemoryError、StackOverflowError | 通常不在业务代码中捕获 |

`finally` 的规则也要特别注意：无论 `try` 中是否发生异常，只要 JVM 没有直接退出，`finally` 通常都会执行。它适合用来释放资源，比如关闭文件流、数据库连接等。

但是不要在 `finally` 中写 `return`。因为 `finally` 的 `return` 会覆盖 `try` 或 `catch` 中已经准备返回的结果，也可能覆盖正在抛出的异常，让问题变得非常隐蔽。

从代码结构上看，比较合理的异常处理思路是：底层代码只负责发现问题并抛出带上下文的异常，上层代码统一捕获并处理，比如返回错误提示、记录日志、回滚事务等。这样职责会更清晰，也更容易排查问题。

# 解决方案

## Java异常体系结构图


*配图说明：Checked异常和Unchecked异常的区别*

Checked异常的典型例子是读取文件：

```java
import java.io.FileInputStream;
import java.io.FileNotFoundException;

public class CheckedExceptionDemo {
    public static void main(String[] args) {
        try {
            FileInputStream inputStream = new FileInputStream("test.txt");
            System.out.println(inputStream);
        } catch (FileNotFoundException e) {
            System.out.println("文件不存在：" + e.getMessage());
        }
    }
}
```

`FileNotFoundException` 是 Checked异常，如果不处理，代码不能通过编译。

Unchecked异常的典型例子是空指针：

```java
public class UncheckedExceptionDemo {
    public static void main(String[] args) {
        String text = null;
        System.out.println(text.length());
    }
}
```

这段代码编译可以通过，但运行时会抛出 `NullPointerException`。所以 Unchecked异常不是“不重要”，而是编译器不强制我们写 `try-catch`。

## try-catch-finally执行顺序详解

先看最普通的情况：

```java
public class TryCatchFinallyDemo {
    public static void main(String[] args) {
        try {
            System.out.println("1. 执行try代码块");
            int result = 10 / 0;
            System.out.println(result);
        } catch (ArithmeticException e) {
            System.out.println("2. 执行catch代码块：" + e.getMessage());
        } finally {
            System.out.println("3. 执行finally代码块");
        }

        System.out.println("4. 程序继续向下执行");
    }
}
```

执行顺序是：先进入 `try`，遇到异常后进入匹配的 `catch`，最后一定执行 `finally`，然后继续执行后面的代码。

再看有 `return` 的情况：

```java
public class FinallyReturnDemo {
    public static void main(String[] args) {
        System.out.println(getNumber());
    }

    private static int getNumber() {
        try {
            return 1;
        } catch (Exception e) {
            return 2;
        } finally {
            return 3;
        }
    }
}
```

这个方法最终返回的是 `3`，不是 `1`。原因是 `try` 中虽然已经准备返回 `1`，但是在方法真正返回之前，`finally` 仍然会执行，而 `finally` 里的 `return 3` 覆盖了原来的返回值。

更推荐的写法是：

```java
public class BetterFinallyDemo {
    public static void main(String[] args) {
        System.out.println(getNumber());
    }

    private static int getNumber() {
        try {
            return 1;
        } finally {
            System.out.println("释放资源或记录必要信息");
        }
    }
}
```

`finally` 只做资源释放，不做返回值控制，这样逻辑更清楚。

## 自定义业务异常类

实际项目里，很多异常不是 Java 自带异常能准确表达的。比如用户余额不足、订单状态不正确、参数不合法等，都可以定义成业务异常。

```java
public class BusinessException extends RuntimeException {
    private final String errorCode;

    public BusinessException(String errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
    }

    public BusinessException(String errorCode, String message, Throwable cause) {
        super(message, cause);
        this.errorCode = errorCode;
    }

    public String getErrorCode() {
        return errorCode;
    }
}
```

使用业务异常时，异常信息要写清楚，最好带上业务上下文：

```java
public class OrderService {
    public void pay(String orderId, int balance, int amount) {
        if (balance < amount) {
            throw new BusinessException("BALANCE_NOT_ENOUGH", "订单" + orderId + "支付失败，余额不足");
        }

        System.out.println("订单支付成功：" + orderId);
    }
}
```

这里我选择让 `BusinessException` 继承 `RuntimeException`，是因为业务异常很多时候希望由上层统一处理，而不是在每一层都被迫 `try-catch`。

## 异常链cause的使用

有时候底层异常不能直接暴露给上层，但又不能丢失原始原因。这时就应该使用异常链，也就是把原始异常作为 `cause` 传进去。

```java
import java.io.FileInputStream;
import java.io.FileNotFoundException;

public class ExceptionCauseDemo {
    public static void main(String[] args) {
        try {
            loadConfig("app.properties");
        } catch (BusinessException e) {
            System.out.println("错误码：" + e.getErrorCode());
            System.out.println("错误信息：" + e.getMessage());
            e.printStackTrace();
        }
    }

    private static void loadConfig(String fileName) {
        try {
            new FileInputStream(fileName);
        } catch (FileNotFoundException e) {
            throw new BusinessException("CONFIG_NOT_FOUND", "配置文件不存在：" + fileName, e);
        }
    }
}
```

这样做的好处是：上层看到的是业务含义明确的异常，排查问题时又可以通过 `cause` 找到最原始的 `FileNotFoundException`。

## 多catch的使用

Java 7 之后可以在一个 catch 中捕获多种异常，适合处理方式相同的场景。

```java
public class MultiCatchDemo {
    public static void main(String[] args) {
        try {
            String numberText = args[0];
            int number = Integer.parseInt(numberText);
            System.out.println("数字是：" + number);
        } catch (ArrayIndexOutOfBoundsException | NumberFormatException e) {
            System.out.println("请输入一个合法的整数参数：" + e.getMessage());
        }
    }
}
```

如果不同异常的处理方式不同，就不要强行合并，应该分开 catch。

```java
public class SeparateCatchDemo {
    public static void main(String[] args) {
        try {
            String numberText = args[0];
            int number = Integer.parseInt(numberText);
            System.out.println("数字是：" + number);
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("缺少启动参数");
        } catch (NumberFormatException e) {
            System.out.println("参数不是合法整数：" + args[0]);
        }
    }
}
```

需要注意的是，catch 的顺序要从具体异常到宽泛异常。如果先 catch `Exception`，后面的具体异常就没有机会被捕获了。

## try-with-resources释放资源

以前释放资源通常写在 `finally` 里：

```java
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class OldResourceCloseDemo {
    public static void main(String[] args) throws IOException {
        BufferedReader reader = null;
        try {
            reader = new BufferedReader(new FileReader("test.txt"));
            System.out.println(reader.readLine());
        } finally {
            if (reader != null) {
                reader.close();
            }
        }
    }
}
```

Java 7 之后更推荐使用 `try-with-resources`，它会自动关闭实现了 `AutoCloseable` 接口的资源。

```java
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class TryWithResourcesDemo {
    public static void main(String[] args) {
        try (BufferedReader reader = new BufferedReader(new FileReader("test.txt"))) {
            System.out.println(reader.readLine());
        } catch (IOException e) {
            System.out.println("读取文件失败：" + e.getMessage());
        }
    }
}
```

相比手写 `finally`，`try-with-resources` 更简洁，也更不容易忘记关闭资源。

## 异常处理最佳实践清单

经过这次整理，我觉得写异常处理时可以按下面这份清单检查：

- 不要写空 catch 块，至少要记录日志或给出明确处理
- 不要只写 `catch (Exception e)`，除非这一层确实是统一异常处理入口
- 不要在 `finally` 中写 `return`
- 异常信息要带上下文，比如订单号、用户ID、文件名
- 能用代码判断避免的 RuntimeException，就不要依赖 try-catch
- 底层异常如果无法处理，就向上抛出，不要假装处理了
- 上层统一处理异常，负责日志、提示、事务回滚等
- 包装异常时保留原始 cause，避免丢失根因
- 关闭资源优先使用 try-with-resources
- 自定义异常命名要清晰，比如 `BusinessException`、`OrderStatusException`

例如下面这种空 catch 就是反模式：

```java
try {
    int result = 10 / 0;
    System.out.println(result);
} catch (Exception e) {
}
```

更好的方式是根据当前层的职责处理异常：

```java
try {
    int result = 10 / 0;
    System.out.println(result);
} catch (ArithmeticException e) {
    throw new BusinessException("CALCULATE_ERROR", "计算失败，除数不能为0", e);
}
```

这里没有把异常吞掉，而是把底层异常包装成更有业务意义的异常，并保留原始原因。

# 总结

这次系统梳理 Java 异常处理机制之后，我最大的感受是：异常处理不是为了“让程序不报错”，而是为了让错误在合适的位置被发现、被记录、被处理。

我的阶段性总结是：

- 不要吞异常，空 catch 块是非常危险的写法
- 异常信息要带上下文，不然排查问题会很困难
- 底层无法处理的异常应该向上抛，上层再统一 catch
- `finally` 适合释放资源，但不要在里面写 `return`
- 关闭文件流、网络连接等资源时，优先使用 `try-with-resources`

以后写代码时，我会尽量避免为了“消除红线”而随便 `try-catch`。真正好的异常处理，应该能帮助我更快定位问题，而不是把问题藏起来。
