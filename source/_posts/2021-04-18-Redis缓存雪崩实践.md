缓存雪崩不是某一个 key 没命中，而是大量缓存同时失效，或者 Redis 整体不可用，流量在短时间内全部落到数据库。数据库一旦变慢，应用线程和连接池继续堆积，故障会从缓存层扩散到整个调用链。

为了验证系统能否扛过这种变化，我们做了一次隔离环境演练。所有流量和故障注入都只在压测集群执行，禁止用生产 Redis 做“断开看看”之类试验。

## 演练目标

```text
场景 A：10 万个商品缓存集中到期
场景 B：Redis 连接连续失败 60 秒
入口流量：稳定 3000 req/s
正常缓存命中率：96%
数据库安全容量：800 query/s
恢复目标：核心商品查询保持可用，数据库不被打满
```

演练前先确认停止条件：数据库 CPU 超过 75%、连接池等待超过 20 或错误率超过 5% 时立即停止注入。压测环境也需要保护，避免影响共享测试服务。

## 场景 A：统一 TTL 在整点集中到期

旧的缓存预热任务每天 09:30 批量写入商品，所有 key 都使用 30 分钟 TTL：

```java
redisTemplate.opsForValue().set(
        key,
        product,
        30,
        TimeUnit.MINUTES
);
```

结果几乎可以按秒观察：

| 时间 | 缓存命中率 | DB QPS | DB 连接等待 | 接口错误率 |
| --- | ---: | ---: | ---: | ---: |
| 09:59:55 | 96% | 120 | 0 | 0 |
| 10:00:01 | 41% | 1,720 | 18 | 1.2% |
| 10:00:04 | 8% | 2,640 | 54 | 17% |
| 10:00:08 | 13% | 1,980 | 61 | 24% |

数据库安全容量只有 800 QPS，却瞬间承接两千多查询。查询变慢后连接释放更慢，进一步放大等待。

## 第一层改造：让过期时间分散

基础 TTL 上增加随机抖动：

```java
public long calculateTtlSeconds(long baseSeconds) {
    long jitter = ThreadLocalRandom.current()
            .nextLong(0, 10 * 60);
    return baseSeconds + jitter;
}

public void cacheProduct(String key, Product product) {
    long ttlSeconds = calculateTtlSeconds(30 * 60);
    // 随机过期避免同一批数据在同一秒集中回源
    redisTemplate.opsForValue().set(
            key,
            product,
            ttlSeconds,
            TimeUnit.SECONDS
    );
}
```

随机范围要结合基础 TTL 和业务新鲜度。30 秒缓存增加 10 分钟抖动显然不合理；30 分钟缓存增加 0 到 10 分钟通常更平滑。

第二轮演练中，过期分散到十分钟，数据库 QPS 峰值降到 480，没有超过安全容量。

随机 TTL 能解决“同时到期”，不能解决缓存节点整体不可用。

## 第二层改造：热点 key 只允许一个请求回源

即使过期时间分散，单个热点商品到期时也可能有数百个并发请求。读取逻辑增加短锁：

```text
读取缓存
  -> 命中：直接返回
  -> 未命中：尝试获取 product:{id}:rebuild 锁
       获取成功：查库、回填、释放锁
       获取失败：短暂等待后重读，或返回可接受的旧值
```

锁必须有较短过期时间，释放时校验持有者标识，避免误删其他线程后来获得的锁。不要让所有请求长时间阻塞等待同一把锁。

对于允许短暂旧数据的商品详情，我们采用逻辑过期：

```text
value：商品数据
logicalExpireAt：业务过期时间
Redis TTL：更长的物理保底时间
```

逻辑过期后，第一个请求异步刷新，其他请求在短窗口继续读取旧值。价格、库存等强一致字段不能直接套用这个策略，应按业务容忍度拆分。

## 第三层改造：限制回源总量

如果 10 万个不同 key 同时失效，每个 key 一把锁仍可能产生 10 万次数据库查询。应用还需要全局回源预算：

```text
数据库安全查询容量：800/s
正常非缓存查询保留：300/s
缓存重建预算：最多 400/s
预留：100/s
```

超过预算时：

- 核心商品读取短期旧值。
- 非核心推荐模块返回空集合或默认结果。
- 后台报表暂停刷新。
- 用户请求收到明确的繁忙响应，而不是无限等待。

降级结果要在产品层面提前确认。返回旧价格可能造成资损，就不能为了可用性随意降级。

## 场景 B：Redis 整体不可用 60 秒

我们在压测集群通过网络故障注入让应用无法连接 Redis。初始版本每次缓存失败后都会立即查库，并重试 Redis 三次：

```text
一个用户请求
  -> Redis 连接超时 200ms
  -> 重试 3 次
  -> 查询数据库
  -> 回填 Redis 再失败
```

不仅数据库流量上涨，每个请求还先浪费约 600ms。错误日志以每秒数千条增长，磁盘 IO 也受到影响。

改造后的策略是：

1. Redis 连续失败达到阈值后快速熔断。
2. 熔断期间不为每个请求重复等待连接超时。
3. 只有核心查询在回源预算内访问数据库。
4. 本地只保留极少量、短时间、可接受旧值的热点数据。
5. 半开状态使用少量请求探测 Redis 恢复。

Redis 恢复后不能立即让全部实例同时重建缓存。每个实例使用随机延迟进入半开，并由预热任务按优先级恢复热点。

## 高可用不能代替应用保护

Redis Sentinel 或 Cluster 能降低单节点故障时间，但故障转移仍有检测、选主、连接重建和数据同步窗口。客户端配置不正确时，高可用集群也可能表现为整体不可用。

需要演练：

```text
主节点故障后客户端多久恢复
连接池是否清理旧连接
故障窗口是否存在写丢失风险
只读副本和主节点切换行为
应用熔断是否早于线程池耗尽
```

缓存高可用解决“尽快恢复缓存”，应用限流和降级解决“恢复前数据库不要被冲垮”，两者缺一不可。

## 预热应该按业务热度执行

全量数据同时预热既慢，又容易再次制造统一 TTL。我们按访问热度分层：

```text
L1：首页和活动核心商品，发布前预热
L2：近 24 小时高频商品，逐批预热
L3：长尾商品，首次访问时按预算加载
```

预热任务本身要有限速、断点和幂等能力。执行结果包括成功数、失败数、耗时和缓存版本，不能只打印“预热完成”。

## 第二次演练结果

| 场景 | 初始版本 | 改造后 |
| --- | ---: | ---: |
| 集中过期 DB QPS 峰值 | 2,640 | 480 |
| Redis 故障 DB QPS 峰值 | 2,780 | 690 |
| Redis 故障接口错误率 | 31% | 3.4% |
| 恢复到 90% 命中率 | 14s 后突然恢复 | 3 分钟平滑恢复 |

改造后没有追求所有请求成功。非核心推荐被降级，一部分请求快速失败，但数据库和订单核心链路保持在安全水位。可控失败比整个系统排队到崩溃更有价值。

## 演练后保留的检查项

```text
[ ] 批量写入使用合理的 TTL 抖动
[ ] 热点 key 有单请求重建或逻辑过期策略
[ ] 全局数据库回源有容量预算
[ ] 缓存超时、重试和熔断不会叠加放大延迟
[ ] 降级结果经过业务确认
[ ] Redis 故障转移经过真实演练
[ ] 恢复后按热度限速预热
[ ] 命中率、回源 QPS、连接池和降级次数有告警
```

缓存雪崩治理不是简单给 TTL 加一个随机数。真正要保护的是整条链路：过期时间分散，热点重建合并，数据库回源有上限，缓存故障时快速降级，恢复时也避免第二次流量冲击。
