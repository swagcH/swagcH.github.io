> 数据库结构承载的是业务事实。代码写错可以快速回滚，错误表结构一旦积累大量数据，修改会同时影响迁移、兼容、性能和历史报表。这篇用一次订单表评审整理设计时真正需要问的问题。

## 先从业务事实开始

设计订单表前，不急着列字段，先确认：

```text
订单由谁创建
一个订单包含哪些商品
金额在哪个时间点确定
状态有哪些合法流转
取消、退款和删除是否保留历史
订单号是否需要对外展示
查询主要按用户、状态还是时间
预计数据量和保留年限
```

“用户可以买商品”不足以支撑表设计。金额是否允许调整、订单是否拆单、退款能否部分发生，都会改变数据模型。

## 1. 主键和业务编号分开

```sql
CREATE TABLE order_info (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_no VARCHAR(32) NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    status TINYINT UNSIGNED NOT NULL,
    total_amount DECIMAL(12, 2) NOT NULL,
    paid_amount DECIMAL(12, 2) NOT NULL DEFAULT 0.00,
    version INT UNSIGNED NOT NULL DEFAULT 0,
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no),
    KEY idx_user_created (user_id, created_at),
    KEY idx_status_created (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`id` 是数据库内部主键，适合聚簇索引和关联；`order_no` 是稳定的业务编号，可以暴露给外部。不要把自增 ID 直接当公开订单号，也不要让一个过长随机字符串承担所有关联主键成本。

业务编号生成要考虑全局唯一、趋势性、时钟回拨和信息泄露。使用雪花算法、号段或数据库序列都可以，但要明确失败和重复检测方式。

## 2. 数据类型按语义选择

### 金额

使用 `DECIMAL` 或最小货币单位整数，不使用浮点数：

```sql
total_amount DECIMAL(12, 2) NOT NULL
```

同时记录币种时，金额精度不能假设永远是两位小数。跨币种系统需要专门的 Money 设计。

### 时间

```sql
created_at DATETIME(3) NOT NULL,
updated_at DATETIME(3) NOT NULL
```

团队必须约定数据库时区和应用转换方式。`TIMESTAMP` 与 `DATETIME` 的范围、时区行为不同，不能只因为示例常见就随意选择。

### 状态

`TINYINT` 节省空间，但数据库里看到 `3` 不直观。需要在代码、文档和数据字典中维护同一映射：

```text
10 CREATED
20 PAID
30 SHIPPED
40 FINISHED
90 CANCELLED
```

给状态值留间隔，后续可以插入中间状态。不要复用已经废弃的数字表示新含义，否则历史数据会被重新解释。

### 文本

字段长度来自业务约束，而不是统一写 `VARCHAR(255)`。手机号、订单号、外部流水号的长度和字符集不同。超长正文放 `TEXT` 时，也要考虑是否真的需要频繁查询和索引。

## 3. NULL 和默认值要表达真实含义

`NULL` 应该表示“未知或不存在”，不是“开发暂时没想好”。

```text
paid_at = NULL：尚未支付
cancel_reason = NULL：没有取消
paid_amount = 0.00：已知支付金额为零
```

把所有字符串默认成空串，会让“未填写”和“明确为空”无法区分。反过来，所有字段都允许 NULL 也会把校验压力推给每个查询。

## 4. 订单明细单独建表

不要把商品列表保存成逗号字符串：

```sql
CREATE TABLE order_item (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_id BIGINT UNSIGNED NOT NULL,
    sku_id BIGINT UNSIGNED NOT NULL,
    sku_name VARCHAR(200) NOT NULL,
    unit_price DECIMAL(12, 2) NOT NULL,
    quantity INT UNSIGNED NOT NULL,
    created_at DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    KEY idx_order_id (order_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`sku_name` 和成交单价是下单时快照。商品后来改名或改价，历史订单仍应保持当时事实。是否同时保存规格、图片和税费，要根据展示和对账需求决定。

## 5. 索引从查询模式出发

先列高频查询：

```sql
-- 用户订单列表
SELECT id, order_no, status, total_amount, created_at
FROM order_info
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT 20;

-- 待处理订单扫描
SELECT id, order_no
FROM order_info
WHERE status = ?
  AND created_at < ?
ORDER BY created_at
LIMIT 500;
```

对应索引 `(user_id, created_at)` 和 `(status, created_at)`。索引字段顺序要匹配过滤和排序，不是简单把区分度最高的字段放最前面。

每个二级索引都会保存主键，并增加写入、存储和维护成本。下面几类索引需要重点检查：

- 被联合索引前缀覆盖的重复索引。
- 低区分度单列索引。
- 为一次临时报表增加、长期无人使用的索引。
- 包含过多长字符串的“万能覆盖索引”。

上线前使用真实数据量查看执行计划，不能只在几十行测试数据上验证。

## 6. 唯一约束是业务防线

应用先查询“订单号是否存在”再插入，在并发下仍可能重复。数据库唯一索引提供最终保证：

```sql
UNIQUE KEY uk_order_no (order_no)
```

幂等请求也可以建立唯一约束：

```sql
UNIQUE KEY uk_user_request (user_id, request_id)
```

捕获唯一键冲突后，要查询并返回原业务结果，而不是统一转换成“系统异常”。

## 7. 外键是否使用

外键能保护引用完整性，但会增加迁移、写入和跨表操作约束。单体且表关系稳定时可以使用；高并发、分库分表或跨服务数据所有权场景通常由应用和对账保证。

无论是否创建数据库外键，关系都必须明确：删除用户后订单如何保留，删除商品后订单快照是否还可展示。没有外键不代表没有约束。

## 8. 逻辑删除不能滥用

```sql
deleted TINYINT NOT NULL DEFAULT 0
```

逻辑删除方便恢复和审计，但会影响唯一索引、所有查询条件和数据量。订单通常不是“删除”，而是取消或关闭；用业务状态表达比统一 `deleted=1` 更准确。

真正需要删除的临时数据，应有明确生命周期和归档任务。不要让所有表永久增长。

## 9. 乐观锁和并发更新

订单状态更新可以带版本号：

```sql
UPDATE order_info
SET status = ?, version = version + 1, updated_at = NOW(3)
WHERE id = ?
  AND status = ?
  AND version = ?;
```

检查受影响行数，零行表示状态已变化或版本冲突。这样比先查后改更能保护合法状态流转。

乐观锁不适合所有高冲突场景。冲突频繁时要重新审视业务串行化、队列或数据库锁策略。

## 10. 表结构变更要可回退

开发环境能瞬间执行的 DDL，在线上大表可能锁表、占满磁盘或造成复制延迟。

变更前确认：

```text
表大小和增长速度
MySQL 版本及 Online DDL 能力
新增索引的磁盘空间
主从复制和延迟
应用新旧版本兼容窗口
失败后的回退方式
```

新增字段优先做到新旧代码都能运行：先加可兼容字段，再发布写入，再迁移历史数据，最后切换读取。不要把表变更和代码行为切换压在同一秒完成。

## 11. 评审清单

```text
[ ] 表名和字段使用统一业务术语
[ ] 主键与公开业务编号分离
[ ] 金额、时间、状态类型符合语义
[ ] NULL 与默认值有明确含义
[ ] 唯一约束覆盖并发重复风险
[ ] 索引来自真实查询和排序
[ ] 历史快照不会被主数据变化污染
[ ] 状态迁移和并发更新有保护
[ ] 数据保留、归档和删除策略明确
[ ] DDL 有容量评估和回退方案
```

好的数据库设计不是一次把未来所有字段都猜出来，而是准确表达当前业务事实，同时为常见演进保留空间。表结构越接近业务语言，后续查询、接口和故障排查就越少依赖口头解释。
