早期上线常见的场景是：开发把 Jar 发给运维，附上一句“替换后重启就行”。顺利时看不出问题，一旦启动失败，大家才开始确认配置改没改、数据库脚本跑没跑、旧包放在哪里。

部署标准化不是增加一堆表格，而是把一次上线变成可重复执行的 Runbook。即使换一个人值班，也能知道前置条件、执行顺序、验证标准和回退边界。

## 发布单先于操作

没有发布单，不开始生产操作。最小发布单包含：

```text
版本：v1.12.0
Git 提交：3a91f2c
构建编号：build-20201018-42
变更范围：订单导出、支付回调幂等修复
影响服务：order-service
数据库变更：V20201018_01__add_payment_unique_key.sql
配置变更：PAYMENT_READ_TIMEOUT 3s -> 5s
计划窗口：20:00-20:30
执行人 / 复核人：
观察指标：
回退触发条件：
```

标题相同的 Jar 不等于同一个版本。发布单必须能对应到唯一 Git 提交和构建产物。

## 0. 确认变更冻结

发布窗口开始前，确认待发布提交不再变化：

```bash
git show --stat 3a91f2c
git tag --contains 3a91f2c
shasum -a 256 order-service.jar
```

校验值应由 CI 生成，并在目标服务器再次核对。不要在服务器上临时修改 Jar、class 或配置后仍沿用原版本号，这会让后续节点无法复现。

需要一起冻结的还有：

- 数据库脚本内容和执行顺序。
- 配置版本。
- 依赖服务版本。
- 灰度节点范围。
- 验证用例和测试数据。

## 1. 上线前检查

我把检查分成业务、系统和恢复能力三组。

### 业务条件

```text
[ ] 需求验收完成，已知问题有明确结论
[ ] 新旧客户端兼容
[ ] 定时任务、消息消费者和批处理影响已确认
[ ] 数据初始化、历史迁移和权限配置已准备
[ ] 客服或业务方知道用户可见变化
```

### 系统条件

```text
[ ] CPU、内存、磁盘和连接池处于正常水位
[ ] 当前无未处理生产告警
[ ] 配置项已经双人复核
[ ] 依赖的数据库、缓存、MQ 和外部接口正常
[ ] 监控看板与日志检索可用
```

不要在系统已经不稳定时叠加发布变量。必须紧急发布时，要在发布单中说明当前故障状态和额外风险。

### 恢复条件

```text
[ ] 上一稳定版本产物可获取且校验通过
[ ] 旧配置版本可恢复
[ ] 数据库变更明确可逆或向后兼容
[ ] 回退操作人和决策人在线
[ ] 回退预计耗时符合业务容忍度
```

“保留旧 Jar”不是完整回退方案。如果新代码已经写入旧版本无法识别的数据，应用回退仍可能失败。

## 2. 数据库变更先做兼容设计

数据库变更优先使用扩展、迁移、收缩三步：

```text
扩展：新增可空字段、表或索引，新旧代码都能运行
迁移：新代码双写或迁移历史数据，持续校验
收缩：确认旧版本退出后，再删除旧字段和兼容逻辑
```

避免在同一个窗口直接重命名字段并立即发布只认识新字段的代码。大表 DDL 还要预估锁时间、临时空间、主从延迟和失败恢复。

执行脚本前：

```text
[ ] 已在相近数据量环境验证
[ ] 脚本带唯一版本号且不可重复修改
[ ] 明确是否幂等
[ ] 评估执行时间、锁和磁盘空间
[ ] 有执行后校验 SQL
[ ] 高风险操作得到数据库负责人授权
```

生产 DDL 和数据修复应由有权限的人按审批执行。不要把未经 Review 的临时 SQL 粘贴进生产终端。

## 3. 先灰度一个节点

多实例服务不要一次替换全部节点。标准顺序是：

```text
从负载均衡摘除一个节点
等待存量请求完成
部署新产物和配置
启动并通过就绪检查
执行冒烟验证
重新接入少量流量
观察一个完整业务周期
逐批替换其余节点
```

摘流和重启会影响服务容量，必须由具备生产权限的操作人执行，并确认剩余节点能够承载当前流量。

一个简单的启动检查不能只看进程：

```bash
curl --fail --silent http://127.0.0.1:8080/actuator/health
curl --fail --silent http://127.0.0.1:8080/api/internal/version
```

版本接口应返回当前 Git 提交、构建号和启动时间，避免流量打到错误产物。

## 4. 冒烟验证要覆盖写路径

只打开首页不足以证明后端可用。订单服务至少验证：

```text
读：查询一条授权范围内的订单
写：创建一笔可清理的测试订单
改：完成一次状态变化
依赖：数据库、缓存和下游调用成功
异步：消息被消费且没有进入死信队列
权限：无权限请求被正确拒绝
```

测试数据要有固定前缀和清理策略，不能污染报表或触发真实通知。涉及支付、短信和外部客户的流程，应使用专门沙箱或受控验证路径。

每项冒烟都记录请求时间、traceId 和结果。这样失败时能直接进入日志检索，而不是重新猜测。

## 5. 观察指标决定是否继续

灰度后至少看四组信号：

| 信号 | 关注点 |
| --- | --- |
| 流量 | QPS、实例流量是否符合灰度比例 |
| 质量 | 错误率、业务失败码、消息失败数 |
| 性能 | P95/P99、慢 SQL、下游耗时 |
| 资源 | CPU、堆内存、GC、线程池、连接池 |

不能只看平均响应时间。少量长尾请求可能已经影响核心用户，但均值仍然正常。

发布前应写清触发条件，例如：

```text
5 分钟错误率高于基线 1 个百分点：暂停扩容
核心接口 P99 连续 3 分钟超过 2 秒：回退灰度节点
出现数据重复或状态不可逆错误：立即停止发布并升级决策
```

阈值根据系统基线设定，不能把示例数字机械搬到所有服务。

## 6. 回退是一项预先设计的动作

回退判断由发布负责人根据既定条件做出，不在故障现场临时争论“再看看”。执行顺序通常是：

```text
停止继续发布
隔离新版本节点
保存日志、线程和关键指标
恢复旧产物与旧配置
通过健康与业务验证
逐步恢复流量
确认数据兼容与积压任务
```

如果数据库变更不可逆，可能只能前向修复，不能简单回滚应用。发布前必须把这种情况写进决策记录，并准备降级开关或兼容代码。

不要为了赶时间删除现场日志或覆盖旧产物。恢复业务和保留证据可以并行安排。

## 7. 发布结束不是群里说一句“好了”

发布完成记录：

```text
实际开始与结束时间
每批节点和当前版本
数据库、配置的实际版本
冒烟结果和 traceId
核心指标与基线对比
期间异常及处理
遗留观察项和负责人
```

至少跨过一个业务高峰或约定观察期后再关闭发布单。定时任务在凌晨执行、账务在次日对账时，十分钟无告警不代表变更已经完全验证。

## 最终 Runbook

```text
发布前：范围冻结 -> 产物校验 -> 条件检查 -> 回退演练
发布中：兼容变更 -> 单节点灰度 -> 冒烟 -> 指标观察 -> 分批扩展
异常时：停止扩展 -> 保存证据 -> 按阈值回退或前向修复
发布后：版本核对 -> 业务验证 -> 持续观察 -> 关闭与复盘
```

标准化发布的意义，是把原本藏在个人经验里的判断变成团队可以执行和复核的步骤。流程不一定让上线更快，却能让每一次快和慢都有证据，让故障发生时不用从“这次到底改了什么”开始查起。
