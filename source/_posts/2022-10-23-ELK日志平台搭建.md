> 这篇记录一次日志平台从“能收集”到“能排查”的建设过程。严格来说，加入 Filebeat 后常被称为 Elastic Stack。组件启动只是基础，真正决定平台质量的是日志字段、索引映射、保留策略和采集链路自身的可靠性。

## 1. 为什么不继续登录服务器 grep

单体阶段，一台机器上的 `app.log` 基本能还原请求。服务拆分后，一次订单请求可能经过：

```text
Gateway
  -> order-service
      -> stock-service
      -> payment-service
      -> RabbitMQ consumer
```

如果每个服务有三个实例，就要在十几份文件里按时间猜测。服务器滚动发布后，旧容器日志还可能已经被删除。

日志平台希望解决四件事：

1. 集中检索，不依赖登录生产服务器。
2. 通过 traceId 串起跨服务请求。
3. 按服务、级别、业务编号和异常类型过滤。
4. 对错误趋势、采集延迟和存储容量建立监控。

它不应该成为无限期保存全部文本的仓库。日志有成本，也可能包含敏感数据，必须从一开始设计范围和生命周期。

## 2. 组件职责

```text
Application：生成结构化日志
Filebeat：读取文件、记录采集位置、轻量转发
Logstash：解析、清洗、补充和路由
Elasticsearch：索引和检索
Kibana：查询、可视化和管理
```

小规模场景可以让 Filebeat 直接写 Elasticsearch，减少 Logstash 成本。需要复杂字段清洗、多目标路由或统一入口时，再加入 Logstash。组件不是越齐全越专业，每增加一层都要处理它的容量和故障。

Elastic Stack 各组件尽量保持同一大版本，并核对官方兼容说明。Elasticsearch、Kibana、Logstash 和 Filebeat 跨大版本混用，常见问题包括协议、模板和安全默认值不一致。

## 3. 先统一应用日志

目标事件：

```json
{
  "timestamp": "2022-10-23T21:00:00.123+08:00",
  "level": "ERROR",
  "service": "order-service",
  "env": "prod",
  "traceId": "4d61c188f9d24b76",
  "spanId": "5a8b2c11",
  "thread": "http-nio-8080-exec-7",
  "logger": "com.example.order.OrderService",
  "bizId": "order-20221023001",
  "message": "create order failed",
  "exception": "java.sql.SQLTimeoutException: query timeout"
}
```

建议字段分为三类：

```text
固定技术字段：timestamp、level、service、env、traceId、thread
业务检索字段：bizId、userType、operation，不记录敏感原值
文本字段：message、exception
```

不要把用户手机号、身份证、Token、密码和完整请求体直接写入日志。需要定位用户时，可以记录脱敏值或内部不可逆标识。

Java 服务通过 MDC 放入 traceId：

```java
public void doFilter(ServletRequest request, ServletResponse response,
                     FilterChain chain) throws IOException, ServletException {
    String traceId = UUID.randomUUID().toString().replace("-", "");
    try {
        MDC.put("traceId", traceId);
        chain.doFilter(request, response);
    } finally {
        // 线程池会复用线程，必须清理 MDC
        MDC.remove("traceId");
    }
}
```

实际项目应优先复用网关或链路追踪组件传入的 traceId，而不是每个服务重新生成。异步线程和消息消费还要显式传递上下文。

## 4. 一行一个 JSON 事件

Java 异常栈天然多行，普通文本采集需要复杂的 multiline 规则。更稳定的方式是由日志框架输出单行 JSON，把异常栈作为字符串字段。

这样 Filebeat 不负责猜测一条事件从哪里开始，能减少错拼和漏拼。代价是单行会很长，因此日志框架、Filebeat 和 Elasticsearch 都要设置合理的单事件大小限制。

应用应保留本地滚动策略，Filebeat 不是日志轮转工具：

```text
按大小或时间切割
限制保留天数和文件数量
压缩历史文件
确保 Filebeat 读取完成后再删除
```

## 5. Filebeat 采集配置

以 Filebeat 7.x 常见的 `log` input 为例：

```yaml
filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /data/logs/order-service/*.json
    json.keys_under_root: true
    json.add_error_key: true
    fields:
      source_type: spring-boot
    fields_under_root: true

output.logstash:
  hosts:
    - logstash-1:5044
    - logstash-2:5044
  loadbalance: true
  compression_level: 3
```

Filebeat 8.x 更推荐 `filestream` input，JSON parser 写法也会变化。升级时需要按目标版本迁移，不能只把 `type` 改名。

检查配置并前台调试：

```bash
filebeat test config -e
filebeat test output -e
filebeat -e -d 'input,publish'
```

调试日志量很大，只在受控时间短暂开启。Filebeat registry 保存文件读取位置，不能随意删除，否则可能导致历史日志重新采集。

## 6. Logstash 只做必要加工

```conf
input {
  beats {
    port => 5044
  }
}

filter {
  date {
    match => ["timestamp", "ISO8601"]
    target => "@timestamp"
  }

  mutate {
    remove_field => ["agent", "ecs", "host", "input"]
  }
}

output {
  elasticsearch {
    hosts => ["https://es-1:9200", "https://es-2:9200"]
    index => "app-log-%{+YYYY.MM.dd}"
    user => "${ES_USER}"
    password => "${ES_PASSWORD}"
    ssl => true
  }
}
```

示例省略了证书路径，生产环境必须正确校验证书，不能为了连通直接关闭 TLS 校验。

应用已经输出 JSON 时，Filebeat 可以把字段展开，Logstash 不需要再对 `message` 做一次 JSON 解析。重复解析会增加 CPU，也容易产生字段覆盖。

复杂 Grok 正则要谨慎。一个低效表达式在日志量升高时可能打满 Logstash CPU。能在应用端结构化的字段，不要留到采集端猜。

## 7. 映射决定日志是否可用

Elasticsearch 动态映射很方便，也很危险。不同服务把同一个字段 `cost` 分别写成字符串和数字，会造成映射冲突；动态业务键会制造大量字段。

一个简化模板：

```json
{
  "index_patterns": ["app-log-*"],
  "template": {
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "level": { "type": "keyword" },
        "service": { "type": "keyword" },
        "env": { "type": "keyword" },
        "traceId": { "type": "keyword" },
        "bizId": { "type": "keyword" },
        "message": { "type": "text" },
        "exception": { "type": "text", "index": false },
        "costMs": { "type": "long" }
      }
    }
  }
}
```

`keyword` 适合精确过滤和聚合，`text` 适合全文检索。异常栈通常只需要展示，可以不建立倒排索引，节省存储。是否关闭索引要根据真实查询需求决定。

## 8. 不要只按天创建索引

按天索引容易理解，但日志量变化后会出现两个问题：小服务产生大量小索引，大服务单日索引又可能过大。

更长期的方案是使用 ILM 或 Data Stream：

```text
Hot：持续写入和高频查询
Warm：只读，降低资源规格
Delete：超过业务保留期自动删除
```

滚动条件可以综合主分片大小、文档数和时间，而不是固定每天零点。不同 Elastic 版本的数据流、模板和 ILM 配置方式不同，需要按实际版本设计。

容量估算至少包含：

```text
每日原始日志量
JSON 和索引膨胀系数
副本数量
保留天数
磁盘高水位预留
故障恢复空间
```

不能等磁盘达到 90% 才第一次讨论保留周期。

## 9. Kibana 中怎么查

常用 KQL 示例：

```text
traceId : "4d61c188f9d24b76"
service : "order-service" and level : "ERROR"
bizId : "order-20221023001"
service : "payment-service" and message : "timeout"
```

一个有效的排查流程是：先按业务时间和 bizId 找入口日志，获得 traceId；再按 traceId 展开所有服务；最后比较每段耗时、错误码和异常栈。

Kibana Saved Search 和 Dashboard 也需要版本管理。只存在某个人浏览器收藏里的查询，不算团队能力。

## 10. 采集链路也会丢日志

需要监控：

```text
Filebeat：harvester、publish 失败、输出阻塞、registry 异常
Logstash：事件吞吐、filter 耗时、persistent queue、失败事件
Elasticsearch：写入拒绝、分片、磁盘水位、索引延迟
Kibana：查询错误和慢查询
```

Logstash 可以开启 Persistent Queue 缓冲 Elasticsearch 短暂不可用，但它不是无限队列。Filebeat 本地文件保留时间也要覆盖最长故障窗口，否则输出恢复前日志文件已经被应用删除。

对于解析失败事件，单独路由到错误索引：

```conf
output {
  if "_dateparsefailure" in [tags] or [error] {
    elasticsearch {
      hosts => ["https://es-1:9200"]
      index => "app-log-parse-failed-%{+YYYY.MM.dd}"
    }
  } else {
    elasticsearch {
      hosts => ["https://es-1:9200"]
      index => "app-log-%{+YYYY.MM.dd}"
    }
  }
}
```

错误索引要有告警和短保留期，不能让失败数据静默堆积。

## 11. 上线前的日志规范

```text
[ ] 所有服务输出统一时间格式和时区
[ ] traceId 能跨网关、Feign 和消息队列传递
[ ] ERROR 包含异常栈，不只打印 getMessage()
[ ] 敏感字段已脱敏或禁止记录
[ ] 字段类型写入索引模板
[ ] 应用日志和索引都有保留策略
[ ] 采集延迟、解析失败和磁盘水位有告警
[ ] 有按 traceId 和业务 ID 的共享查询模板
```

## 建设后的变化

ELK 搭建完成后，最大的变化不是“搜索速度更快”，而是排查过程开始有统一入口。开发不再先问日志在哪台机器，而是先拿到时间、业务编号和 traceId。

但平台不会自动产生好日志。字段随意、异常栈缺失、敏感信息失控时，集中存储只会把问题放大。应用日志规范、采集可靠性和生命周期管理三者一起落地，日志平台才从一个大搜索框变成真正的故障分析工具。
