# 背景

为什么会研究这个问题

服务数量增加后，登录服务器看日志的方式开始变得低效。一次请求可能经过网关、订单服务、库存服务和消息消费者，如果每个服务都登录机器 grep 日志，排查效率会很低。因此我开始搭建 ELK 日志平台，把分散日志集中采集、存储和检索。

# 问题

遇到了什么情况

搭建过程中主要遇到三个问题：日志格式不统一，导致字段无法检索；Logstash 解析规则写得太随意，数据进 Elasticsearch 后结构混乱；日志量上来后磁盘增长很快，如果不设置索引生命周期，很容易把机器打满。

# 分析

排查过程

```text
日志链路：
app.log
  -> Filebeat
  -> Logstash
  -> Elasticsearch
  -> Kibana
```

```json
{
  "timestamp": "2022-10-23T21:00:00",
  "level": "ERROR",
  "service": "order-service",
  "traceId": "abc123",
  "message": "create order failed"
}
```

日志平台不是简单收集文本，而是要让日志结构化。只有字段固定，才能按 traceId、service、level、bizId 快速过滤。

# 解决方案

具体操作

```yaml
filebeat.inputs:
  - type: log
    paths:
      - /data/logs/*.log
    fields:
      service: order-service
```

```conf
filter {
  json {
    source => "message"
  }
}
output {
  elasticsearch {
    hosts => ["http://elasticsearch:9200"]
    index => "app-log-%{+YYYY.MM.dd}"
  }
}
```

```text
落地规则：
1. 应用统一 JSON 日志格式
2. 必须打印 traceId
3. ERROR 日志必须有异常栈
4. 索引按天切分
5. 保留周期按业务价值设置
```


# 总结

经验沉淀

ELK 的核心价值是让日志可检索、可关联、可追溯。平台搭起来只是第一步，更重要的是日志规范。没有 traceId、业务 id 和统一字段，ELK 也只能变成一个更大的文本搜索框。
