![RabbitMQ消息丢失排查技术图](/images/posts/2021/rabbitmq-message-loss-cover.svg)

现象是订单已经支付，积分却没有到账。支付服务日志里有“message sent”，积分消费者没有任何记录，队列的 `ready` 和 `unacked` 都是 0。

排查消息丢失时，不能只问“RabbitMQ 里有没有”。一条消息要经过业务事务、生产者、交换机、队列、消费者和消费结果六段。我们为这笔支付建立了一条消息轨迹，逐段确认最后一次成功在哪里。

## 先确定唯一消息身份

本次业务信息：

```text
paymentNo=P202110240091
orderNo=O202110240318
eventType=PAYMENT_SUCCEEDED
messageId=01FJQ6D7C2M4P8
occurredAt=2021-10-24T15:41:22
```

`messageId` 是每次业务事件的唯一标识，应该进入：

- 生产事件表。
- 消息 Header。
- Producer 日志。
- Broker confirm 和 return 回调。
- Consumer 日志。
- 消费幂等表。

只有订单号不够。一笔订单可能有支付成功、退款、关闭等多种事件，也可能重试发送同一个事件。

## 第一站：业务事务是否真的生成事件

支付表显示状态已经成功，但旧实现直接在事务里发送消息：

```java
@Transactional
public void completePayment(PaymentCallback callback) {
    paymentRepository.markSuccess(callback.getPaymentNo());
    rabbitTemplate.convertAndSend(
            "payment.events",
            "points.payment.success",
            buildEvent(callback)
    );
}
```

这里存在两个相反窗口：

```text
数据库提交成功，发送失败 -> 支付成功但没有积分事件
消息发送成功，数据库回滚 -> 积分收到一个不存在的成功事件
```

当前日志说明代码执行过 `convertAndSend`，但“方法没有抛异常”只表示消息交给了客户端发送流程，不等于已经进入目标队列。

## 第二站：Broker 是否确认接收

检查配置发现 Publisher Confirm 没有开启，因此没有证据说明 Broker 接受了这条消息。

开启：

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
```

发送时关联 messageId：

```java
CorrelationData correlationData = new CorrelationData(event.getMessageId());
rabbitTemplate.convertAndSend(
        PAYMENT_EXCHANGE,
        PAYMENT_SUCCESS_ROUTING_KEY,
        event,
        message -> {
            message.getMessageProperties()
                    .setMessageId(event.getMessageId());
            return message;
        },
        correlationData
);
```

Confirm 回答“交换机是否收到”：

```java
rabbitTemplate.setConfirmCallback((correlation, ack, cause) -> {
    String messageId = correlation == null
            ? null
            : correlation.getId();
    if (ack) {
        messageTraceService.markBrokerConfirmed(messageId);
        return;
    }

    // nack 必须进入可重试状态，不能只打印日志
    messageTraceService.markPublishFailed(messageId, cause);
    log.error("message_publish_nacked messageId={} cause={}",
            messageId, cause);
});
```

Confirm 是异步结果。业务线程返回成功时，回调可能还没有执行，所以发送状态要持久化，并由后台任务处理长时间未确认的记录。

## 第三站：交换机能否路由到队列

继续核对应用实际配置：

```text
交换机：payment.events
生产 routing key：points.payment.sucess
队列绑定 key：points.payment.success
```

生产 key 中的 `success` 少了一个 `c`。交换机存在，因此 Broker 可以返回 confirm ack；但没有任何队列匹配 routing key。

旧配置 `mandatory=false`，无法路由的消息被 Broker 丢弃，生产者也收不到 Return。队列 `ready=0` 正好符合这个路径。

开启 mandatory 后，ReturnsCallback 记录路由失败：

```java
rabbitTemplate.setReturnCallback((message, replyCode, replyText,
                                  exchange, routingKey) -> {
    String messageId =
            message.getMessageProperties().getMessageId();
    messageTraceService.markUnroutable(
            messageId, exchange, routingKey, replyText);
    log.error(
            "message_unroutable messageId={} exchange={} routingKey={} reply={}",
            messageId, exchange, routingKey, replyText
    );
});
```

Return 回答“交换机收到了，但有没有队列接住”。Confirm ack 不能代替 Return。

本次直接根因就是 routing key 拼写错误，加上未启用 Return，导致消息在交换机阶段静默消失。

## 第四站：队列是否具备持久化条件

修正路由后，还要检查：

```text
exchange 是否 durable
queue 是否 durable
message deliveryMode 是否 persistent
绑定是否与预期一致
是否配置 TTL、最大长度和溢出策略
队列删除或重建是否经过变更流程
```

队列持久化、消息持久化和 Broker 磁盘可靠性是不同层面。只设置消息持久化，但发送到临时队列，Broker 重启后队列仍会消失。

Publisher Confirm 表示 Broker 按当前配置接收并处理，具体持久化保证要结合 RabbitMQ 集群类型、镜像或 Quorum Queue 配置评估。

## 第五站：消费者什么时候 ack

另一类“消息丢失”发生在消费者。旧消费者使用自动确认，业务处理抛异常前消息已经被确认，队列不会再投递。

手动确认的基本顺序：

```java
@RabbitListener(queues = POINTS_PAYMENT_QUEUE, ackMode = "MANUAL")
public void consume(PaymentSucceededEvent event,
                    Message message,
                    Channel channel) throws IOException {
    long deliveryTag =
            message.getMessageProperties().getDeliveryTag();

    try {
        pointsService.grantOnce(event);
        // 业务事务成功后才确认
        channel.basicAck(deliveryTag, false);
    } catch (RetryableException exception) {
        // 当前消息重新入队；需要配合重试次数，防止无限热循环
        channel.basicNack(deliveryTag, false, true);
    } catch (Exception exception) {
        // 不可重试错误送往死信路径，等待人工或补偿处理
        channel.basicNack(deliveryTag, false, false);
    }
}
```

如果 `pointsService` 已提交数据库，但进程在 `basicAck` 前退出，消息会重复投递。因此可靠消费一定会面对重复。

## 第六站：消费端必须幂等

积分服务用 `message_id` 建立唯一处理记录：

```sql
CREATE TABLE consumed_message (
    message_id VARCHAR(64) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    consumed_at DATETIME NOT NULL,
    PRIMARY KEY (message_id)
);
```

积分写入和消费记录放在同一个本地事务：

```java
@Transactional
public void grantOnce(PaymentSucceededEvent event) {
    if (consumedMessageRepository.exists(event.getMessageId())) {
        return;
    }

    pointsRepository.grant(
            event.getUserId(),
            event.getPoints(),
            event.getOrderNo()
    );
    // 唯一约束是并发重复消费的最终防线
    consumedMessageRepository.save(
            event.getMessageId(),
            event.getEventType()
    );
}
```

先查再写仍有并发窗口，必须依赖唯一约束并把重复键转换成“已处理”。幂等键要对应业务事件，不能用每次重试都变化的新 UUID。

## 用 Outbox 补上数据库与发送之间的空隙

支付状态和待发送事件写入同一个数据库事务：

```text
支付回调事务：
  更新 payment=SUCCESS
  插入 outbox_event=PENDING
  一起提交

发布任务：
  读取 PENDING
  发送 RabbitMQ
  等待 Confirm / Return
  更新 SENT 或 RETRY
```

这样只要支付成功事件已经提交，就能被后续任务再次发现。它仍然可能重复发送，因此消费者幂等不能省略。

Outbox 表需要：

- 唯一事件 ID。
- 状态与重试次数。
- 下一次重试时间。
- 错误摘要。
- 创建和确认时间。
- 分页扫描索引和归档策略。

重试使用退避，不要在 Broker 不可用时不停查询和发送。

## 最终消息轨迹

修复后，一条消息可以查到：

```text
15:41:22.104 BUSINESS_COMMITTED
15:41:22.181 PUBLISH_STARTED
15:41:22.196 BROKER_CONFIRMED
15:41:22.214 CONSUME_STARTED
15:41:22.247 BUSINESS_APPLIED
15:41:22.251 CONSUMER_ACKED
```

超过正常时间仍停在某一阶段时，监控直接告警：

```text
PENDING 太久          -> 发布任务或 Broker
PUBLISH_STARTED 无确认 -> 网络、连接或 Confirm
UNROUTABLE             -> exchange、routing key、binding
队列 ready 持续增长    -> 消费能力不足
unacked 持续增长       -> 消费慢、卡住或未确认
死信增长               -> 不可重试异常或次数耗尽
```

## 可靠消息检查表

```text
[ ] 每个业务事件有稳定 messageId
[ ] 业务状态与 Outbox 同事务提交
[ ] Publisher Confirm 持久化处理结果
[ ] mandatory + Return 发现无法路由
[ ] exchange、queue、message 持久化配置明确
[ ] 消费成功后才 ack
[ ] 重试有次数、退避和死信出口
[ ] 消费端以业务事件做幂等
[ ] 每个阶段都有可查询状态和超时告警
```

消息系统很难提供真正的“只处理一次”。工程上更可行的目标是：生产至少送达，消费允许重复但结果幂等，每个阶段都能追踪和补偿。做到这些，“消息丢了”才会变成一个能够准确定位到站点的问题。
