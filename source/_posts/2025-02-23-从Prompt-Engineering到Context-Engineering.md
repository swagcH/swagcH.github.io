刚开始用 AI 写代码时，我把主要精力放在“怎么写出更厉害的提示词”上：你是一名资深工程师、请深入思考、请给出最佳实践。它们偶尔有用，但面对真实项目，决定结果的往往不是形容词，而是模型到底看到了哪些事实。

为了确认这个判断，我拿一个相同的小需求做了三轮实验。任务是给 Spring Boot 项目的订单查询接口增加一个 `deliveryStatus` 字段。三轮使用同一个模型，只改变输入上下文，不手工修正中间结果。

<!-- more -->

## 实验规则

项目的真实约束如下：

```text
JDK 8 + Spring Boot 2.x
Controller 返回统一的 ApiResult<OrderDetailVO>
配送状态来自 delivery_record 表，不在 order_info 表
一笔订单可能有多条配送记录，以 created_at 最新一条为准
无配送记录时返回 NOT_STARTED
不允许改变现有接口路径和字段含义
```

评价结果时，我没有使用“看起来不错”这种标准，而是列了六项检查：

| 检查项 | 分值 |
| --- | ---: |
| 找到正确的接口和返回对象 | 2 |
| 找到配送状态的真实数据来源 | 2 |
| 正确处理多条记录 | 2 |
| 正确处理空记录 | 1 |
| 遵守 JDK 8 与现有项目风格 | 1 |
| 给出并通过对应测试 | 2 |

满分 10 分。这个分数不是严谨的模型评测，只用来比较上下文改变后的结果。

## 第一轮：一句话需求

我只输入：

```text
给订单详情接口增加 deliveryStatus 字段，请直接修改代码。
```

模型很快给出了一套完整方案：修改 Entity、DTO、Mapper 和数据库脚本，还建议在 `order_info` 表增加 `delivery_status` 字段。

代码组织得很像一个正常 Spring Boot 项目，甚至主动补充了 Swagger 注解。但项目根本没有它假设的 `OrderEntity`，状态也不应该存到订单表。

第一轮得分：**2/10**。

得到的两分来自“字段确实加到了一个返回对象里”和“代码大致兼容 JDK 8”。其余内容主要由常见项目模式补全。模型不是故意忽略设计，它只是没有看到真实设计。

这轮让我意识到一个不太舒服的事实：输出越完整，越容易让人忘记检查前提。若我只浏览文件名，很可能会把这份错误方案当成高效率。

## 第二轮：把提示词写得更专业

第二轮仍然没有提供仓库，只把提示词改成结构化版本：

```text
角色：你是一名资深 Java 后端工程师。

任务：为订单详情接口增加 deliveryStatus 字段。

要求：
1. 遵循分层架构和 SOLID 原则；
2. 兼容 JDK 8；
3. 考虑空值、异常和性能；
4. 添加完整单元测试；
5. 修改前先分析，修改后总结影响。
```

第二轮的回答更谨慎。模型列出了待确认问题，提出可能从物流表获取状态，并给出 Service 聚合的伪代码。它没有直接要求改表，也提醒要检查 N+1 查询。

但只要进入具体代码，问题仍然存在：

- 猜测项目使用 `ResponseEntity`；
- 创建了不存在的 `DeliveryStatusEnum`；
- 默认调用 `findTopByOrderIdOrderByCreatedAtDesc`；
- 测试使用 Mockito 5，而项目锁定的是 Mockito 2；
- 没有办法证明修改位置正确。

第二轮得分：**4/10**。

更清晰的提示词改善了任务纪律，却没有补上项目事实。它让模型更像一个会先问问题的工程师，但不能让工程师凭空看到仓库。

## 第三轮：设计模型能够工作的上下文

第三轮没有继续润色角色，而是先准备上下文包。

### 1. 给出项目地图

```text
请求入口：OrderController#getDetail
业务编排：OrderQueryService#getDetail
返回对象：OrderDetailVO
订单查询：OrderMapper#selectDetail
配送记录：DeliveryRecordMapper#selectLatestByOrderId
同类实现：AfterSaleQueryService#getDetail
测试入口：OrderQueryServiceTest
```

这张地图不是凭感觉写的。我先在仓库里搜索接口路径、类型引用和 Mapper 方法，确保每个名字真实存在。

### 2. 提供必要代码，而不是整个仓库

我让模型读取上述六个文件，同时补充 `pom.xml` 中的 Java 与测试依赖版本。没有把无关 Controller、生成目录、历史日志全部塞进去。

### 3. 写清楚业务状态表

| 最新配送记录 | `deliveryStatus` |
| --- | --- |
| 不存在 | `NOT_STARTED` |
| `CREATED` | `PREPARING` |
| `PICKED_UP` | `DELIVERING` |
| `SIGNED` | `COMPLETED` |
| 未知值 | `UNKNOWN`，并记录告警日志 |

自然语言中的“按最新记录判断”很容易漏掉空值和未知值。状态表能让模型与人使用同一份边界定义。

### 4. 限定工作方式

最终输入变成：

```text
先阅读我列出的文件，说明当前调用链和最小修改范围。
不要创建仓库中不存在的通用框架，也不要修改表结构。
计划确认后再修改，每次只处理一个职责。

验收条件：
- 原有订单详情字段保持不变；
- 四类配送记录映射符合状态表；
- 无记录与未知状态有测试；
- 执行项目现有测试命令；
- 最后列出实际修改文件和仍未验证的风险。
```

这里真正起作用的不是措辞更长，而是输入中包含可定位的文件、确定的业务规则和可执行的完成条件。

## 第三轮发生了什么

模型先还原了实际调用链：Controller 只转发参数，`OrderQueryService` 负责组装 `OrderDetailVO`，同类的售后服务已经采用 Mapper 查询最新记录再映射状态的方式。

它提出只修改三个文件：

```text
OrderDetailVO.java
OrderQueryService.java
OrderQueryServiceTest.java
```

由于 `DeliveryRecordMapper#selectLatestByOrderId` 已存在，不需要新建 Mapper 或改 SQL。映射逻辑也没有额外创造枚举，而是复用了项目中的 `DeliveryNodeEnum`。

测试第一次执行时，有一个未知状态用例失败。原因不是业务代码，而是测试夹具默认给 `createdAt` 留空，Mapper 模拟数据排序时触发空指针。模型根据真实失败信息修复了测试数据，再次执行通过。

第三轮得分：**9/10**。

扣掉的一分来自它最初建议把映射方法放进 VO。我认为状态解释属于查询服务，不应让纯返回对象依赖配送领域枚举，因此人工审查后调整了位置。

## 三轮结果放在一起

| 轮次 | 输入重点 | 得分 | 主要问题 |
| --- | --- | ---: | --- |
| 一句话需求 | 目标 | 2 | 大量猜测项目结构 |
| 结构化 Prompt | 角色、原则、步骤 | 4 | 行为更谨慎，事实仍缺失 |
| Context Engineering | 文件、规则、约束、验证 | 9 | 基本可用，仍需架构判断 |

这次实验并不能证明提示词不重要。清楚的任务表达仍然能减少歧义，但在代码仓库里，它只是上下文的一部分。

我对两者的区分是：

```text
Prompt Engineering
关注“这一句话怎样表达得更有效”。

Context Engineering
关注“为了完成任务，模型在每一步应该看到什么事实、工具和反馈”。
```

后者更像设计一条信息流水线。它不仅包含用户的第一段输入，还包括仓库检索、文件选择、构建日志、测试结果、团队规范和前一步产生的决策。

## 上下文也会变质

上下文不是越多越好。我在后续任务中遇到过三个反例。

### 过期上下文

需求文档写的是旧接口，代码已经迁移到新服务。模型严格遵循文档，反而改错位置。重要事实要标明来源与时间，冲突时以当前可执行代码和明确决策为准。

### 相互冲突的上下文

全局规范要求所有异常转换成统一错误码，模块内却保留了旧的直接抛出方式。若不说明本次遵循哪一层，模型可能随机选择。冲突不能靠增加更多文本解决，需要人做决策。

### 没有优先级的上下文

我曾一次提供十几个“参考实现”。模型混用了其中三种风格。后来只给一个最接近的主参考，其余资料明确标注“仅用于理解字段，不复制结构”，结果稳定很多。

所以，上下文设计还需要三条规则：

1. 保证来源真实且尽量新；
2. 冲突信息写明优先级；
3. 每份材料说明它在任务中的用途。

## 我现在使用的上下文清单

开始一个代码任务前，我通常检查下面这些信息是否齐全：

```text
[ ] 用户问题与业务目标
[ ] 当前可复现的现象
[ ] 入口、调用链和关键数据结构
[ ] 语言、框架和依赖版本
[ ] 可以复用的相邻实现
[ ] 明确不能改变的行为
[ ] 异常、空值、并发和权限边界
[ ] 要执行的测试与构建命令
[ ] 修改范围和回滚方式
```

简单任务不必把每一项写成长文，但缺失项要心里有数。尤其是“怎样算完成”，如果人自己都没有答案，模型只能生成一个听起来合理的终点。

从 Prompt Engineering 走向 Context Engineering，对我最大的改变不是提示词变长了，而是开始把 AI 编程当成工程协作：先准备事实，控制信息流，再用真实反馈纠偏。模型负责快速探索和执行，人负责选择上下文、处理冲突并对结果签字。

这也许没有“一句话生成整个系统”那么有戏剧性，却更接近可以重复使用的生产力。
