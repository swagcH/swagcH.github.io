> 写在前面：磁盘问题不只有“空间满了”。容量还有很多但文件创建失败，可能是 inode 用完；接口突然变慢但 CPU 不高，可能是 IO 等待；文件已经删除但空间不释放，可能是进程仍持有句柄；文件系统变成只读，则可能涉及底层错误。

这篇整理成一份值班口袋手册。先分级和保留证据，再进入容量、inode、删除文件、IO 延迟或只读文件系统分支。涉及删除、重启、数据库和文件系统修复的操作必须由对应负责人授权。

## 先按风险分级

| 等级 | 典型现象 | 首要目标 |
| --- | --- | --- |
| P0 | 文件系统只读、数据库写失败、核心服务不可用 | 隔离风险，保护数据 |
| P1 | 使用率超过 95%、inode 耗尽、IO 延迟持续影响业务 | 停止增长，恢复余量 |
| P2 | 使用率或延迟持续上升，预计 24 小时内越线 | 定位来源，计划处置 |
| P3 | 单次波动，无业务影响 | 记录基线，观察趋势 |

同样 90% 使用率，20G 根分区和 10TB 数据盘的剩余时间完全不同。分级要结合增长速度、剩余容量和业务用途，不只看百分比。

## 前五分钟只做只读检查

```bash
date -Is
hostname
df -hT
df -ih
findmnt
lsblk -f
vmstat 1 5
iostat -xz 1 5
```

这组命令回答：

```text
哪个挂载点容量用尽
哪个挂载点 inode 用尽
设备与挂载点如何对应
文件系统类型和挂载选项
是否存在 IO 等待
哪个块设备延迟异常
```

先记录时间和输出，再做清理。恢复后才能与同一组基线比较。

`iostat` 需要 `sysstat` 工具包，缺失时不要在故障现场临时安装未知软件；使用已有监控替代。

## 分支 A：容量使用率高

从告警挂载点逐层向下，`-x` 避免跨文件系统：

```bash
du -xhd1 /var 2>/dev/null | sort -h
du -xhd1 /var/log 2>/dev/null | sort -h
```

不要从根目录无差别执行高开销扫描。大目录 `du` 会产生大量 IO，业务已经抖动时应缩小路径、降低执行频率，必要时参考文件系统或监控平台已有统计。

定位大文件可以在明确目录中执行：

```bash
find /var/log -xdev -type f -size +500M -printf '%s %p\n' 2>/dev/null | sort -n
```

`find` 同样需要遍历目录。命中后先确认文件归属、是否正在写、保留要求和是否已采集，不能看到大文件就删除。

## 分支 B：df 很高，du 却很小

`df` 统计文件系统已占用块，`du` 遍历仍有目录项的文件。差值很大时检查已删除但仍被进程持有的文件：

```bash
lsof +L1
```

典型输出：

```text
java  1842  app  17w  REG  253,1  18G  /var/log/order/app.log (deleted)
```

处理优先级：

```text
让应用日志框架滚动并重开
使用服务支持的平滑重载
摘流后正常重启单个实例
最后才评估是否操作具体文件描述符
```

直接终止进程或截断描述符都有业务风险。执行前确认文件类型、进程职责、事务和剩余实例容量，由应用负责人操作。

空间释放后再次运行 `df` 和 `lsof +L1`，证明句柄已经消失，而不是只看命令返回成功。

## 分支 C：inode 用尽

`df -h` 可能还有大量空间，`df -i` 却达到 100%。一个空文件也需要 inode，海量小日志、缓存或临时文件会导致无法创建新文件。

先从已知高风险路径估算文件数量：

```bash
find /var/tmp -xdev -type f -printf '%h\n' 2>/dev/null | sort | uniq -c | sort -n | tail
```

在百万级目录执行 `find` 可能很慢，应先结合应用配置、目录更新时间和监控缩小范围。

常见来源：

- 每次请求创建独立临时文件但不清理。
- 日志按请求或任务拆成小文件。
- Session、缓存落盘无过期。
- 邮件队列、爬虫或批处理产生大量碎片。
- 容器存储层残留。

处理时优先暂停继续产生文件的任务，再按应用定义的生命周期清理。只删当前文件、不修复生产逻辑，inode 很快再次耗尽。

## 分支 D：空间正常但 IO 延迟高

`iostat -xz` 常看：

| 指标 | 含义 | 注意 |
| --- | --- | --- |
| `r/s w/s` | 每秒读写请求 | 与业务基线比较 |
| `rkB/s wkB/s` | 吞吐 | 高吞吐不一定高延迟 |
| `await` | 请求平均等待时间 | 读写混合值可能掩盖差异 |
| `aqu-sz` | 平均队列长度 | 持续增长表示积压 |
| `%util` | 设备忙碌程度 | SSD、RAID、云盘不能单独解读 |

不要使用“`%util=100%` 就一定是磁盘极限”的单一规则。并行设备和虚拟块存储的含义不同，延迟、队列、吞吐和云盘额度要一起看。

定位进程：

```bash
pidstat -d 1 5
iotop -oPa
```

`iotop` 需要权限并可能未安装。使用前确认生产诊断规范。

把高 IO 进程对应到行为：

```text
Java：日志暴增、Heap Dump、文件导出
MySQL：慢查询、刷脏页、备份、索引构建
容器运行时：镜像拉取、日志、层清理
系统任务：压缩、备份、病毒扫描
未知进程：先确认来源，不直接终止
```

还要看 `vmstat` 的 `si/so`。内存不足导致 swap 时，磁盘忙只是第二现场。

## 分支 E：文件系统变成只读

应用日志可能出现：

```text
Read-only file system
Input/output error
EXT4-fs error
XFS metadata I/O error
```

先保存：

```bash
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
journalctl -k --since '30 minutes ago'
dmesg -T | tail -200
```

这可能是文件系统为了保护数据在检测到错误后切换只读，也可能是挂载配置本来如此。不要直接 `mount -o remount,rw` 掩盖问题，更不能在已挂载生产文件系统上随意执行 `fsck`。

正确动作通常需要：

```text
停止或迁移写入流量
保存内核与存储事件
联系系统和存储负责人
确认备份与副本
在维护窗口离线检查或修复
恢复后做数据一致性验证
```

P0 场景优先保护数据，不能为了让应用尽快写入而跳过文件系统判断。

## 常见占用来源与正确负责人

### 应用日志

由应用或统一日志策略滚动，设置单文件大小、保留天数和总量上限。确认采集成功后再删除归档。不能同时让 Logback 和 `logrotate` 无协调地管理同一文件。

### Docker 或容器数据

先区分容器日志、镜像、可写层和 Volume。清理由平台负责人通过容器运行时机制执行，不能手工删除 `/var/lib/docker` 下的文件。

### MySQL Binlog、Redo、临时文件

由 DBA 使用数据库命令、保留策略和复制状态处理。手工删除数据库目录中的 binlog 或表文件可能破坏恢复与复制。

### Heap Dump 与 Core Dump

确认是否已安全转存并仍有排障价值，再按事件保留策略清理。Dump 可能包含敏感数据，不传到个人存储。

### 临时文件

确认创建进程、有效期和是否仍打开。修复清理任务与命名规则，避免只做一次人工删除。

## 操作授权矩阵

| 动作 | 风险 | 执行要求 |
| --- | --- | --- |
| `df`、`findmnt`、受控 `du` | 低到中 | 值班人员，注意 IO 开销 |
| 暂停日志或批任务 | 中 | 应用负责人确认影响 |
| 日志滚动、单实例摘流重启 | 中 | 发布/值班流程与容量确认 |
| 数据库日志清理 | 高 | DBA 审核复制与恢复策略 |
| 容器存储清理 | 高 | 平台负责人使用正式工具 |
| 文件系统修复、重新挂载 | 很高 | 系统/存储负责人，维护窗口 |
| 盲删未知文件、底层数据库文件 | 不可接受 | 禁止 |

高风险命令不应该出现在“通用一键清理脚本”里。脚本不知道当前目录属于数据库、容器、正在运行的任务，还是唯一一份故障证据。

## 恢复验证

释放空间或降低 IO 后，至少验证：

```text
[ ] df 容量与 inode 回到安全线
[ ] 增长来源已经停止或受控
[ ] lsof 不再存在异常 deleted 大文件
[ ] iostat 的 await 和队列回到基线
[ ] 文件系统保持预期读写状态
[ ] 应用日志、临时文件和数据库可以正常写
[ ] 核心接口 P95/P99 与错误率恢复
[ ] 消息、任务和复制积压开始下降
[ ] 清理没有破坏审计、备份和回退能力
```

业务恢复后继续观察一个完整高峰或任务周期。磁盘指标下降不代表上层数据已经自动补齐。

## 预防比应急清理更便宜

```text
容量：使用率 + 剩余 GiB + 预计耗尽时间
inode：使用率与文件创建速率
IO：await、队列、吞吐和云盘额度
日志：写入速率、滚动失败、采集延迟
容器：镜像、日志和 Volume 配额
数据库：binlog 保留、备份和临时空间
Dump：独立目录、容量上限和保留流程
```

告警应在还有选择时触发。剩余 15% 但预计两小时耗尽，比使用率 95% 且三个月不增长更紧急。

这份口袋手册的核心只有三句话：先确认是空间、inode、IO 还是文件系统错误；先阻止继续增长，再由资源所有者释放；恢复后同时验证底层指标和业务结果。磁盘故障真正危险的不是命令不会用，而是在压力下执行了一个无法撤销的错误动作。
