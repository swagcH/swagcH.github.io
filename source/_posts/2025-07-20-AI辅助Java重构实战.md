这次想记录一个更接近存量项目的 AI 使用场景：拆解一个 186 行的 `createOrder` 方法。

它同时做参数校验、商品查询、价格计算、库存扣减、订单落库、优惠券核销和通知发送。方法虽然长，却已经稳定运行两年。面对这种代码，最危险的需求不是“帮我重构”，而是“帮我一次重写得更优雅”。

重构的目标应该是改善内部结构而不改变外部行为。AI 可以加快识别重复和生成小函数的速度，但前提是我们先固定行为，再让每一步差异足够小。

## 旧方法为什么不敢动

下面是原方法的压缩版。真实代码还有活动价、渠道价和赠品逻辑，这里只保留职责边界：

```java
@Transactional
public OrderResult createOrder(Long userId, Long productId,
                               Integer quantity, String couponCode,
                               String addressId, String requestId) {
    // 校验参数和幂等记录
    validateRequest(userId, productId, quantity, requestId);
    Product product = productMapper.selectById(productId);
    if (product == null || !product.isOnSale()) {
        throw new BusinessException("PRODUCT_UNAVAILABLE");
    }

    // 计算价格后依次修改多类业务数据
    BigDecimal amount = calculateAmount(product, quantity, couponCode);
    stockService.deduct(productId, quantity);
    Order order = saveOrder(userId, product, quantity, amount, addressId);
    couponService.consume(userId, couponCode, order.getId());
    requestRepository.markSuccess(requestId, order.getId());
    notificationClient.sendOrderCreated(order);
    return OrderResult.from(order);
}
```

仅看这段就能发现几个问题：

- 六个基础类型参数容易传错位置，调用含义不直观；
- 业务校验、计算和副作用混在同一抽象层；
- 外部通知在数据库事务中，超时会长期占用连接；
- 优惠券为空、库存扣减失败、重复请求等分支藏在内部方法；
- 测试只能从入口准备大量 Mock，失败后很难看出是哪条规则变化。

不过“看见坏味道”和“知道怎样安全修改”是两件事。直接让 AI 按 SOLID 原则重写，它曾给出十一个新类、一套领域事件和一个当前项目根本没有的消息队列。结构更漂亮，风险也扩大了十倍。

我最后给这次改动设了三个约束：

```text
不改变接口、数据库和错误码
不新增第三方依赖
每一步都能单独编译、测试和回退
```

## 第零步：先建立行为护栏

原方法只有两个正常流程测试。开始重构前，我让 AI 根据所有条件分支生成“行为清单”，再逐项与产品规则、线上日志和现有代码核对。

最后补了这些特征测试：

| 场景 | 要固定的行为 |
| --- | --- |
| 重复 `requestId` | 返回第一次创建的订单，不重复扣库存 |
| 商品下架 | 返回 `PRODUCT_UNAVAILABLE` |
| 数量超过限购 | 返回 `PURCHASE_LIMIT_EXCEEDED` |
| 优惠券为空 | 按原价创建，不调用核销 |
| 优惠券失效 | 整笔订单不落库、不扣库存 |
| 库存不足 | 返回原错误码，不保存订单 |
| 通知超时 | 订单仍创建成功，产生可重试通知任务 |

最后一条不是原代码行为，而是本次明确要修复的缺陷，因此单独作为需求变更，不伪装成纯重构。

测试先在旧代码上运行。除了“通知超时”之外全部通过，说明我们至少拥有一张当前行为快照。没有这一步，重构后测试全绿也可能只是因为测试跟着实现一起改错了。

## 第一步：用参数对象给入口命名

六个参数经常成组出现，先提取为命令对象。这一步不动业务逻辑：

```java
public final class CreateOrderCommand {

    private Long userId;
    private Long productId;
    private Integer quantity;
    private String couponCode;
    private String addressId;
    private String requestId;

    // 省略标准 getter/setter，项目仍使用 JavaBean 方式绑定参数
}
```

Controller 负责将原请求转换成 `CreateOrderCommand`，Service 入口变成：

```java
public OrderResult createOrder(CreateOrderCommand command) {
    // 暂时只转发字段，确保第一步不改变执行顺序
    return doCreateOrder(command);
}
```

AI 最初使用了 Java `record`。它非常适合不可变数据载体，却不兼容这个 JDK 8 项目。模型知道现代 Java 的常见写法，并不代表它会始终记住当前仓库版本；编译是最直接的纠偏工具。

参数对象也不是越多越好。这里只有一组数据跨 Controller、校验器和应用服务反复传递，提取后能减少长参数列表。如果只是某个私有方法的两个值，没有必要为“面向对象”新建类型。

## 第二步：把规则校验从流程中移开

旧方法中的校验散落在查询前后。我将不产生副作用的规则提取到 `OrderCreationValidator`：

```java
public class OrderCreationValidator {

    public void validate(CreateOrderCommand command, Product product) {
        if (command == null || command.getUserId() == null) {
            throw new BusinessException("INVALID_ORDER_REQUEST");
        }
        if (product == null || !product.isOnSale()) {
            throw new BusinessException("PRODUCT_UNAVAILABLE");
        }
        if (command.getQuantity() == null || command.getQuantity() <= 0) {
            throw new BusinessException("INVALID_QUANTITY");
        }
        if (command.getQuantity() > product.getPurchaseLimit()) {
            throw new BusinessException("PURCHASE_LIMIT_EXCEEDED");
        }
    }
}
```

这里选择提前抛出，避免多层 `if` 嵌套。校验器只依赖输入和已查询商品，没有数据库写入，因此可以直接覆盖边界测试。

不是所有校验都被搬走。优惠券有效性依赖实时状态，并且核销需要并发控制，它仍由优惠券服务负责。把“名字像校验”的代码全部塞进一个类，只会形成新的大类。

AI 在这一步帮我找出了三段重复的数量判断，也指出两个错误码文本不同。我没有让它自动统一错误码，因为对外错误码是接口契约；看似重复的字符串可能承载兼容行为。

## 第三步：让价格计算成为纯计算

价格逻辑最适合先解耦，因为相同输入应该得到相同输出，不需要数据库或网络。

原逻辑直接返回一个金额，调用方无法知道优惠来自哪里。重构后用 `OrderPrice` 表达明细：

```java
public final class OrderPrice {

    private final BigDecimal originalAmount;
    private final BigDecimal discountAmount;
    private final BigDecimal payableAmount;

    public OrderPrice(BigDecimal originalAmount,
                      BigDecimal discountAmount) {
        this.originalAmount = originalAmount;
        this.discountAmount = discountAmount;
        // 金额在同一个对象内保证不小于零，避免规则散落到调用方
        this.payableAmount = originalAmount.subtract(discountAmount)
                .max(BigDecimal.ZERO);
    }

    // 省略只读 getter
}
```

计算服务只负责规则：

```java
public OrderPrice calculate(Product product, int quantity,
                            CouponSnapshot coupon) {
    BigDecimal original = product.getSalePrice()
            .multiply(BigDecimal.valueOf(quantity));
    BigDecimal discount = coupon == null
            ? BigDecimal.ZERO
            : coupon.discountFor(original);
    return new OrderPrice(original, discount);
}
```

纯计算测试不再需要启动 Spring：输入单价、数量和优惠券快照，断言原价、优惠和应付金额即可。用 `BigDecimal.compareTo` 比较金额，避免 `equals` 因小数位不同产生误判。

这一步还暴露了旧代码的一个隐含行为：优惠后金额可以是负数，保存前才在另一个方法里修正为零。重构没有顺手“优化”规则，而是先用测试固定，再把修正逻辑移动到 `OrderPrice` 构造器。移动与修改必须分开，否则出了问题无法判断是哪一种变化导致。

## 第四步：重新画事务边界

旧方法上的 `@Transactional` 包住了所有操作，包括通知 HTTP 请求。网络慢两秒，数据库连接就多占用两秒；通知失败还会回滚订单与库存，而对方可能已经收到请求，形成更难处理的不一致。

重构后把数据库内的原子操作放进独立组件：

```java
@Transactional
public Order persist(CreateOrderContext context) {
    stockService.deduct(context.getProductId(), context.getQuantity());
    Order order = orderRepository.save(context.toOrder());
    couponService.consume(context.getCoupon(), order.getId());
    requestRepository.markSuccess(context.getRequestId(), order.getId());
    // 通知任务与订单在同一事务落库，提交后可由任务可靠重试
    notificationTaskRepository.saveOrderCreatedTask(order.getId());
    return order;
}
```

应用服务只编排步骤：

```java
public OrderResult createOrder(CreateOrderCommand command) {
    OrderResult duplicated = duplicateRequestResult(command.getRequestId());
    if (duplicated != null) {
        return duplicated;
    }

    Product product = productRepository.findById(command.getProductId());
    validator.validate(command, product);
    CouponSnapshot coupon = couponService.prepare(command);
    OrderPrice price = pricingService.calculate(
            product, command.getQuantity(), coupon);

    CreateOrderContext context = contextFactory.create(
            command, product, coupon, price);
    return OrderResult.from(transactionService.persist(context));
}
```

通知任务由现有定时任务发送，成功后更新状态，失败按退避策略重试。这里没有为了“解耦”突然引入 Kafka，因为项目已经有可靠任务表。架构选择应服从现有基础设施和故障处理能力。

还要注意 Spring 事务代理：如果把 `persist` 写成同一个类的 `private` 方法，或通过 `this.persist()` 自调用，`@Transactional` 不会按预期经过代理。将事务方法放进独立 Bean，既明确边界，也避开自调用失效。

## 第五步：删除重复之前，再跑一次全量验证

新结构稳定后，原来的私有方法有一部分不再被调用。AI 很适合搜索引用、列出候选删除项，但删除前我做了三层检查：

```text
IDE / 仓库全文引用搜索
编译主代码与测试代码
运行订单模块回归测试
```

有一个 `calculateAmount` 看似无引用，实际被 SpEL 规则通过方法名调用，普通静态搜索没有找到。幸好集成测试启动规则时失败，避免了误删上线。

动态调用、反射、XML Mapper、序列化字段和框架约定都是 AI 重构的薄弱区。模型读取了 Java 引用，不代表它已经看到运行时所有关系。

## AI 在这次重构中犯过的错

除了使用 `record`，还有几类建议被人工拒绝：

1. 用 `Stream.toList()` 收集结果，JDK 8 不支持；
2. 把所有返回值改成 `Optional` 字段，增加序列化与调用复杂度；
3. 统一替换历史错误码，破坏客户端兼容；
4. 引入领域事件和新消息中间件，超出问题范围；
5. 在没有并发测试的情况下，把重复请求判断改成先查后写；
6. 为了减少类数量，把校验、价格和上下文工厂合并成新的 Helper 大类。

这些建议并不荒唐，它们在另一个项目里可能成立。问题在于模型倾向输出“普遍合理”的设计，工程师要判断它是否适合当前版本、团队和风险预算。

## 怎样证明重构没有把事情弄坏

最终验证不只是一句“测试通过”：

```text
原有 42 个订单模块测试通过
新增 18 个特征与边界测试通过
接口契约快照无变化
数据库迁移文件无变化
正常订单与重复请求各完成一次联调
通知超时演练中，订单提交成功且重试任务可见
并发请求仍由 request_id 唯一约束兜底
```

代码指标也有变化：入口方法从 186 行降到 24 行，六个参数变成一个命令对象，价格规则可以脱离 Spring 单测。类数量增加了四个，但每个类对应稳定职责，不是为了追求数字拆分。

我没有把“方法越短越好”当目标。真正的改善是：阅读入口时能看清业务顺序，修改价格不需要理解通知，调整通知也不会碰库存事务。

## 这类任务最适合怎样使用 AI

我的顺序是：

```text
先让 AI 画现状，不写代码
再让 AI 枚举行为和风险
人确定边界与优先级
一次只做一种重构手法
每步查看差异并运行测试
最后让 AI 做遗漏检查，人做合并判断
```

AI 在“快速读取、发现重复、生成测试骨架、执行机械移动”上很强；人在“哪些行为是契约、哪种抽象值得存在、风险是否可以接受”上不能缺席。

重构不是把旧代码替换成一份更现代的代码，而是在持续可工作的前提下，让下一次变化更容易。让 AI 参与后，这个过程可以更快，但“小步、测试、审查”反而比以前更重要，因为我们现在拥有了以极快速度制造大面积改动的能力。
